# 01｜基础、规划与工具：从回答问题到完成任务

[首页](../README.md) · [专题索引](../README.md#topics) · [文献目录](../catalog/01_basics.md)

前置阅读：如果还不熟悉模型参数、训练与推理、token 和上下文这些概念，可以先看[大模型前置知识](../docs/llm_primer.md)。本章在这些概念之上解释一个系统怎样行动起来，读之前不需要学过任何 Agent 框架。

## 方向背景：为什么需要从语言模型走向行动系统

设想周五晚上，你想让一个 AI 助手帮忙做一件很日常的事：把服务器上过去一周跑过的二十几组训练实验整理成一张周报表格，标出哪几组崩了，和基线比一比，最后把表格发给导师。如果你把这句话丢给一个普通的聊天模型，它会给你一段相当靠谱的回答：先用某条命令列出日志目录，再写个脚本解析每个日志里的验证集指标，崩掉的实验通常会在末尾留下报错，记得和基线对齐随机种子。每一步都说得头头是道，可表格并没有出现，邮件也没有发出去。

真要把这件事做完，系统得真的去列目录、打开文件。它可能发现有三组实验的日志格式和别的不一样，只好回头改解析方式；可能发现其中一组只跑了一半，要判断它算崩溃还是还在跑；算完数字还要自己核对一遍，确认没有把训练集指标抄成验证集指标。最后发邮件这一步会改变外部世界，发错了收不回来，最好先停下来让你确认。聊天模型做不到这些，原因很简单：模型参数里存着大量知识，却看不到你服务器此刻的状态，它写出一段正确的操作描述，那段操作也没有因此被执行和检查。Agent 研究的出发点，就是把语言推理和可执行的动作接起来，让系统根据每一步的反馈推进目标，最后交付一件做完了的事。

这样一来，研究对象就从一次生成变成了一个反复转动的循环：观察环境，选择动作，调用工具，接收反馈，再判断是否完成。循环拉长以后，错误会一路传下去。第三步读错了一列，第十五步算出的平均值就是错的，而到那时已经很难追溯是哪一步出的问题。所以怎样安排步骤、怎样挑选该看的信息、出错以后怎样恢复，都成了这个方向的基础问题。

也正因为一个 agent 由模型和模型外面的一整套执行设施共同组成，一个系统表现变好，原因可能是交给模型的动作更顺手，可能是反馈更充分，也可能只是多花了预算，模型本身未必变强了。读这个方向的论文，第一步就是分清一项改进到底来自哪里。

## 一、先看全景：把工作循环拆开

> **本节要点：** agent 的每一轮都在转同一个循环：模型提出动作，模型外面的执行框架校验并执行，工具返回的观察再送回模型。计划、动作和观察是三样不同的东西，评测时要查的是环境里真的发生了什么。下一步由代码预先写定的系统叫工作流，由模型临场决定的才叫 agent。

可以把一个 agent 想成一个坐在没有窗户的房间里的人。他看不到外面，只能往门缝外递纸条，比如"帮我读一下 exp07 的日志"；门外的助手先看看这张纸条合不合规矩，再照着去做，把看到的结果抄在纸上递回来。房间里的人读完回条，再决定下一张纸条写什么。房间里的人就是语言模型，它唯一会做的事是写字；门外的助手负责其余的一切，英文叫 harness，本章译为"执行框架"。这个比喻是本章为了入门打的，它想说明一件事：模型提出动作，执行框架真正去做，两者是分开的。

把这个循环摊开来看，每一轮的输入里有用户的目标、当前已知的状态、可用工具的说明，以及还剩多少预算，它们一起组成模型看到的上下文。模型据此提出下一步动作，通常是一次带参数的工具调用。执行框架先检查工具名存不存在、参数合不合格式、这个动作有没有权限，任何一项不合格，调用就不会发出去，错误信息退回模型。通过检查的调用被真正执行，它要么改变了环境，要么取回了信息；工具实际返回的内容叫观察。执行框架把观察写进任务记录，再用记录重新组装下一轮的输入。当系统达到明确的成功条件、发现无法继续、需要人来确认，或者预算用完时，循环停止。

![agent 的一轮工作循环](../assets/basics/overview-loop.svg)

*图：一轮工作循环。青色虚线框是执行框架管辖的部分，目标和模型在框外；两条虚线分别是参数或权限不合法时退回模型，以及达到条件时离开循环。*

图里模型只占一个框，校验、执行、检查、记录都由执行框架负责。这就是为什么不训练模型、只改框架，系统行为也可能大不一样。

循环里有三样东西最容易混在一起：计划、动作和观察。计划负责组织步骤，安排先做什么后做什么；动作是从可执行的操作中选出一个并填好参数；观察是工具实际返回的信息。拿周报来说，模型在计划里写下"解析全部日志"，这时服务器上什么也没有发生；它生成一条读取 exp07 日志文件的调用，这是一次动作，执行框架会把它真正发出去；文件内容返回到上下文里，读到第 12 个 epoch 的 loss 变成了 nan，系统才第一次真正知道 exp07 崩了，这是观察。同样的道理，模型写出"已经运行了测试"，测试并没有因此被运行。读论文时如果分不清某个数字衡量的是哪一样，就很容易高估一个系统。

![计划、动作与观察](../assets/basics/plan-act-obs.svg)

*图：计划、动作和观察常常出现在同一段输出附近，含义却完全不同。只有右边那一栏来自环境，前两栏都还是模型写下的文字。*

执行框架还决定了另一件事：下一步由谁决定。Anthropic 在 [工作流与 Agent 的工程区分](https://www.anthropic.com/engineering/building-effective-agents) 一文里，把由开发者预先写好代码路径的系统叫作工作流，把由模型拿到观察以后自己决定下一步、自己判断何时停下的系统叫作 agent。在工作流里，第一次模型调用的输出交给一段代码检查，通过了进入第二次调用，没通过就按写好的规则重来，每一步走向哪里都是确定的；在 agent 里，步数事先无法预知。两种方式没有高下之分。作者的建议是从最简单的方案出发，任务定义清楚、需要可预测时用工作流，只有面对步数无法预知的开放问题时才交给 agent。

![工作流与 agent](../assets/basics/workflow-vs-agent.svg)

*图：工作流与 agent 的区别在于下一步由谁决定。下排是 Building effective agents 总结的五种工作流模式，它们都由增强型大模型这个基本单元组合而成。*

图下排的五种工作流模式，都由同一个基本单元搭起来，也就是带检索、工具和记忆的增强型大模型。提示链把任务切成前后相接的几步，前一步的输出就是后一步的输入；路由先给输入分类，再交给专门的流程；并行化让几段子任务同时跑，或者对同一个问题多次作答再投票；编排者与工作者由一个中心模型临场拆分任务，再派给其他模型去做；评估者与优化者让一个模型负责生成，另一个模型负责评价并给出反馈。从左往右，模型自己决定的东西越来越多，最右边已经很接近 agent。

### 一张阶梯和一条时间轴

> **要点：** 这个领域八年来的关注点，一路从模型本身移到了模型外面的执行系统。

有了这个循环，就能看清这个领域是怎样一步步走过来的。下面的阶梯从下往上读，每一级都在补上一级暴露出的缺口。最初的问题是模型只会在纸面上推理，于是第一阶段让推理和动作交替起来；动作离不开工具，第二阶段研究模型怎样学会用工具；工具调用一多，步骤之间的依赖和失败后的纠错成了问题，这是第三阶段的规划与反思；把整个循环放进真实网站和代码仓库里检验以后，人们发现交给模型的接口本身就影响成败，这是第四阶段；到了第五阶段，模型普遍会用工具了，瓶颈移到了模型外面的执行框架和上下文。左边的箭头画的就是这个转移，最下面的橙色框是贯穿各阶段的边界问题：成绩变好了，事情是否真的做成了。每一级右端标着本章第三节里接着追问这一级问题的分支。

## 二、发展主线：从会说，到会做，再到在真实环境里持续地做

这条主线把几篇长文的视角叠在了一起。Lilian Weng 在 2023 年画下的"大脑加三组件"地图，回答了一个 agent 由哪些部分组成；Chip Huyen 在 2025 年用工具、规划、失败模式重新组织了同一片领域，补上了工程上的教训；Anthropic 和 OpenAI 的几篇工程文章则记录了此后的转向，研究者和工程师的注意力从"让模型学会调用工具"移到了"模型外面那整套执行系统该怎么设计"。顺着时间读下来，这个领域大致走过了五个阶段，每一个阶段都是上一个阶段把问题暴露出来之后出现的。

> **本节要点：** 第一阶段让新观察能改变模型下一步想什么；第二阶段让模型学会选工具、填参数；第三阶段处理多次调用之间的依赖和失败后的纠错；第四阶段在真实环境里检验整个循环，发现接口本身是变量；第五阶段研究模型外面的执行框架。每一阶段都用结构卡和对照表写明补上了什么、留下了什么代价。

### 第一阶段：先想一想，再动手

> **要点：** 先让模型把推理写在纸面上，再让它把问题分派给外部模块，最后把思考和动作交替起来。ReAct 让新观察第一次能改变模型下一步想什么，今天几乎所有 agent 的主循环都从这里长出来。

故事的起点是推理。2022 年的 [Chain-of-Thought](https://arxiv.org/abs/2201.11903) 发现，只要在提示里给出几个带中间推理步骤的示例，大模型在算术和常识推理上的表现就会明显变好。模型第一次在给出答案之前先写下一段推理，这段推理人可以读，也可以检查。

可推理写得再好，模型也没法知道今天的汇率，或者某个文件里写了什么，因为这些信息不在它的参数里。同一年，AI21 Labs 的 [MRKL Systems](https://arxiv.org/abs/2205.00445) 提出让语言模型和外部的知识源、计算器这类模块协作：模型只负责判断问题该交给哪个模块，由擅长的模块算出结果，再组合成答案。这是"语言模型加外部工具"思路较早的系统化表述。它的局限在于，问题分派出去以后，模型不会根据返回结果再调整。

[ReAct](https://arxiv.org/abs/2210.03629) 补上了这一环。它让模型交替写出"思考"和"动作"：先想一想当前缺什么信息，再发出一次搜索，读到返回结果之后接着想，再决定下一步。这样一来，新观察能够改变下一步的选择，第一节那个模型提出动作、执行框架去做、观察送回模型的循环，就是从这里来的。Lilian Weng 把 ReAct 放在规划组件的"自我反思"一节里介绍；姚顺雨在 The Second Half 里则把"推理加行动"视为让 agent 获得泛化能力的关键配方之一，他的说法是，语言通过推理在 agent 中实现泛化。今天几乎所有 agent 框架的主循环，都可以看作 ReAct 的某种变体。

### 第二阶段：学会用工具

> **要点：** ReAct 靠提示引导模型用工具。下一步的问题是模型能否真正学会用工具：一条路把工具使用训进模型参数，一条路让大模型当调度者。工具一多，"会不会用"就成了需要专门测量的能力；工具还分只读和写入两类，后者风险大得多。

ReAct 证明了模型可以在提示的引导下使用工具，可提示里能放的示例有限，换一批工具就要重写提示。于是下一个问题是：模型能不能通过训练真正学会用工具，知道什么时候该调用、调用哪一个、参数从哪里来？

2023 年初 Meta 的 [Toolformer](https://arxiv.org/abs/2302.04761) 给出了一个几乎不需要人工标注的回答，它让模型自己造训练数据。模型先在普通文本里插入候选的 API 调用，比如在一句涉及计算的话里插一个计算器调用；执行这些调用，拿到返回结果；再比较把结果放回文本以后，后面的文字是否更容易预测。只有让预测变容易的调用会被留下，用这些自动筛出来的数据微调模型。筛选标准来自语言建模本身，所以每个 API 只要少量示范，模型就自学了何时调用计算器、搜索引擎和翻译工具。

同年浙江大学和微软的 [HuggingGPT](https://arxiv.org/abs/2303.17580) 走的是另一条路，工具始终留在模型外面。ChatGPT 当控制器，先把用户请求拆成子任务，再根据 Hugging Face 上的模型描述为每个子任务挑一个模型，调用这些模型去执行，最后把结果汇总成回答。一个把工具使用训进参数，一个让大模型读说明来挑工具，这两种思路后来一直并行发展。

![Toolformer 与 HuggingGPT](../assets/basics/s2-toolformer.svg)

*图：上半部分是 Toolformer 自监督造训练数据的五步，下半部分是 HuggingGPT 的四步。前者把工具使用训进参数，后者让大模型留在外面当调度者。*

工具一多，"会不会用"就成了需要认真测量的能力。[API-Bank](https://arxiv.org/abs/2304.08244) 把工具增强的对话组织成可评测的任务；[Gorilla](https://arxiv.org/abs/2305.15334) 针对大量真实 API 研究调用的准确性，模型在写调用时去检索最新的接口文档；[ToolLLM](https://arxiv.org/abs/2307.16789) 收集了大规模真实 API 并构造训练数据。从这时起，演示"能调用一个工具"已经不够，要回答的是面对陌生接口能否正确选择和执行。想更系统地了解这一阶段，可以读 [工具学习综述](https://arxiv.org/abs/2304.08354)。

模型学会用工具以后，风险也随之而来。Chip Huyen 把工具分成两类：只读的工具用来感知环境，比如搜索和读文件；写入类工具会改变环境，比如发邮件、改数据库。只读动作做错了，通常只是浪费一次调用，可以放心让 agent 反复去做；写入动作做错了，可能收不回来。在周报任务里，列目录和读日志都是只读的，发给导师的那封邮件才是写入动作。所以执行框架应当在写入动作发出之前设一道确认点，把控制权交还给人。

![只读工具与写入工具](../assets/basics/s2-read-write.svg)

*图：Chip Huyen 的两类工具。只读动作扩展模型能看到的东西，写入动作扩展它能做的事，写入之前加一道确认点。*

### 第三阶段：规划与反思

> **要点：** 一次调用成功以后，问题变成多次调用怎样拼成一件完整的工作。任务分解这一侧，计划从清单变成树、变成交给规划器的形式化描述，再变成带依赖的调度图；反思这一侧，失败的经验被写成文字带到下一次，可没有外部反馈时，反思本身也会出错。

一次调用成功了，多次调用却未必能拼成一件完整的工作。前一个调用的结果可能是后一个调用的参数；有些步骤可以同时跑，有些必须等前面的反馈。系统因此要决定怎样分解目标，以及什么时候推翻原来的安排。Lilian Weng 把这些问题都放在"规划"组件之下，又细分为任务分解和自我反思两部分。

任务分解最直接的做法是 [Plan-and-Solve](https://arxiv.org/abs/2305.04091)：让模型先写出一份分成几个子任务的计划，再照着计划一步步求解。可一份计划只有一条路，走进死胡同就回不来。[Tree of Thoughts](https://arxiv.org/abs/2305.10601) 因此把推理组织成一棵树，每一步生成好几个候选思路，由模型评估哪个值得继续，被放弃的思路就此打住，必要时还可以回溯到上一层。还有一条思路干脆把求解交给有正确性保证的专门程序：[LLM+P](https://arxiv.org/abs/2304.11477) 让大模型把自然语言描述的规划问题翻译成 PDDL，这是一种用来写明初始状态、目标和可用动作的形式化语言，交给传统规划器求解，再把解翻译回自然语言。

这三项工作组织的都还是推理过程，离真实的工具调用隔着一层。一旦计划里安排的是真实调用，规划就带上了调度的味道。ReAct 每发一次调用都要停下来等观察，再把越来越长的历史重新喂给模型，[ReWOO](https://arxiv.org/abs/2305.18323) 针对的就是这种反复往返：先由一个模块一次写出全部步骤，后面步骤要用的结果先用占位符代替，再由几个执行模块去调用工具，最后由一个汇总模块读全部证据给出答案（图里分别标作 Planner、Worker 和 Solver），推理过程不必停下来等每一个观察返回。[LLMCompiler](https://arxiv.org/abs/2312.04511) 更进一步，像编译器一样分析函数调用之间的依赖，把调用排成依赖图，互不依赖的调用 1 和调用 2 同时发出，调用 3 等它们都回来再执行。到这里，规划已经从"写一份待办清单"变成了一个带依赖关系的调度问题。

![第三阶段：五种组织计划的方式](../assets/basics/s3-planning.svg)

*图：五种组织计划的方式。前三行组织的是推理过程，后两行开始安排真实的工具调用，规划变成了调度问题。*

计划再好，执行中也会失败，于是有了反思这一侧。代表工作是 [Reflexion](https://arxiv.org/abs/2303.11366)：行动者尝试任务，评估给出成败或分数，模型据此用自然语言写一段反思存进记忆，下一次尝试时带上。模型的权重从头到尾没有变，变的是下一次尝试能读到的那段文字。可反思本身也可能出错。DeepMind 等机构 2023 年的 [Large Language Models Cannot Self-Correct Reasoning Yet](https://arxiv.org/abs/2310.01798) 发现，在没有外部反馈的情况下，模型自我纠错后，推理题上的表现有时反而会下降。原因在于，模型拿来判断自己对不对的，还是同一个可能出错的模型。所以反思靠不靠得住，要看有没有测试结果、环境返回或标准答案这样的外部依据来告诉系统这次到底对不对。

![Reflexion 的一轮与反思的边界](../assets/basics/s3-reflexion.svg)

*图：Reflexion 的一轮，以及反思靠不靠得住的两种情况。左边的绿色框有外部反馈，右边的橙色框只靠模型自查。*

Chip Huyen 对这一阶段的评价很冷静。她主张把规划和执行分开，先用启发式规则或另一个模型检查计划是否合理，再去执行；她也直言，基础模型到底能不能规划仍有争议，因为规划需要预判每个动作的后果。反思和纠错在她看来很有用，却也不是必需的，因为它们会带来额外的延迟和成本。Lilian Weng 在文末同样把长程规划列为当时的主要挑战之一：模型遇到意外错误时，很难调整原来的计划。

| P2 | 思维树搜索 | 2023 | [Tree of Thoughts](https://arxiv.org/abs/2305.10601) | 每一步生成多个候选思路，由模型评估后选择往哪条分支走，可以广度或深度优先搜索并回溯 | 推理可以同时探索多条路线、放弃死路，适合需要试错和前瞻的问题 | 每一层都要生成和评估多个候选，模型调用次数成倍增加 |
| P3 | 交给经典规划器 | 2023 | [LLM+P](https://arxiv.org/abs/2304.11477) | 模型把自然语言规划问题翻译成 PDDL，经典规划器求解，再译回自然语言 | 求解交给有正确性保证的规划器，模型只做它擅长的翻译 | 问题要能写成 PDDL 这样的形式化描述，翻译错了规划器也救不回来 |
| P4 | 推理与观察解耦 | 2023 | [ReWOO](https://arxiv.org/abs/2305.18323) | 写计划的模块一次写出全部步骤并用占位符引用结果，执行模块调用工具，汇总模块读全部证据作答 | 推理不必等每个观察返回，省掉反复往返的冗余提示，作者在 HotpotQA 上报告约 5 倍的 token 效率 | 计划在看到观察之前就写好，中途发现情况不对时很难临时改路线 |
| P5 | 并行函数调用 | 2023 | [LLMCompiler](https://arxiv.org/abs/2312.04511) | 规划器把调用排成依赖图，分派单元在依赖满足时派出任务，执行器并行运行 | 互不依赖的调用同时跑，作者报告相对 ReAct 时延最多降低 3.7 倍、成本最多节省 6.7 倍 | 收益取决于调用之间有多少能并行；依赖图本身要规划正确 |
| P6 | 语言反思 | 2023 | [Reflexion](https://arxiv.org/abs/2303.11366) | 失败后让模型用自然语言写反思存进记忆，下次尝试时带上 | 不改权重也能从失败里学，改变的是下一次尝试能拿到的信息 | 反思本身可能出错，没有外部反馈时自我纠错可能变差；还会增加延迟和成本 |

### 第四阶段：走进真实环境

> **要点：** 单项测试里看不出各个环节接起来以后会在哪里断。一批环境型基准把整个循环放进真实网站和代码仓库里检验，成功由环境来判；SWE-agent、CodeAct 和 Agentless 又说明，交给模型的接口和动作空间是和模型能力并列的研究变量。

前三个阶段的工作大多在单项任务上测：一道推理题，一次工具调用，一份计划。可第一节说过，循环拉长以后错误会一路传下去，只有放进完整的任务里，各个环节连接处的问题才会暴露出来。2022 到 2023 年，一批环境型基准相继出现。它们的共同点是成功由环境来判，模型自己说做完了不算；差别在于环境离真实有多近，从模拟网站，到真实网站上事先录下的操作，再到可以本地部署、真会响应操作的真实网站。[WebShop](https://arxiv.org/abs/2207.01206) 搭了一个模拟购物网站，agent 要按文字描述去搜索、浏览、选规格并下单，买到的商品是否符合描述决定得分，作者还把训练出的 agent 放到 amazon 和 ebay 上试过。[Mind2Web](https://arxiv.org/abs/2306.06070) 从 137 个真实网站、31 个领域收集了两千多个任务，每个任务都配有人工完成的动作序列；真实网页的 HTML 太长，作者先用一个小模型筛选，再交给大模型选动作。[WebArena](https://arxiv.org/abs/2307.13854) 搭了电商、论坛、代码协作和内容管理四类可以本地部署的网站，还配了地图等工具和使用手册，按功能是否正确来判定任务完成，论文报告最好的 GPT-4 agent 端到端成功率只有 14.41%，人类是 78.24%。

![第四阶段：四个环境](../assets/basics/s4-envs.svg)

*图：四个环境型基准。每张卡片写着任务来源、agent 要做的事，以及成功怎么判或关键做法。*

软件工程方向的 [SWE-bench](https://arxiv.org/abs/2310.06770) 要求 agent 修复真实开源仓库里的问题，交出的补丁要能通过测试才算数。读懂代码、定位问题、修改和测试彼此依赖，任何一环掉链子都会失败，它因此很快成为衡量 agent 的标志性基准。

在这类环境里，研究者发现模型的成败很大程度上取决于交给它什么样的操作。下面三项工作用的模型可以完全一样，差别只在交给模型的动作空间：一组专门设计的命令，任意的 Python 代码，或者一条模型不能改动的固定流程。2024 年的 [SWE-agent](https://arxiv.org/abs/2405.15793) 把这件事叫作"agent 与计算机接口"：同一个模型，给它设计得更好的命令，比如按窗口翻看的文件查看器、仓库内搜索和文件编辑，修复成功率就会明显提升。同年的 [CodeAct](https://arxiv.org/abs/2402.01030) 从动作格式入手，让 agent 直接写可执行的 Python 代码作为动作，解释器执行以后把结果或报错还给模型，一段代码里还能写循环、存变量、调用多个工具；作者在 17 个模型上报告，相比常见的动作格式，成功率最多高出 20%。也有工作反过来问：真的需要那么多自主性吗？[Agentless](https://arxiv.org/abs/2407.01489) 用一条固定的流程去做同样的软件任务，先定位、再修复、再验证，模型在每一步里干活，却不决定下一步做什么，结果相当有竞争力。

![同一类修复任务的三种接口](../assets/basics/s4-aci.svg)

*图：SWE-agent 的专用命令、CodeAct 的代码动作和 Agentless 的固定三步。三行的模型可以相同，变化的是动作空间。*

Anthropic 在 2024 年底的 Building effective agents 里，把这一阶段的经验总结成了一条建议：先找最简单的方案，很多应用只要优化好单次模型调用、配上检索和示例就足够，只有面对步数无法预知的开放问题时，才交给 agent 自己决定。他们也分享了一个接口设计的例子。在为 SWE-bench 搭 agent 时，模型离开根目录后经常把相对路径用错，他们把工具改成必须使用绝对路径，模型随后就用得毫无差错。作者因此主张，给 agent 设计接口，应该和给人设计界面投入同样多的心思。

### 第五阶段：执行框架与上下文工程

> **要点：** 基础模型普遍能可靠地调用工具以后，瓶颈移到了模型外面：工具怎么写、什么信息进入上下文、反馈回路怎么搭。Anthropic 和 OpenAI 的工程文章给出了做法，2026 年的综述把执行框架的工作整理成六项职责。

到了 2025 年，基础模型已经普遍能可靠地调用工具，瓶颈慢慢转移到了模型外面。同样的模型，放进不同的执行框架里，表现可以差得很远；工具说明多写一句、返回内容少给一半，结果也会跟着变。第四阶段已经看到接口是变量，这一阶段的研究对象扩大到了执行框架管理的一切，尤其是工具和上下文。

Anthropic 2025 年 9 月的两篇文章是这个转向的标志，它们的出发点是同一个限制：模型的上下文窗口是有限的，每个进入窗口的 token 都应当带着有用的信号。Effective context engineering for AI agents 指出，系统提示、工具说明、历史消息和工具返回都在争用同一个窗口，窗口放得越满，模型从中准确找回信息的能力越弱，作者把这种现象叫作上下文腐化。工程上的目标因此是找到"能最大化期望结果概率的最小一组高信号 token"，常用手段有四种：即时检索只留下文件路径这类轻量的标识，用到时再读；压缩把旧的历史总结成摘要；结构化笔记让 agent 把要点写到窗口外面，需要时再取回；子 agent 分头去探索，只把摘要交回主 agent。Writing effective tools for agents 从工具这一侧落实同一个原则：把现成 API 端点直接包装成工具往往不合适，工具应该围绕少数高价值的工作流来设计，用命名空间划清边界，优先返回人能读懂的名字，少给低层标识符，并用分页、过滤和截断控制返回量。文中提到 Claude Code 默认把工具返回限制在 25,000 个 token 以内。

![上下文工程与工具设计](../assets/basics/s5-context.svg)

*图：左边是几路信息争用有限的上下文窗口，以及上下文工程的四种做法；右边是写工具的几条原则。*

OpenAI 在 2026 年 2 月的 harness engineering 报告把这件事推到了极致。团队在不手写代码的前提下，由 Codex 写出了整个产品，工程师的精力全部花在设计环境上。他们用一个简短的 AGENTS.md 当作指向文档目录的地图，替代一份上千页的手册，因为手册太长会挤占上下文；把架构规则写进 linter 和结构测试，由它们机械地执行，报错信息里直接附上修复建议，agent 读到就能照着改；让应用本身对 agent 可读，能启动、能看日志和指标；再让后台 agent 定期扫描代码里逐渐积累的坏模式，像垃圾回收一样清理。作者特别提到，agent 失败时，修复办法通常是补上缺失的工具、抽象或结构，单纯让它再试一次很少奏效。

到 2026 年 6 月，Jianyuan Guo 等人的综述 [From Question Answering to Task Completion](https://arxiv.org/abs/2606.20683) 把这一阶段的经验整理成了一张完整的地图。他们把 agent 看作基础模型与执行框架的组合，执行框架承担六项职责：观察，把终端输出、代码差异、截图和网页结构变成模型能读的形式；上下文，决定什么信息在什么时候、以什么形式进入窗口；控制，编排循环，决定何时停止、重试和委派；动作，把模型输出映射成函数调用、命令行和浏览器操作；状态，保存计划、检查点、日志和文件；验证，用测试、验证模型、沙箱和权限关卡去检查和约束执行。第一节那张工作循环图里，除模型以外的每个框都能在这里找到负责它的职责。作者还把 agent 工程的演进归纳为四种范式：提示工程关心措辞，工作流与上下文工程关心流程和信息的组织，执行框架工程关心执行过程的控制，智能体原生训练则借助交互环境把 agent 行为训练进模型参数，让模型和执行框架一起演化。他们特别说明，四种范式至今同时存在，后来的并没有取代先前的。

### 边界：成绩变好了，事情真的做成了吗？

> **要点：** 每往前走一个阶段，"怎么知道真的变好了"就更难回答。循环可能断在没有外部反馈的自我纠错上，断在 agent 宣布完成却没做完上，断在工具返回的文字上，也可能断在评测设定和现实之间。

循环越长、越复杂，一个总的成功率就越难说明问题出在哪里。Chip Huyen 在文章里专门留了一节讲失败模式和评估：规划会失败在无效工具、无效参数和错误的参数值上，工具会返回错误的结果，效率也会在步数、成本和时间上出问题；最微妙的一种，是 agent 自信地宣布完成，事情其实没做完。她建议为规划单独建数据集，为每个工具单独测试，并且把效率和一个基线放在一起比较。这样评测时就能按失败类型分别计数，看清断点在哪一环。

![工作循环在哪里断掉](../assets/basics/boundary.svg)

*图：橙色框是断点，箭头指向它出问题的那一环；底部是 Chip Huyen 的失败分类。*

图里把工作循环缩成四个框，四个橙色框各指向一处断点：没有外部反馈的自我纠错落在模型提出动作这一环，宣布完成落在检查这一环，工具返回的文字落在观察这一环，返回的内容可能出错，甚至夹带诱导系统越权的指令。Lilian Weng 在 2023 年担心的是自然语言接口不可靠，当时指的是模型输出的格式出错；到今天，不可靠的文字也可能从工具那一侧流进来。

最下面横跨整个循环的那一条，是姚顺雨在 The Second Half 里提出的疑问。当一套配方能把各种基准一个个刷上去，新方法打败旧基准就不再稀奇；真正要紧的，是评测设定和现实之间的差距。现实中的 agent 要和人来回交互，要在一连串相关任务中积累经验，而大多数基准让 agent 独自运行，把每道题当作互不相关的样本。他把这个落差称为效用问题，认为这是 AI 当下最重要的问题。所以读任何一篇报告"成功率提升"的论文时，都可以问一句：这个提升衡量的是格式正确、调用正确，还是任务真正完成？代价又是多少？这些问题在三.6 和第四到七节里还会展开。

## 三、前沿研究方向

经典工作搭起了模型提出动作、执行框架执行、观察送回模型的循环，前沿研究追问的是这个循环在哪些环节仍然不可靠。按模型每一轮面对的顺序，它先要用工具表达动作，再要安排多步之间的依赖，然后要从返回的内容里挑出证据；循环外面，执行框架本身需要被理解和改进，模型训练要和执行框架对得上，一次行动结束以后系统还要能安全地继续。六个分支就按这个顺序排开，收录的都是 2026 年的新论文。读每一篇时都值得问两个问题：它改的是模型、接口还是框架？它用什么证据说明改进是真的？

> **本节要点：** 六个分支分别研究工具接口、规划、观察、执行框架的改进、训练与框架的配合，以及一次行动之后能否安全继续。每个分支用一行"主线位置"挂回第二节的阶段。

### 1. 工具接口决定了模型能够怎样行动

给 agent 设计工具，很像给新同事配一套办公权限和操作手册。工具接口规定了模型可以调用什么，也规定了它能看到多细的参数说明、每次返回多少结果、失败时收到怎样的报错。接口越通用，模型要承担的选择和解释负担就越重；接口越专用，换一个环境又可能失灵。评价接口时还要分清三个层次的指标：输出了合法的 JSON，调用了正确的工具，最终完成了任务。前一层成立推不出后一层，三者混在一起报告很容易让人误判。

> 主线位置：第二阶段与第四阶段的交汇处。接 Toolformer、Gorilla 的工具学习，SWE-agent 的 agent 与计算机接口，以及 CodeAct 的代码动作；工程上对应 Anthropic《Writing effective tools for agents》。

> **要点：** 先有受控实验证明，只换工具的包装方式就能改变成本。随后的论文分别调整三处：动作写成 JSON 还是程序，调用在生成完以后还是生成中途启动，模型对工具的理解来自说明文档还是训练。

先看一个受控的对照实验。**[The Harness Effect](https://arxiv.org/abs/2607.06906)** 固定任务和模型，只替换编排层，也就是上下文怎样组装、工具怎样暴露、失败怎样处理，看任务成本怎样变化。作者报告，在其企业任务样本上，成本、时延和 token 使用都下降了，质量的变化则受模型能力影响。它说明工具的包装方式会改变整个交互过程，这和 Anthropic 搭 SWE-bench agent 时的经历是同一个道理：模型离开根目录后经常把相对路径用错，他们把工具改成必须使用绝对路径，错误就消失了。它的样本是小规模的固定任务，收益能否推广到其他企业流程，还要另外检验。

既然包装方式本身是变量，就要问哪些地方可以调。最明显的一处是动作的表达形式。拿周报任务来体会：助手要读取二十几组实验的日志，接口可以只允许一次读一个文件，也可以接受一组文件名，还可以让模型写一段程序，用循环把文件挨个读进来。一次读一个文件要来回二十几次，好处是每一步都能单独审计，错一步也只影响这一步；一次读一组，来回少了，一次返回的内容却变多了，要靠分页和截断控制；写一段程序，循环、变量和依赖都能直接表达，可要读懂整段程序才能审计，写错一处会影响很多步。

![读二十几个日志的三种接口](../assets/basics/b1-read-logs.svg)

*图：示意。读二十几个日志的三种接口，从左到右表达力越来越强，单步审计越来越难。*

[The Bitter Lesson of Tool Calling](https://arxiv.org/abs/2608.06370) 正面比较了这件事：原生 JSON 调用每次生成一个结构化调用，程序式调用让模型写一段调用工具的程序。它接着第四阶段的 CodeAct 往下走，那项工作让 agent 直接写可执行的 Python 代码当作动作。程序的好处在于能直接表示循环、变量和依赖，需要连续取多个返回值时，模型不必在每一轮重新组织同一段逻辑。代价也来自这里：程序能表达的动作越多，执行环境越要把它们限制住，部署时还要根据每个工具的权限，约束程序能执行哪些操作。这篇论文在第五节还有更详细的介绍。

[Harness as a Language](https://arxiv.org/abs/2609.26891) 把程序这条路推得更远。它研究能否只用一个很小的可编程执行原语来表达复杂的 agent 行为，从而省掉为记忆、委派和递归分别堆叠的专门模块。核心原语少了，运行时的行为却未必更容易理解；程序可以递归调用模型以后，预算、监控和终止条件都要定得更清楚。

第二处可以调的是调用什么时候启动。程序式调用要等整段程序生成完才执行，生成和等待工具返回是串行的。[Speculative Programmatic Tool Calling](https://www.alphaxiv.org/abs/2608.spec-ptc) 在程序还在生成的时候，就提前启动那些已经能够解析出来的工具调用，让生成和等待重叠起来，有点像 CPU 的流水线。它不改变调用什么，只改变已经确定的调用何时启动。能省多少时间，取决于工具的延迟、调用之间的依赖，以及提前执行是否安全，比如一次写入动作就不宜在程序写完前抢先发出。

第三处是模型对工具本身的理解。一次调用失败，原因可能在接口，也可能是模型没学会工具能做什么，或者没学会从上下文里找到参数的依据，后一种情况改接口救不了。[MidTool](https://arxiv.org/abs/2608.20314) 从中期训练数据入手，组织真实的 API、文档和工作流，让模型学到工具能做什么、参数从哪里来、调用怎样组合。[Salesforce Koa](https://arxiv.org/abs/2609.15066) 则把工作流规格扩展成多轮的模拟任务，再用任务结果形成训练信号。两篇和第二阶段的 Toolformer、ToolLLM 一脉相承，都想通过训练把工具使用学进模型。具体的训练方法在[第 04 章](04_training_data.md)和[第 05 章](05_rl_and_distillation.md)展开。

![工具接口的三个旋钮](../assets/basics/b1-knobs.svg)

*图：工具接口的三个旋钮，右侧是本节对应的论文；顶部是 The Harness Effect 的受控替换。*

图里每个旋钮往右拧，表达力更强，执行环境要承担的约束也更多。比较两个系统时，最好先确认它们只在其中一个旋钮上有差别，并且把工具权限和总预算固定住。

### 2. 规划：把待办清单写长之后，还缺什么

把一个大任务拆成很多小任务，听上去总是更稳妥，可经验丰富的人都知道，拆解本身就可能出错。规划要解决的是行动之间的依赖：哪些步骤可以独立进行，哪些必须等前面的结果出来，发现某个假设错了以后又该怎样修改计划。拆出更多子任务未必降低难度，因为拆解时可能漏掉约束，执行者还得把结果按约定的格式交回来。所以比较规划方法时，分解质量、执行成本和重新规划的触发条件要一起看。

> 主线位置：第三阶段。接 Plan-and-Solve、Tree of Thoughts、LLM+P、LLMCompiler 的分解与调度，以及 Anthropic 文中的编排者与工作者模式；Chip Huyen 主张的"规划与执行分开"是这一节的默认参照。

> **要点：** 规划值不值得做，取决于任务有多少要读过才知道的不确定性。这一节的论文分别研究哪个角色需要大模型、规划在什么条件下值得、什么时候才该开始分解，以及组合多个单元时整体表现能不能预测。

先要回答什么时候真的需要规划。一个计划至少要说清三件事：当前要解决哪个子问题，依赖哪些已经确认的事实，以及怎样知道这一步做完了。在周报任务里，如果日志格式统一、检查规则已知，一段固定程序通常就够了；只有当文件格式、依赖关系和异常情况要读过之后才能确定时，系统才需要根据观察调整步骤。所以规划的必要性来自任务的不确定性，任务描述看起来复杂与否倒在其次，这也正是 Anthropic 区分工作流和 agent 的出发点。

[An Empirical Study of Harness Design for Coding Agents](https://arxiv.org/abs/2609.20804) 把这个问题放进了受控实验。它固定执行循环，分别改变规划、动作空间和上下文管理，把系统表现拆成可以分别检验的变量。作者在所测模型和编码任务上报告：上下文管理的主要收益来自减少窗口溢出；规划对较弱的模型主要帮着提高准确率，对较强的模型则更多体现为节约成本；让已经移出窗口的内容可以重新取回，在该设置下并没有额外提高准确率。这些结果说明组件的作用会随模型和预算变化，加了规划的系统未必更好。

规划之外还有分工的问题：计划里的每个角色是否需要同样大的模型。**[Think Big, Search Small](https://arxiv.org/abs/2607.07548)** 把分层搜索拆成三个角色，负责拆问题、派子查询的委派者，负责检索和抽取证据的执行者，以及负责回答的生成者。它固定回答的角色，分别调整前两个角色的模型规模。作者报告，在其多跳问答实验中，结果对委派模型的规模更敏感，而用大模型的轨迹蒸馏出来的小执行器可以保持竞争力。这种按角色定位瓶颈的实验设计值得借鉴；至于结论能不能推广到操作类、证明类或机器人任务，还得另行验证。

困难任务还要决定什么时候开始分解。一个还不可靠的方案如果过早被拆成许多子任务，后面的执行就会围绕一个错误的前提忙个不停。[Stellar Colosseum](https://arxiv.org/abs/2609.15983) 面向数学和理论计算机研究，先探索候选策略，用一道"准备度检查"判断路线是否成熟，成熟了才进入证明分解，还不成熟就回去继续探索，验证中的发现再送回受影响的部分。它说明规划除了分解，还包含对路线是否成熟的判断，这和 Tree of Thoughts 先评估候选再决定是否展开的思路相通。这套设计出自特定的科研场景，它的复杂程度不适合当作所有 agent 的默认模板。

![规划分支的三个实验视角](../assets/basics/b2-planning.svg)

*图：上：按角色拆分搜索 agent；中：固定执行循环、只改三个组件的受控实验；下：先判断路线是否成熟再分解。*

当分解出的子任务交给不同的单元去做，规划就和组合问题缠在了一起。[Raven](https://arxiv.org/abs/2609.33439) 把由模型和专用执行框架组成的单元用于跨领域分工，由上层负责协调子任务、处理执行依赖和整合结果。被组合的单元可能各有不同的工具和经验，这有点像第二阶段的 HuggingGPT 在 agent 层面的再现，HuggingGPT 让 ChatGPT 当控制器，把子任务分派给不同的外部模型。这样的系统要检查接口是否兼容、错误怎样传播、整合要花多少成本，单凭各个单元的成功率很难预测整体表现。

[Codebook Agent](https://arxiv.org/abs/2609.02264) 研究的是多个 agent 之间怎样通信：怎样为任务选择通信结构，又怎样衡量这个结构的实际代价。它发现通信图画得稀疏，未必就能减少 token 或提高效率，要验证的是局部工作能否转化成最终结果。把它和 [Mo' Models, Mo' Problems](https://arxiv.org/abs/2609.17306) 一起读，"多 agent 更强"就拆成了两个问题：选哪些模型，以及让它们怎样协作。两者的深入比较放在[协作章](08_collaboration.md)。

这几篇工作合起来，对规划研究提了一个朴素的要求：报告规划带来的收益时，要同时报告不规划和固定流程这两条基线，并且把计划、审查和协调额外花掉的预算算进去。

### 3. 观察：下一步需要什么，就去看什么

工具把内容返回来之后，系统并没有自动得到可用的证据。一次搜索可能返回一百处匹配，一段视频可能有几个小时，原样贴进上下文窗口，检索问题只是变成了一个更贵的阅读问题，而且窗口塞得越满，模型从中准确找回信息的能力越弱。挑选观察也和普通的文本摘要不一样：摘要想保留整体内容，决策用的观察则必须留下下一步要用的证据，包括还没解决的约束和可能推翻当前假设的信息。如果只保留看起来相关的片段，系统可能把自己的错误解释越描越深，所以要特别检查失败信息有没有在清理时被一起扔掉。

> 主线位置：第五阶段的上下文工程。接 ReAct 把观察送回模型的循环，回应 Lilian Weng 列出的"有限上下文长度"挑战；工程上对应 Anthropic《Effective context engineering for AI agents》里的即时检索与压缩。

> **要点：** 返回的内容太多，有用的证据很稀疏。这一节的论文分别研究先看哪里、留下什么，以及调用工具后的收益到底来自新信息，还是来自调用时写下的意图。

最常见的"太多"来自搜索。[A New Role for Relevance](https://arxiv.org/abs/2607.24223) 研究相关性估计在 agent 与语料的多轮交互中能起什么作用。传统检索用相关性一次性选出若干文档；这篇工作把相关性和类似 grep 的细粒度探索联系起来，用它决定先搜哪里、先给模型看哪些证据片段。由此可以看出，检索器找到了"可能相关的文件"，离 agent 完成证据的定位、组合和验证还差好几步，这是检索增强问答走进多步研究任务以后冒出来的新问题。

多模态任务让这个问题更加突出，因为一段长视频的信息量远远超过上下文能装下的范围。下面三篇要回答的是同一个问题：下一次该看视频的哪一段，或者调哪个工具，才能消除眼下最大的不确定性；看完更多帧本身算不上目标。它们的差别在于怎样挑：先粗看再放大，按问题调专门的工具，或者再加上外部检索。[OmniReasoner](https://arxiv.org/abs/2607.19339) 先用较低的成本粗看一遍长音视频，再决定要不要放大某个时间段。[Online Video Agent Harness for Long Video Understanding](https://arxiv.org/abs/2609.12818) 从给定的视频和用户问题出发，按需调度专门的工具并汇合证据。[AdaVDR](https://arxiv.org/abs/2608.25559) 把视频理解和外部检索结合起来，并在中间结果不可靠时回退。

执行轨迹是第三种"太多"。用来改进 agent 的轨迹往往很长，又夹杂大量重复的失败。**[STRACE](https://arxiv.org/abs/2607.07702)** 先在一批轨迹的层面减少重复出现的失败，再在单条轨迹里沿着步骤之间的依赖，保留那些可能解释失败原因的步骤。和简单截断相比，它想保住诊断所需的结构，最近的文本只占其中一部分。论文报告的因果定位要结合它的干预方式和评测设定来理解，依赖图上被保留下来的节点，还不能直接当作已经证明了的真实根因。

![观察：下一步需要什么，就去看什么](../assets/basics/b3-observation.svg)

*图：左边是三种返回太多的情况，中间是四种选择方式，右边是下一步要用的证据；下方是 TextCall 的对照设计和观察进入状态的三种形式。*

挑选观察的前提，是观察真的带来了新信息。可调用工具后成绩变好了，收益未必来自工具返回的内容。[Thinking With Tools, Not With Pixels](https://arxiv.org/abs/2608.09682) 设计了一个对照，图里叫 TextCall：模型照常写下工具调用，比如要放大图像的哪个位置、为什么放大，但返回的图像被换成占位符。如果删掉被认为关键的图像以后效果依然保留，起作用的就可能是调用时写下的目标和位置，也就是调用帮模型理清了思路。这个结果推不出所有视觉工具都没用，它提醒我们把"获得新证据"和"帮模型理清思路"分开测量。

长期任务还要决定观察以什么形式留在后面的状态里。[CompactionRL](https://arxiv.org/abs/2607.05378) 把上下文压缩放进训练过程，让模型自己学会怎样压缩；Anthropic 上下文工程文章里的压缩，则是由工程师写规则把旧的历史总结成摘要。[MemHarness](https://arxiv.org/abs/2607.28272) 讨论积累下来的经验怎样按当前任务重新组织；[Catastrophic Remembering](https://arxiv.org/abs/2608.11095) 则提醒，持续积累下来的指令越来越多以后，过时的那部分也会变成负担。三篇合起来说明，"保留全部历史"远远算不上完整的状态管理方案，具体机制在[记忆章](02_memory.md)。

### 4. 执行框架本身怎样被理解和改进？

当一个 agent 只有几十行循环代码时，开发者对每个行为由哪里控制一清二楚；等系统长大了，同一个行为可能同时牵涉提示词、工具包装、错误重试和状态存储。修改框架改变的是模型被要求怎样工作，模型内部存储的知识并没有动，可两者又会相互影响：更严格的控制规则可能帮了小模型，也可能限制了强模型的探索空间。所以研究框架优化，首先要标出哪些部分可以修改、候选修改由谁提出、用什么独立标准挑选，再区分修改是只适配了固定任务，还是能迁移到新任务。

> 主线位置：第五阶段。接 SWE-agent 与 Agentless 的框架对照，对应 OpenAI《Harness engineering》里"失败时补上缺失的工具和结构"的做法；更激进的自动改写与递归改进见[第 03 章](03_skills_and_self_improvement.md)。

> **要点：** 改进执行框架要先回答三个问题：哪些部分可以改，谁来提出修改，用什么独立标准挑选。自动改进最常见的坑，是修改只适应了开发时用的那批任务。

一轮框架改进通常从失败轨迹和运行诊断出发：先定位某个行为对应哪段代码，再提出对指令、工具或循环的修改，交给独立的任务验证，最后提交或回退，新的运行又会产生新的诊断。

![执行框架改进的一轮](../assets/basics/b4-harness-improve.svg)

*图：上排是一轮框架改进的流程，下排把本节论文按"哪些可改、谁来提、用什么挑"三个问题归类。*

第一步定位就不容易。框架长大以后，让模型"优化一下这个 agent"往往无从下手，它得先找到某个行为对应的实现在哪里。[Harness Handbook](https://arxiv.org/abs/2607.13285) 用静态分析加上模型辅助，把行为和源代码的位置联系起来，再引导 agent 一步步找到相关的实现。找到了正确的修改位置，和改完以后任务表现真的提高，是两步：前者是框架维护的前提，离后者还有一段距离。它也说明让系统结构对维护者可读很重要，这和 OpenAI 报告里"让应用对 agent 可读"的思路相通。

可以改的部分也不止代码。[MemoHarness](https://arxiv.org/abs/2607.14159) 把框架拆成六个可编辑的控制维度，它不给所有任务套同一个固定配置，转而保存运行诊断和跨任务经验，再为新案例挑选合适的控制方式。[Recursive Experiential-Working Memory Evolution](https://arxiv.org/abs/2608.24876) 把记忆分成记录当前进度的部分和积累经验技能的部分，让失败更容易定位到具体的记忆组件，再做带验证的局部更新。两者都在利用经验，经验决定的却是不同的对象，前者决定框架怎样控制，后者决定改哪一块记忆。

谁来提出修改，是第二个问题。**[Better Harnesses, Smaller Models](https://arxiv.org/abs/2607.08938)** 让一个专门负责改框架的 agent 从失败轨迹里寻找适配，同时考虑换用更便宜的模型。它适合接在三.1 的 The Harness Effect 后面读，那项工作固定任务和模型、只替换编排层。标题里的成本降幅对应论文特定的任务和计费条件，不适合拿来估算自己的部署预算。值得追问的是：小模型在怎样的执行安排下，能够接手原本交给大模型的任务？搜索框架本身花掉的开销有没有被计入？选出来的框架到了新任务上还有没有效？[SoL-Pi](https://arxiv.org/abs/2609.20519) 让一个自动研究循环提出修改，从中筛选可以复用的机制，涉及动作执行、上下文压缩、观察处理和委派阅读。[HarnessDev](https://arxiv.org/abs/2609.01437) 则反过来测量模型本身能不能当这个提出修改的角色，它把"创建和改进一个能运行的执行框架"作为评价对象，区分从最小起点搭建和根据反馈演化两种情形。它揭示了旧评价习惯的一个盲点：一个模型在现成框架里干活很好，未必就擅长设计框架。

用什么标准挑选，是第三个问题，也是自动改进最容易出事的地方。如果修改只是适应了开发时用的那批任务，系统并没有获得通用能力，这就是过拟合。[HarnessCompass](https://arxiv.org/abs/2608.01918) 正面处理这个问题：它只允许与具体任务无关的修改，引入更主动的反馈，并且分组件优化，减少组件之间的互相干扰。读这类工作时，最重要的实验条件是验证任务是否独立于开发任务，以及修改之后有没有把其他能力一起弄坏，迭代了多少轮倒在其次。

最后两篇把视线从修改过程移到了框架的设计目标上。[Language model harnesses are compositional generalizers](https://www.alphaxiv.org/abs/2607.language-model-harnesses) 研究框架怎样组织可复用的行动，以及这能否帮助组合泛化；[The Evolution of AI Office](https://www.alphaxiv.org/abs/2609.evolution-ai-office-agents) 则把办公 agent 的目标放在可检查、可修改的交付物上。两者一个关心框架内部，一个关心任务怎样算完成。拿周报来说，周报交了以后，导师下周想加一列新指标，这张表能不能被顺手改好，同样是衡量一个 agent 的标准。

### 5. 训练模型与修改框架，能不能各做各的？

前面几个分支大多假设模型不动、只改框架。可模型总要训练，而训练用的轨迹是在某一套工具和上下文规则下产生的；部署时的框架又决定了模型会遇到哪些状态。如果两边各自变化，训练时学会的动作格式、对反馈的理解，甚至什么时候该停下来的习惯，都可能在部署时失效。这里有三个层次的问题：动作接口是否兼容，模型在部署时遇到的状态是否和训练时一样，模型和框架能否一起优化。第一个靠约定就能解决，后两个通常要重新收集轨迹或检验迁移。

> 主线位置：第二阶段的工具学习与第五阶段的执行框架在这里交汇。接 Toolformer、ToolLLM 的训练路线；模型与框架共同演化的更多讨论见[第 03 章](03_skills_and_self_improvement.md)和[第 05 章](05_rl_and_distillation.md)。

> **要点：** 训练用的轨迹要和部署时的框架对得上。一条路让训练直接接在部署时用的框架上，从模型调用的边界记录交互；另一条路把复杂框架带来的好行为学进模型。

动作接口兼容了，训练仍可能对不上，问题出在训练记录本身。部署时的框架会截断历史、合并请求，或者改变工具返回的格式，训练器却需要知道模型每一次做决定时实际看到了什么，并把奖励对应到正确的模型输出上。如果训练器看到的是框架加工前的原始记录，它优化的可能是部署时根本不会出现的状态。这就像用一份排版过的笔记去复盘一场考试，复盘时看到的内容和考场上看到的并不一样。

有三篇工作专门处理这个落差。它们共用一个思路：让部署时的框架照常运行，在模型调用的边界上设一个代理，把每次请求和响应转给被训练的模型，同时记录下来交给训练器。[ClawGym II](https://arxiv.org/abs/2608.16798) 以黑箱方式把复杂的框架和强化学习连起来，环境放在隔离的执行沙箱里。[Agent Lightning v1.0](https://arxiv.org/abs/2608.17528) 强调由部署框架掌握交互循环，训练器只观察模型的请求和响应；这样做就要从记录里重建出每次决策的输入，重新分词、重算每个输出的概率，再估计每个动作比平均水平好多少，强化学习据此更新模型。[LEGO-RL](https://arxiv.org/abs/2608.17393) 同样关注原生编码框架和强化学习的连接，还把环境崩溃、奖励漏洞以及训练与执行之间的差异纳入了讨论。三篇的差别在工程切入点：ClawGym II 重在把任意复杂的框架当黑箱接上，Agent Lightning 重在轨迹重建的一致性，LEGO-RL 重在训练中出现的故障。

![训练与部署框架的连接](../assets/basics/b5-train-deploy.svg)

*图：上：部署框架掌握交互循环，代理设在模型调用边界，训练器据记录重建轨迹；下：比较时的四组条件。*

另一条路线反过来问：复杂框架带来的好行为，能不能学进模型里，部署时就不必保留那么多专门的逻辑？[Harness-Zero](https://arxiv.org/abs/2609.24974) 研究框架蒸馏，也就是用复杂框架下产生的轨迹训练模型，让模型在简单框架里也能做出类似的行为。难点在于两个框架的动作空间和模型能看到的信息不一致，所以学到的东西要能在目标框架里执行，照抄复杂框架下的文字行不通。与它相邻的 [Co-Evolving Harnesses and Models](https://arxiv.org/abs/2609.09134) 讨论为什么让弱模型直接模仿强模型的完整轨迹未必有效，并研究另一种纠正方式：先在弱模型自己的轨迹里找到出错的那一步，只修正那一处。

这组工作让"模型强还是框架强"这种二选一的问法显得过于简单，模型、接口和训练信号会相互适应。比较时可以设置四组条件：原始系统，只更新模型，只更新框架，两者同时更新，并且把工具权限和总预算对齐。没有这样的区分，就很难知道增益能不能迁移到另一个部署环境。

### 6. 一次行动成功之后，系统还能安全继续吗？

完成了当前这个动作，整个任务未必就结束了，后续行动也未必仍然得到授权。写对了一个文件之后，系统可能接着去覆盖别的文件；一次查询有权限，查到的敏感信息却不一定可以随意传播。所以一个合理的工作循环，在每次动作之后都要能区分三种状态：还需要更多证据，需要人来决定，任务已经完成。分不清这三种状态，继续执行这件事本身就会成为失败的来源，动作做得再准也补救不了。

> 主线位置：边界。接 Chip Huyen 对写入动作风险的提醒，以及 Anthropic 在沙盒中充分测试、配好护栏的建议；OpenAI 报告里的机械化约束和后台清理也属于这一层。

> **要点：** 一次动作之后，系统要先判断该继续、该请人决定还是该停下。这一节的论文分别研究自动修改能否撤回、风险出现在系统生命周期的哪个阶段，以及安全怎样和任务完成一起优化。

完成眼前的任务和保持长期可用是两件事。在周报任务里，如果助手为了让表格好看，顺手清理掉几组"看起来没用"的崩溃日志，周报是交了，下周排查问题时却无从下手。同样，让 agent 自动修改工具配置，可能让这一次任务快了，却破坏了以后的权限检查。所以检查最终答案之外，还要问：系统改了什么？改动能不能撤回？失败之后由谁来处理？

[EvoUndo](https://arxiv.org/abs/2608.28363) 把"自动修改之后能否恢复"当作一个独立的条件来研究。修改可能产生持久的副作用，保存一份旧提示词恢复不了这些变化，所以作者在不同于修改创建时的状态下检验修改能否撤回。在 600 个未见过的任务里，他们找到了 197 个提升了能力、却没有通过可恢复性检验的修改。[HarnessRisk](https://arxiv.org/abs/2608.17597) 则按生命周期来组织安全测试，把配置、能力扩展、运行、状态保存、动作控制和事件恢复六个阶段放在一起。它表明，风险可能发生在模型刚读到恶意提示的那一刻，也可能通过保存下来的状态和扩展组件一路延续下去。

![一次行动之后](../assets/basics/b6-safe.svg)

*图：左上是一次动作之后的三个出口，右上是 EvoUndo 的可恢复性验证，中间是 HarnessRisk 的六个生命周期阶段。*

既然风险出现在整个生命周期里，安全就很难靠"再加一句安全提示"解决。[SafeEvolve](https://arxiv.org/abs/2609.02786) 研究执行框架和策略怎样利用经验共同改善安全性；[EvoSafeHarness](https://arxiv.org/abs/2609.05903) 针对特定的模型和领域去搜索合适的防护框架。这类优化都应当同时报告任务完成情况和约束遵守情况，因为一个为了安全拒绝所有任务的系统，和一个为了完成任务无视限制的系统，都没有回答真正的问题。更完整的威胁与评价分类在[安全章](07_safety.md)。

落到工程上，持续执行可以先从明确的运行边界入手：工具声明自己接受的输入范围，可以挡住无效调用；不可逆操作前设置确认点，可以控制副作用；任务保留预算和退出条件，失败之后记录下实际的状态，事后才能恢复。

## 四、把不同路线放在同一张比较表里

六个分支涉及几十篇论文，可它们改动的对象只有几类：工具的表达形式，规划与组件安排，观察的筛选，经验与局部配置，框架的自动修改，训练与部署的连接，框架行为的内化，以及运行生命周期中的约束。真实的系统往往同时改了好几样，如果不分开检查，就会把整套系统的收益全记在某一个组件头上。下面这张表按改动的对象排列，写明每一类想解决的困难、要付出的代价，以及证明收益时必须保留的对照。

> **本节要点：** 六个分支改动的对象归成八行。第二节末尾的总对照按方法家族比较，这里按改动的对象比较；最右边一列可以拿来审自己的实验设计。

| 改变什么 | 代表入口 | 主要想解决的困难 | 通常要付出的代价 | 必须保留的对照 |
|---|---|---|---|---|
| 工具表达形式 | Bitter Lesson、Harness as a Language | 多次调用的依赖与组合不易表达 | 更复杂的执行与权限检查 | 同模型、同工具能力、同预算 |
| 规划与组件安排 | Empirical Harness Study、Stellar Colosseum | 步骤依赖不清，过早分解 | 额外计划、审查和协调 | 无规划或固定流程基线 |
| 观察与证据选择 | A New Role for Relevance、OmniReasoner、Online Video Agent Harness | 有用证据稀疏，返回内容太多 | 选择观察的决策与工具开销 | 随机或固定取样、去掉新观察 |
| 经验与局部配置 | MemoHarness、Recursive Experiential-Working Memory Evolution | 一个固定框架不适合所有情况 | 存储、检索、经验失效处理 | 无记忆、错误记忆、未见任务 |
| 框架的自动修改 | HarnessCompass、SoL-Pi | 手工调整慢，组件相互干扰 | 搜索与验证成本，回归风险 | 固定模型、独立验证集 |
| 训练与部署连接 | ClawGym II、Lightning、LEGO-RL | 训练轨迹与原生运行不一致 | 轨迹重建和训练基础设施 | 相同部署框架的训练前后对照 |
| 框架行为内化 | Harness-Zero、Co-Evolving | 专用框架复杂且难迁移 | 蒸馏数据与额外训练 | 同一个目标框架、纠正与模仿对照 |
| 生命周期约束 | EvoUndo、HarnessRisk | 一次改进留下难恢复副作用 | 恢复验证、权限与记录成本 | 完成率和风险同时报告 |

这些路线可以组合，组合本身也需要证据。比如一个系统同时用了程序式调用、记忆、多 agent 和反思，就有四个可能增加成本的部分，只看最后分数高，说明不了每个部分都必要。Anthropic 那篇文章反复强调从最简单的方案出发，道理也在这里：逐个去掉组件做对照，研究结论才能被理解、能被迁移。

## 五、代表研究：接口、计算与团队组成

工具接口、模型内部的计算方式和团队的组成，都会影响任务表现，它们改变的却是不同的层次。下面三项研究正好各占一层。读的时候先认出论文真正改动的变量是什么，再把任务质量和执行成本放进同一套比较条件里。

> **本节要点：** 三项研究分别改动接口形式、模型内部的计算和团队的组成。要判断改进来自哪里，就得在同样的工具权限和预算下比较。

### The Bitter Lesson of Tool Calling｜2608.06370

[原文](https://arxiv.org/abs/2608.06370)。它比较两种接口：模型一次次生成结构化的 JSON 调用，或者生成一段调用工具的程序。程序可以自然地表达循环、依赖和并行，也带来了代码执行和错误处理的额外要求。作者在函数调用基准 BFCL v4 上比较了 14 个模型，报告程序式调用在其中 11 个上与原生 JSON 调用持平或更好，并另外考察了并行分支和上下文干扰。收益并非在每个模型上都一致，复杂调用场景也没法用一个总分完全概括。题目借用了 Rich Sutton 那篇著名短文《The Bitter Lesson》的名字。

**研究意义：** 它说明，模型能力之外，接口形式本身也会影响任务表现。这和第四阶段的两项发现一脉相承：SWE-agent 给同一个模型换上更好用的命令，修复成功率明显提升；CodeAct 让动作写成代码，成功率最多高出 20%。**比较条件：** 要保持工具权限一致，统计失败的调用，并把代码运行的成本算进去，才能判断收益确实来自接口的表达能力。

### Looped Language Models Improve Compositional Tool Calling｜2608.18171

[原文](https://arxiv.org/abs/2608.18171)。它研究让模型在内部循环计算，也就是把同一组网络层反复用好几遍，是否有助于完成彼此依赖的多步工具调用。研究区分了孤立的 API 调用和组合任务，并讨论了按需决定循环次数时性能和成本之间的权衡。

**研究意义：** "循环"可以发生在模型内部，也可以发生在模型和工具之间。前者改的是模型一次生成里的计算，后者是模型提出动作、工具执行、观察再送回模型的来回，两者是不同的机制。此文的主问题属于[效率与架构](13_efficiency.md)，在本章作为交叉阅读。**局限：** 要核对训练配方和计算预算是否匹配，计算量更大带来的收益，没法全部归功于架构本身。

### Mo' Models, Mo' Problems: How to best select model pools when designing Multi-Agent Systems｜2609.17306

[原文](https://arxiv.org/abs/2609.17306)。一个多 agent 系统要先选出一组候选模型，叫模型池。作者比较了几种选模型池的策略，区分在生成之前把任务分给某个模型的路由，和在生成之后合并多个模型答案的聚合，并在其设置中观察到，扩大模型池未必带来改善。

**研究意义：** 模型池应当按成员之间的互补性来构建，成员数量多少只是表面。实验应当比较新加入的成员是否提供了独有的能力，以及路由和聚合能否利用这种差异。**局限：** 候选模型、聚合器、任务类型和预算都会影响结论，本章不把论文中关于特定模型家族的结论推广到所有系统。进一步阅读见[协作专题](08_collaboration.md)。

这三篇合在一起，提出了一个可以检验的问题：改进究竟来自更好的模型、更多的计算，还是更合适的系统接口？三者应当分开比较，别把所有增益都笼统地记作"agent 更强了"。

## 六、系统设计中的关键区分

本章反复出现几组容易混淆的概念。它们看起来都是常识，可在读论文和做实验时，一不留神就会把左边一列当成右边一列来报告。Chip Huyen 提到的"agent 以为自己完成了任务"，很大程度上就是这几组区分没有守住的结果。

> **本节要点：** 五组容易混淆的概念，左边一列常被当成右边一列来报告。守住这几组区分，才说得清一次成功究竟依赖了什么。

| 容易混淆 | 正确的区分 |
|---|---|
| Agent 与固定工作流 | 看下一步是否由模型动态决定，用没用大模型说明不了问题 |
| 规划与执行 | 计划只是候选步骤；工具结果才说明动作有没有发生 |
| 工具会返回文字与工具可信 | 外部文字可能错误，甚至包含诱导系统越权的指令 |
| 调用格式正确与任务完成 | 参数符合格式只是起点，结果与约束还要检查 |
| 多尝试几次与方法更好 | 重试提高成本，比较时应一起报告预算 |

要检查这几组区分，前提是有完整的执行记录：每一步模型写了什么、执行框架实际做了什么、环境返回了什么。没有这份记录，就很难定位一次成功究竟依赖了什么。

## 七、研究机会

以周报为例：助手要把一周二十几组训练实验整理成表格，标出崩溃的实验，和基线比较，再发给导师。从说出怎么做到把周报真正交到导师手里，中间跨过了三道坎。先要把一句模糊的请求变成一串可以执行、可以修正的步骤，这是规划阶段留下的问题；再要让执行系统根据实际遇到的情况调整自己，这是执行框架阶段的问题；最后还得保证每一步做完以后，系统仍然处在一个可以恢复、可以继续的状态，这是边界上的问题。三道坎合起来，就是姚顺雨所说的效用问题落到基础系统上的样子：基准上的成功率很高，真实工作流里的事情却未必做成了。

> **本节要点：** 三个研究问题依次对应周报的三道坎：开放目标怎样变成任务结构，执行框架怎样按任务状态自适应，长任务里的行动单元怎样做到可恢复、可组合。

![周报的三道坎与三个研究问题](../assets/basics/opportunities.svg)

*图：周报从"说出怎么做"到交到导师手里的三道坎，分别对应规划阶段、执行框架阶段和边界，下面挂着本节的三个研究问题。*

**1. 如何把开放目标转化为可执行、可修正的任务结构？**

真实的目标往往没有完整的规格，依赖关系也常常要等工具执行以后才显现出来。在周报任务里，"哪些实验算崩溃"这件事，要读过日志才知道该怎么定义：只跑了一半的实验，可能是崩了，也可能还在跑。所以预先生成的清单只能当作起点，需要的是一种任务表示，能够逐步补全前提、发现缺失的步骤并更新计划。Lilian Weng 在 2023 年就把"遇到意外时调整计划"列为难点，Chip Huyen 也对模型的规划能力存疑，这个问题至今没有很好的答案。评价的关键，是看系统在新环境和不完整信息下，能否减少对人工流程设计的依赖，同时让目标和状态始终可以被检查。

**2. 如何让执行框架根据任务状态自适应，摆脱固定配方？**

工具暴露多少、观察粒度多细、重试和停止规则怎样定，这些通常都是开发者预先设好的，不同任务需要的组合却并不相同。Anthropic 的工具与上下文工程文章给出了大量手工经验，OpenAI 的报告展示了人怎样一点点把环境调到适合 agent；下一步自然是把这些经验变成系统自己可以做出的选择，也就是把框架配置变成一个受约束的决策问题。难点在于分清收益来自减少交互、改善依赖的表达，还是仅仅多花了预算。实验上应当在未见过的任务和不同的模型上检验配置能否迁移，避免只是对固定基准搜出了一套更合适的提示。

**3. 如何在长任务中形成可恢复、可组合的行动单元？**

单次工具调用缺少对前提、后果和失败恢复的统一描述，多个局部正确的动作组合起来也未必可靠。可以研究带"状态契约"的行动接口，也就是每个动作都声明自己需要什么前提、会造成什么改变、失败了怎样回退，再在执行过程中动态核查这些契约。周报助手在删除任何一个日志之前，如果都能说清这一步可不可以撤回，误删崩溃日志这类事故就不会发生。研究的重点是，面对工具失败、环境变化和不可逆操作时，系统能否定位受影响的依赖，恢复必要的状态，然后继续完成目标。这也回应了姚顺雨的另一个观察：真实世界里的任务是一个接一个连续发生的，一个 agent 今天留下的状态，就是它明天开始工作的环境。
