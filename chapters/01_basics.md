# 01｜基础、规划与工具：从回答问题到完成任务

[首页](../README.md) · [专题索引](../README.md#topics) · [文献目录](../catalog/01_basics.md)

前置阅读：若还不熟悉模型参数、训练与推理、token 和上下文，先看[大模型前置知识](../docs/llm_primer.md)。本章在这些概念上解释系统如何行动，不要求已经学过 Agent 框架。

## 方向背景：为什么需要从语言模型走向行动系统

语言模型擅长根据输入生成内容，但完成任务还需要获取新信息、改变外部状态并检查结果。知识存在于模型参数中，并不意味着模型能够访问当前环境；生成一段正确的操作描述，也不等于相应操作已经执行。Agent 研究的出发点，就是把语言推理与可执行动作连接起来，使系统能够在反馈中推进目标，而不只交付一次回答。

这种转变把研究对象从单次生成扩展为一个闭环：观察环境、选择动作、执行工具、接收反馈、更新状态，以及判断是否完成。闭环中任何一环失效，都可能使局部正确的输出无法形成可靠结果。任务越长，早期错误、信息缺失和状态变化对后续决策的影响越明显，规划、观察管理与错误恢复因此成为基础问题。

本章先建立最小工作循环，再讨论工具接口、规划、观察、执行框架、训练适配与持续执行。比较方法时需要区分模型能力与系统设计：更好的结果可能来自更合适的动作空间、更充分的反馈或更大的预算，而不一定来自模型本身变强。

## 1. 把工作循环拆开

输入包含用户目标、当前已知状态、工具说明以及尚余预算。模型提出下一步动作；执行框架检查工具名、参数与权限；工具改变环境或返回信息；系统把观察送回模型。达到明确的成功条件、无法继续或用完预算时，循环终止。

```text
目标与当前状态 → 提出动作 → 校验参数和权限 → 执行工具
       ↑                                      ↓
       └──── 更新任务记录 ← 检查结果 ← 返回观察 ───┘
                        ↓
                  完成 / 停止 / 请人处理
```

“规划”负责组织步骤、协调依赖，并根据反馈调整行动；“工具调用”是选择可执行操作；“观察”是工具实际返回的信息。三者必须区分：写出“运行了测试”不是执行测试，计划中列出“修复错误”也不是检查通过。

这里的 *harness* 译为“执行框架”：它承接模型、工具和环境，管理循环、日志、预算及停止条件。它不是模型本身；改变框架可以在不训练模型的情况下改变系统行为。区分框架改进与模型训练，是读近期论文的第一道门槛。[工作流与 Agent 的工程区分](https://www.anthropic.com/engineering/building-effective-agents)

## 2. 发展脉络：从工具调用到完整任务系统

语言模型走向 Agent，并不是单纯多接几个工具，而是逐步承担原本由人或外部程序负责的决策。首先要让语言输出成为可执行动作，其次要让动作保持依赖关系，再利用反馈纠错，最后把整个循环放进实际任务中。下面沿这几个问题说明工具学习、规划、反思与执行框架的联系；它们可以并行发展，不是一条新方法依次淘汰旧方法的路线。

### 2.1 从生成文字到选择并使用工具

接入工具以后，模型除了组织答案，还要决定何时调用、调用哪个接口、怎样传参以及如何利用结果。[ReAct](https://arxiv.org/abs/2210.03629)将推理与行动交替组织，使新观察能够改变下一步选择；[Toolformer](https://arxiv.org/abs/2302.04761)则研究模型怎样通过训练学习工具使用。两者分别从执行循环和学习信号切入同一个缺口。

工具集合扩大后，选择和参数生成也需要系统评价。[API-Bank](https://arxiv.org/abs/2304.08244)把工具增强对话组织成任务；[Gorilla](https://arxiv.org/abs/2305.15334)与 [ToolLLM](https://arxiv.org/abs/2307.16789)进一步研究 API 使用与训练。于是，能调用一个工具的演示，逐渐发展为面对不同接口能否正确选择和执行的能力问题。

### 2.2 从单个调用到有依赖的行动序列

一个调用成功，并不意味着多个调用能组成完整工作。前一个结果可能是后一个参数，一些步骤可以并行，另一些必须等待反馈。系统因此需要决定怎样分解目标，以及何时改变原有安排。

[Plan-and-Solve](https://arxiv.org/abs/2305.04091)研究先规划再求解的提示方式，[Tree of Thoughts](https://arxiv.org/abs/2305.10601)通过探索与评价多个候选思路组织搜索。它们提供任务分解和候选选择的基础，但推理组织不能直接等同于外部行动。[ReWOO](https://arxiv.org/abs/2305.18323)进一步处理推理与工具观察的关系，[LLMCompiler](https://arxiv.org/abs/2312.04511)则把函数调用的依赖与并行执行作为系统问题。

### 2.3 从一次尝试到带着反馈继续工作

预先安排再完整的计划，也可能遇到工具错误或未预见的状态。因此，Agent 不仅需要执行原计划，还要判断错误、修改后续动作，并保留有用经验。[Reflexion](https://arxiv.org/abs/2303.11366)将任务反馈整理为语言反思，供后续尝试使用。这与当前回合生成更长的推理不同：它改变的是下一次尝试能够获得的信息。

反馈也可能被误解，所以反思不能代替外部检查。这个限制引出记忆与验证的分工：记忆负责保存经验，环境和验收机制负责检查经验是否改善实际结果。行动持续发生以后，两者都成为执行循环的一部分。

### 2.4 用实际任务检验整个执行循环

只有完整任务才能暴露各环节连接后的问题。[WebShop](https://arxiv.org/abs/2207.01206)提供网页购物环境，[Mind2Web](https://arxiv.org/abs/2306.06070)提供网页任务的学习材料；[WebArena](https://arxiv.org/abs/2307.13854)进一步用可复现的网站承载操作任务。模型需要把观察与多步动作连接起来，而不只是独立回答一个工具问题。

软件方向的 [SWE-bench](https://arxiv.org/abs/2310.06770)要求修复真实仓库问题，使理解代码、定位、修改与测试相互依赖。[SWE-agent](https://arxiv.org/abs/2405.15793)研究 Agent 与计算机的交互界面怎样支持这些步骤；[Agentless](https://arxiv.org/abs/2407.01489)则说明结构化、较少自主循环的流程同样值得比较。研究由此不再只是增加自治程度，而是判断任务究竟需要哪些动态决策。

这些路线汇合后，基础问题从怎样调用工具，扩展为怎样让信息、决策、行动与反馈形成稳定循环。后面的前沿研究分别改进这些环节及其连接，而不是仅为系统增加模块。

## 3. 前沿研究方向

经典工作建立了工具与反馈相连的执行循环，前沿研究进一步追问这个循环在哪些环节仍然不可靠。可以从模型面对的决策顺序展开：先研究工具如何表达，再研究任务怎样规划、观察怎样筛选，随后讨论执行框架与模型训练如何配合，最后检查行动结束后能否安全继续。下面六个方向分别对应接口、决策、信息、系统、学习和运行边界，近期论文放在各自解决的瓶颈中比较，而不是按发布日期排列。

### 1. 工具接口决定了模型能够怎样行动

工具接口同时规定动作空间与信息空间：系统不只决定“可以调用什么”，也决定模型看到多细的参数说明、返回多少结果，以及失败怎样表达。接口越通用，模型承担的选择与解释负担可能越大；接口越专用，环境迁移时又可能失效。因此，这个分支应先分清接口设计、工具选择和调用序列组织，不能把合法 JSON、正确调用与最终完成任务当作同一个指标。

**[The Harness Effect](https://arxiv.org/abs/2607.06906)** 这项工作在固定任务和模型的条件下替换编排层，考察上下文组装、工具暴露和失败处理怎样改变任务成本。作者报告其企业任务样本上成本、时延和 token 使用下降，质量变化则受模型能力影响。它适合说明“工具包装”会改变整个交互过程，而不是证明任意新框架都优于旧框架；小规模固定任务上的收益也不能直接外推到所有企业流程。

以批量文件检查为例，工具接口可以只允许逐个读取文件，也可以接受一组文件名，或允许程序通过循环组织读取。三者看起来都能完成检查，实际上给模型的动作空间不同。第一种最容易逐步审计，却需要更多往返；第三种表达力强，但一次错误程序可能影响多个步骤。接口设计因此同时影响能力、代价和可控性。

近期的 [The Bitter Lesson of Tool Calling](https://arxiv.org/abs/2608.06370)比较原生 JSON 调用与程序式调用，适合放在这条发展线上读。关键不是把“代码”当成天然更聪明的形式，而是注意它能直接表示循环、变量与依赖。需要连续取多个返回值时，这种表达方式可能减少模型重复组织同一逻辑的负担；然而代码能表达的动作也必须由执行环境限制。部署时还需根据工具权限限制程序能够执行的操作。

[Harness as a Language](https://arxiv.org/abs/2609.26891)把这个想法继续推进：它研究能否用一个足够小的可编程执行原语来表达更复杂的 Agent 行为，而不是为记忆、委派和递归分别堆叠专门模块。这里值得追问的是“简化了哪一层”。核心原语少，不代表运行行为容易理解；程序可以递归调用模型后，还需要清楚的预算、监控和终止约束。它与前一篇工具接口比较相连，但研究目标更接近执行系统的表达方式。

还有一类改进关注动作何时开始。[Speculative Programmatic Tool Calling](https://www.alphaxiv.org/abs/2608.spec-ptc)讨论在程序仍在生成时，提前启动已经能够解析的工具调用，以重叠生成和等待时间。这与选择工具、规划依赖的作用不同：前者决定调用什么，执行调度则决定已确定的调用何时启动。调度收益取决于工具延迟、依赖关系，以及提前执行是否安全。

工具接口还存在学习的一面。[MidTool](https://arxiv.org/abs/2608.20314)从中期训练数据入手，组织真实 API、文档和工作流，使模型学习工具能做什么、参数从何而来、调用怎样组合。[Salesforce Koa](https://arxiv.org/abs/2609.15066)则把工作流规格扩展成多轮模拟任务，再通过任务结果形成训练信号。这两篇工作的联系在于：一次工具失败未必只靠改接口就能解决，也可能暴露出模型没有学会理解工具或利用上下文的参数依据。具体训练方法在[第 04 章](04_training_data.md)与[第 05 章](05_rl_and_distillation.md)展开。

### 2. 规划不是把待办清单写得更长

规划需要解决的是行动依赖：哪些步骤可以独立进行，哪些必须等到前面的结果出来，发现假设错误后又如何修改计划。把问题拆成更多子任务并不必然降低难度，因为拆解本身可能遗漏约束，执行者还要把结果按正确接口交回。比较规划方法，应同时考虑分解质量、执行成本与重新规划的触发条件，而不是只看计划是否详细。

**[Think Big, Search Small](https://arxiv.org/abs/2607.07548)**将分层搜索中的任务委派、检索执行与答案生成分开，并固定回答角色来比较前两类角色的容量。作者报告其多跳问答实验对委派模型规模更敏感，经过轨迹蒸馏的小执行器可以保持竞争力。这里真正值得借鉴的是按角色定位瓶颈的实验设计：并非每个环节都需要同样大的模型，也不能把这一分工结论不加验证地推广到操作、证明或机器人任务。

一个计划至少应回答：当前要解决什么子问题，依赖哪些已经确认的事实，怎样知道该步骤完成。对于格式与检查规则已知的一组文件，固定程序通常足够；若文件格式、依赖关系和异常情况需要在读取后才能确定，系统才更需要根据观察调整步骤。这说明规划的必要性来自任务的不确定性，而不是任务描述看起来复杂。

[An Empirical Study of Harness Design for Coding Agents](https://arxiv.org/abs/2609.20804)没有只比较几个完整框架，而是在固定执行循环下分别改变规划、动作空间和上下文管理。这种组件对照把系统表现拆成可以分别检验的变量。作者在所测模型与编码任务上报告：上下文管理的主要收益来自减少窗口溢出；规划对较弱模型更像准确率帮助，对较强模型则更多表现为成本节约；让已卸载的内容能够重新取回，在该设置中并未额外提高准确率。这些结果说明，组件的作用会随模型和预算变化，不能仅凭“有规划、有恢复接口”就认为系统更好。更合适的研究问题是“在什么条件下值得规划，以及值得为此付出多少成本”，而不是“规划是否一定有用”。

困难任务还需要决定什么时候分解。过早把一个尚不可靠的方案拆成许多子任务，会让后续执行围绕错误前提忙碌。[Stellar Colosseum](https://arxiv.org/abs/2609.15983)在数学和理论计算机研究中先探索候选策略，用准备度检查决定何时进入证明分解，再把验证发现送回受影响的部分。它说明规划不仅包含分解，还包含对路线是否成熟的判断。这个设计来自特定科研场景，不能直接拿其复杂程度作为所有 Agent 的默认模板。

规划与模块组合也会相互影响。[Raven](https://arxiv.org/abs/2609.33439)把模型与专用执行框架组成的单元用于跨领域分工，由上层协调子任务、执行依赖和结果整合。它与把一个模型叫很多次不同：被组合的单元可能拥有不同的工具和经验。这样的系统需要检查接口兼容、错误传播和整合成本，不能只按子代理各自的成功率预测整体表现。

[Codebook Agent](https://arxiv.org/abs/2609.02264)从另一个角度研究多代理组织：如何为任务选择通信结构，怎样衡量这个结构的实际代价。把通信图画得稀疏，不必然减少 token 或提高效率；能否把局部工作转成最终结果才是要验证的目标。与 [Mo' Models, Mo' Problems](https://arxiv.org/abs/2609.17306)一起读，可以把“多代理更强”拆成两个问题：选哪些模型，以及让它们怎样协作。两者的深入比较在[协作章](08_collaboration.md)。

### 3. 观察不是越多越好，关键是下一步需要什么

观察选择不是普通的文本摘要。摘要试图保留整体内容，决策观察则必须保留下一步会用到的证据，包括尚未解决的约束和能够否定当前假设的信息。删除重复内容可以降低成本，但若只保留看似相关的片段，也可能把错误解释自我强化。因此要同时比较信息量、证据覆盖与后续决策质量，尤其检查失败信息是否被“清理”掉了。

**[STRACE](https://arxiv.org/abs/2607.07702)**面向用于优化 Agent 的执行轨迹，先在批次层面减少重复失败，再沿文本依赖结构保留可能解释失败的步骤。与简单截断的区别，在于它试图保存诊断所需的结构，而不只是保留最近的文本。报告中的因果定位仍需结合论文的干预与评测方式理解；依赖图上保留下来的节点，不应仅凭名称就被视为已经证明的真实因果根源。

工具返回内容之后，系统还没有自动获得可用证据。假设搜索工具一次返回一百处命中，模型仍要判断哪些与问题有关、是否需要打开上下文、不同文档能否相互印证。如果把所有结果原样贴进窗口，可能只是把检索问题变成了更昂贵的阅读问题。

[A New Role for Relevance](https://arxiv.org/abs/2607.24223)研究相关性如何参与语料交互，而不仅是用于一次性选出若干文档。它把相关性估计与类似 grep 的细粒度探索联系起来，关注搜索顺序和优先呈现的证据片段。由此引出一个重要区分：检索器找到“可能相关的文件”，不等于 Agent 已完成证据定位、组合与验证。这也是检索增强问答进入多步研究任务后出现的新问题。

多模态任务让这个问题更明显。[OmniReasoner](https://arxiv.org/abs/2607.19339)先以较低成本观察长音视频，再决定是否放大某个时间段，强调选择观察的时间位置。[Online Video Agent Harness for Long Video Understanding](https://arxiv.org/abs/2609.12818)从给定视频和用户问题出发，按需调度专门工具并汇合证据。[AdaVDR](https://arxiv.org/abs/2608.25559)进一步把视频理解与外部检索结合，并在中间结果不可靠时考虑回退。三者的共同问题不是“怎样看完更多帧”，而是“下一次观察能够消除哪种不确定性”。

不过，调用工具后成绩变好，还不能说明收益真的来自工具返回的新信息。[Thinking With Tools, Not With Pixels](https://arxiv.org/abs/2608.09682)保留工具调用的结构化文字，却去掉返回图像，用这种对照检查收益来源。它提供了一种很值得学习的分析方法：如果删除被认为关键的信息后仍保留效果，可能真正起作用的是调用时写出的目标、位置或意图。不要因此推断所有视觉工具都无用；应当把“获得新证据”与“改善模型组织思路”分开测量。

长期任务还要决定观察如何进入后续状态。[CompactionRL](https://arxiv.org/abs/2607.05378)把上下文压缩放入训练过程；[MemHarness](https://arxiv.org/abs/2607.28272)讨论经验在当前任务中如何重新组织；[Catastrophic Remembering](https://arxiv.org/abs/2608.11095)提醒我们持续积累的指令也可能成为负担。它们分别涉及压缩、经验使用和过时信息治理。基础章把三者并列，是为了说明“保留全部历史”不是一个完整的状态管理方案；具体机制在[记忆章](02_memory.md)。

### 4. 执行框架本身怎样被理解和改进？

修改框架与修改模型的区别，在于前者通常改变模型被要求怎样工作，而不是它内部存储的知识。但两者会相互影响：更强的控制规则可能帮助小模型，也可能限制强模型的探索空间。研究框架优化时，应先标出可修改部分、候选提出方式和独立选择标准，再区分固定任务适配与跨任务迁移，避免把挑选最佳演示配置误当作通用改进。

**[Better Harnesses, Smaller Models](https://arxiv.org/abs/2607.08938)**把自动框架适配与模型成本选择放在一起研究，适合接在固定模型的编排对照之后阅读。标题中的成本降低幅度对应论文特定任务与计费条件，不能直接用于估算自己的部署预算。这里应追问的是：小模型在怎样的执行安排下能够承担原本交给大模型的任务，搜索框架本身的开销是否被计入，以及选定框架对新任务是否有效。

当系统只有几十行循环代码时，开发者容易知道每个行为由哪里控制。系统长大以后，同一行为可能同时涉及提示词、工具包装、错误重试和状态存储。此时，让模型“优化一下这个 Agent”并不充分：它先要找到行为对应的实现位置。

[Harness Handbook](https://arxiv.org/abs/2607.13285)把这一步当作研究问题。它用静态分析和模型辅助组织，把行为与源代码位置联系起来，再引导代理逐步找到相关实现。读这篇时应区分“找到正确修改位置”和“修改后真正提高任务表现”：前者是框架维护的重要前提，却不是后者的充分条件。它也说明，代码搜索之外，还需要让系统结构对维护者可理解。

[MemoHarness](https://arxiv.org/abs/2607.14159)关注另一种改进：不对每个任务套用同一个固定配置，而是保存运行诊断与跨任务经验，再为新案例选择适合的控制方式。它与[Recursive Experiential-Working Memory Evolution](https://arxiv.org/abs/2608.24876)形成对照：后者区分当前进度和经验技能，让失败更容易定位到具体记忆组件，再进行带验证的局部更新。两者都利用经验，但经验决定的是不同对象，不能只用“加记忆”概括。

[HarnessCompass](https://arxiv.org/abs/2608.01918)直接面对自动改进容易过拟合的问题：修改如果只适应开发任务，很难说明获得了通用能力。其作者提出任务无关约束、更主动的反馈和分组件优化，试图减少错误方向与组件之间的干扰。这里最重要的实验条件不是迭代多少次，而是验证任务是否独立，以及修改后有没有把其他能力一起损害。

[HarnessDev](https://arxiv.org/abs/2609.01437)把“创建和改进可运行执行框架”本身作为评价对象，区分从最小起点构建系统与根据反馈演化系统。它帮助我们发现旧评价习惯的盲点：一个模型在现成框架里做事很好，不代表它也善于设计框架。[SoL-Pi](https://arxiv.org/abs/2609.20519)则在自动研究循环中筛选可复用机制，涉及动作执行、上下文压缩、观察处理和委派阅读。两篇分别偏重能力测量与机制探索，读时应避免把它们当作同一种排行榜。

[Language model harnesses are compositional generalizers](https://www.alphaxiv.org/abs/2607.language-model-harnesses)从框架与组合泛化的关系提出问题；[The Evolution of AI Office](https://www.alphaxiv.org/abs/2609.evolution-ai-office-agents)则将办公 Agent 的目标放在可检查、可修改的交付物上。两者连接了框架设计的两个层面：内部怎样组织可复用的行动，外部怎样定义任务完成。由此比较系统时，既要检查流程能否迁移，也要检查产物能否继续被使用和修改。

### 5. 训练模型与修改框架，能不能各做各的？

训练轨迹由某种工具和上下文规则产生，部署框架又决定模型会遇到哪些状态。如果两者独立变化，训练时有效的动作格式、反馈解释甚至停止习惯都可能不再适用。这个分支应分开研究接口兼容、状态分布变化与模型—框架联合优化：前者能靠约定解决，后两者通常需要重新收集轨迹或检验迁移，不能只通过一次工具调用成功就宣布适配完成。

对齐还涉及训练记录本身。框架截断历史、合并请求或改变工具返回格式后，训练器仍需还原每次决策实际看到了什么，并把奖励对应到正确的模型输出。否则，即使动作接口兼容，训练也可能在优化部署时不会出现的状态。

[ClawGym II](https://arxiv.org/abs/2608.16798)以黑箱方式连接复杂框架与强化学习，使用隔离的执行环境和模型调用边界的代理来收集交互。[Agent Lightning v1.0](https://arxiv.org/abs/2608.17528)强调由部署框架持有环境交互循环，而训练器观察模型请求和响应；这样做需要处理轨迹重建、分词和优势计算等一致性问题。[LEGO-RL](https://arxiv.org/abs/2608.17393)同样关注原生编码框架与策略优化的连接，并把环境崩溃、奖励漏洞和训练执行差异纳入讨论。这三篇可以放在同一组：它们都试图减少“为了训练而重写一个不同 Agent”的落差，但工程切入点并不相同。

另一条路线问：能否把复杂框架带来的好行为学进模型，部署时不再保留那么多专门逻辑？[Harness-Zero](https://arxiv.org/abs/2609.24974)研究框架蒸馏，特别处理源框架与目标框架的动作空间、可见信息并不一致的问题。它不是简单复制教师的文字；学习信号必须能在目标系统中执行。和它相邻的 [Co-Evolving Harnesses and Models](https://arxiv.org/abs/2609.09134)讨论为什么直接模仿较强模型的完整轨迹未必有效，并研究同策略纠正的作用。

这组工作让“模型强还是框架强”的二选一问法显得过于简单。模型、接口与训练信号会相互适应。比较时可以设置原始系统、仅更新模型、仅更新框架、同时更新两者四组条件，并匹配工具权限与总预算。如果没有这样的区分，就很难知道增益是否能迁移到另一个部署环境。

### 6. 一次行动成功之后，系统还能安全继续吗？

完成当前动作，不代表整个任务已经结束，也不代表后续行动仍获授权。写入正确文件之后，系统可能继续覆盖其他文件；一次查询有权限，不代表随后获得的敏感信息可以任意传播。因此这里要先讨论停止条件、后续授权与可撤销性，再讨论行动正确率。合理的工作循环应区分“需要更多证据”“需要人工决定”和“任务已经完成”，否则继续执行本身也会成为失败来源。

完成眼前任务与维持长期可用不是同一件事。让 Agent 自动改工具配置，可能使一次任务更快，却破坏之后的权限检查；让它删除旧文件，可能释放空间，却删除了恢复所需的证据。因此，检查最终答案之外，还要问系统改了什么、改动是否可逆、失败之后由谁处理。

[EvoUndo](https://arxiv.org/abs/2608.28363)把自动修改之后能否恢复作为独立条件，研究修改在不同状态下的可逆性。它与“保存一份旧提示词”不同：修改还可能产生持久副作用，恢复过程需要覆盖这些变化。[HarnessRisk](https://arxiv.org/abs/2608.17597)则从生命周期组织安全测试，把配置、能力扩展、运行、状态保存、动作控制和事件恢复放在一起。这表明，风险不只发生在模型刚读到恶意提示的那一刻，也可能通过状态和扩展组件延续。

[SafeEvolve](https://arxiv.org/abs/2609.02786)研究执行框架与策略如何利用经验共同改善安全；[EvoSafeHarness](https://arxiv.org/abs/2609.05903)关注针对模型和领域优化防护框架。这些思路都不能被简化成“再加一个安全提示”。任何优化都应该同时报告任务完成与约束遵守：如果系统为了安全而拒绝所有任务，或者为了完成任务而忽视限制，都没有回答真正的问题。更完整的威胁与评价分类在[安全章](07_safety.md)。

持续执行可以先从明确的运行边界入手：工具声明输入范围，不可逆操作设置确认点，任务保留预算与退出条件，失败后记录实际状态。这些机制分别限制无效调用、控制副作用和支持恢复，再与任务所需的规划和学习方法结合。

## 4. 把不同路线放在同一张比较表里

工具接口、推理预算、框架组织与模型训练改变的是不同环节。下面按这些改动对象比较方法，明确各自解决的瓶颈、引入的成本和必要对照，避免把整套系统的收益全部归给单个组件。

| 改变什么 | 代表入口 | 主要想解决的困难 | 通常要付出的代价 | 必须保留的对照 |
|---|---|---|---|---|
| 工具表达形式 | Bitter Lesson、Harness as a Language | 多次调用的依赖与组合不易表达 | 更复杂的执行与权限检查 | 同模型、同工具能力、同预算 |
| 规划与组件安排 | Empirical Harness Study、Stellar Colosseum | 步骤依赖不清，过早分解 | 额外计划、审查和协调 | 无规划或固定流程基线 |
| 观察与证据选择 | A New Role for Relevance、OmniReasoner、Online Video Agent Harness | 有用证据稀疏，返回内容太多 | 选择观察的决策与工具开销 | 随机或固定取样、去掉新观察 |
| 经验与局部配置 | MemoHarness、Recursive Experiential-Working Memory Evolution | 一个固定框架不适合所有情况 | 存储、检索、经验失效处理 | 无记忆、错误记忆、未见任务 |
| 框架的自动修改 | HarnessCompass、SoL-Pi | 手工调整慢，组件相互干扰 | 搜索与验证成本，回归风险 | 固定模型、独立验证集 |
| 训练与部署连接 | ClawGym II、Lightning、LEGO-RL | 训练轨迹与原生运行不一致 | 轨迹重建和训练基础设施 | 相同部署框架的训练前后对照 |
| 框架行为内化 | Harness-Zero、Co-Evolving | 专用框架复杂且难迁移 | 蒸馏数据与额外训练 | 同一个目标框架、纠正与模仿对照 |
| 生命周期约束 | EvoUndo、HarnessRisk | 一次改进留下难恢复副作用 | 恢复验证、权限与记录成本 | 完成率和风险同时报告 |

这些路线可以组合，但组合本身也需要证据。例如，“程序式调用＋记忆＋多代理＋反思”有四个可能增加成本的部分。只有最后分数高，不能说明每个部分都必要。做组件消融不是为了让系统显得简单，而是让研究结论能被理解和迁移。

## 5. 代表研究：接口、计算与团队组成

工具接口、模型内部计算和团队组成都可能影响任务表现，但它们改变的是不同层次。下面用三项研究说明如何识别主要变量，并将任务质量与执行成本放在同一套比较条件中。

### The Bitter Lesson of Tool Calling｜2608.06370

[原文](https://arxiv.org/abs/2608.06370)。它比较两种接口：模型逐次生成结构化 JSON 调用，或生成调用工具的程序。程序可以自然表达循环、依赖和并行，但也增加代码执行与错误处理的要求。作者在 BFCL v4 上比较 14 个模型，报告程序式调用在其中 11 个上与原生 JSON 调用持平或更好，并另外考察并行分支与上下文干扰。这是有条件的实证方向：收益不是每个模型都一致，复杂调用场景也不能被单个总分完全概括。

**研究意义：** 它说明，模型能力之外，接口形式也会影响任务表现。**比较条件：** 需要保持工具权限一致，统计失败调用，并计入代码运行成本，才能判断收益是否来自接口表达。

### Looped Language Models Improve Compositional Tool Calling｜2608.18171

[原文](https://arxiv.org/abs/2608.18171)。它研究让模型内部进行循环计算，是否有助于存在依赖关系的多步工具调用。研究区分孤立 API 调用和组合任务，并讨论自适应计算的性能与成本权衡。

**研究意义：** “循环”可以发生在模型内部，也可以发生在模型与工具之间；两者不是同一件事。此文主问题属于[效率与架构](13_efficiency.md)，在本章作为交叉阅读。**局限：** 需要核对训练配方和计算预算是否匹配，不能把更大计算量的收益都归于架构本身。

### Mo' Models, Mo' Problems: How to best select model pools when designing Multi-Agent Systems｜2609.17306

[原文](https://arxiv.org/abs/2609.17306)。作者比较模型池的选择策略，区分生成前路由与生成后聚合，并在其设置中观察到扩大模型池未必带来改善。

**研究意义：** 模型池需要按成员的互补性而非数量构建。实验应比较新增成员是否提供独有能力，以及路由与聚合能否利用这种差异。**局限：** 候选模型、聚合器、任务类型和预算都影响结论；本章不把论文中的模型家族结论推广到所有系统。进一步读[协作专题](08_collaboration.md)。

这三篇共同提出一个可检验的问题：改进来自更好的模型、更多计算，还是更合适的系统接口？本指南建议把它们分开比较，而不是把所有增益统称为“更强 Agent”。

## 6. 系统设计中的关键区分

| 容易混淆 | 正确的区分 |
|---|---|
| Agent 与固定工作流 | 是否由模型动态决定下一步，不是有没有用了大模型 |
| 规划与执行 | 计划是候选步骤；工具结果才说明动作有没有发生 |
| 工具会返回文字与工具可信 | 外部文字可能错误，甚至包含诱导系统越权的指令 |
| 调用格式正确与任务完成 | 参数符合格式只是起点，结果与约束还要检查 |
| 多尝试几次与方法更好 | 重试提高成本，比较时应一起报告预算 |

这些维度共同决定系统的执行行为。具体系统实现不同，但如果没有执行记录，就很难定位一次成功究竟依赖什么。

## 7. 研究机会

基础系统研究需要进一步连接可靠接口、持续执行与能力归因。下面从真实工作流出发，讨论如何让工具、状态和验证共同支持任务完成，并辨认模型与外围系统各自带来的收益。

**1. 如何把开放目标转化为可执行、可修正的任务结构？**

真实目标往往缺少完整规格，依赖关系也可能在工具执行后才显现。可以研究能够逐步补全前提、发现缺失步骤并更新计划的任务表示，而不把预先生成的清单当作最终结构。关键评价是系统在新环境和不完整信息下，能否少依赖人工流程设计，同时保持可检查的目标与状态。

**2. 如何让执行框架根据任务状态自适应，而不是依赖固定配方？**

工具暴露、观察粒度、重试与停止规则通常由开发者预设，不同任务却需要不同组合。研究机会是让框架选择成为受约束的决策问题，并区分收益来自减少交互、改善依赖表达还是增加预算。应在未见任务和不同模型上检验配置迁移，避免只对固定基准搜索出更合适的提示。

**3. 如何在长任务中形成可恢复、可组合的行动单元？**

单次工具调用缺少对前提、后果和失败恢复的统一描述，多个局部正确动作也可能不能可靠组合。可以研究带状态契约的行动接口，以及执行中对契约的动态核查。重点是面对工具失败、环境变化和不可逆操作时，系统能否定位受影响的依赖、恢复必要状态，并继续完成目标。
