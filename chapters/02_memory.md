# 02｜记忆：怎样记得住、用得对，也忘得掉

[首页](../README.md) · [专题索引](../README.md#topics) · [文献目录](../catalog/02_memory.md)

## 方向背景：为什么智能体需要记忆

持续执行任务的系统不能只依赖眼前的一次输入。目标、约束、已完成的步骤和外部环境都会随时间变化；当交互超出上下文窗口，或任务跨越多个会话，系统需要保留能够支持后续决策的信息。记忆研究因此不只是扩充存储容量，而是让过去的经验以合适的形式参与当前行动。

上下文窗口、外部记忆与模型参数承担不同职责。上下文是当前计算直接使用的输入，外部记忆提供可检索、可修改的长期记录，参数则承载训练形成的知识与行为倾向。把历史全部保存下来并不能自动解决问题：系统仍须判断信息的来源、时效、适用范围与冲突关系，也要知道哪些内容应该遗忘。

本章围绕状态结构、经验整理、上下文压缩、写入与删除策略、模型内部记忆、系统成本及多模态记忆展开。各分支共同面对一个取舍：保存得更多可能增加检索和推理负担，压缩得更强又可能丢失以后才有用的证据。可靠记忆需要同时支持延续任务、接受纠正和追踪依据。

## 一、先建立一个能用于设计的概念框架

阅读本章需要区分模型计算与外围系统操作。**token** 是模型处理文本的基本单位，不一定对应一个汉字或一个词；**训练**通过数据与优化算法调整参数，**推理**则使用已有参数处理当前输入。把一条记忆加入提示上下文通常只改变本次推理的输入，不等于模型已经把它学进参数。更完整的前置知识见[大模型基础](../docs/llm_primer.md)。

把助手想成坐在书桌前的人。**上下文窗口**是桌面，模型本次计算直接看到的内容放在这里；**外部记忆**是档案柜，聊天、文件、事件、摘要都可以存进去；检索负责搬回有关资料。**参数记忆**则更像训练形成的熟练程度，不能像便签那样逐条精确改写。还有介于两者之间的循环状态或快权重：它们在处理输入时变化，保存历史影响，却未必能还原成可读文字。[RAG](https://arxiv.org/abs/2005.11401)与 [MemGPT](https://arxiv.org/abs/2310.08560)是理解外部资料和工作窗口关系的起点。

两种底层机制会在后文反复出现。**嵌入（embedding）**把文本或图像编码为向量，检索器按向量关系找候选；例如先找与“用户偏好变化”相关的历史片段，再判断哪条仍然有效。**注意力（attention）**在模型内部根据当前查询读取相关表征；**KV 缓存**保存先前 token 的键和值，避免生成每个新 token 时重复计算历史。它是推理中间状态，不是已经整理好的事实库；压缩 KV 与删除用户档案也不是同一种操作。

记忆还可按用途区分为情景、语义和程序性记忆，分别对应经历、事实与方法。这个分类不要求建立三个数据库，而是强调不同更新语义：经历需要解释，事实可能失效，方法具有适用条件。来源、时间与状态决定记录应如何参与后续决策。

设计时最好把读写过程拆开。**写入**决定保留什么；**组织**决定内容如何连接；**检索**决定取回什么；**应用**决定取回后是否采纳；**维护**负责修改、合并、过期与删除。一个系统答错问题，可能是证据从未写入，也可能是检索没有找对，或者旧规则压过了新要求。只更换向量数据库，无法同时修复这些不同故障。

还要区分任务内与跨任务记忆。编程任务中暂存测试结果，是为了这一次能继续；跨周保存用户偏好，是为了未来少解释一次。前者往往可以在任务结束后清空，后者需要更严格的来源、作用范围和删除机制。记忆的生命周期，应当由用途决定，而不是由存储容量决定。

## 二、发展脉络：从查资料，到维护不断变化的工作状态

记忆研究的核心问题，不是怎样存下更多文字，而是怎样让外部信息和过去经历在下一次决策时仍然可用。这个目标从补充参数之外的知识，扩展到保存交互经历、管理有限上下文，再到处理事实更新与经验迁移。前一种能力不会自动带来后一种，因此检索、存储管理与状态维护需要分别理解。

2020 年的 [Retrieval-Augmented Generation](https://arxiv.org/abs/2005.11401)回答了一个基础问题：模型不知道的事实，能否从外部索引中取来再生成答案？这降低了把所有知识压入参数的必要性。但交互任务还需要保存系统自身经历过的决定、约束与结果。知识检索因此需要与经历管理结合。

2023 年的 [Generative Agents](https://arxiv.org/abs/2304.03442)把经历记录、反思和计划联系起来，使模拟人物能够根据过去行动。经历会不断增长，有限窗口却不能一直容纳全部历史；同年的 [MemGPT](https://arxiv.org/abs/2310.08560)借鉴操作系统，让系统主动在不同存储层之间搬运信息。前者强调经历怎样影响行为，后者强调有限工作空间怎样支持更长的任务。

然而，能存、能取，仍然不代表能更新正确。[LongMemEval](https://arxiv.org/abs/2410.10813)把信息抽取、跨会话推理、时间推理、知识更新和拒答放进同一评测；[A-MEM](https://arxiv.org/abs/2502.12110)则通过动态笔记、索引和关联来组织记忆。两者对应新的需求：评价不能只检查是否找到旧句子，结构也不能在创建以后永远不变。

这些经典工作把记忆从静态资料库推进为可更新的工作状态。接下来的难点是让状态保持正确，让经验能够复用，并在有限资源下及时提供行动所需的信息。

## 三、前沿研究方向

近期记忆研究的共同变化，是从保存历史转向维护能够支持行动的信息。分支首先讨论状态怎样组织、经验何时整理，再进入有限上下文的压缩与记忆操作的学习；随后比较记忆是否必须外置，以及成本和多模态输入怎样改变设计。这个顺序从内容走向控制与部署。不同路线可能同时出现在一个系统中，需要比较它们保存了什么、怎样影响下一步决策，以及信息变化后能否继续有效。

2026 年的相关工作中，焦点进一步落在状态变化、维护成本和经验适配上。[Are We Ready For An Agent-Native Memory System?](https://arxiv.org/abs/2606.24775)从存储、抽取、检索路由和维护拆解系统，报告不同工作负载需要不同结构；[LongMemEval-V2 官方项目](https://github.com/xiaowu0162/LongMemEval-V2/)把评测推进到网页与企业环境中的工作经验、环境陷阱和前提识别。记忆不再只是“以前说过什么”，还要服务“在这个环境里怎样把事情做对”。

### 1. 存聊天记录，还是维护一份当前状态？

原始记录回答“发生过什么”，当前状态回答“现在有哪些事实仍然有效、还有什么没完成”。两者不能简单替代：只保存状态会丢失修改依据，只保存历史则把识别冲突与失效信息的负担留给每次推理。研究这类记忆，首先要看状态更新是否保留来源、时间与未决条件，再看它如何应对撤销和矛盾，而不是仅比较摘要长度。

**[Filesystem-Based Memory for LLM Agents: Organization, Evolution, and Sustainability](https://arxiv.org/abs/2607.26637)**（`2607.26637`） 把文件系统当作正式研究对象：管理者组织文件，搜索者带来源回答，执行者贡献经验。作者比较目录组织、原样堆放与分块检索，发现组织更稳定的收益在搜索成本，而非自动带来更好的答案。这解释了为什么“目录很整齐”不等于“助手更聪明”：分类节省找文件的时间，却不能替代正确理解。随着文件增长，管理者和工具的能力也会影响目录是否失控。

**[Mi-Memory: A Lifecycle Memory Framework for Personal AI](https://arxiv.org/abs/2607.18975)**（`2607.18975`） 将视角扩大到个人设备上的记忆生命周期，用带类型的证据、诊断记录、策略变更和回滚记录连接不同模块。它与文件系统研究的区别，是把修改和部署责任也纳入设计。报告明确区分受控模块评估、初步内部结果和设计层证据；因此适合学习系统如何拆分，不能把某个模块的分数当作整个跨设备服务已被验证。

**[Agentic Context Management: Solving Agent Memory and Cost by Treating Them as Lifecycle and Architecture Problems](https://arxiv.org/abs/2607.21503)**（`2607.21503`） 同样把记忆看成生命周期，但更强调组织作用域、提前准备信息和按预算压缩。它指出，持续重复输入不断增长的历史会累积费用。与之相比，**[LiveMem: Maintaining Memory State Continuity in Long-Running LLM Inference](https://arxiv.org/abs/2608.02515)**（`2608.02515`） 不是把外部资料组织得更好，而是在模型内部维护独立于当前窗口的固定容量状态，使原始证据移出窗口后仍可能影响回答。前者侧重服务与信息管理，后者涉及模型改造、后训练和有状态推理。

**[Can Agent Memory Systems Track Evolving State?](https://arxiv.org/abs/2608.19652)**（`2608.19652`） 则给出判断这些设计是否抓住问题的工具：StateMemBench 区分回答采用了当前状态、已被替代的旧状态，还是其他错误；StateMem 显式记录替代关系与依赖。作者还把状态方法用作现有记忆系统的轻量包装，并设置等长度、等成本对照，报告其中一部分提升可归因于状态结构，而非仅仅增加了上下文。这为“显式表示哪个事实已经失效”提供了实证支持；结论仍限于 StateMemBench 的场景、所测模型与后端，不能直接等同于所有长期业务流程中的收益。

对于持续变化的任务要求，状态管理需要记录生效时间、替代关系及受影响的任务。旧内容可留作审计，但不应继续作为当前规则。这个区分还关系到冲突处理：保留历史是为了追溯，维护状态是为了行动，二者不必使用同一个检索入口。

### 2. 经验应该在写入时总结，还是等遇到新任务再整理？

提前总结相当于为未来用途下注：压缩得越具体，调用时越方便，却越可能遗漏尚未预见的用途；保留原始经验则增加后续检索与整理成本。两条路线真正的分歧是何时支付抽象成本，以及在什么证据下扩大适用范围。因此需要分别评估一次经验的写入代价、跨任务命中率与误用率，不宜把存得更少本身当成更好的学习。

**[MemHarness: Memory Is Reconstructed, Not Replayed](https://arxiv.org/abs/2607.28272)**（`2607.28272`） 针对旧经验与新状态不匹配的问题，让策略先批判、重构检索结果，再行动，并用 GRPO 训练。GRPO 是一种强化学习方法，根据同一任务一组候选轨迹的相对回报优化策略；例如比较不同经验使用方式最终是否完成任务。作者在 ALFWorld、WebShop 等设置中报告收益。其关键不是“多一段提示”，而是让经验变成针对当前状态的建议；代价是额外训练和决策过程，迁移边界仍需看具体环境变化。

**[Just-in-Time Memory: Learning to Curate Task-Adaptive Memory for LLM Agents](https://arxiv.org/abs/2609.27334)**（`2609.27334`） 与 MemHarness 都强调使用时适配，但改动的位置不同：MemHarness 在每个决策步根据当前状态重构已检索经验；JitMem 保留原始轨迹，将原本在写入阶段完成的整理移到读取阶段，得知当前任务后再生成紧凑、任务相关的记忆，并用该任务的结果直接训练整理器。两者都在使用时适配经验，但分别改变决策中的重构过程和读取阶段的整理过程，因此需要比较各自的存储对象与反馈路径。保留原始轨迹减少了提前总结造成的不可逆信息损失，却增加存储、访问控制和读取时处理负担，不能只计算最终输入缩短了多少。

**[LifeMem: Enabling Lifelong Experience Reuse for LLM Agents](https://arxiv.org/abs/2609.12655)**（`2609.12655`） 走的是另一条路线：按底层工作流程聚类历史轨迹，提炼可复用技能，再同时检索技能和经历。它面向多个环境中的持续任务流，适合与即时整理比较：哪些规律值得提前固化，哪些细节应在使用时再生成？作者也观察任务流顺序的影响，这意味着同一套记忆策略可能因学习顺序不同而表现不同。

**[Grounding Agent Memory: Environment-Probing Curation for Enterprise Agents](https://arxiv.org/abs/2609.11060)**（`2609.11060`） 说明，历史轨迹本身也可能错。它给异步整理者受限、只读的环境工具，核查候选记忆、限定范围并更新过时知识，而不改变任务智能体与正式写入权限。这种方案用环境证据修正回忆，比只读旧日志多了一道校验；但能否复用取决于环境是否允许低成本、安全地查询当前事实。

**[When Deep Research Agents Stagnate: Enhancing Reasoning with Retrieval-Aware Agent Control](https://arxiv.org/abs/2608.15191)**（`2608.15191`） 把记忆使用与停止搜索联系起来，用搜索新颖度、信息覆盖等信号帮助研究助手调整行动，避免反复检索而没有进展。它属于这一组，因为有用的记忆不仅包含内容，还包括“我们已经找过什么”。这些研究共同覆盖了经验复用的几个环节：留下原始经历，提炼稳定流程，遇到任务时重建建议，必要时核对现实，并判断继续搜索是否还有价值。

### 3. 怎样压缩上下文，而不是压丢任务？

上下文压缩可以删除内容、改变表示，也可以将一部分信息转移到可重新查询的外部存储。删除一行工具输出与合并两个语义状态承担的风险不同：前者可能缺证据，后者可能混淆历史与当前事实。评估时除了平均任务得分，还应检查关键证据稀疏、需要回看原文、早期条件在末尾才生效等情况，才能知道压缩是否只是利用了简单样本的冗余。

**[SWE-Pruner Pro](https://arxiv.org/abs/2607.18213)**从编码模型自己的内部表示预测工具输出各行是否保留，并加入与输出长度相关的表示，而不是再调用一个独立的大型裁剪器。作者在多轮任务中报告节省 token 且保持任务质量。其研究重点是让选择器复用执行模型已有信号；应同时检查额外预测头的开销、错误裁剪后的恢复，以及任务变化时相关性信号是否仍可靠。

**[CompactionRL: Reinforcement Learning with Context Compaction for Long-Horizon Agents](https://arxiv.org/abs/2607.05378)**（`2607.05378`） 把任务执行和摘要生成共同纳入强化学习，并处理跨压缩片段的学习信号。摘要好不好，由后续能否继续完成编程任务来检验，而非只看文字是否通顺。这需要训练资源，也要求任务奖励能够反映信息丢失；若验收只检查最终格式，一份漏掉关键约束的摘要仍可能得到错误奖励。

**[ACM: Agentic Context Management for Long Horizon Tasks](https://arxiv.org/abs/2607.23809)**（`2607.23809`） 为智能体提供上下文编辑工具，移出的内容进入外部存储，之后还可以查询；它再用示范和后训练教模型何时使用这些工具。与不可逆摘要相比，这种“从工作区移走但不销毁”更容易补查证据。不过，保留数据不等于随时能准确找回：检索路径、外部存储成本和恢复延迟仍是系统的一部分。

**[ContextPilot: Teaching Agents for Proactive Context Management via Fine-grained RL](https://arxiv.org/abs/2608.28476)**（`2608.28476`） 进一步增加计划、长期记忆与软卸载工具，并围绕关键编辑决策分支采样，估计更细粒度的行动贡献。它与 CompactionRL 都让上下文管理参与训练，但着力点不同：前者偏向编辑动作的选择与反馈，后者强调压缩后长轨迹怎样学习。工具变多能增加灵活性，也扩大了要探索和验证的行动空间。

**[Zero-Mem: Zero-Token Memory Operations for LLM Agents](https://arxiv.org/abs/2607.29377)**（`2607.29377`） 提出值得保留的反向基线：整理与检索阶段不调用生成式模型，而用实体关系图和时间层次组织原始轨迹。所谓零 token 指这些记忆操作不消耗生成式模型输入输出，并不意味着编码器、索引或存储免费。**[LeanMem: Simple and Efficient Long-Term Memory for LLM Agents](https://arxiv.org/abs/2608.03463)**（`2608.03463`） 则按信息特点分别保存画像、事件和原始记录，只更新变化中的事件，并按查询分配检索预算；它追问的是哪些内容根本不必反复总结。

已确认的目标、持续变化的任务状态与可再次检索的证据，不应强行压成同一种文本。比较方法时，应分别测试压缩后直接继续与允许补充检索后继续，并计算完整成本，避免把外部补查的贡献归给摘要本身。

### 4. 谁来教系统写什么、删什么，并分清是谁说的？

记忆管理本身也是策略：在有限空间中保存哪些信息，要根据未来任务收益而不是当下文本长度决定。难点是收益往往延迟出现，一条暂时没用的约束可能决定最终是否合规；来源不同的陈述也有不同可信度。因此，训练写入和删除策略时需要区分内容相关性、事实可靠性与授权范围，不能让“经常被检索”自动等于“值得长期相信”。

**[AttriMem: Attribution-Guided Process Feedback for Agent Memory Construction](https://arxiv.org/abs/2607.21106)**（`2607.21106`） 研究记忆构建的细粒度反馈，把最终答案中记忆 token 的贡献转成局部奖励，与整体任务奖励结合。这样可以缓解“答案错了，却不知道该改哪次写入”的问题。但贡献归因依赖回答过程和所用模型，重要的未使用证据也可能被低估；适合查看跨回答模型评测，而不只看训练曲线。

**[Why Does CLAUDE.md Keep Growing? Catastrophic Remembering in Agentic Coding](https://arxiv.org/abs/2608.11095)**（`2608.11095`） 从另一端研究指令不断累积：作者观察仓库中的指令生命周期，并在可验证设置中测试保留规则理由的作用。与 AttriMem 的“如何奖励写入”不同，它追问“为什么不敢删除”。现实仓库观察能揭示积累现象，受控实验帮助测试机制，但两者的条件不同。对实践最有用的提醒，是记下规则为解决哪个失败而存在，以及什么时候可以重新验证。

**[Agent Memory Distillation: Empowering Small LLM Agents with Hierarchical Teacher Memory](https://arxiv.org/abs/2608.07169)**（`2608.07169`） 把强教师的成功轨迹整理成工作流、子任务、函数调用三层记忆，让较小模型在任务开始或工具出错时获得不同帮助。这里没有更新学生参数，因此“蒸馏”指通过结构化记忆传递能力。它依赖教师轨迹质量，也受学生能否执行建议限制；复杂示范不是越完整越好，粒度是否合适同样重要。

**[Reality Monitoring in Large Language Models: Self-Knowledge That Transforms with Conversation Memory](https://arxiv.org/abs/2607.23927)**（`2607.23927`） 直接测试模型能否区分用户说过的话与自己生成的内容，发现表现随对话记忆结构和延迟条件变化。这是记忆可靠性的另一个维度：检索到一段话，还要知道它是观察、猜测还是用户确认。**[Jev-Mem: System-One-Controlled Agentic Memory for Efficient AI Agents](https://arxiv.org/abs/2609.23986)**（`2609.23986`） 则把快速记忆控制与较慢的复杂推理解耦，用轻量控制器处理类型、路由、预算和停止；它关联本组，是因为读写决策未必都要交给昂贵的生成模型。

这组方法共同要求我们把“记忆内容”和“记忆政策”分开记录。一次失败可能意味着删掉错误事实，也可能意味着修改错误的写入规则。若两者混在一起，系统会不断加例外，最终连用户明确纠正也无法覆盖旧策略。训练奖励、来源标记和可回滚的规则维护，需要相互配合。

### 5. 记忆一定要放在文件或数据库里吗？

存储载体决定了更新和解释方式。外部文字容易检查与撤销，参数更新则可能把信息与已有能力混在一起；连续向量便于检索，但未必能直接说明存了什么。比较这些方案，应先区分知识保存、查询接口与生成使用三个环节，再考察归因、删除和迁移，不能只按是否出现一个数据库来判断系统有没有记忆。

**[Co-LMLM](https://arxiv.org/abs/2607.07707)**在预训练中将事实知识外部化，使用连续查询键配合可读文本值，使生成时取回的知识仍有可追溯内容。这与运行后总结对话的 Agent 记忆不同，改变的是模型学习与取用知识的方式。**[Self-Guided Test-Time Training](https://arxiv.org/abs/2607.09415)** 则先选择问题相关片段，再用这些片段做测试时参数适应；作者报告，用随机片段训练可能损害表现。这组比较说明，外部检索与临时参数更新服务于不同环节，选择哪些证据比机械扩大上下文更关键。

**[Metis: Memory Foundation Model](https://arxiv.org/abs/2607.26760)**（`2607.26760`） 把原生记忆定义为持续演化的内部状态及模型自己执行的读写过程，并提出 Metis 原型和记忆相关训练。它试图缩短“外部系统整理—模型重新阅读”的链条。与文件记忆相比，内部表示可参与端到端优化，但也更难逐条查看、纠正和删除；评估时应把易用性与训练、部署条件一起考虑。

**[Memory Decoder at Scale: A Pretrained, Parametric Long-Term Memory](https://arxiv.org/abs/2607.27919)**（`2607.27919`） 将长期记忆模块与基础推理模型分开扩展，研究参数化记忆的规模化训练，并处理索引与检索分布的工程瓶颈。它回答“增加记忆容量是否一定要扩大整个模型”，不等于给普通助手插入一个随写随生效的用户数据库。预训练记忆模块的知识，与持续变化的个人状态，更新频率和验证要求都不同。

**[Memory Attention](https://arxiv.org/abs/2609.28399)**（`2609.28399`） 用按 token 索引的记忆与上下文键来构造注意力值，并讨论查表、预取和 CPU 卸载。这是计算结构层面的复用，不能直接读成“保存了用户经历”。**[Fast Weight Attention for Continual Learning](https://arxiv.org/abs/2608.27763)**（`2608.27763`） 则分析循环快权重的在线更新规则，区分时间对齐方式对应的学习目标；它表明，相同的固定容量状态也可能在优化不同问题。比较时不应只按“用了记忆”归为一类。

**[SketchSSM: Write to the Full State, Read from a Compact Sketch](https://arxiv.org/abs/2609.33051)**（`2609.33051`） 保留完整状态写入，却用紧凑草图近似读取，减少每个解码步访问大状态的流量。这同样通过改变内部状态的读写方式节省计算，与压缩自然语言记录处于不同层次。近似是否可用，需要同时看一般任务与长距离召回，而不是只测吞吐。

这一组工作把记忆从系统外部延伸到模型内部，比较重点也随存储对象发生变化。事实条目、经验轨迹、token 表征与循环状态具有不同的读写接口：逐条删除用户资料需要可定位的记录，减少每步读取巨大状态的负担则更直接依赖内部结构。应先确定更新、撤销与读取需求，再选择相应的记忆载体。

### 6. 记忆更省 token，就真的更便宜吗？

记忆系统会把成本在时间上重新分配：写入时花一次摘要或索引开销，可能换来以后多次读取节省；但低复用任务可能永远收不回这笔成本。完整比较应考虑生成记忆、更新索引、检索、读取及失败恢复，报告冷启动与长期使用两种情形。否则，一个预先准备了昂贵记忆库的方案，容易看起来比从原始输入开始的基线更便宜。

**[Language Models Can Control Their Own Attention](https://arxiv.org/abs/2609.02737)**（`2609.02737`） 让模型声明本步需要全局、特定区域还是局部注意力，由推理引擎减少 KV 读取。它直接减少读取范围，但判断错了就可能漏掉远处证据。**[On-Demand Attention: Language Models Know When to Recall](https://arxiv.org/abs/2609.20734)**（`2609.20734`） 采取局部优先：轻量召回头决定是否需要重新计算全局注意力，同时保留完整历史 KV。两者都尝试少读历史，后者明确保留再访问机会，因此计算节省与存储节省不能混为一谈。

**[Sliding-window beats linear attention](https://arxiv.org/abs/2608.28444)**（`2608.28444`） 强调简单基线：滑动窗口配合 attention sinks，在所比较设置中能匹敌或超过后训练的线性注意力方案。这里的滑动窗口只保留最近一段上下文；attention sinks 指会持续吸收注意力的少量位置，相关方法通常额外保留这些位置以稳定推理。题名很强，阅读时更要检查模型、任务和内存预算；它提供的是应认真比较的简单方案，不是对所有线性架构的永久判决。与学习何时全局读取相比，固定窗口实现简单，却需要确认远距离证据不会被持续排除。

**[The Embedder's Dilemma: LLMs Are Better, but at What Cost?](https://arxiv.org/abs/2608.12875)**（`2608.12875`） 从检索前端算账：比较大模型与专用嵌入模型在多个任务上的质量、费用和速度，展示相近总体表现下可能相差很大的成本。它与注意力论文优化不同层级，却都反对只看单项质量分数。**[From LLM Inference to Agentic Workloads: Characterization and Implications for Serving Systems](https://arxiv.org/abs/2608.15127)**（`2608.15127`） 则以 AgentSysBench 测量完整智能体工作负载，指出工具、沙箱和状态管理可能成为主要耗时来源；优化一次模型调用，未必能缩短整个任务。

因此建议把成本至少拆成构建、维护、检索、生成和环境执行五项，再区分首次使用与多次复用。昂贵建库可能在大量查询后摊薄，也可能因资料很快过期而永远回不了本。服务多个用户时，还应记录并发与尾部延迟：平均查询很快，却偶尔为了重建记忆阻塞数十秒，对实时助手仍然不够。

一个实用对照是：固定最终任务质量门槛，比较达到门槛所需的总费用；另一个是固定费用，看错误分布是否改变。前者适合部署选型，后者适合研究归因。只比较最终提示长度，会漏掉不少真正昂贵的工作。

### 7. 当记忆来自视频、手机和语音，问题怎样变化？

多模态记忆首先要对齐事件，而不是分别存更多截图和录音。同一物体可能在不同视角出现，同一句话也需要时间、说话人和环境才能解释。连续感知还带来隐私与过时信息的问题：系统看过，不代表应该永久保留；能够检索，也不代表允许用于任何任务。因此要同时研究时间组织、证据定位、存储预算和访问范围。

**[LightMem-Ego](https://arxiv.org/abs/2607.11487)**将第一人称视觉与音频对齐到共同时间线，再组织当前、短期和长期记忆，按查询选择检索层级。它与仅把视频转成一段文本摘要的路线不同，强调流式积累和分层访问。长期使用还需要把隐私、耗电和检索可靠性纳入评价，检验分层记忆在持续数据流中的维护成本。

**[StreamTTT: Reconciling Real-Time Perception and Long-Term Memory in Streaming VLMs](https://arxiv.org/abs/2608.13416)**（`2608.13416`） 用在线更新的快权重保存远期视频历史，把较短 KV 窗口留给当前画面。它针对实时感知与回顾过去之间的冲突，依赖相应训练和输入协议。**[OneStreamer: Unifying Perception, Memory, and Proactive Response in Streaming Video Interaction](https://arxiv.org/abs/2610.01762)**（`2610.01762`） 则学习生成带时间的局部描述与事件摘要，让文字记录补充最近视觉窗口，并学习何时从等待转为回应。前者把历史压入状态，后者保留较可读的证据；两者都要在未来问题尚未出现时决定留下什么。

**[MobileMem: Learning from a Year of Mobile Experiences](https://arxiv.org/abs/2608.13606)**（`2608.13606`） 把场景拉长到移动设备的持续经历，利用用户应用会话构建连贯的长轨迹，测试知识更新、时间推理和隐式偏好。它的价值是让记忆面对更接近日常使用的变化，但合成轨迹的连贯性与真实用户行为仍应区分。手机上记住很多内容，还要考虑敏感数据和跨应用边界，而不能只把对话基准做得更长。

**[VoiceMem: Streaming Dual-Brain Memory for Real-Time Interaction](https://arxiv.org/abs/2608.26005)**（`2608.26005`） 将语音交互记忆分成信息与情感两条通路，并考虑流式读写、训练和可替换的部署后端。这说明，长期助手不只需要事实召回，还要在交互时限内作答；但情感或画像分数并不能自动证明用户体验长期改善。**[GraphMemix: Query-Aware Evidence Forests for Long-Term Multimodal Agent Memory](https://arxiv.org/abs/2608.26983)**（`2608.26983`） 则以查询相关的证据森林组织多模态记忆，在预算内选择支持当前问题的片段与关系，避免离线统一摘要和简单相似度检索的不足。

流式多模态记忆需要同时保留内容、时间与跨模态对应关系。过早生成语义摘要可能丢失细节，保留全部原始观察又增加检索成本。时间索引与原始片段回查可以互补，是否需要图结构或内部状态取决于证据链中实际的瓶颈。

## 四、方法对照：同样叫记忆，实际改变了什么？

记忆方法的差别首先在于保存和更新的对象：事实状态需要纠正，程序经验需要复用，内部表示与外部索引又有不同的访问成本。下面据此比较方法及其检验条件，而不把所有收益归结为记住了更多内容。

| 问题 | 代表方法 | 主要代价 | 重点检验条件 |
|---|---|---|---|
| 旧事实覆盖新要求 | 状态关系、替代标记、生命周期管理 | 更新冲突处理与审计成本 | 长期真实修改、删除和恢复测试 |
| 旧经验不适用 | 使用时重构、即时整理、环境核查 | 原始轨迹保留、额外读取或训练 | 跨环境迁移与完整成本对照 |
| 历史挤满工作窗口 | 摘要训练、可恢复卸载、分类型存储 | 信息损失风险、检索与训练开销 | 后续任务成败而非摘要质量 |
| 不知写删是否有效 | 贡献归因、教师分层记忆、来源追踪 | 奖励和教师依赖 | 反事实贡献、长期遗忘后果 |
| 外部读写成为瓶颈 | 原生状态、参数模块、快权重、状态草图 | 模型改造与可解释性下降 | 定向纠正、删除与部署可迁移性 |
| 读取历史太慢 | 声明式注意力、按需全局读取、简单窗口 | 召回误判或完整 KV 存储 | 同质量端到端费用与尾部延迟 |
| 连续多模态输入 | 流式状态、时间描述、证据子图 | 实时预算、模态损失、隐私维护 | 真实长期用户与跨模态证据审计 |

这些路线改变的层次不同：外部系统可以直接调整记录与检索，参数或内部状态方案则往往需要相应训练和推理实现。比较时先确定部署条件，再考察同一任务下的质量、维护成本与恢复能力。

## 五、开放问题与研究机会

记忆研究的难点逐渐从“能否找回一条记录”转向“如何长期维护可用经验”。值得推进的方向包括动态状态的纠正、面向未来的记忆选择、跨任务复用的边界，以及持续运行中的维护成本。这些问题需要在任务流中观察，单次历史问答难以完整覆盖。

**1. 如何从不断变化的历史中维护可修正的当前状态？**

事实更新、目标变化和互相矛盾的证据，使记忆不能只是持续追加的摘要。可以研究带来源、时间、有效条件和依赖关系的记忆状态，让一次纠正传播到受影响的结论。例如，任务目标改变以后，旧计划中的哪些步骤应失效，已经完成的哪些工作仍可复用，需要分别处理。评价应同时考察状态正确性、纠错延迟和后续任务完成，检验系统是在维护当前事实，还是仅找回了曾经正确的记录。

**2. 如何根据未来决策价值学习写入、检索和遗忘？**

写入时通常不知道未来任务，一条当前无用的信息可能很久以后才成为关键证据。研究机会是用带延迟需求的任务流训练记忆策略，将未来收益与整理、读取、补查成本共同纳入目标。实验需要改变查询时间和任务类型，并保留稀有但重要的线索，避免策略只优化近期摘要质量。已经丢失的信息能否通过重新观察补回，也是决定保存优先级的重要条件。

**3. 如何让经验跨任务复用，同时保持隔离与可撤销？**

不同用户、项目和环境可以共享方法，却不应无条件共享私有事实或过期规则。可以研究事实、技能与个性化偏好的不同迁移机制，明确适用范围，并追踪原始记录、摘要、图关系、缓存及参数更新之间的派生关系。删除一条记录后，还需检验后续行为是否继续受其影响；环境变化后，则要观察系统能否识别旧经验失效、补充证据或停止套用规则。

**4. 如何避免记忆增长演变为长期维护负担？**

持续运行会带来重复条目、索引退化、来源冲突和检索成本漂移。研究机会是让系统主动合并、归档和修复记忆，同时保留可回查的依据。评测应覆盖较长任务流，并一起报告存储增长、过期比例、冲突处理成本和任务表现。只有把维护动作本身计入预算，才能判断紧凑内部状态与外部可审计记忆分别适合哪些需求。
