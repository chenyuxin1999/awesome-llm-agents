# 02｜记忆：怎样记得住、用得对，也忘得掉

[首页](../README.md) · [专题索引](../README.md#topics) · [文献目录](../catalog/02_memory.md)

## 方向背景：为什么智能体需要记忆

一个好的长期助手，要记得住约束、跟得上更新，也知道哪些话已经作废。设想你请一个助手陪你写毕业论文，前后要写好几个月。第一周你告诉它：导师要求所有图的坐标轴都用英文，实验结果统一放在 results_v2 文件夹里，引用格式用 ACL。第三周导师改了主意，结果改放 results_v3，因为 v2 里有一组数据跑错了。到了第六周，你让它帮你重画第四章的图。一个好的助手应当记得坐标轴要用英文，记得去 v3 里取数据，也记得 v2 那组数据为什么作废；它还应当知道你上个月随口说过的"先用柱状图凑合一下"只是权宜之计，早就不算数了。

今天的很多系统会在这里以三种方式栽跟头。最常见的情况是它什么都没记住，每次对话都从头开始，你得把要求重新讲一遍。稍好一些的系统把聊天记录全存了下来，可它从记录里检索出来的，很可能恰好是第一周那句"结果放在 results_v2"，于是它信心十足地画出了一张用错数据的图。还有一种情况更隐蔽：系统记住的东西越来越多，提示越来越长，模型反而开始忽略夹在中间的关键约束，回答变慢、变贵，也变得更不可靠。

这三种失败说明，记忆研究要回答的问题远比"把历史存下来"复杂。目标、约束、已完成的步骤和外部环境都会随时间变化；交互一旦超出模型一次能读的长度，或者任务跨越多个会话，系统就得自己决定保留什么、以什么形式保留、什么时候取回、取回之后信不信，以及什么时候该把旧的东西忘掉。存得越多，检索和推理的负担越重；压缩得越狠，又越可能丢掉以后才派得上用场的证据。一个可靠的记忆系统，要能让任务延续下去，能接受纠正，也能说清楚自己的每条判断依据从何而来。

## 先读这几篇

这一章的主线借自下面几篇长文。它们出自长期在一线做 agent 和记忆系统的研究者与工程团队，叙事里有取舍、有立场。建议按顺序读。

| 顺序 | 文章 | 为什么读 |

| 1 | Lilian Weng，[LLM Powered Autonomous Agents](https://lilianweng.github.io/posts/2023-06-23-agent/)（2023-06） | 这篇经典长文把 agent 拆成规划、记忆和工具三个部件，其中的记忆一节至今仍是最好的入门。她借用人类记忆的分类做了一张对照表：感觉记忆对应原始输入的嵌入表示，短期记忆对应上下文里的学习，长期记忆对应一个可以随时查询的外部向量库，并顺手介绍了 LSH、ANNOY、HNSW、FAISS、ScaNN 这几种近似最近邻检索算法。文中对 Generative Agents 记忆流的讲解也很清楚：按新近程度、重要程度和相关程度给记忆打分，再定期把观察提炼成更高层的反思。 |
| 2 | Letta，[Agent Memory: How to Build Agents That Learn and Remember](https://www.letta.com/blog/agent-memory/)（2025-07） | MemGPT 原班人马创办的 Letta 写的记忆总论，也是本章发展主线的骨架。文章把 agent 的记忆分成四层：最近消息组成的缓冲区，固定放在上下文里、可以被 agent 自己改写的核心记忆块，存在窗口外面、可以检索的完整对话历史，以及经过加工、建了索引的归档知识。它的核心判断有两条：记忆说到底是决定"此刻往上下文窗口里放哪些 token"的问题；检索只是支撑记忆的一种工具，它本身算不上记忆。文章顺着无状态模型、有状态 agent、MemGPT、后台整理记忆的 sleep-time 智能体这条线往下讲，正好构成了一条演进脉络。 |
| 3 | LangChain，[Context Engineering](https://langchain.com/blog/context-engineering-for-agents)（2025-07） | 这篇文章把散落在各家产品里的上下文管理手法归成四类：写出去（把信息存到窗口之外，比如草稿本和长期记忆）、选进来（把需要的东西取回窗口）、压一压（摘要和裁剪）、隔开来（让子 agent 或沙箱各管一摊）。它还把情景、语义、程序性三类记忆对应到少样本示例、事实和指令文件上。文中引用了 Simon Willison 遇到的一个例子：ChatGPT 从记忆里调出了他的所在地，擅自画进了一张他要的图片里。这个例子很适合用来理解"选错了记忆"有多尴尬。 |
| 4 | 季逸超（Peak Ji），[Context Engineering for AI Agents: Lessons from Building Manus](https://manus.im/en/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)（2025-07） | Manus 团队把 agent 框架推倒重写了四次之后总结出的六条经验，全部来自生产环境。作者认为 KV 缓存命中率是生产级 agent 最重要的单一指标，因为输入与输出的 token 比例大约是一百比一；他主张把文件系统当作不受窗口限制、可由 agent 自己操作的外部记忆，并要求所有压缩都必须"可恢复"，比如网页内容可以丢掉，网址必须留下。文中还有两条反直觉的建议：让 agent 反复改写一份 todo.md 来把目标"背诵"到注意力的近处；把出错的步骤留在上下文里，让模型看到失败，从而少犯同样的错误。 |
| 5 | Anthropic，[Effective context engineering for AI agents](https://anthropic.com/engineering/effective-context-engineering-for-ai-agents)（2025-09） | Anthropic 应用 AI 团队的系统总结。文章提出"上下文腐化"（context rot）的说法：窗口里的 token 越多，模型准确回忆其中信息的能力就越弱，这种退化是渐进的，所有模型都有。因此上下文应当被看作一份边际收益递减的"注意力预算"，目标是找到能让期望行为最可能发生的、最小的一组高信号 token。文章给长程任务开了三味药：压缩（快满时总结并重开）、结构化笔记（把进度写到窗口外的文件里）和子 agent（在干净的窗口里干细活，只交回一两千 token 的摘要）。它还提倡"即时检索"：手里只留文件路径、查询和链接这样的轻量引用，用到时再加载。 |
| 6 | Letta，[Continual Learning in Token Space](https://letta.com/blog/continual-learning)（2025-12） | 这篇文章把记忆问题往前推了一大步，作为本章主线的最后一个阶段。作者认为，一个 agent 由权重和上下文两部分组成，持续学习也就有两条轴；在权重上做持续学习会遇到灾难性遗忘、隐私和奖励稀疏等老问题，所以从经验中学习的主要机制应当是更新学到的上下文。token 空间里的记忆可读、可以随模型升级迁移，遗忘只需删掉 token，还能像代码一样做版本管理和回滚。它的结论是："权重是暂时的，学到的上下文才会留下来。" |
| 7 | Letta，[Memory Models: Towards Agents That Learn](https://www.letta.com/blog/towards-agents-that-learn/)（2026-06） | 上一篇的续作。Letta 在研究中观察到，通用的前沿模型给长期运行的 agent 写记忆并不可靠：反复精炼之后的记忆会变得空泛、有损，有时又过于具体、推广不开，而且未必能稳定地改变 agent 在不同会话、不同模型上的行为。他们把原因部分归到训练上：今天的强化学习环境默认 agent 是无状态的，模型从来没有被训练去优化跨任务、跨会话的学习，而"把任务做完"和"从任务里学到东西"又常常彼此冲突。文章由此提出专门负责创建和整理记忆的"记忆模型"：内循环让带着记忆的 agent 依次完成一串任务、边做边更新记忆，外循环用强化学习根据下游奖励去更新记忆模型本身。它的理由是，模型换代快、贬值也快，积累下来的记忆却会越用越值钱。这是一篇立场与规划性质的文章，文中还没有记忆模型的实验数字。 |
| 8 | Wei-Chieh Huang、Kai Shu 等，[A Survey of Agent Memory in the Second Half: Towards Self-Evolving and Long-Horizon Agents](https://arxiv.org/abs/2602.06052)（2026-01，2026-08 更新至 v4） | 这篇综述把视野拉到 2026 年。作者借用了"下半场"的说法：研究重心正从模型创新和基准分数，转向在真实世界里定义问题、严格评测；在编程 agent、深度研究和电脑操作这类长程、动态、依赖用户的场景里，agent 很快就会超出上下文窗口，报告出来的成绩和实际效用之间留着一道落差，作者认为要靠记忆来填补。全文用三个维度统一组织 agent 记忆：存储载体，分成模型内部状态和外部仓库；认知机制，即感觉、工作、情景、语义和程序记忆；记忆主体，分成服务用户个性化的记忆和积累 agent 自身经验的记忆。在此之上，它分别梳理单 agent 和多 agent 场景里的存储、检索、更新、压缩与遗忘，讨论记忆管理怎样从提示驱动、微调一路走到用强化学习端到端地学习，最后整理了记忆效用的评测方法和六个开放挑战。作者的一个判断是，没有哪一种存储载体能在所有场景里胜出，混合设计越来越常见。 |

表外还有一篇主张记忆离不开 harness 的短文，适合想多读一点时看：Letta CTO Sarah Wooders 的 [Why Memory Isn't a Plugin](https://www.letta.com/blog/why-memory-isnt-a-plugin/)（2026-04）。她的论证从 harness 出发，harness 指模型外面那层负责组装上下文、调用工具、保存交互的程序：指令文件怎么加载、压缩时保留什么、交互是否存下来可查，全都由它决定，所以记忆无法作为插件外挂到 agent 上。她还半开玩笑地说，检索只是记忆的一小部分，而且很难打败朴素的 grep。

## 一、先看全景：桌面、档案柜和五个阶段

> **本节要点：** 模型这一次只看得见"桌面"，也就是上下文窗口；其余的记忆要么放在"档案柜"里等着被搬回来，要么已经长进了参数。一条记忆要经过写入、组织、检索、应用、维护五步，每一步出错的病根不同。记忆研究走过的五个阶段，是记忆系统替自己做的决定越来越多的过程。

记忆可以放在三个地方：桌面、档案柜和参数，用一个坐在书桌前的人来比喻最好懂。上下文窗口是桌面，模型这一次计算能直接看到的东西都摊在这里。桌面大小有限，于是旁边放着一个档案柜，聊天记录、文件、事件和摘要都可以存进去，这叫外部记忆；需要时，检索负责把相关的资料从柜子里搬回桌面。至于这个人经过多年训练形成的熟练程度，对应的是模型参数里的知识，叫参数记忆，它只有通过训练才会改变，也不能像便签那样逐条精确地改写。把一条记忆放到桌面上，只改变了模型这一次读到的输入，参数纹丝未动，模型并没有因此"学会"这条信息。更完整的前置知识见[大模型基础](../docs/llm_primer.md)。

![书桌、档案柜和参数：记忆放在哪里](../assets/memory/overview-desk.svg)

*图：记忆的全景。青色桌面是上下文窗口，灰色档案柜是外部记忆，下排是参数记忆、推理中间状态和维护操作；各框里的内容是常见的例子，具体系统各有取舍。*

图里的桌面上通常摊着四样东西：系统指令和预加载的规则文件，比如编程助手启动时读进来的 CLAUDE.md；一块 agent 自己可以改写的记忆块，记着用户偏好和当前目标；最近的消息和工具输出；以及这一次从档案柜里取回的资料。下排中间那一格是模型计算过程中产生的中间状态，它们随输入变化，却还原不成可读的文字。

这张图里最要紧的是两处。第一处是桌面和档案柜之间的两条箭头，检索把资料搬回桌面，写入把桌面上的东西存出去。几乎所有记忆系统的设计，说到底都在回答这两条箭头什么时候走、搬什么东西；Letta 把记忆定义为"此刻往上下文窗口里放哪些 token"的问题，指的就是这里。第二处是右下角的维护框，负责修改、合并、过期和删除。一个只会往档案柜里塞东西、从不整理的系统，迟早会把第一周那句早已作废的"结果放在 results_v2"原封不动地搬回桌面。

既然一条记忆要先被存进去、再被搬回来、最后被用上，设计时就可以把这个过程拆成五步。写入决定保留什么，组织决定内容之间怎样连接，检索决定取回什么，应用决定取回之后要不要采纳，维护负责修改、合并、过期和删除。拆开的好处是能对症下药。拿论文助手来说，如果"改放 v3"这句话压根没被存下来，问题出在写入；如果 v3 和 v2 两条记录各自躺在库里、互相不知道对方，问题出在组织；如果取回来的恰好是第一周那句 v2，问题出在检索；如果 v3 已经摆上了桌面，模型却仍然听从一条更早的规则，问题出在应用；如果 v2 作废之后始终没有被标记失效，问题出在维护。五种病根各不相同，换一个更快的向量数据库只能治其中一种。

![记忆读写的五个环节](../assets/memory/rw-cycle.svg)

*图：读写五环节与对应的故障。橙色框是论文助手在每一步出错时的表现，底部一段说明不同的病根需要不同的药方。*

图上方那条虚线表示，维护过的内容会进入下一轮的写入和检索，所以前一步的疏忽会一路传下去。

存进去的内容也分三类，它们的更新方式各不相同。认知科学把记忆分成情景记忆、语义记忆和程序性记忆，分别对应经历、事实和方法，Lilian Weng 的长文和 LangChain 的文章都沿用了这个分类。在论文助手的例子里，"第三周导师改了主意"是一段经历，它需要解释才能派上用场；由此得出的"结果放在 results_v3"是一条事实，它将来可能再次过期；"画图前先检查坐标轴语言"是一条做法，它有自己的适用条件。为此专门建三个数据库并无必要，决定一条记录该怎样参与后续决策的，是它的来源、时间和当前状态。

记忆的寿命也不一样，一条记忆能活多久，应当由它的用途来决定。编程任务中暂存的测试结果，是为了这一次任务能接着做下去，任务结束后往往可以清空；跨周保存的用户偏好，是为了将来少解释一遍，它就需要更严格的来源记录、作用范围和删除机制。

![三类内容与两种寿命](../assets/memory/memory-kinds.svg)

*图：情景、语义、程序三类记忆的更新方式，以及任务内和跨任务两种寿命各自需要的管理；例句取自本章开头的论文助手。*

有了桌面和档案柜，就能看清记忆研究这几年怎样一步步走过来：每往上一级，记忆系统要替自己做的决定就多一些。下面这架梯子从下往上读。最初，记忆只是去外面查别人写好的知识，查什么由固定流程决定；接着，agent 开始记录自己的经历，并决定哪些经历值得取回；经历多到桌面放不下以后，模型要自己决定什么换进桌面、什么换出去；再往后，桌面上放什么成了一整套工程手艺；最后，写什么记忆本身成了一种要训练的能力。最底下橙色的一条是边界：记得多和记得对是两件事。

![记忆研究的五个阶段](../assets/memory/stages.svg)

*图：五个阶段加一条边界。每一级写着代表工作，右端是本章第三节对应的分支。*

按时间排开，这几个阶段并不是排着队依次登场的。2023 年一年之内，记录经历、调度窗口和诊断长上下文这三类工作几乎同时出现，阶段二到阶段四的种子都在那一年埋下；到 2025 年，上下文工程的几篇长文集中在夏天发表，阶段五的论文和博客也接连出来；边界那一行则从 2024 年的 LongMemEval 一直延续到 2026 年的系统评测。

## 二、发展主线：从查资料，到在上下文里持续学习

记忆研究这几年的演进可以读成五个阶段，每往后走一个阶段，记忆系统要做的决定就更多一些，"记得对不对"这个问题也变得更难回答。这条主线主要借自 Letta 的那篇记忆总论，再用 Lilian Weng、LangChain、Manus 和 Anthropic 的文章把中间几段补充完整，最后接上 Letta 关于 token 空间持续学习的判断。五个阶段依次是：先学会从外面查资料，再学会记住自己的经历，接着学会把有限的窗口当成内存来调度，然后发展出一整套"上下文工程"的手艺，最后开始把记忆看作 agent 持续学习的主要途径。

> **本节要点：** 阶段一把知识放到模型外面的索引里；阶段二让 agent 记录并归纳自己的经历；阶段三让模型自己决定什么放进窗口；阶段四发现窗口变大也解决不了问题，于是把记忆当作上下文管理来做；阶段五主张从经验中学习主要靠更新上下文，并开始训练专门写记忆的模型。

| 阶段 | 内容 | 代表工作 | 本章对应分支 | 速查卡 |
|---|---|---|---|---|
| 阶段一 | 从外部取知识：检索增强生成 | RAG、向量检索与近似最近邻算法 | （基础概念，见第一节）；三.5 作对照 | A1、A2 |

### 阶段一：模型不知道的事，先去外面查

> **要点：** 记忆研究的起点是把知识放到模型外面的索引里，用到时再查。这一步解决了"知识"问题，可查的始终是别人写好的静态资料，agent 自己的经历还没有地方放。

记忆研究的起点，是把模型不知道的知识放到模型外面的索引里，用到时再查。故事从一个很朴素的问题开始：模型在预训练里没见过的事实，能不能临时从外面查来再回答？2020 年 Facebook AI 等机构的 [Retrieval-Augmented Generation](https://arxiv.org/abs/2005.11401)（RAG）给出了肯定的回答。它把一个检索器和一个生成模型接在一起。检索器先把问题编码成一串数字，也就是一个向量，这种编码叫嵌入；维基百科的每个段落事先也编码成了向量，存成一份索引，意思相近的文字，向量也靠得近。检索器拿问题的向量去索引里找最近的几个段落，连同问题一起交给生成模型写出答案。两边是这样学来的：检索器先单独预训练，它内部有两个网络，一个给问题算向量，一个给段落算向量；RAG 训练时以生成出正确答案的概率为目标，同时微调给问题算向量的那个网络和生成模型，给段落算向量的那个网络和段落索引都保持不动。论文把这份索引称为"非参数记忆"，和生成模型参数里的"参数记忆"相对。这样一来，知识就不必全部压进参数，想让系统知道一件新事，只要往索引里加东西，模型本身不必动。

![检索增强生成（RAG）](../assets/memory/s1-rag.svg)

*图：RAG 的一次问答。紫色是两个模型，灰色是外部索引，琥珀色是取回的段落；左下角是论文比较的两种用法。琥珀色小字是一次问答流过每一步的内容，问题取自论文的示意图，向量数字是编的；底部一行是各部分怎么学来的。*

图左下角记着论文比较过的两种用法：一种是整段回答共用同一批段落，另一种是每生成一个 token 都可以换用不同的段落。

Lilian Weng 在 2023 年的长文里，把这件事放进了 agent 的框架：长期记忆就是一个可以随时查询的外部向量库。向量库可能存着上百万条记录，逐条比较太慢，所以实践中大多用近似最近邻算法，牺牲一点精度换取速度。她在文中逐一介绍的 LSH、ANNOY、HNSW、FAISS 和 ScaNN，至今仍是各种记忆系统的底层零件。

这个阶段解决的是"知识"问题，却还没碰到"经历"问题。RAG 查的是一份静态的、别人写好的资料库；一个持续工作的 agent 还需要记住自己做过的决定、遇到的约束和得到的结果。Letta 在文章里专门强调了这条界线：检索是支撑记忆的工具，它本身还算不上记忆。

**速查：阶段一的两种做法。** 两张卡的结构几乎一样，都是"编码、入库、按相似度取回"；差别在于 A1 把检索和生成接成了一个完整的问答系统，A2 则是 Weng 在 agent 语境里对"长期记忆"给出的最简定义。

|---|---|---|---|---|---|---|
| A1 | 检索增强生成 | 2020 | [RAG](https://arxiv.org/abs/2005.11401) | 预训练的神经检索器从维基百科稠密向量索引里取出相关段落，交给 seq2seq 生成模型作答；论文比较了整段共用一批段落和逐 token 换用段落两种做法 | 模型没见过的事实可以临时查来，知识存在索引里，更新知识只需更新索引，模型不用重训 | 查的是别人写好的静态资料，碰不到 agent 自己的经历；答案好坏很大程度上取决于检索有没有找对 |

### 阶段二：记住自己经历过什么

> **要点：** 查别人写好的资料之后，agent 自己的经历放在哪里？它开始把自己的观察、反思和计划按时间记成一长串文字，按新近、重要、相关三项打分取回，并定期把经历归纳成更高层的认识。新麻烦随之出现：经历越积越多，窗口却是有限的。

要补上经历这一块，agent 得先把自己经历的事记下来，最直观的例子是 Generative Agents。2023 年，斯坦福和 Google 的 [Generative Agents](https://arxiv.org/abs/2304.03442) 在一个像素小镇里放进了二十五个由大模型驱动的居民，让人第一次直观地看到"有记忆的 agent"是什么样子。每个居民都有一条记忆流，用自然语言记下自己观察到的每一件事，每条记录还带着创建时间和最近访问时间。记忆流很快就会比窗口长得多，所以要做决定时，系统得从中挑出值得放上桌面的那几条。更进一步，零散的观察本身指导不了行动，系统还会定期把一批观察归纳成更高层的看法，叫作反思，再把反思也存回记忆流。Lilian Weng 的长文对这套机制有很细致的讲解。

![Generative Agents 的记忆流、检索与反思](../assets/memory/s2-genagents.svg)

*图：Generative Agents 的三步。① 检索按三项分数排序，② 重要度累计到阈值时触发反思，③ 计划也写回记忆流；虚线表示反思写回记忆流，可以被以后的反思再引用。图中的例句是示意，数字取自论文。*

挑选值得放上桌面的记录，靠三个分数相加。新近分按距上次被访问过去了多少个游戏小时做指数衰减，衰减系数是 0.995；重要分在写入时由模型打出，从 1 分的琐事到 10 分的大事，论文举的例子是"打扫房间"得 2 分、"约心仪的人出去"得 8 分；相关分是这条记忆和当前查询的嵌入向量有多接近。三项各自归一化到 0 到 1 之间，权重都取 1，相加得到总分，分数最高、又放得进窗口的那几条进入提示。下图拿论文里 Isabella 筹备情人节派对的场景演一遍：打扫房间这条又旧又琐碎、和问题也不沾边，三项都排在最后；邀请 Maria 这条重要、相关，虽然不是最新的，总分仍然最高。

![Generative Agents 给三条记忆打分](../assets/memory/pic-ga-scores.svg)

*图：示意。上面三行是记忆流里的候选记录和它们的原始分数，下面三行把每项分数缩放到 0 到 1 再相加，总分高的两条进入提示。衰减系数、重要分的范围和反思阈值来自论文，记录内容和其余数字是为说明编的。*

反思的时机也由重要分决定：最近感知到的事件重要分之和一旦超过 150，就触发一次反思，实际运行中每个居民一天大约反思两三次。系统把最近 100 条记录交给模型，让它提出 3 个最值得回答的高层问题，再拿这些问题去检索证据，最后写出洞见，每条洞见都注明它引用了哪几条记录。洞见写回记忆流以后，可以被新的反思再引用，于是层层叠成一棵反思树，叶子是原始观察，越往上越抽象。

计划也存进同一条记忆流：居民先给一天排出五到八段粗略的安排，再拆成以小时计的动作，再拆成 5 到 15 分钟的动作，遇到值得反应的事情时，就从这一刻起重新计划。

同一年，[Reflexion](https://arxiv.org/abs/2303.11366) 从另一个角度说明了经历的价值：任务失败之后，让模型用自然语言写一段反思，下一次尝试时带上它。LangChain 在梳理"写出去"这类手法时，把 Reflexion 和 Generative Agents 并列为"由 agent 自己生成长期记忆"的两个源头。两者都在加工经历，Generative Agents 是定期归纳，Reflexion 是失败后总结教训。

加工经历的设计多了，就需要一套共同的词汇。随后的 [Cognitive Architectures for Language Agents](https://arxiv.org/abs/2309.02427)（CoALA）没有提出新的加工方式，它借鉴认知科学里的经典认知架构，给这类设计定了一套共同的词汇：记忆分成服务当前决策的工作记忆，以及情景、语义、程序三类长期记忆；检索把长期记忆读进工作记忆，推理读写工作记忆，学习再把内容写回长期记忆，每个决策周期先规划、再执行。

这个阶段留下了一个新的麻烦：经历会不断增长，窗口却是有限的。记忆流越写越长，总有一天会塞不进桌面。

**速查：阶段二的三种做法。** 三张卡都有一条绕回去的虚线，那是经历被加工之后重新回到记忆里的路径；它们的差别在于加工的方式，B1 是定期归纳，B2 是失败后写反思，B3 则是给"读进来、写回去"定出一套通用的动作分类。

|---|---|---|---|---|---|---|
| B1 | 记忆流与反思 | 2023 | [Generative Agents](https://arxiv.org/abs/2304.03442) | 观察用自然语言写进记忆流；检索按新近、重要、相关三项归一化后相加排序；重要度累计超过阈值时，从最近一百条记录里提出三个高层问题，检索证据后写出带引用的反思，存回记忆流 | 零散的经历被归纳成能指导以后行动的认识；论文的消融实验显示观察、计划、反思三部分对行为的可信度各有贡献 | 记忆流只增不减，越写越长，迟早塞不进窗口；三项分数的权重是人定的固定值 |

### 阶段三：把窗口当成内存来调度

> **要点：** 窗口放不下全部经历，就得有人决定什么留在窗口、什么移到外面。2023 年的一项工作借用操作系统管内存的办法，让模型自己发指令把内容换进换出；后来的系统把它细化成几层记忆，或者把"抽取新事实、改写旧记忆"做成了生产流水线。

调度窗口有几种不同的做法，差别在于窗口里放什么由谁决定，下图先把它们并排摆开。左列是阶段一的检索增强生成，查什么由固定流程决定，训练只教检索器和生成模型怎么查、怎么答；中列让模型自己发函数调用，决定什么换进窗口、什么换出去；右列每轮用一条流水线抽取新事实、改写旧记忆。中列和右列都不训练，换进换出和增删改的决定都交给通用大模型临场判断。

![谁来决定窗口里放什么：三种范式](../assets/memory/s3-compare.svg)

*图：三种决定窗口内容的做法并排对比。每列一种做法，四行依次是做什么、训练信号从哪来、怎么用、代价；RAG 的训练方式据原论文。*


同样在 2023 年，伯克利的 [MemGPT](https://arxiv.org/abs/2310.08560) 借用操作系统的思路回答了这个问题。操作系统面对的困境如出一辙：内存很小，数据很多，于是把数据分层存放，常用的放在内存里，不常用的换到磁盘上，需要时再换回来。MemGPT 把上下文窗口当成内存，把窗口外的存储当成磁盘，并且让模型自己通过函数调用决定什么时候把什么东西换进换出。Letta 的文章对它的评价是，它在固定的窗口限制下"制造出了记忆无限的错觉"。

具体来说，窗口里的内容被分成三段：最上面是只读的系统指令，交代每一层记忆该怎么用、函数该怎么调；中间是一块固定大小、可读可写的工作区，存放关键事实和用户偏好，只能通过函数调用来修改；最下面是一个先进先出的消息队列，滚动保存最近的对话和函数的输入输出，队首永远是一条摘要，概括此前被移出窗口的消息。窗口外面有两种存储：召回存储保存所有收发过的消息，所以被移出窗口的消息仍然可以搜到；归档存储存放任意长度的文本。模型的输出被解析成函数调用，可以搜索召回存储、读写归档存储、改写工作区，结果追加回消息队列，检索结果分页返回，免得一次把窗口塞爆。

![MemGPT 的虚拟上下文管理](../assets/memory/s3-memgpt.svg)

*图：MemGPT 的结构。左边青色是主上下文，右边灰色是外部上下文，中间粉色的函数调用负责两边搬运；下排是队列管理器处理窗口溢出的四步，百分比是论文给出的示例取值。琥珀色小字把论文助手的记忆放进各层，是示意。*

图下排是这套设计最像操作系统的地方。一个队列管理器盯着窗口的占用：到了警告线，论文的例子是窗口的七成，它往队列里插一条"内存压力"警告，模型看到后可以把要紧的内容存进工作区或归档存储；窗口满了，它移出一批旧消息，论文的例子是窗口的一半，再用旧摘要加上被移出的消息生成新的摘要。被移出的消息一直留在召回存储里，需要时还能查回来。下图用论文助手把这三个时刻画了出来：第 3 周窗口到了警告线，模型趁机把“改放 v3”写进工作区；窗口满了以后，前两周的消息被换成一段摘要，原话搬进了召回存储。

![MemGPT 的窗口逐渐填满后发生了什么](../assets/memory/pic-memgpt-queue.svg)

*图：示意。三个方框是同一个上下文窗口在三个时刻的内容，从上往下依次是只读的系统指令、可改写的工作区和先进先出的消息队列；被移出的消息进入下方的召回存储，可以用函数搜回来。消息内容是为说明编的，70% 和 50% 是论文举的例子。*

MemGPT 后来发展成了 Letta，这套思路也被细化成了四层记忆。Letta 的文章把记忆分成四层：最近的消息缓冲区；固定在窗口里的核心记忆块，存放用户信息、agent 的人设和当前目标，每个块都有标签、说明、内容和字数上限，agent 可以自己改写；存在窗口之外、可以按需搜索的完整对话历史；以及存进向量库或图数据库的归档记忆。窗口快满时，旧消息被移出之前先做摘要，旧摘要和新摘要再递归地合并，于是越久远的内容在上下文里分量越轻。

MemGPT 和 Letta 回答了"放哪里"，却没有细说一条新信息来了以后，旧记忆该怎么改。2025 年的 [Mem0](https://arxiv.org/abs/2504.19413) 把这一步做成了面向生产环境的流水线。每来一轮新对话，它先参考对话摘要和最近的若干条消息，从中抽取候选事实；再拿每条候选去和最相似的几条旧记忆比对，由模型通过一次工具调用在增加、更新、删除和不动四种操作里选一种。在论文助手的例子里，"结果改放 v3"进来时，理想的操作是更新那条 v2 的记录。它的图版本 Mem0g 把实体存成节点、关系存成边，和新信息冲突的旧关系会被标记为失效，保留下来供时间推理使用。作者在 LOCOMO 基准上报告，和把全部历史塞进上下文的做法相比，p95 延迟降低了 91%，token 开销节省了 90% 以上。

*图：示意。第 3 周那句“改放 results_v3”进来以后，Mem0 先抽出候选事实，再和最相似的几条旧记忆比较，由模型在增加、更新、删除、不动四种操作里选了更新，第 17 条记录从 v2 改成 v3 并记下原因。相似度是为说明编的。*

### 阶段四：上下文工程成了一门手艺

> **要点：** 长上下文的实证研究发现，窗口变大，模型也未必用得好窗口里的东西。各家团队于是把记忆当作更大的"上下文管理"问题来做，归纳出写出去、选进来、压一压、隔开来四类手法，并把它们和推理成本连在一起考虑。

窗口变大也免不了调度，2023 年的两项实证研究说明了这一点。窗口太小，才需要调度，于是有一个自然的想法：等模型的窗口足够大，把全部历史都放进去，调度就不需要了。下图左右两半各是一项研究。左边是 [Lost in the Middle](https://arxiv.org/abs/2307.03172)：它把关键信息放在长输入的不同位置，发现模型在信息位于开头或结尾时表现最好，落在中间时准确率明显下降，即使是专门为长上下文设计的模型也是如此。右边是 [StreamingLLM](https://arxiv.org/abs/2309.17453)，它研究的是存储上的限制。模型生成每个新 token 时，要回看之前所有 token 在内部算出的两组向量，叫键和值，系统把它们存起来免得重算，这份存储叫 KV 缓存，图里每一格就是一个 token 的键和值。缓存不能无限长，常见做法是只保留最近一段；图中第二行把开头几格也挤掉了，模型随即崩溃，第三行额外留下开头那几格，性能就大体恢复。原因画在最上面：新 token 把大量注意力分给开头几个位置，作者把它们称为"注意力汇点"。Anthropic 后来把这类现象统称为"上下文腐化"：窗口越满，模型越难准确调用其中的信息。

![窗口装得下，模型也未必用得好](../assets/memory/pic-long-window.svg)

*图：示意。左边 20 份文档里只有一份写着答案，折线是答案放在不同位置时的准确率；右边三行是 KV 缓存的三种留法，深色格留在缓存里，上方柱子是新 token 分给各位置的注意力。问题、准确率数字和柱高都是为说明编的；U 形走势、挤掉开头会崩溃、留下开头能恢复，这几点来自两篇论文。*

既然窗口不能靠变大解决问题，记忆就成了"每一步往窗口里放什么"的问题。Andrej Karpathy 把这件事形容为"在每一步把恰好合适的信息填进上下文窗口的精妙艺术与科学"，"上下文工程"这个说法随之在 2025 年流行开来。LangChain 把各家的手法归成四类：写出去，把信息存到窗口之外；选进来，把需要的东西取回窗口；压一压，在窗口内做摘要和裁剪；隔开来，把细活交给拥有干净窗口的子 agent。

Manus 的季逸超从生产经验出发，给这几类手法补了几条具体规矩，其中一条把记忆设计和推理成本连在了一起。他把文件系统当成 agent 的外部记忆，因为它不受窗口大小限制、能够持久保存、agent 也可以自己读写；他要求压缩必须可以恢复，网页正文可以删，网址必须留着，以后还能重新打开。一个典型的 Manus 任务大约要调用五十次工具，为了不在长循环里迷失目标，agent 会建一份 todo.md，边做边勾掉已完成的项，借此把全局计划不断"背诵"到上下文的末尾，那里正是模型注意力最集中的地方。他还特别看重 KV 缓存命中率：提示开头那一段只要和上一次完全相同，它的 KV 缓存就能直接复用，缓存命中的输入 token 价格只有未命中时的十分之一。所以提示前缀要保持稳定，上下文最好只追加、不改写。这条建议把记忆设计和推理成本直接联系在了一起。

![上下文工程的四招](../assets/memory/s4-context.svg)

*图：上下文工程的四类手法围绕同一个窗口。每类手法下的条目来自 Manus 和 Anthropic 的文章，“选错了”一条指 LangChain 文中引用的 Simon Willison 的例子：ChatGPT 从记忆里调出他的所在地，擅自画进了他要的图片里。*

Anthropic 的文章把这些手法整理成了一套方法论。它把窗口看作一份边际收益递减的注意力预算，主张"即时检索"：agent 手里只拿着文件路径、查询语句和链接这样的轻量引用，真正需要时再通过工具加载，Claude Code 预先加载 CLAUDE.md、其余内容用 glob 和 grep 现查，就是这种混合策略。对长程任务，它推荐压缩、结构化笔记和子 agent 三种手段，并给出了一个很实用的调优顺序：调压缩提示时，先追求召回，保证该留的都留下，再慢慢提高精度，删掉多余的部分。

学术界同期也在把"上下文"本身当作可以优化的对象。2025 年的 [Agentic Context Engineering](https://arxiv.org/abs/2510.04618)（ACE）发现，让模型反复把经验重写成一大段文字，细节会在一轮轮改写中流失。于是它改为维护一份条目化的经验手册，一个模型做题，一个模型从结果里提炼教训，再由一个模型把教训写成小条目并入手册，每次只对相关条目做增删改。

### 阶段五：记忆成为持续学习的主要途径

> **要点：** 一个长期工作的 agent 能否越用越好？Letta 认为从经验中学习主要靠更新上下文，因为写成文字的经验可读、可迁移、可删除，比在权重上持续学习更现实。在后台整理记忆和让笔记自己长出链接的两项工作为它提供了支撑；到 2026 年，Letta 发现通用模型写记忆并不可靠，于是主张专门训练负责写记忆的模型。

上下文工程解决的主要是"这一次任务"的问题。可一个长期工作的 agent 还会遇到更深一层的问题：它能不能从一次次任务中真正学到东西，并且越用越好？

Letta 在 2025 年 12 月的文章里给出了鲜明的回答：从经验中学习主要靠更新上下文，因为在权重上持续学习很难落地。在权重上做持续学习已经研究了几十年，至今很少在生产中落地：新训练会冲掉旧能力，也就是灾难性遗忘；很难替代精心设计的训练流程；把用户数据混进共享权重有隐私风险；强化学习的奖励又很稀疏。相比之下，把学到的东西写成上下文里的 token，有一系列实际的好处：人可以读懂，可以随模型升级迁移，遗忘只需删除，还能版本化和回滚。作者因此主张把持续学习重新定义为"在一连串任务中不断优化上下文"，把记忆操作当作一等的工具调用来训练。

![在 token 空间里持续学习](../assets/memory/s5-token-learning.svg)

*图：阶段五的三块内容。上排是 Letta 的判断，左下是 sleep-time 的后台整理，右下是记忆模型的内外两层循环；底部一条说明这条路线和权重互补。左下琥珀色小字是论文助手的一次后台整理，是示意。*

这个判断有两篇论文作为支撑，它们都在回答"写成文字的记忆由谁、在什么时候整理"。由 Letta 团队成员与伯克利研究者合作完成的 [Sleep-time Compute](https://arxiv.org/abs/2504.13171) 把整理放在空闲时：在用户还没提问的时候，让模型预先对上下文做推理和整理，等真正的问题来了，就能用更少的计算、更低的延迟给出准确的回答。Letta 的 sleep-time 智能体就建立在这个想法上：前台 agent 负责对话和做任务，另一个 agent 在空闲时整理两者共用的记忆块。2025 年的 [A-MEM](https://arxiv.org/abs/2502.12110) 则把整理放在每次写入时：它借鉴卡片笔记法，让每条新记忆都生成自己的笔记、关键词和标签，主动和已有记忆建立链接，必要时还会反过来更新旧笔记，记忆的结构因此在使用中持续演化。

到 2026 年 6 月，Letta 发现这条路的前提并不牢靠：通用模型很擅长使用上下文，却不擅长为将来写出持久有用的上下文。反复精炼的记忆会变得空泛而有损，有时又过于具体、无法推广，而且未必能稳定地改变 agent 在不同会话和不同模型上的行为。他们认为原因之一在于训练目标，"完成任务"和"学习"常常是相互冲突的两个目标。于是他们主张专门训练记忆模型：内循环让 agent 带着记忆完成一系列任务，外循环用强化学习优化"写下的记忆能否提升以后的表现"。

同一年的综述 [A Survey of Agent Memory in the Second Half](https://arxiv.org/abs/2602.06052) 从更宽的角度印证了这个走向。作者认为，记忆正在变成一种可以训练、可以自我演化的能力：短期记忆决定执行过程中哪些经历被感知、挑选和抽象，长期记忆再把它们沉淀成可复用的知识和技能；写入、整理、检索和遗忘这些操作的策略，也越来越多地用强化学习端到端地学出来，手工规则的分量在下降。

这条路线并没有否定权重。Letta 自己也承认两者互补：参数记忆效率更高，积累在 token 空间里的记忆也可以通过合成数据蒸馏进权重。

**速查：阶段五的四种做法。** 四张卡最右边的框都是"整理过的东西"，它们的差别在于整理发生在什么时候、由谁来做：E1 在问题到来之前，E2 在每次写入时，E3 把整理本身当作 agent 要学的技能，E4 干脆把负责整理的模型单独拿出来训练。

| E2 | 自组织的笔记网络 | 2025 | [A-MEM](https://arxiv.org/abs/2502.12110) | 每条新记忆生成带描述、关键词、标签的笔记，主动和相似的旧记忆建立链接，必要时反过来更新旧笔记的内容和属性 | 记忆不再是固定的存取结构，可以在使用中持续演化；作者在六个基础模型上报告优于已有基线 | 每次写入都要调用模型生成笔记、建链接、改旧笔记，写入开销较大；旧笔记被改写后，原貌需要另行保存 |

| E4 | 记忆模型 | 2026 | [Letta：Memory Models](https://www.letta.com/blog/towards-agents-that-learn/) | 专门训练负责创建和整理记忆的模型；内循环带着记忆完成一串任务，外循环用下游奖励做强化学习，更新记忆模型本身 | 针对"通用模型写记忆不可靠、训练环境默认无状态"的问题，让"写下的记忆能否提升以后的表现"成为优化目标 | 立场与规划性质的文章，文中还没有实验数字 |

### 边界：记得多，和记得对，是两件事

> **要点：** 能存、能取，离"能正确地更新"和"能真正忘掉"都还有很长的距离。2024 年的一个评测把知识更新和时间推理的难处量化了出来，2026 年的工作把评测搬进了真实环境，而删除一条记录之后它派生出的东西还在不在，至今没有好答案。

能存、能取，离"能正确地更新"还有很长的距离。2024 年的 [LongMemEval](https://arxiv.org/abs/2410.10813) 把这个差距量化了出来：它把信息抽取、跨会话推理、时间推理、知识更新和拒答五种能力放进同一个评测，结果显示，商业聊天助手和长上下文模型在需要跨越持续交互记住信息时，准确率下降了约 30%。知识更新和时间推理尤其难，因为它们要求系统知道"哪条信息现在仍然有效"，光能找到旧句子是不够的。论文助手要知道结果已经从 results_v2 改放到 results_v3，考的正是这种能力。

2026 年的工作把这个问题推向了更真实的场景。[Are We Ready For An Agent-Native Memory System?](https://arxiv.org/abs/2606.24775) 从存储、抽取、检索路由和维护四个方面拆解现有的记忆系统，报告不同的工作负载需要不同的结构；[LongMemEval-V2 官方项目](https://github.com/xiaowu0162/LongMemEval-V2/)则把评测推进到网页和企业环境，考察工作经验、环境陷阱和前提识别。记忆要回答的问题，从"以前说过什么"变成了"在这个环境里怎样把事情做对"。

![边界：记得多和记得对](../assets/memory/boundary.svg)

*图：上半部分是 LongMemEval 的五种能力，橙色两项最难，右边是 2026 年两项把评测搬进真实环境的工作；下半部分是一条派生链，删掉最左边的原始记录，右边三种派生物的影响未必随之消失。*

还有一个边界问题同样棘手：怎样真正忘掉，记忆一旦被加工，删除就不再简单。LangChain 文中引用过 Simon Willison 的遭遇：ChatGPT 从记忆里调出他的所在地，擅自画进了他要的图片里，让他觉得自己的上下文窗口"不再属于自己"。想纠正这种事，就得能删掉记忆。Letta 说 token 空间里遗忘很简单，删掉 token 就行；加工过的派生物却没有这么好删。图下半部分的派生链画的就是这个过程：原始记录里写着 v2 那组数据，摘要把它浓缩成一句"结果在 v2"，图数据库里又多出一条"实验指向 v2"的关系，如果再把这些经验蒸馏进权重，它就成了参数的一部分。删除只作用在最左边的原始记录上，右边三种派生物的影响未必随之消失。Manus 和 Anthropic 都强调压缩要可恢复，可"可恢复"要求多留副本，"可删除"要求副本越少越好，两者在设计上常常互相拉扯。

## 三、前沿研究方向

2026 年的记忆研究有一个共同的变化：从"保存历史"转向"维护能够支持下一步行动的信息"。这个转向带出了七个问题。先是内容本身：记忆该是一份历史还是一份当前状态，经验该在什么时候整理。然后是有限的窗口：怎样压缩才不丢任务，写什么、删什么由谁来教。再往后是载体和代价：记忆是否一定要放在模型外面，省下的 token 是否真的等于省钱。最后是输入形式：当记忆来自视频、手机和语音，问题又怎样变化。不同路线常常同时出现在一个系统里，读每一篇时都可以问三个问题：它保存了什么，它怎样影响下一步决策，信息变了之后它还能不能保持正确。

> **本节要点：** 七个分支依次讨论状态与历史、经验的整理时机、上下文压缩、写入与删除策略、模型内部的记忆、成本，以及多模态的连续输入。每个分支用一行"主线位置"挂回第二节的阶段。

### 1. 存聊天记录，还是维护一份当前状态？

记忆既要保存原始历史，也要维护一份当前状态，两者谁也替代不了谁。回到论文助手，它的聊天记录里同时躺着"结果放在 results_v2"和"结果改放 results_v3"两句话。原始记录忠实地回答了"发生过什么"，可要回答"现在哪些事实仍然有效、还有什么没完成"，就需要另一种东西：一份随时更新的当前状态。只保存状态，系统会丢掉修改的依据，说不清 v2 为什么作废；只保存历史，识别冲突和失效信息的负担就落在了每一次推理上。所以研究这类记忆，首先要看状态更新时有没有保留来源、时间和尚未解决的条件，再看它怎样应对撤销和矛盾。

> 主线位置：阶段三向阶段五的过渡。接 MemGPT 的分层存储与 Letta 的可改写记忆块，并直面 LongMemEval 揭示的知识更新难题。

> **要点：** 这一组工作都在回答同一个问题：怎样从一份不断变长的历史里，维护出一份能指导下一步行动的当前状态。它们的差别在于把功夫下在哪一层：组织原始材料，管理整个生命周期，把状态放进模型内部，或者直接检验系统能否分清新旧状态。

![历史日志与当前状态](../assets/memory/b1-state.svg)

*图：左边是只追加的历史日志，右边是随时更新的当前状态，中间的维护步骤记下来源、时间和替代关系；下排是本分支几篇工作各自落在哪一块。*

图里右边的当前状态就是论文助手该有的样子：绿色一行是此刻有效的事实，结果目录是 v3，第三周起生效，替代了 v2，来源是导师；两行橙色是已经失效的内容，v2 留作审计并写明作废原因，柱状图被标成过期的权宜之计；最后一行是一条依赖关系，那些基于 v2 画出来的旧图需要标记重画。

最贴近 Letta 和 Manus 实践的路线，是把记忆组织成文件。**[Filesystem-Based Memory for LLM Agents: Organization, Evolution, and Sustainability](https://arxiv.org/abs/2607.26637)**（`2607.26637`） 把文件系统当作正式的研究对象，设计了三个角色：一个负责组织文件，一个负责带着来源回答问题，一个负责贡献经验。作者比较了按目录组织、原样堆放和分块检索三种做法，发现组织得更好，最稳定的收益体现在搜索成本上，答案质量并没有因此自动变好。分类能节省找文件的时间，却代替不了正确的理解。随着文件越来越多，负责组织的模型和工具的能力也会影响目录会不会最终失控。

把视野从一个 agent 扩大到一台个人设备，问题就变成了记忆的整个生命周期：谁改了什么、改动怎样部署、出了问题怎样回滚。**[Mi-Memory: A Lifecycle Memory Framework for Personal AI](https://arxiv.org/abs/2607.18975)**（`2607.18975`） 用带类型的证据、诊断记录、策略变更和回滚记录把不同模块连接起来，把修改和部署的责任也纳入了设计。报告本身明确区分了受控的模块评估、初步的内部结果和设计层面的论证，所以它最适合用来学习一个系统该怎样拆分；某个模块的分数，还不足以说明整个跨设备服务已经得到了验证。

**[Agentic Context Management: Solving Agent Memory and Cost by Treating Them as Lifecycle and Architecture Problems](https://arxiv.org/abs/2607.21503)**（`2607.21503`） 同样把记忆看成生命周期问题，更强调组织作用域、提前准备信息和按预算压缩。它指出，每一轮都把不断增长的历史重新输入一遍，费用会持续累积，这和 Manus 重视 KV 缓存命中率是同一个出发点。

和这些外部方案形成对照的是 **[LiveMem: Maintaining Memory State Continuity in Long-Running LLM Inference](https://arxiv.org/abs/2608.02515)**（`2608.02515`），它没有去把外部资料组织得更好，转而在模型内部维护一份独立于当前窗口、容量固定的状态，让原始证据移出窗口之后仍有可能影响回答。这需要改造模型、做后训练，推理时也要带着状态运行。

这些设计到底有没有抓住问题，需要专门的检验。**[Can Agent Memory Systems Track Evolving State?](https://arxiv.org/abs/2608.19652)**（`2608.19652`） 构建的 StateMemBench 会区分一个回答用的是当前状态、已经被替代的旧状态，还是别的错误；配套的 StateMem 则显式记录替代关系和依赖关系。作者把这种状态方法做成现有记忆系统的轻量包装，并设置了等长度、等成本的对照实验，报告其中一部分提升确实来自状态结构本身，单纯增加上下文解释不了。这为"显式标出哪个事实已经失效"提供了实证支持。结论的适用范围限于 StateMemBench 的场景以及所测的模型和后端，搬到各种长期业务流程上时，收益还要重新检验。

落到实践上，旧内容可以留作审计，却不该继续充当当前规则。保留历史是为了追溯，维护状态是为了行动，两者完全可以使用不同的检索入口。

### 2. 经验应该在写入时总结，还是等遇到新任务再整理？

提前总结经验，相当于为未来的用途下注。总结得越具体，将来调用时越方便，也越可能漏掉当初没有预见到的用途；保留原始经验则把麻烦推给了以后，检索和整理的成本都会增加。两条路线真正的分歧，在于什么时候支付抽象的成本，以及在什么证据下才扩大一条经验的适用范围。所以评估时要分别看一次经验的写入代价、跨任务的命中率和误用率；存得少，本身算不上学得好。

> 主线位置：阶段二到阶段五。接 Generative Agents 的反思、Reflexion 的语言反馈和 A-MEM 的笔记演化，回应 Letta"通用模型写出的记忆会空泛有损"的观察。

> **要点：** 一条经验从发生到被使用要经过好几个时刻，本分支的论文把整理放在不同的时刻：写入时就固化成技能，知道新任务后再生成，行动前按当前状态重构，或者行动后判断还要不要继续找。另有一篇用环境证据核对记忆是否属实。

![经验在什么时候整理](../assets/memory/b2-when.svg)

*图：上排是一条经验从发生到被使用的五个时刻，箭头下方标出“早整理”和“晚整理”各自的代价；中排是本分支论文分别把整理放在哪个时刻，底部绿框是旁路的环境核查。上排琥珀色小字是论文助手的一条经验在五个时刻的样子，是示意。*

最早的整理发生在写入时。**[LifeMem: Enabling Lifelong Experience Reuse for LLM Agents](https://arxiv.org/abs/2609.12655)**（`2609.12655`） 按底层的工作流程把历史轨迹聚类，从中提炼出可以复用的技能，再同时检索技能和经历。它面向的是跨越多个环境的持续任务流。作者还观察了任务流顺序的影响，发现同一套记忆策略可能因为学习顺序不同而表现不同，这一点对设计实验很有提醒意义。

晚一步的做法是保留原始轨迹，等知道了新任务是什么再整理。**[Just-in-Time Memory: Learning to Curate Task-Adaptive Memory for LLM Agents](https://arxiv.org/abs/2609.27334)**（`2609.27334`） 把原本在写入阶段完成的整理工作挪到读取阶段，等知道了当前任务，再生成紧凑的、与任务相关的记忆，并直接用这个任务的结果来训练负责整理的模型。名字里的"Just-in-Time"和 Anthropic 提倡的即时检索思路相通，都是用到时才加工。保留原始轨迹减少了提前总结造成的不可逆损失，却也增加了存储、访问控制和读取时的处理负担，最终输入缩短了多少只是账本的一半。

再晚一步，是在每次行动之前根据当前状态重构经验。**[MemHarness: Memory Is Reconstructed, Not Replayed](https://arxiv.org/abs/2607.28272)**（`2607.28272`） 让 agent 在行动前先批判、重构检索到的经验，把它变成针对当前状态的建议，并用 GRPO 训练这个过程。GRPO 是一种强化学习方法，它让模型对同一个任务生成一组候选轨迹，再根据它们之间的相对回报来优化；放在这里，就是比较不同的经验使用方式最终能否完成任务。作者在 ALFWorld、WebShop 等环境中报告了收益，代价是额外的训练和更长的决策过程。和 JitMem 相比，两者都在使用时适配经验，JitMem 改的是读取时的整理，MemHarness 改的是决策中的重构，比较时要分别看它们存的是什么、反馈从哪里来。

最晚的一处在行动之后。有用的记忆除了内容，还包括"我们已经找过什么"。**[When Deep Research Agents Stagnate: Enhancing Reasoning with Retrieval-Aware Agent Control](https://arxiv.org/abs/2608.15191)**（`2608.15191`） 用搜索新颖度、信息覆盖率等信号帮研究助手判断继续搜索还有没有价值，避免反复检索却毫无进展。

这条时间线之外还有一个更根本的问题：历史轨迹本身也可能是错的。**[Grounding Agent Memory: Environment-Probing Curation for Enterprise Agents](https://arxiv.org/abs/2609.11060)**（`2609.11060`） 给负责整理的后台进程配备了受限的、只读的环境工具，让它去核查候选记忆、限定适用范围并更新过时的知识，同时不改变执行任务的 agent，也不碰正式的写入权限。这和 Letta 让 sleep-time 智能体在后台整理记忆的思路一脉相承，又多了一道用环境证据校验的工序。它能不能复用，取决于环境是否允许低成本、安全地查询当前事实。

### 3. 怎样压缩上下文，又不把任务压丢？

窗口快满了总得删掉点什么，可几种压缩做法的风险很不一样。上下文压缩可以直接删除内容，可以改写成摘要，也可以把一部分信息挪到能够重新查询的外部存储里：删掉一行工具输出，可能缺了证据；把两条记录合并成一句话，则可能把历史和当前事实搅在一起。比如把论文助手的"结果放在 results_v2"和"结果改放 results_v3"两条记录合成一句"结果在 v2 和 v3 文件夹里"，模型就再也分不清哪个目录现在有效。所以评估压缩方法时，平均任务得分只能说明一部分问题，还要专门检查关键证据很稀疏、需要回看原文、早期条件到末尾才生效这些情况。

> 主线位置：阶段四，上下文工程里的"压一压"。接 Anthropic 的压缩与 Manus"可恢复压缩"的原则，背景是 Lost in the Middle 揭示的长上下文退化。

> **要点：** 压缩有三种形态，删除、不可逆的摘要和可恢复的卸载，风险各不相同。压缩周围还有四个可以单独研究的决定：什么时候压，压什么，谁来记，压成什么。实测发现，现有压缩器会丢掉大部分附带约束。

![压缩上下文的四个决定与三种形态](../assets/memory/b3-compaction.svg)

*图：上排四个框是压缩周围的四个决定及其代表工作和报告的数字；下排是压缩本身的三种形态及其风险；底部一条是压缩丢失附带约束的实测。*

最轻的一种压缩是直接裁剪工具输出。**[SWE-Pruner Pro](https://arxiv.org/abs/2607.18213)** 利用编码模型自己的内部表示，预测工具输出的每一行是否值得保留，并加入了与输出长度相关的表示，省去了再调用一个独立的大型裁剪模型。作者在多轮任务中报告，这种做法节省了 token，同时保持了任务质量。读的时候可以看看额外预测的开销有多大，裁错了之后能不能恢复，以及任务变化时相关性信号是否依然可靠。

第二种形态是写摘要，删掉的原文就回不来了，所以摘要好不好至关重要。Anthropic 说调压缩提示要先保召回，可"该留的"到底是什么，靠人来判断终究有限。**[CompactionRL: Reinforcement Learning with Context Compaction for Long-Horizon Agents](https://arxiv.org/abs/2607.05378)**（`2607.05378`） 干脆把任务执行和摘要生成一起纳入强化学习，收益报告在编程任务上；摘要没有说明奖励的具体来源，按常理应是压缩之后任务能否完成（这是推断）。难点在于训练信号要跨越压缩前后的两段轨迹，论文专门处理了这一点。它也要求任务奖励能够反映出信息的丢失；如果验收只检查最终格式，一份漏掉关键约束的摘要照样可能拿到奖励。

第三种形态是 Manus 坚持的可恢复压缩，**[ACM: Agentic Context Management for Long Horizon Tasks](https://arxiv.org/abs/2607.23809)**（`2607.23809`） 把这个原则做成了模型能力。它为 agent 提供上下文编辑工具，被移出窗口的内容进入外部存储，之后仍然可以查询；再用示范数据和后训练教模型什么时候使用这些工具。数据还在，未必就能随时准确地找回来，检索路径、外部存储成本和恢复延迟都是系统的一部分。**[ContextPilot: Teaching Agents for Proactive Context Management via Fine-grained RL](https://arxiv.org/abs/2608.28476)**（`2608.28476`） 在此基础上加入了计划、长期记忆和可撤回的卸载工具，并在关键的编辑决策处多采样几条分支，以便更精细地估计每个编辑动作的贡献：只用整条轨迹最后的奖励时，每个中间编辑动作分到的功劳都一样，多采样分支后，就能比较同一处换一种编辑最终结果差多少。它和 CompactionRL 都让上下文管理参与训练，ContextPilot 关心编辑动作怎样选择、怎样获得反馈，CompactionRL 关心压缩之后的长轨迹怎样学习。

上面几篇琢磨的，是压缩这个动作本身怎样做好。2026 年夏天连着出现的四篇工作，把目光移到了压缩周围的四个决定上，每篇管一个，也都给出了可以互相比较的数字。

**什么时候压。** 常见的做法是窗口快满了就压，或者每隔固定长度压一次。**[Self-Compacting Language Model Agents](https://arxiv.org/abs/2606.23525)**（`2606.23525`）指出，时机本身就很关键：一段推导做到一半时压缩，等于把草稿纸撕掉一半。它给 agent 一个压缩工具和一份很轻的评分标准，定期问模型几个问题：手头有没有具体的结论，轨迹是不是正在收敛，是不是卡住了，下一步清不清楚。子任务刚收尾、思路正在收拢时才压，推导中途或者陷入僵局时就先等等。整套方法不需要微调，在六个数学和搜索基准、七个模型上，相比不压缩的基线，数学最高提升 18.1 分，搜索提升 5 到 9 分，单题成本还降低了 30% 到 70%。作者还发现，不加提示时，模型自己察觉不到上下文正在变差，这份评分标准补上了这一点。

**压什么。** 决定压之后，还要决定动哪些内容。**[Self-GC: Self-Governing Context for Long-Horizon LLM Agents](https://arxiv.org/abs/2607.00692)**（`2607.00692`）把上下文里的每一项都当成有生命周期的对象：用户的发言、工具返回的片段、技能的状态各自建了索引，一个旁路的规划模型逐项建议折叠、遮罩还是剪掉，再由外围程序负责保留可恢复的副本、选择安全的提交时机，并尽量照顾 KV 缓存的命中。在 33 个困难会话上，它剪掉了约 44% 的前缀 token，84.85% 的后续回答完全不受影响，规则方法只能做到 54.55% 到 69.70%；上线之后，白天的平均输入 token 降了 10% 到 15%。

**谁来记。** 前两篇都让执行任务的 agent 自己管上下文。**[Remember When It Matters: Proactive Memory Agent for Long-Horizon Agents](https://arxiv.org/abs/2607.08716)**（`2607.08716`）换了个分工。它要对付的问题，作者叫作"行为状态衰减"：任务早期定下的约束和计划，随着轨迹变长被埋进上下文深处，甚至被挤出窗口，到了需要的时候没能影响决策。它的办法是在执行 agent 旁边放一个独立的记忆 agent，像一位坐在旁边记笔记的助手，持续维护一份结构化的记忆库，每一步决定是插一句简短的提醒，还是保持安静，执行 agent 本身一行不改。这个设计让 Terminal-Bench 2.0 的 pass@1 提高了 8.3 个百分点，τ²-Bench 提高了 6.8 个百分点。消融实验里最有意思的一条是，每一步都提醒反而不如有选择地提醒，记忆 agent 的价值很大一部分在于懂得什么时候闭嘴。作者还用监督微调和 GRPO 训练了一个 27B 的开源记忆 agent，效果部分迁移到了 Terminal-Bench 上。

**压成什么。** 最后一篇关心压缩的产物。**[AREX: Towards a Recursively Self-Improving Agent for Deep Research](https://arxiv.org/abs/2607.21461)**（`2607.21461`）面向深度研究任务。它的出发点是，找到一个同时满足多条约束的答案很难，检查一个候选答案却可以逐条约束地做，所以研究 agent 应当一边验证一边改进答案。为了让这个循环撑得够久，它学会了一个更新上下文的工具，把冗长的历史压成一份紧凑的"研究状态"，里面只保留已经验证过的证据和还没满足的约束。外层循环逐条审计草稿答案，找出还没落实的论断，再定向补充研究。训练用了合成任务、高质量轨迹、agentic 中期训练和长程强化学习，奖励特别照顾那些找到决定性证据、或者纠正了错误方向的关键步骤；这部分奖励由哪个部件算出、怎样认定关键步骤，摘要没有说明。作者做了 4B 和 122B-A10B 两个规模的模型，报告在 BrowseComp 等基准上明显胜过同等规模的基线，并能和激活参数多得多的模型相比。

压缩到底丢了什么，近两个月的几篇工作开始正面回答。前面四篇让上下文管理从"写一份好摘要"变成一组分工明确的决策，每个环节都可以单独训练、单独评测，可丢了什么目前主要靠最终任务分数间接判断。**[Lost in Context Compaction](https://arxiv.org/abs/2608.11242)**（`2608.11242`）关注"在我确认之前不要删邮件"这类应当一直有效的附带约束：在一个收件箱实验里，压缩之后的 100 个会话里有 30 个擅自删了邮件，压缩之前一个都没有；在作者搭的评测上，现有压缩器平均只保留了 17% 的约束，而把约束单独抽出来、压缩后再附回去，就能保留九成以上。

![压缩把一条附带约束弄丢了](../assets/memory/pic-compaction-constraint.svg)

*图：示意。左边是压缩前的上下文，第一句里就有“确认之前不要删”；右边是压缩后的摘要，它记下了做过什么，却漏了这条约束，agent 于是直接删了邮件。下方是论文报告的数字和补救办法。对话内容是为说明编的。*

还有三篇分别回答压缩里的另外三个具体问题：哪些历史推理删了不碍事，什么时候压，以及训练会压缩的 agent 时怎样不把未来的信息漏进来。**[When Can Agents Forget Their Reasoning?](https://arxiv.org/abs/2609.29875)**（`2609.29875`）提出一种不需训练的做法，按重要性给历史推理分块排序，删掉次要的部分，同时原样保留动作、工具调用和观察；它的分析发现，当任务推导出的结果已经存进代码、文件或工具输出这类外部位置时，历史推理就更容易被替换掉。**[AutoCompact](https://arxiv.org/abs/2610.02163)**（`2610.02163`）把"什么时候压"直接训练进编码 agent 的策略里，在 SWE-bench Verified 上绝对提升 9.2 个百分点。**[MemoryWalker](https://arxiv.org/abs/2609.00865)**（`2609.00865`）则提醒，训练中途会删减上下文的 agent 时，每删一次，有效的历史就分出一个岔，训练数据其实是一棵树，常见的训练方式会把未来的信息泄漏进来。CompactionRL 和 ContextPilot 都用强化学习训练上下文的压缩与编辑，读它们的结果时值得把这一点放在心上。

在这些越来越复杂的方案旁边，有两篇工作提供了值得认真对待的反向基线，它们追问的是哪些整理根本没有必要交给大模型去做。**[Zero-Mem: Zero-Token Memory Operations for LLM Agents](https://arxiv.org/abs/2607.29377)**（`2607.29377`） 在整理和检索阶段完全不调用生成式模型，改用实体关系图和时间层次来组织原始轨迹。所谓"零 token"，指的是这些记忆操作不消耗生成式模型的输入输出，编码器、索引和存储依然各有成本。**[LeanMem: Simple and Efficient Long-Term Memory for LLM Agents](https://arxiv.org/abs/2608.03463)**（`2608.03463`） 则按信息的特点分别保存用户画像、事件和原始记录，只更新正在变化的事件，并根据查询分配检索预算。Sarah Wooders 说检索很难打败朴素的 grep，这两篇的思路和她的说法相通。

比较压缩方法时，应当分别测试"压缩后直接继续"和"允许补充检索后继续"两种情形，并计算完整的成本，以免把外部补查的功劳算到摘要头上。

### 4. 谁来教系统写什么、删什么，并分清是谁说的？

记忆管理本身就是一种策略：在有限的空间里保存哪些信息，应当看它对未来任务的价值，眼下这段文字有多长倒在其次。难处在于价值往往延迟兑现，一条暂时用不上的约束，可能最后决定了任务是否合规；不同来源的陈述，可信程度也各不相同。所以训练写入和删除策略时，需要把内容是否相关、事实是否可靠、授权范围是否允许这三件事分开考虑，一条信息被检索得多，并不说明它值得长期相信。

> 主线位置：阶段五，让记忆的写入和维护成为可训练的能力。接 MemGPT 的自管理函数调用和 Letta"把记忆操作当作一等工具调用来训练"的主张。

> **要点：** 一条信息进入长期记忆前要过三关：相关吗，可靠吗，允许吗。这一组论文分别研究怎样给写入更细的奖励、规则为什么删不掉、强模型的经验怎样交给弱模型、模型能否分清话是谁说的，以及读写判断能否交给轻量的控制器。

![写什么、删什么、是谁说的](../assets/memory/b4-policy.svg)

*图：上排是一条信息进入长期记忆前要过的三道判断，虚线是 AttriMem 把答案的成败分回到每次写入；中排三个框是本分支其余几篇工作；下排区分记忆内容和记忆政策。上排琥珀色小字是论文助手的一条候选信息依次过关、存下、被用上，是示意。*

第一关"相关吗"最难训练，因为一次写入好不好，要等很久以后的答案才知道。**[AttriMem: Attribution-Guided Process Feedback for Agent Memory Construction](https://arxiv.org/abs/2607.21106)**（`2607.21106`） 把最终答案中各段记忆的贡献算出来，转化成写入阶段的局部奖励，再和整体任务奖励结合起来。下图用论文助手的三条记忆来看这件事。左边只有整体任务奖励：第 8 周答对了，三次写入拿到的是同一个 1，连"今天下雨"那条也被奖励；答错时，同样不知道该改哪一次写入。右边按答案里用到了哪条记忆分配局部奖励，撑起答案的 results_v2 那条分得最多，用不上的那条分不到。

![只给整体奖励和把贡献分回每次写入](../assets/memory/pic-attrimem.svg)

*图：示意。上排是第 1 周写下的三条记忆，中间是第 8 周的提问，任务奖励由回答和标准答案比对得出；左右两栏是每次写入分到的奖励。记忆内容和数值是为说明编的；把答案的贡献转成写入阶段的局部奖励、再与整体任务奖励结合，来自 AttriMem 摘要。*不过，贡献归因依赖回答的过程和所用的模型，那些重要却没被用上的证据，也可能被低估；所以读这篇时，跨回答模型的评测结果比训练曲线更有参考价值。

从另一端看，问题恰恰是删不掉。**[Why Does CLAUDE.md Keep Growing? Catastrophic Remembering in Agentic Coding](https://arxiv.org/abs/2608.11095)**（`2608.11095`） 研究编码 agent 的指令文件为什么越写越长。CLAUDE.md 是编程助手每次启动时预先读进来的规则文件，属于程序性记忆。作者观察了真实仓库里指令的生命周期，又在可以验证效果的设置下测试了"同时保留规则理由"的作用。它说明规则越积越多，往往是因为没人知道某条规则还能不能删。对实践最有用的提醒是：每写下一条规则，就记下它是为了解决哪个失败而存在，以及什么时候可以重新验证它。

写记忆的能力也可以从强模型传给弱模型。**[Agent Memory Distillation: Empowering Small LLM Agents with Hierarchical Teacher Memory](https://arxiv.org/abs/2608.07169)**（`2608.07169`） 把强模型的成功轨迹整理成工作流、子任务、函数调用三层记忆，让较小的模型在任务开始时或工具出错时获得不同层次的帮助。这里小模型的参数没有更新，所以"蒸馏"指的是借助结构化记忆传递能力。它依赖强模型轨迹的质量，也受限于小模型能不能执行这些建议；示范并非越完整越好，粒度合不合适同样重要。

第二关"可靠吗"的前提，是知道一句话是谁说的。**[Reality Monitoring in Large Language Models: Self-Knowledge That Transforms with Conversation Memory](https://arxiv.org/abs/2607.23927)**（`2607.23927`） 直接测试模型能否区分用户说过的话和自己生成的内容，发现表现会随对话记忆的结构和延迟条件而变化。检索到一段话之后，还得知道它是观察、猜测还是用户确认过的事实。

这三关的判断未必都要交给昂贵的生成模型。**[Jev-Mem: System-One-Controlled Agentic Memory for Efficient AI Agents](https://arxiv.org/abs/2609.23986)**（`2609.23986`） 把快速的记忆控制和较慢的复杂推理分开，用一个轻量控制器处理类型、路由、预算和停止判断。

这组方法共同提醒我们，要把"记忆内容"和"记忆政策"分开记录。一次失败可能意味着要删掉一条错误的事实，也可能意味着要修改一条错误的写入规则。两者一旦混在一起，系统就会不断地加例外，到最后连用户明确的纠正也盖不过旧策略。

### 5. 记忆一定要放在文件或数据库里吗？

记忆放在哪种载体里，决定了它怎样更新、怎样解释，而三.1 到三.4 讨论的都只是放在模型外面的文字。外部文字容易检查、容易撤销；参数更新则可能把新信息和已有能力搅在一起；一串连续的向量便于检索，却未必说得清里面存了什么。比较这些方案时，应当先把知识保存、查询接口和生成时的使用这三个环节分开，再考察归因、删除和迁移；有没有一个数据库，并不是判断系统有没有记忆的标准。

> 主线位置：与主线平行的另一条腿，把记忆放进模型内部。对应 Letta 所说的"权重与上下文互补"，也接 Lilian Weng 把短期记忆看作上下文内学习的视角，可与阶段一的 RAG 对照。

> **要点：** 这个分支的论文把记忆从外部文字一步步搬进模型内部。越靠外，越容易逐条查看、纠正和删除；越靠内，越能和模型一起端到端地优化，也越依赖模型改造和训练。

![记忆的存储载体光谱](../assets/memory/b5-carriers.svg)

*图：从左到右，记忆离可读的外部文字越来越远，离模型内部的计算越来越近；两条反向的箭头分别是两端各自的长处。*

离外部文字最近的一组，仍然保留可读的文本，只是把它嵌进了模型的学习过程。**[Co-LMLM](https://arxiv.org/abs/2607.07707)** 在预训练阶段就把事实知识放到模型外面，用一串连续向量当查询键、可读的文本当取回的值，让生成时取回的知识仍然能追溯到具体内容。它改变的是模型学习和取用知识的方式，可以看作 RAG 在预训练阶段的一个远亲。**[Self-Guided Test-Time Training](https://arxiv.org/abs/2607.09415)** 则先挑出和问题相关的片段，再把这几段当作训练样本，在测试时临时更新参数；作者报告，如果用随机片段来训练，表现反而可能受损，说明选对证据比机械地扩大上下文更关键。

再往里走一步，是让模型自己拥有记忆。**[Metis: Memory Foundation Model](https://arxiv.org/abs/2607.26760)**（`2607.26760`） 把"原生记忆"定义为一种持续演化的内部状态，以及由模型自己执行的读写过程，并提出了 Metis 原型和相应的训练方法。它想缩短"外部系统整理好，模型再重新阅读"这条链路。它和 Letta 的记忆模型目标相近，路径却相反：Letta 让记忆留在 token 空间，Metis 把它收进模型内部，代价是更难逐条查看、纠正和删除。**[Memory Decoder at Scale: A Pretrained, Parametric Long-Term Memory](https://arxiv.org/abs/2607.27919)**（`2607.27919`） 把长期记忆做成一个和基础推理模型分开扩展的参数模块，研究它的规模化训练：记忆模块在 300B token 上预训练，学的目标是检索近邻后得到的下一个词分布；作者还处理了索引和检索分布方面的工程瓶颈。它回答的问题是"增加记忆容量是否一定要扩大整个模型"。预训练出来的记忆模块里的知识，和不断变化的个人状态，在更新频率和验证要求上都相差甚远。

最里面的一组改的是模型的计算结构本身，它们记住的是计算中可以复用的东西，和用户的经历无关。**[Memory Attention](https://arxiv.org/abs/2609.28399)**（`2609.28399`） 用按 token 索引的记忆和上下文键来构造注意力值，并讨论了查表、预取和卸载到 CPU 内存等实现问题。**[Fast Weight Attention for Continual Learning](https://arxiv.org/abs/2608.27763)**（`2608.27763`） 研究的是快权重，也就是在读输入的过程中被不断改写、用来暂存历史影响的一组参数。它分析了快权重的在线更新规则，发现不同的时间对齐方式对应着不同的学习目标，所以看起来一样的固定容量状态，可能在优化完全不同的问题。**[SketchSSM: Write to the Full State, Read from a Compact Sketch](https://arxiv.org/abs/2609.33051)**（`2609.33051`） 针对的是状态空间模型，这类模型不保留全部历史，而是把历史持续压进一个固定大小的状态里。它保留完整的状态写入，读取时却只用一份紧凑的草图来近似，从而减少每一步访问大状态的流量。近似读取是否可用，要同时看一般任务和长距离召回，只测吞吐是不够的。

这条光谱上，事实条目、经验轨迹、token 表征和循环状态各有各的读写接口：逐条删除用户资料，需要能够定位的记录；减轻每一步读取巨大状态的负担，则更依赖内部结构的设计。先想清楚更新、撤销和读取各需要什么，再选择相应的记忆载体。

### 6. 记忆更省 token，就真的更便宜吗？

记忆系统的成本远比"提示有多长"复杂，它会把开销在时间上重新分配。Manus 的作者算过一笔账：缓存命中的输入 token 价格只有未命中时的十分之一，同一段内容读一次花多少钱，要看它前后怎样安排。写入时花一次摘要或建索引的钱，可能换来以后多次读取的节省；可如果一条记忆很少被复用，这笔投入就永远收不回来。完整的比较应当把生成记忆、更新索引、检索、读取以及失败后的恢复都算进去，并分别报告第一次使用和长期使用两种情形。否则，一个预先准备了昂贵记忆库的方案，很容易显得比从原始输入开始的基线更便宜。

> 主线位置：阶段四，上下文工程里的成本一侧。接 Manus 对 KV 缓存命中率的强调、Anthropic 的注意力预算，以及 StreamingLLM 的注意力汇点。

> **要点：** 一组论文想办法让模型生成时少读历史，差别在于读多少由谁决定：模型自己声明、按需召回，还是固定的窗口。另一组把账算到检索前端和整个 agent 工作负载上。

![记忆的完整成本账与读取方式](../assets/memory/b6-cost.svg)

*图：左边是一份完整成本账的五项开销，两种颜色分别是首次使用和多次复用（条形长度为示意）；右边是四种读历史的方式，深色格是实际读取的 KV。*

注意力这一侧，有两篇工作让模型生成时少读历史。模型生成每个新 token 时，默认要读一遍之前所有 token 的 KV 缓存，历史越长，读得越多。**[Language Models Can Control Their Own Attention](https://arxiv.org/abs/2609.02737)**（`2609.02737`） 让模型自己声明这一步需要全局、特定区域还是局部的注意力，再由推理引擎据此减少 KV 读取。它直接缩小了读取范围，可一旦判断失误，就可能漏掉远处的证据。**[On-Demand Attention: Language Models Know When to Recall](https://arxiv.org/abs/2609.20734)**（`2609.20734`） 采取局部优先的策略：平时只读最近一段，一个轻量的判断模块决定是否需要重新读取全部历史，完整的 KV 缓存一直保留着。两者都在少读历史，后者保留了重新访问的机会，所以计算上的节省和存储上的节省要分开来看。

**[Sliding-window beats linear attention](https://arxiv.org/abs/2608.28444)**（`2608.28444`） 则为最简单的固定窗口正名。滑动窗口只保留最近的一段上下文，再加上 StreamingLLM 发现的开头那几个注意力汇点；线性注意力是另一类把历史压成固定大小状态、以求省算力的架构。在作者比较的设置中，前者能够匹敌甚至超过经过后训练的线性注意力方案。题名说得很满，读的时候更要看清模型、任务和内存预算；它提供的是一个应当认真比较的简单基线，还谈不上对所有线性架构的最终判决。

成本也不只出在注意力上。**[The Embedder's Dilemma: LLMs Are Better, but at What Cost?](https://arxiv.org/abs/2608.12875)**（`2608.12875`） 从检索的前端算账，比较用大模型和用专用的嵌入模型把文本编码成向量，在多个任务上的质量、费用和速度，发现总体表现相近时成本可能相差很大。**[From LLM Inference to Agentic Workloads: Characterization and Implications for Serving Systems](https://arxiv.org/abs/2608.15127)**（`2608.15127`） 用 AgentSysBench 测量完整的 agent 工作负载，指出工具、沙箱和状态管理可能成为主要的耗时来源，所以优化一次模型调用，未必能缩短整个任务。

所以成本至少要拆成构建、维护、检索、生成和环境执行五项，再区分首次使用和多次复用。昂贵的建库开销可能在大量查询之后被摊薄，也可能因为资料很快过期而永远回不了本。服务多个用户时，还应当记录并发情况和尾部延迟：平均查询很快，可偶尔为了重建记忆阻塞几十秒，对实时助手来说仍然不够用。一个实用的对照办法是固定最终任务质量的门槛，比较达到门槛所需的总费用，适合部署选型；另一个办法是固定费用，看错误的分布有没有变化，适合研究归因。

### 7. 当记忆来自视频、手机和语音，问题怎样变化？

当记忆来自连续的视频、手机和语音，首先要解决的是事件对齐。Lilian Weng 在长文里把人类的感觉记忆对应到原始输入的嵌入表示上，可在 2023 年，这一层还几乎只停留在文字上。当助手开始戴在你头上、装在你手机里、和你实时语音对话，多存几张截图和几段录音解决不了对齐。同一个物体可能从不同的视角出现，同一句话也需要时间、说话人和周围环境才能被正确解释。连续感知还带来了隐私和信息过时的问题：系统看过的东西，未必应该永久保留；能检索到的东西，也未必允许用于任何任务。所以这里要同时研究时间组织、证据定位、存储预算和访问范围。

> 主线位置：阶段二在多模态上的延伸，并同时触及阶段四的预算问题和"能否忘掉"的边界。接 Lilian Weng 的感觉记忆与 Generative Agents 的记忆流。

> **要点：** 感知输入不会停下来，这一组论文都要在问题出现之前决定留下什么。它们的差别在于留下的形式：分层的时间线，模型内部的状态，带时间戳的文字，分开的信息与情感两条通路，或者按查询挑出的证据子图。

![连续多模态输入的记忆](../assets/memory/b7-multimodal.svg)

*图：顶部是一条不断进来的多模态输入流，下面五条泳道是本分支论文各自留下的东西，右侧的小标签是它们的记忆形式；底部一条是手机场景的隐私与适用范围问题。*

第一种留法是分层的时间线。**[LightMem-Ego](https://arxiv.org/abs/2607.11487)** 把第一人称视角的视觉和音频对齐到一条共同的时间线上，再把记忆组织成当前、短期和长期三层，根据查询选择从哪一层检索。它强调的是流式积累和分层访问，结构上很像把 Letta 的分层记忆搬到了多模态场景，Letta 的四层是最近消息、核心记忆块、完整对话历史和归档知识。要长期使用，还需要把隐私、耗电和检索可靠性纳入评价。

视频模型内部同样面临"桌面太小"的问题：KV 缓存装不下几小时的画面。**[StreamTTT: Reconciling Real-Time Perception and Long-Term Memory in Streaming VLMs](https://arxiv.org/abs/2608.13416)**（`2608.13416`） 用在线更新的快权重来保存久远的视频历史，把较短的 KV 窗口留给当前画面，以此调和实时感知和回顾过去之间的冲突。**[OneStreamer: Unifying Perception, Memory, and Proactive Response in Streaming Video Interaction](https://arxiv.org/abs/2610.01762)**（`2610.01762`） 则学习生成带时间戳的局部描述和事件摘要，用文字记录补充最近的视觉窗口，并学习什么时候从等待转为主动回应。前者把历史压进模型内部的状态，后者保留了更可读的文字证据。

**[MobileMem: Learning from a Year of Mobile Experiences](https://arxiv.org/abs/2608.13606)**（`2608.13606`） 把场景拉长到手机上的持续经历，利用用户的应用会话构建连贯的长轨迹，测试知识更新、时间推理和隐式偏好。它可以看作 LongMemEval 在手机上的延伸，LongMemEval 测的正是信息抽取、跨会话推理、时间推理、知识更新和拒答这些长期记忆能力；不过合成轨迹的连贯性和真实用户的行为仍然要区分开。手机上记住很多东西，还得考虑敏感数据和跨应用的边界，单把对话基准做得更长解决不了这些问题。

语音交互对时延的要求最苛刻。**[VoiceMem: Streaming Dual-Brain Memory for Real-Time Interaction](https://arxiv.org/abs/2608.26005)**（`2608.26005`） 把语音交互中的记忆分成信息和情感两条通路，并考虑了流式读写、训练和可替换的部署后端。它说明长期助手除了召回事实，还得在交互时限内作答；情感或画像上的分数，还不足以证明用户体验得到了长期改善。

按查询挑出证据，是另一种留法。**[GraphMemix: Query-Aware Evidence Forests for Long-Term Multimodal Agent Memory](https://arxiv.org/abs/2608.26983)**（`2608.26983`） 则按查询把相关的片段和关系组织成一片"证据森林"，在预算之内挑选能支持当前问题的部分，以此弥补离线统一摘要和简单相似度检索的不足。

流式多模态记忆需要同时保留内容、时间和跨模态的对应关系。过早地生成语义摘要可能丢掉细节，保留全部原始观察又会推高检索成本。时间索引和原始片段回查可以互相补充；至于要不要引入图结构或内部状态，取决于证据链在哪一环最常断掉。

## 四、方法对照：同样叫记忆，实际改变了什么？

七个分支都叫"记忆"，改变的东西却大不相同。有的改的是事实状态，它需要能被纠正；有的改的是程序性经验，它需要能被复用；还有的改的是模型内部表示或外部索引，它们各有各的访问成本。如果不分开看，就容易把所有收益都笼统地归结为"记住了更多内容"。下面这张表按要解决的问题把方法排开，并列出各自的主要代价和最该检验的条件。

> **本节要点：** 七个分支面对的困难归成七行。第二节末尾的总对照按方法的来历比较，这里按要解决的问题比较。

| 问题 | 代表方法 | 主要代价 | 重点检验条件 |
|---|---|---|---|
| 旧事实覆盖新要求 | 状态关系、替代标记、生命周期管理 | 更新冲突处理与审计成本 | 长期真实修改、删除和恢复测试 |
| 旧经验不适用 | 使用时重构、即时整理、环境核查 | 原始轨迹保留、额外读取或训练 | 跨环境迁移与完整成本对照 |
| 历史挤满工作窗口 | 摘要训练、可恢复卸载、分类型存储 | 信息损失风险、检索与训练开销 | 后续任务成败，摘要文字质量次之 |
| 不知写删是否有效 | 贡献归因、教师分层记忆、来源追踪 | 奖励和教师依赖 | 反事实贡献、长期遗忘后果 |
| 外部读写成为瓶颈 | 原生状态、参数模块、快权重、状态草图 | 模型改造与可解释性下降 | 定向纠正、删除与部署可迁移性 |
| 读取历史太慢 | 声明式注意力、按需全局读取、简单窗口 | 召回误判或完整 KV 存储 | 同质量端到端费用与尾部延迟 |
| 连续多模态输入 | 流式状态、时间描述、证据子图 | 实时预算、模态损失、隐私维护 | 真实长期用户与跨模态证据审计 |

这些路线作用在不同的层次上：外部系统可以直接调整记录和检索方式，参数或内部状态方案则往往需要相应的训练和推理实现来配合。比较时，先确定部署条件，再在同一个任务下考察质量、维护成本和恢复能力。

## 五、开放问题与研究机会

下面四个开放问题，来自论文助手要跨过的三道坎和随之而来的维护负担。要让它在第六周画出一张正确的图，它得跨过三道坎：先要知道 results_v3 已经取代了 results_v2，并记得为什么；再要在一大堆往来对话里挑出"坐标轴用英文"这条此刻真正要紧的约束，同时别把"先用柱状图凑合"这种早已过期的权宜之计当真；最后，经过几个月的合作，它最好还能学到你和导师的习惯，越用越顺手，而那些你明确说过要删掉的东西，也真的不再影响它。这三道坎分别对应状态维护、面向未来的读写选择和跨任务的经验复用。三道坎都跨过以后，还剩下第四个问题：记忆越积越多，谁来维护它。四个问题都需要在持续的任务流中观察，单次的历史问答很难完整覆盖。

> **本节要点：** 四个开放问题依次是：维护可修正的当前状态，按未来价值学习读写，跨任务复用经验同时保持可撤销，以及不让记忆的增长变成维护负担。

**1. 如何从不断变化的历史中维护可修正的当前状态？**

事实会更新，目标会改变，证据之间还会互相矛盾，这些都让记忆无法只靠持续追加的摘要来维持。一个有前景的方向，是研究带有来源、时间、生效条件和依赖关系的记忆状态，让一次纠正能够传播到所有受影响的结论上。比如任务目标改变之后，旧计划中的哪些步骤应当失效，已经完成的哪些工作仍然可以复用，需要分别处理；在论文助手的例子里，导师发现 v2 里有一组数据跑错、改用 v3 之后，基于 v2 画的那几张图也应当被标记出来。评价时应当同时考察状态是否正确、纠错有多快以及后续任务能否完成，以此检验系统维护的究竟是当前的事实，还是只找回了一条曾经正确的记录。

**2. 如何根据未来决策价值学习写入、检索和遗忘？**

写入的时候，系统通常还不知道未来会遇到什么任务，一条眼下没用的信息，可能很久以后才成为关键证据。这里的研究机会是用带有延迟需求的任务流来训练记忆策略，把未来的收益和整理、读取、补查的成本一起放进优化目标，这也正是 Letta 训练记忆模型想要做的事。实验设计上，需要变换查询的时间和任务的类型，并刻意保留一些稀有但重要的线索，防止策略只学会优化近期的摘要质量。已经丢掉的信息能不能通过重新观察补回来，也是决定保存优先级的重要条件。

**3. 如何让经验跨任务复用，同时保持隔离与可撤销？**

不同的用户、项目和环境可以共享方法，却不应当无条件地共享私有事实或过期规则。可以研究事实、技能和个性化偏好各自的迁移机制，明确每一类的适用范围，并追踪原始记录、摘要、图关系、缓存和参数更新之间的派生关系。删除一条记录之后，还要检验系统以后的行为是否仍然受它影响；环境变化之后，则要观察系统能否识别出旧经验已经失效，主动补充证据，或者停止套用旧规则。Letta 期望记忆能跨越模型的更新换代传承下去，这个愿景越是诱人，可撤销性就越重要。

**4. 如何避免记忆增长演变为长期维护负担？**

系统持续运行下去，会出现重复的条目、退化的索引、相互冲突的来源和逐渐漂移的检索成本。编码 agent 的指令文件 CLAUDE.md 里的规则只加不删、越写越长（见三.4），就是一个缩影。这里的研究机会是让系统主动合并、归档和修复记忆，同时保留可以回查的依据，Letta 设想的 sleep-time 后台整理是一条可能的路径。评测应当覆盖足够长的任务流，并一起报告存储增长、过期比例、冲突处理成本和任务表现。只有把维护动作本身也计入预算，才能判断紧凑的内部状态和外部可审计的记忆，分别适合哪些需求。
