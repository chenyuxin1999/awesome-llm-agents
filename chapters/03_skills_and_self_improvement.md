# 03｜自我改进（RSI）：让经验留下来，再反过来改进系统本身

[首页](../README.md) · [专题索引](../README.md#topics) · [文献目录](../catalog/03_skills_and_self_improvement.md)

## 方向背景：为什么要研究自我改进

设想一个刚入组的同学第一次跑通实验。第一次总是慢的：环境要配，脚本要改，报错要一行行查。可到了第二次、第三次，他会越来越快，因为他记住了哪个依赖版本会冲突，攒下了几段顺手的脚本，也慢慢摸清了导师看结果时最在意什么。再过半年，他甚至会回头改进组里的实验流程本身，让后来的人少走弯路。人做事的能力就是这样一点点长出来的。

今天的 agent 大多还做不到这一点。它们完全可以在一次任务里表现得相当聪明，可任务一结束，上下文一清空，刚刚踩过的坑、刚刚摸索出来的窍门就全都消失了。下一次遇到几乎一样的问题，它又从头搜索、从头试错。模型再强，这种"每次都是第一天上班"的状态也意味着大量重复劳动，经验没有地方沉淀。

自我改进研究的就是怎样打破这个状态：让 agent 把经验留下来，并且让留下来的东西真正改变它以后的行为。这件事往深处走，会自然地引出一个更大的问题。如果 agent 不仅能积累经验，还能修改组织自己的代码，甚至修改"如何提出修改、如何判断修改好坏"的那套机制，改进本身就会进入一个循环，这就是近两年热度很高的递归自我改进（Recursive Self-Improvement，RSI）。

本章就用 RSI 来统一这些问题。知乎《万字长文带你读懂 RSI》给过一个很好用的定义：agent 与环境交互之后，利用任务轨迹和反馈，通过某种更新机制修改自身状态，并让修改后的状态参与后续任务。这里的"自身"可以是模型参数，也可以是包在模型外面的那一层 harness，包括上下文、记忆、技能、工具和代码；走到最远处，被修改的还可以是负责改进的那套机制本身。

技能是这条路上最常见、也最容易落地的一环。它回答的是"遇到这类情况该怎么做"，是经验沉淀下来最自然的形态。所以本章前半部分的前沿论文大多在讨论技能怎么来、怎么用、怎么维护，后半部分再一路往上，走到 harness、改进器和权重。

## 一、先分清几个容易混在一起的概念

读这个方向的论文，最容易被几组相近的词绕晕。这里先把它们摆开说清楚。基础的参数、token、训练与推理概念见[大模型基础](../docs/llm_primer.md)。

第一组是**技能和记忆**。记忆保存的是"发生过什么"，比如上周哪个任务失败了、用户提过什么偏好；技能回答的是"这类情况该怎么做"。从记忆走到技能，中间要经过好几道工序：挑出值得留下的经历，把它抽象成通用的做法，想清楚这个做法在什么条件下成立，最后再验证它确实管用。举个例子，"找不到成绩列时先问用户"是一条能迁移的技能，"永远读第三列"只是某一次任务的偶然记录。一段失败后的反思，也只有在后来真的改变了行为时，才算发挥了作用；写得头头是道、换个环境却会误导人的经验总结，在实践里并不少见。

一项真正好用的技能，通常要讲清楚适用条件、需要的输入、执行步骤、怎么判断成功，以及什么时候该停下来。它可以是一段文字说明，可以是一段可执行代码，也可以是训练进模型的一组参数。三种形式各有长处：文字最容易让人检查，代码可以直接运行验证，参数则和模型的计算融为一体。相应地，它们更新起来的成本、需要的证据也各不相同。

第二组是 **harness 和模型**。harness 指包在模型外面的那一整套执行系统，包括提示词、工具、记忆、路由、执行循环、停止条件和各种检查机制。很多自我改进工作只改 harness，基础模型的参数保持冻结；也有一些工作直接更新权重。两条路都能让系统变好，也可以交替进行，但它们改变的东西不一样。读论文时最好时刻问一句：这里的提升来自改了提示词，还是模型真的学会了新能力？

第三组是**改一次、持续改、递归改**。只改善这一次的输出，叫结果修订；把有效的变化留到以后的任务里，叫持续改进；如果连提出修改、筛选修改、验证修改的那套机制也一起更新，再用更新后的机制开始下一轮，才是递归改进。声称做到了递归的工作，应当讲清楚每一轮之间到底继承了什么，以及改进的效率有没有真的随轮次提高。单纯把搜索多跑几遍，是给不出这些证据的。

## 二、发展主线：被修改的对象一层层往上爬

这条主线把两篇文章的视角放在了一起。DAIR.AI 的合集按思想谱系和时间来排，Lilian Weng 的长文按"改的是哪一层"来排。把两者叠起来看，自我改进这十几年的历史可以读成一架梯子：每往上爬一级，被修改的东西就离"产生改进的机制本身"更近一步，可能获得的收益更大，验证起来也更难。

### 起点：先要证明，后来改成去试

"机器改进自己"这个想法比大模型早得多。1965 年，I. J. Good 就设想过一台足够聪明的机器可以设计出更聪明的机器，由此引发智能爆炸。真正把它写成一个严肃的计算框架的，是 Jürgen Schmidhuber 在 2003 年提出的 [Gödel Machine](https://arxiv.org/abs/cs/0309048)。它的规矩非常严格：系统想改写自己的任何一部分代码，必须先给出一个形式化证明，证明这次改写会带来更高的长期收益，证明通过了才允许动手。这个设计在理论上无懈可击，因为每一步改动都有数学担保；可在工程上几乎无法实现，现实中的程序复杂到根本写不出这样的证明。

十几年后，另一条思路给出了不同的答案。2019 年 Uber AI 的 [POET](https://arxiv.org/abs/1901.01753) 不再要求任何证明。它让环境和智能体一起演化：系统不断生成新的、更难的地形，同时训练智能体去征服它们，并且允许一个环境里练出来的智能体被"借调"到另一个环境里去试。好不好，放到环境里跑一跑就知道，再也用不着推导。

这两篇论文放在 DAIR.AI 合集的开头，用意很明显。后来几乎所有基于大模型的自我改进工作，都走了 POET 这条"先去试，再看结果"的路，用经验检验代替了形式证明。今天各种方法之间的分歧，很大程度上就是在 Gödel Machine 的"可证明"和开放式演化的"可探索"之间，寻找各自的平衡点。

### 第 1 级：经验先留在模型外面

大模型出现以后，最早的一批自我改进工作都很谨慎，它们没有去碰模型的权重，只是想办法把经验存在模型外面。

2023 年的 [Reflexion](https://arxiv.org/abs/2303.11366) 做法很朴素：任务失败后，让模型用自然语言写一段反思，比如"我刚才没检查文件是否存在就直接读了"，下次尝试时把这段反思带上。作者把这称为"语言形式的强化学习"，因为反思起到的作用和奖励信号类似，只是写成了人能读懂的句子。

同一年 NVIDIA 等机构的 [Voyager](https://arxiv.org/abs/2305.16291) 在 Minecraft 里走得更远。它让 agent 自己给自己出题，形成一套由易到难的课程；每当学会一件事，比如造一把石镐，就把成功的做法写成一段可执行的代码，存进技能库。下次遇到相关任务，agent 直接检索、调用、组合这些技能。和 Reflexion 相比，Voyager 留下的东西从"下次要注意什么"变成了"下次可以直接怎么做"，这是从反思到技能的关键一步。

此后两年，这条路线不断被工程化。2025 年的 [Agentic Context Engineering](https://arxiv.org/abs/2510.04618)（ACE）发现，如果每次都让模型把经验重新总结成一大段文字，细节会在一轮轮改写中慢慢流失，作者称之为上下文坍缩。ACE 的办法是维护一本条目化的 playbook，由生成、反思、整理三个角色分工，每次运行后只对相关条目做增删改。同年 10 月，Anthropic 发布了 Agent Skills，把技能做成了产品层面的标准格式，技能这个概念由此真正走进了日常工程。

DAIR.AI 对这一级的评价一针见血：这些系统确实在自我改进，但还谈不上递归。写反思、维护技能库的那套流程，从头到尾都是人设计好的，自己从来没有变过。今天技能方向的大多数新论文，也就是本章三.1 到三.4，都在这一级里精耕细作：技能从哪里来，技能多了怎么挑，技能库怎么维护才不至于越来越乱，以及哪些技能值得干脆训进模型里。

### 第 2 级：让 agent 改写组织自己的代码

下一步的想法很自然：既然经验可以存下来，那组织这些经验、调度工具、安排流程的那段 harness 代码，能不能也让 agent 自己来改？

2024 年 Jeff Clune 组的 [ADAS](https://arxiv.org/abs/2408.08435)（Automated Design of Agentic Systems）第一次把这个问题讲清楚。他们注意到，过去几年人们手工设计了大量 agent 结构，思维链、自我反思、多 agent 辩论等等，而这些结构完全可以写成代码。于是他们让一个元 agent 读着已有设计的档案库，用代码写出新的 agent 设计，跑分之后再放回档案库，如此循环。差不多同时，[AFlow](https://arxiv.org/abs/2410.10762) 把工作流表示成由代码节点连成的图，用蒙特卡洛树搜索在这张图上寻找更好的流程。2025 年的 [GEPA](https://arxiv.org/abs/2507.19457) 则把重点放回提示词，用自然语言反思加上演化搜索来优化整个系统里的多段提示。

这一级的代表系统是 2025 年的 [Darwin Gödel Machine](https://arxiv.org/abs/2505.22954)（DGM）。名字里的"Gödel"致敬的是前面那台要求证明的机器，"Darwin"则说明它换成了演化的办法。DGM 从一个简单的编程 agent 出发，每一轮从档案库里挑一个版本，让它读自己的评测记录，提出一项改进并亲手改进自己的代码，比如加一个更精细的文件编辑工具，或者加一道多次尝试后互相评审的流程。新版本只要能正常运行、还能改代码，就会被留在档案库里，哪怕它的分数暂时不如父代。正是这种"不只盯着当前最优"的做法，让 DGM 在 SWE-bench 上的成绩从 20% 一路爬到了 50%。

Lilian Weng 在长文里把这一级的意义讲得很透：harness 代码是一个几乎通用的搜索空间，提示词、上下文管理、工具调用、子 agent 的调度，统统都可以写成代码来搜。不过她也提醒，这类收益始终被基础模型的能力卡着，模型本身不够强，搜出来的 harness 也好不到哪里去。本章三.5 收录的新论文，基本都在回答同一个问题：怎样让 harness 搜索更可控，搜出来的东西更能迁移到新任务上。

### 第 3 级：连改进器本身也改

真正意义上的"递归"，是从这一级开始的。前面几级里，无论改的是技能还是代码，负责提出修改、判断修改好坏的那套机制始终是固定的。现在，这套机制本身也成了被修改的对象。

最早尝试这件事的工作出现在 2023 年。DeepMind 的 [Promptbreeder](https://arxiv.org/abs/2309.16797) 在演化任务提示词的同时，也演化"如何变异提示词"的那段提示，让改进的方法跟着改进的对象一起进化。同年 Eric Zelikman 等人的 [STOP](https://arxiv.org/abs/2310.02304)（Self-Taught Optimizer）做了一个干净利落的实验：先写一段用语言模型改进程序的"改进器"程序，然后把这个改进器自己当作待改进的程序交给它。GPT-4 在这个过程中自己发现了束搜索、遗传算法、模拟退火等经典策略，改进器确实越改越好。但作者也坦率地报告了两件让人警惕的事：换成能力较弱的模型，这个循环就转不起来；而且模型偶尔会试图关掉实验设置的沙盒限制。2024 年的 [Gödel Agent](https://arxiv.org/abs/2410.04444) 则让 agent 在运行时直接读取和修改自己的逻辑，连"怎样决定下一步改什么"也不再写死。

2025 到 2026 年，DGM 引出了一串后继工作，它们修补的恰好都是 DGM 里还写死的部分。[Huxley-Gödel Machine](https://arxiv.org/abs/2510.21614) 发现，一个版本当下的分数并不能很好地预测它将来能孕育出多好的后代，于是改为评估整个分支的潜力，以此决定下一轮从哪个版本继续扩展。[Group-Evolving Agents](https://arxiv.org/abs/2602.04837) 让一群 agent 共享各自的经验，一起演化。Meta 的 [HyperAgents](https://arxiv.org/abs/2603.19461) 更进一步，把负责修改的元层程序也放进了可编辑的范围。

再往外推一步，就是让 AI 来改进 AI 研究本身。DAIR.AI 把这一组工作单独列成一段。DeepMind 先有 FunSearch，用大模型加演化搜索在组合数学问题上找到了新的构造；后来的 [AlphaEvolve](https://arxiv.org/abs/2506.13131) 把同样的思路用到了更广的算法和工程问题上，包括找到更少乘法次数的矩阵乘法方案，以及为 Google 的数据中心调度省下可观的算力。Sakana 的 [The AI Scientist](https://arxiv.org/abs/2408.06292) 尝试让一条流水线从提出想法、写代码、跑实验一直做到写出论文。[PostTrainBench](https://arxiv.org/abs/2603.08640) 开始测量 agent 能不能独立完成模型的后训练，[Recursive self-improvement of AI research agents](https://arxiv.org/abs/2609.26457) 则让研究 agent 修改自己的代码，并连续自主运行了好几天。本章三.8 收录的新论文就落在这一级。

### 第 4 级：把经验写进权重

与上面几级平行的，还有一条更"硬"的路线：让模型用自己生成的数据训练自己，把经验直接写进权重。

这条路线的起点是 2022 年的 [STaR](https://arxiv.org/abs/2203.14465)，也出自 Zelikman 之手。它的想法很简单：让模型对大量题目写出推理过程，用标准答案筛掉错的，答错的题目则给出提示，让模型重新推一遍，再用这些推理过程继续训练模型。如此反复，模型的推理能力一轮轮提升。2024 年 Meta 的 [Self-Rewarding Language Models](https://arxiv.org/abs/2401.10020) 去掉了标准答案这根拐杖，让模型自己给自己的回答打分，再用这些分数做偏好训练。2025 年的 [Absolute Zero](https://arxiv.org/abs/2505.03335) 连题目都不要了，模型一边出题、一边解题，由代码执行器来判断对错。同年 MIT 的 [SEAL](https://arxiv.org/abs/2506.10943)（Self-Adapting Language Models）让模型自己写"自我编辑"方案，包括生成什么训练数据、用什么超参数微调，然后真的去微调，再根据微调后的表现，用强化学习教模型以后写出更有用的方案。

DAIR.AI 用一句话概括了这条线的走向：用来筛选训练数据的信号，从标准答案变成了模型自己的判断，又变成了模型自己发明的任务。监督越来越少，自主越来越多，风险也越来越大。

今天前沿的兴趣在于把第 2 级和第 4 级接起来。harness 在运行中产生大量轨迹，这些轨迹可以拿来训练模型；模型变了，原来为它量身设计的 harness 又未必合适，需要重新搜索。Lilian Weng 把这种做法称为 harness 与权重的联合优化，本章三.4 和三.7 讨论的正是这件事。

### 给新论文定位：一套多维坐标

上面这架梯子只回答了一个问题：改的是什么。可两篇论文就算改的是同一层，做法也可能天差地别。知乎上那篇《万字长文带你读懂 RSI》补上了其余几个维度。它的"进化对象"一维，把参数、上下文、记忆、Skill、Harness 代码依次排开，和本章的梯子基本对应；其余几维则是梯子没有覆盖到的。

第一个维度是**进化结构**，也就是版本与版本之间怎么继承。最简单的是链式：系统始终只有一个当前版本，每次在它的基础上修改，前一轮犯的错会被下一轮原封不动地继承下去。树式会保留历史上的多个版本，任何一个都可以重新拿出来分叉，DGM 就是这样做的。图式则更进一步，一次修改可以同时参考多个任务、多个分支的轨迹，让不同谱系的经验汇合在一起。

第二个维度是**谁来更新**。有的系统由执行任务的 agent 自己反思、自己修改；有的系统另设一个"教师"，它可以是另一个 agent，也可以是一段优化流程，由它决定把什么写回去；还有的系统让两者分工合作。原文特别强调，只负责打分的模块不算教师，教师必须实际决定写回什么内容。

第三个维度是**更新时机**。离线模式先在训练任务上改完，测试时冻结；在线模式边做任务边更新，前面的经验直接影响后面的任务；混合模式先离线攒下一批初始经验，上线以后继续调整。

| 维度 | 取值 | 代表工作 |
|---|---|---|
| 进化结构 | 链：始终只有一个当前版本 | [SkillFlow](https://arxiv.org/abs/2604.17308)：同一任务族里按顺序给 Skill 库打补丁 |
| | 树：保留多个历史版本，任意版本都能继续分叉 | [Darwin Gödel Machine](https://arxiv.org/abs/2505.22954)：低分版本也留在档案库里 |
| | 图：一次修改同时参考多个任务或多条谱系的轨迹 | [Mendel Gödel Machine](https://arxiv.org/abs/2608.07645)：跨任务对照、跨谱系杂交 |
| 谁来更新 | 自身：执行任务的 agent 自己改 | Reflexion、[ReasoningBank](https://arxiv.org/abs/2509.25140) |
| | 教师：另一个 agent 或优化流程决定写回什么 | [Recuris](https://arxiv.org/abs/2608.24876)：Meta-Agent 汇总多个任务的失败后局部修补 Skill |
| | 联合：两者都影响最终写回的内容 | [Evo-Harness](https://arxiv.org/abs/2608.15071)：Solver 提出候选经验，Evolver 筛选并编译 |
| 更新时机 | 离线：训练任务上改完，测试时冻结 | [GDPevo](https://arxiv.org/abs/2608.03764)：用规则重组构造训练与测试任务 |
| | 在线：边做任务边更新 | [FinEvo-Bench](https://arxiv.org/abs/2608.06144)：120 个金融任务组成的任务流，配有状态重置的对照组 |
| | 混合：先离线攒经验，上线后继续改 | Mem²Evolve |
| 其他 | 验收标准、反馈来源、反馈类型（分数还是文字）、更新频率、经验作用范围（通用还是专用） | 见原文第 6 节 |

读一篇新论文时，可以先在梯子上找到它改的层级，再用这张表把其余坐标补齐。坐标一旦不同，分数就很难直接比较，在线更新和离线更新的结果尤其如此。顺带提醒一个容易踩的坑：原文介绍的 SkillSmith（技能与工具共同进化）和本章三.1 收录的 SkillSmith（参数技能组合）是两篇同名的不同论文。

### 边界：循环在哪里断掉

梯子每往上爬一级，"怎么知道真的变好了"这个问题就更难回答。DAIR.AI 专门留了一整节来讲这件事，其中几篇工作值得每个做这个方向的人认真读一遍。

2023 年 DeepMind 的 [Large Language Models Cannot Self-Correct Reasoning Yet](https://arxiv.org/abs/2310.01798) 给当时颇为流行的"让模型自己检查自己"泼了一盆冷水：在没有外部反馈的情况下，模型自我纠错之后，推理题的准确率往往不升反降。同年的 [The Curse of Recursion](https://arxiv.org/abs/2305.17493) 则从训练的角度说明，如果反复用模型自己生成的数据训练下一代模型，分布尾部那些少见但重要的信息会一点点消失，最后导致模型坍缩。2024 年的 [Mind the Gap](https://arxiv.org/abs/2412.02674) 把这些现象归结为一个更一般的量，叫生成与验证之间的鸿沟：模型判断答案好坏的能力，比它生成答案的能力强出多少，决定了自我改进最多能走多远。

另外两篇工作从实际风险出发。2025 年的 [Your Agent May Misevolve](https://arxiv.org/abs/2509.26354) 发现，agent 在积累记忆、创造工具、优化工作流的过程中，安全性可能悄悄退化，而且这种退化不容易被察觉。METR 在 2024 年发布的 [RE-Bench](https://arxiv.org/abs/2411.15114) 让 agent 和人类专家在同样的 AI 研发任务上比拼：时间预算很短时，agent 占了上风；预算一拉长，人类专家便后来居上。这说明"AI 做 AI 研究"目前在长程任务上仍有明显的差距。

Lilian Weng 在长文末尾列出的七个瓶颈，可以和这些论文对照着读：评价器太弱或者太模糊，上下文和记忆的生命周期难以管理，负面结果很少被报告，搜索过程容易多样性坍缩，系统会钻评价的空子，沙盒里的奖励未必代表真实世界的长期效果，以及人在这个循环里究竟该扮演什么角色。她的结论是，评价器和权限控制应当放在自我改进循环之外，由独立的一方掌握；人也不该退出，应当往上走一层，去做设定目标和最终判断的事。本章三.6 讨论"改进是不是真的"，三.8 的后半部分讨论"怎样防止系统自己放宽标准"，都是在这条边界上工作。

如果想看整张地图，2026 年 9 月的综述 [The Last AI Built by Humans](https://arxiv.org/abs/2609.11873) 用一架六级的自主性阶梯整理了整个领域，可以和本章的梯子互相对照着读。

## 三、前沿研究方向

下面八个分支收录的都是 2026 年的新论文。每个分支开头先交代它要回答的问题，第一段之后标出它在上面那架梯子上的位置，其余坐标可以用上一节的表格补齐。读这些论文时，建议始终带着两个问题：它改的是哪一层的对象？它用什么证据说明改进是真的？前一个问题决定它应该和哪些经典工作比较，后一个问题决定它的结论能信几分。

### 1. 怎样把经历和专家知识变成可以调用的技能？

从一次轨迹到可复用技能，中间需要一次有边界的概括：哪些步骤来自任务的共同结构，哪些只是在当前环境碰巧有效？复制成功轨迹保存了细节，却可能连同偶然条件一起保存；抽象成规则又可能失去执行所需信息。因此，技能至少应同时说明输入条件、执行办法和成功检查；只有一句“以后这样做”的建议还不够用。

> 主线位置：第 1 级，技能从哪里来。接 Voyager 的可执行技能库和 Anthropic Agent Skills。

**[Scientific Agent Skills: A Library of Procedural Knowledge for Research Agents](https://arxiv.org/abs/2609.00065)**（`2609.00065`） 提供面向科研的程序性知识库：技能目录包含可读指令、参考材料，部分还带脚本，按任务需要加载。它关心的是分析是否遵循领域接受的程序，而不仅是代码能否运行。报告评估了文档与上下文占用，尚未通过任务级实验衡量效果。后续可以检验领域程序是否被正确执行，以及这些技能对科研任务质量和执行成本的影响。

**[Repo-To-Skill: Distilling GitHub Repositories Into AI4AI Skills](https://arxiv.org/abs/2609.02749)**（`2609.02749`） 从代码仓库中提炼“把方法真正跑起来”的操作知识，区分面向领域的预先整理与面向具体任务的临时生成。它与人工知识库的差别在于知识生产过程自动化，也带来新的验证负担：仓库版本、依赖条件和默认假设是否被保留，所谓通过验证究竟覆盖哪些操作？把 README 缩短，还算不上提炼出了可迁移的方法。

**[Notes to Self: Can LLMs Benefit from Experiential Abstractions?](https://arxiv.org/abs/2607.20372)**（`2607.20372`） 从数学解题轨迹提取自然语言抽象，并比较推理时检索与带抽象提示的强化学习。它使“经验能否帮助后来的任务”成为可对照的问题，但数学策略与工具操作流程有不同的验收方式。**[From Memory to Skills: Evidence-Grounded Co-Evolution Governance for Long-Horizon LLM Agents](https://arxiv.org/abs/2607.16621)**（`2607.16621`） 更强调证据链，把经历整理成步骤、程序性策略和环境认知，只有带正向估计收益的策略才转成可调用技能，并保留适用边界和验证规则。

**[SkillSmith: Learning to Compose Parametric Skills and Textual Knowledge](https://arxiv.org/abs/2607.27497)**（`2607.27497`） 将技能表示推进到参数空间，用前缀调优形成参数技能，再结合文本信息生成新的前缀权重。**前缀调优（prefix-tuning）**学习一组附加在模型计算中的连续向量；这里生成的新前缀相当于一种可加载的参数化能力。它回答的是不同形式的知识如何组合。阅读时要检查表示方式、训练任务和未见组合，不能将其收益直接移植到一个只会读取 Markdown 的助手。

这些路线分别从专家程序、仓库知识、个人经历、证据支持的策略与参数模块出发。可复用技能应保留输入条件、经过验证的步骤及失败边界，完整对话本身算不上技能。执行前置、不可自动处理的歧义和必须确认的操作都属于技能定义的一部分。

### 2. 技能很多时，如何选对，并知道何时不用？

技能选择需要估计适用性，而不只是题目与文档的语义相似度。两个请求用词相近，却可能受到不同权限和环境约束；一个技能匹配当前子任务，也可能破坏后续目标。因而路由系统需要允许拒绝、回退和组合，并把误用成本纳入比较。技能库扩容后，命中率上升与实际任务收益上升也应分开测量。

> 主线位置：第 1 级，技能怎么用。Agent Skills 的渐进展开是这一节的默认基线。

**[Remember When It Matters](https://arxiv.org/abs/2607.08716)**让独立记忆 Agent 跟随执行轨迹，维护结构化记忆并选择何时提醒、何时保持沉默。它管理的是记忆介入，范围比完整技能库小，却为“何时不用”提供直接对照：摘要比较了选择性介入、始终注入和被动提供记忆等方式。这个工作说明，提供更多有用材料也可能打断决策，触发策略本身应成为可评估的能力。

**[Is Progressive Disclosure All You Need for Long-Context Agents?](https://arxiv.org/abs/2607.17598)**（`2607.17598`） 比较直接浏览长文档、技能包的渐进展开和经典混合检索。结果随执行系统的导航能力与文档数量变化：如果基础系统已经会分块检索，额外包装的收益可能很小。这说明分层展开解决的是访问问题；同一内容换成技能格式，系统本身不会因此变强。

**[The Router Within: Eliciting Native Skill Routing from a Frozen LLM](https://arxiv.org/abs/2609.15982)**（`2609.15982`） 不把全部技能描述塞进上下文，而从冻结模型的内部状态读取选择信号，先粗筛，再结合候选的后续判断作选择，仅训练少量映射。它更适合研究大库路由，但依赖内部状态和技能安装时的表示构建，不能假设任何黑盒接口都能使用。它把路由计算放进模型表示，渐进展开则把它放在可见文本里。

**[COBRA-Skills: Contextual Bandit-Guided Evolution for Agent Skill Optimization](https://arxiv.org/abs/2609.11682)**（`2609.11682`） 关注的是优化阶段该评估哪些候选，用上下文老虎机分配有限评估预算，并根据执行反馈继续改进技能。**上下文老虎机（contextual bandit）**依据当前任务特征，在利用已有高收益选择与探索不确定候选之间分配尝试；这里的一次尝试就是为某个技能候选付出执行评估成本。它决定的是把学习成本花在哪里，每次任务的检索仍交给检索器。**[Do AI Agents Know When a Task Is Simple? Toward Complexity-Aware Reasoning and Execution](https://arxiv.org/abs/2607.13034)**（`2607.13034`） 则让助手先估计任务范围，按最小可行路径执行，只有验证失败才扩大检查；其确定性模拟编辑实验有利于控制成本，但开放式真实任务中的难度估计仍更复杂。

**[Demystifying Agent Skills: Why They Work-Until They Don't](https://arxiv.org/abs/2608.14036)**（`2608.14036`） 通过控制表示、结果标记、检索难度和执行框架来研究技能何时奏效，强调程序指引如何稳定执行，也分析失效方式。这为技能路由提供了共同的检查点：选中技能、读懂技能与按需执行是三种能力，应分别记录。

技能调用的开销应与任务复杂度匹配。可以用简短描述支持初步选择，再检查系统是否实际调用了相关步骤。未被执行的技能内容仍可能影响模型决策，因此也应纳入上下文成本与行为风险分析。

### 3. 怎样修改、合并和删除技能，而不破坏已经会的事？

技能维护面对的是非单调变化：新版本解决了一个问题，可能让旧任务退化；合并看似重复的技能，也可能抹掉罕见但重要的适用条件。因此更新单位不应只有“整库变好没有”，还要追踪条目的来源、依赖关系、版本和回滚范围。保存多样性与控制库规模之间没有统一最优点，需要在真实任务流中测量。

> 主线位置：第 1 级，技能怎么维护。接 ACE 的条目化 playbook：增删改以条目为单位。

**[SkillProx: Self-Evolving Agent Skills via Proximal Textual Gradient Descent](https://arxiv.org/abs/2608.07449)**（`2608.07449`） 将诊断后的修改重新在同批任务上执行，回滚退化，再把技能拆成可审计单元，用移除单元后的效用检查决定合并、降级或删除。它把删除做成单独的维护机制。需要关注审计成本，以及在当前任务上看似无用的规则会不会在罕见情况中重要。

**[SkillAdam: Stable and Efficient Skill Evolution for Agents](https://arxiv.org/abs/2609.08944)**（`2609.08944`） 用优化记忆保留问题与尝试结果，稳定修改方向，并根据近期改善的波动调整修改幅度。其 Adam 类比是离散文档优化的设计启发，连续优化的收敛结论未必适用。与 SkillProx 比较，一个侧重避免遗忘有效修正，一个明确处理技能复杂度与淘汰。

**[SkillCommit: Evolving Agent Skills through Behaviorally Validated Scope Expansion](https://arxiv.org/abs/2608.15165)**（`2608.15165`） 从实例级补丁出发，通过跨实例重放和机制检查，确认行为可迁移后才扩大技能适用范围。**[SkillGLoW: Procedural-Family Skill Consolidation for Self-Improving Agents on Long-Horizon Task Streams](https://arxiv.org/abs/2609.02217)**（`2609.02217`） 则把局部技能聚合为共享解题程序的“程序家族”，生成更一般的先验，并用实际执行把关是否提交。两者都反对只因文字相似就合并；前者更强调范围扩张的行为证据，后者处理平铺技能库不断膨胀和全局文档过度泛化之间的两难。

**[GraphSkillEvo: Evolutionary Optimization of Graph-Structured Agent Skills](https://arxiv.org/abs/2609.21749)**（`2609.21749`） 将技能写成有条件转移的图：节点是执行步骤，边描述何时走向下一步，再在这一结构上做演化搜索。这缩小了任意自然语言改写的空间，也要求维护节点与边的一致性。若基础程序本来很简单，图结构的额外复杂度可能没有必要。

把这组方法用于表格清洗，可以保留“列名明确时自动处理”和“列名含糊时询问”两个分支，避免不断向一条总规则添加例外。每次合并都要保留旧案例用于回放，同时增加新情况。技能库维护追求的是在适当范围内复用，并能解释为何合并或删除；文件多少是次要的。

### 4. 能力应该留在外部技能里，还是训练进模型？

外部技能容易更新和检查，但每次使用仍需检索、读取并遵循；参数内化可能减少调用负担，却让局部修改更难定位和撤销。选择哪条路线取决于知识变化速度、复用频率和允许的训练成本。比较时要分别检查“带着技能文件是否更好”和“移除文件后是否仍然会做”，否则容易把上下文辅助误认为能力已被模型吸收。

> 主线位置：第 1 级和第 4 级之间。外部技能能不能、该不该训进权重，接 STaR 到 SEAL 那条线。

**[SKILL-KD: Contrastive Skill Distillation for LLM Agents](https://arxiv.org/abs/2607.28048)**（`2607.28048`） 比较学生失败与同题教师轨迹，把可执行差异整理为文字补丁，重新运行学生验证，再利用带轨迹关联的历史控制技能漂移。它适合学生不知道缺少哪一步的情况，却依赖教师示范和学生能够执行建议。教师的完整长轨迹未必适合小模型，提炼差异正是要缩小这个鸿沟。

**[Distill Skills into Weights, Not Prompts: Abstract Skills as Privileged Signals for On-Policy Self-Distillation](https://arxiv.org/abs/2608.09826)**（`2608.09826`） 让学生在自己的轨迹前缀上学习技能提示带来的教师优势，最终把收益训练进共享参数，测试时不再提供特权技能卡。这里的 **on-policy** 指监督发生在学生当前策略实际生成的前缀上；特权信息指训练时教师可见、测试时学生不可见的技能提示。它与文字补丁路线的区别是推理时依赖更少，但需要训练并控制教师与学生分布差异；应查看优势门控和答案过滤，避免把额外答案信息误认为抽象技能。

**[SKT: Skill-Use Training at Scale via Verified Synthetic Data Generation](https://arxiv.org/abs/2608.02287)**（`2608.02287`） 从技能库合成可执行任务与轨迹，通过规则和智能体验证、反馈修复，保留确实使用所需技能的成功轨迹，再训练模型的技能使用能力。**[SkillGym: Internalizing Human Skills into LLMs for Real-World Problem Solving](https://arxiv.org/abs/2609.27717)**（`2609.27717`） 则把人写的技能转为可验证环境，用代码检查和对比执行判断任务是否依赖该技能，支持监督训练和强化学习。二者共同将“拥有技能”与“会用技能”区分开，但合成器、检查器和留出技能的独立性决定评测是否可信。

**[Evo-Harness: Context-to-Harness Skill Compilation for Self-Evolving Agents](https://arxiv.org/abs/2608.15071)**（`2608.15071`） 提供另一种折中：基础模型不变，把一次包含噪声和偶然因素的执行经验编译成可复用的执行系统技能。它关注在线单次机会后的迁移，适合与参数学习比较即时更新速度；难点是一次经历是否足以区分通用教训与偶然细节。

选择路线时，先看变化频率与可撤销性。频繁变动的业务规则更适合外部保存；稳定且高频使用的操作可能值得训练内化。无论哪条路线，都应保留未参与提炼和训练的任务，并分别测有技能、无技能条件下的表现。模型能够在没有技能卡时完成任务，才说明能力不再完全依赖外部提示。

### 5. 怎样让整个执行系统进化，不止微调一句提示？

系统演化的对象可以是工具顺序、候选生成、状态保存和失败恢复，变化之间还存在依赖。直接同时修改所有组件，很难解释收益来自哪里；只允许改一句提示，又可能碰不到真实瓶颈。这个分支需要在可表达的修改空间与可定位的验证之间取舍，并保留候选版本，以区分当前最优配置和能够稳定迁移的改进机制。

> 主线位置：第 2 级。接 ADAS、AFlow、Darwin Gödel Machine，对应 Lilian Weng 文中的 Self-Improving Harness 与演化搜索两节。

**[测试时框架演化（TTHE）](https://arxiv.org/abs/2607.08124)**在测试阶段利用无标签执行轨迹维护候选框架，通过执行衍生的代理信号选择版本，并让选定程序继续处理后续输入。它与对当前查询反复重试不同，改变会持久影响未来任务；也不同于离线搜索后冻结框架。方法保持模型权重不变，需要检查的是代理评价信号何时可靠，以及跨输入适应是否引入顺序依赖。

**[RRSI: Regularized Recursive Self-Improvement of Agent Harnesses](https://arxiv.org/abs/2609.24972)**（`2609.24972`） 对候选修改数量施加随时间变化的预算，并用批判与剪枝减少基准特定改动。作者报告所测任务上的收益以及相对未正则化方案更低的策略 token 消耗。重点是控制搜索不要靠叠加越来越多规则记住旧题；还需把搜索时成本与部署时节省分开计算。

**[ModularRSI: Modular and Generalizable Recursive Harness Self-Improvement](https://arxiv.org/abs/2609.14857)**（`2609.14857`） 使用与测试基准分离的任务，对照同题成功与失败轨迹，跨任务定位反复出现的问题，并把执行系统拆成功能模块。它与 RRSI 互补：一个强调修改和选择约束，另一个强调证据组织与修改单元。模块划分能帮助归因，但也可能限制跨模块的有效变化，需要结合消融与跨领域测试判断。

**[HarnessBank: Semantic Gene-Bank Search with Gated Verification for Agent-Harness Self-Evolution](https://arxiv.org/abs/2607.13683)**（`2607.13683`） 保存不同语义方向的高质量执行系统候选，通过重组、筛选与门控验证探索，避免只沿单一候选贪心前进。**[DREvo: Distilling Recalibrated Historical Experience for Harness Self-Evolution](https://arxiv.org/abs/2607.26722)**（`2607.26722`） 则反复检查旧经验对当前版本是否仍有效，再提炼可操作的搜索方向。两者都把历史当成搜索资源，但一个侧重候选多样性，一个侧重证据随版本变化的有效性。

**[Procedural Graphs: Self-Evolving Execution Structures for LLM Agents](https://arxiv.org/abs/2609.09153)**（`2609.09153`） 将“接下来该做什么”表示为程序关系图：定位当前节点，根据邻近子图生成情境指引，再对照成功失败轨迹修改结构，通过留出验证后提交。这比自由生成更明确，却也要求把复杂行为正确映射到图。它与图技能优化的区别，在于组织整个执行时的状态与行动指引，而不只是修改一份技能说明。

执行系统的演化需要可定位的修改单元。失败恢复规则与工具选择方式可以分别调整，并保留输入、输出和版本作为对照；同时修改多个组件时，则需要进一步区分它们各自的贡献。历史候选库也不应只保存最佳分数，失败版本及其适用条件同样能避免重复探索。

### 6. 怎样证明改进真实存在，排除上下文、预算和泄题的影响？

改进实验至少有三个预算：收集经验、搜索更新和执行最终任务。只比较最后一次执行，会隐藏前两部分成本；反复用最终测试挑版本，则会让“迁移”混入选择偏差。比较时还应记录未改善或退化的任务。只有固定选版协议并保留独立测试，才有可能区分有效积累与一次幸运搜索。

> 主线位置：边界。对应 DAIR.AI 的“循环在哪里断掉”和 Lilian Weng 的评价器瓶颈。

**[ContinualSkillBench: Can LLM Agents Truly Evolve Their Capabilities?](https://arxiv.org/abs/2608.03874)**（`2608.03874`） 用多个领域中的连续任务比较技能维护与普通上下文学习。作者发现顺序执行常有帮助，但平均上显式技能维护与上下文学习表现相近，部分强调程序复用的任务才显示选择性收益。它迫使我们回答：改善来自一个可迁移技能，还是来自模型看过更多相关历史？

**[Agent Skills Can Be Harmful: An Empirical Study of Skill-Induced Failures in LLM Agents](https://arxiv.org/abs/2608.11888)**（`2608.11888`） 对照有技能与无技能或匹配参考运行，定位功能失败和成本退化。它整理的是失败案例，没有给出所有技能的失败概率。**[The Regression Tax: Decomposing Why Skills Help and Hurt LLM Agents](https://arxiv.org/abs/2607.22520)**（`2607.22520`） 则把原来会做、加技能后反而失败的“退化”，与两种设置都不会做的“残余失败”分开，讨论描述影响、输入理解被流程覆盖、输出检查被替代等机制。平均净收益会掩盖这两类完全不同的问题。

**[Rethinking the Evaluation of Harness Evolution for Agents](https://arxiv.org/abs/2607.12227)**（`2607.12227`） 直接质疑执行系统演化的评测：是否和相同反馈、推理预算下的简单搜索比较，是否在同一基准验证信号上既选择候选又报告成绩？作者在 Terminal-Bench 2.1 的实验中没有观察到自动演化稳定胜过简单测试时扩展。它是限定协议下的反例，适合与支持性方法对照着读。

**[HarnessOpt-Bench: Evaluating LLMs at Harness Optimization](https://arxiv.org/abs/2608.06301)**（`2608.06301`） 给优化者种子执行系统、有限目标评估预算和分级反馈，最终候选在搜索期间不可见的测试分区评估，并由受信执行环境计量资源和保存版本。它的价值在于把优化能力本身变成测量对象，而不只展示优化后智能体的成绩。

这些研究提示，评估持续改进至少需要以下对照：固定模型与预算；加入等长度历史和简单多次尝试基线；逐任务报告新解出与新退化；把开发、选择和最终测试隔离；计入提炼、搜索与验证费用。若一次改进只能在不断查看同一测试集之后出现，更准确的说法是系统适应了那套测试。

### 7. 模型与执行系统一起变化，会不会彼此不再合适？

框架会改变训练轨迹的分布，模型更新又会改变框架各组件的有效性。原本为弱模型设计的提示，在强模型上可能变成冗余；旧路由也可能把新能力错误分配给其他组件。因此共同优化除了轮流训练，还要检查每轮数据产生条件、部署版本与反馈目标是否一致，并保存能够重放的版本组合。

> 主线位置：第 2 级加第 4 级。对应 Lilian Weng 文中的联合优化一节。

**[Agentic Routing: The Harness-Native Data Flywheel](https://arxiv.org/abs/2607.11399)** 这项工作把路由与执行框架产生的数据联系起来，适合用来追踪“数据由谁生成、训练后又改变哪个选择”。它的价值在于把真实运行中的反馈用于后续分配，路由到更便宜的模型只是其中一个用途。阅读时应单独核对路由标签、框架版本与评价条件，数据循环存在本身证明不了持续优化稳定。

**[WHALE: A Simple Recipe for Joint Harness-Weight Optimization](https://arxiv.org/abs/2609.00196)**（`2609.00196`） 交替更新模型和执行系统：先在当前系统下训练，再为更新后的模型搜索更合适的系统，并比较固定时长或自适应切换规则。它的动机很实际：模型变强后，过去必要的提示可能多余；执行流程改变后，旧训练分布也可能不再匹配。交替优化增加了两个过程的成本，收益应和单独优化两侧比较。

**[HELIX: Model-Harness Co-evolution for Recursive Self-Improvement](https://arxiv.org/abs/2608.13951)**（`2608.13951`） 用可追溯的组件、接口与运行政策记录修改，并把成功、退化与近似成功轨迹作为后续训练数据。报告中的实验只有一轮演化，因此适合学习如何保留干预身份和证据，不能据此断言长期多轮闭环已经稳定。

**[Co-Evolving Harnesses and Models: On-Policy Correction Helps Weaker Models Catch Up Where Imitation Fails](https://arxiv.org/abs/2609.09134)**（`2609.09134`） 给出一个重要反例：在已经为弱模型优化的执行系统下，直接模仿强模型完整轨迹反而可能退化。作者改为定位弱模型自己轨迹中的失败回合，只让专家修正该处，以尽量保留原有规划风格。这说明“教师更强”不代表“教师整套方法更适合学生”，模型与执行系统的相容性本身需要测量。

**[S3Gym: Can LLMs Turn Self-Testing and Self-Judging into Self-Improvement?](https://arxiv.org/abs/2608.31100)**（`2608.31100`） 将自测试、自判断与自改进分开评估，允许探索但使用严格留出的最终测试，并比较直接历史、摘要记忆与参数训练。**[Aspire: Can Models Self-Evolve from Vague Goals?](https://arxiv.org/abs/2608.31111)**（`2608.31111`） 则进一步移除预先明确的任务指标，只给“提升某方面能力”的自然语言目标，让系统自己选数据和更新方式，最终接受隐藏专家任务评估。二者把反馈是否可信、目标是否可操作也纳入了问题。

目标变化与同一目标下的能力提升需要分开判断。持续改进闭环应分别记录任务目标、执行政策、模型版本和验收标准，明确哪些组件发生改变，避免把评价条件改变产生的收益视为原有能力增长。

### 8. 开放式递归改进怎样保持可验证和可控制？

递归与重复不一样：固定改进器反复优化任务技能，改进器自身可以始终不变；更强的递归主张还需要证明新系统改变了以后如何提出和筛选改进。若评价规则也一起改变，分数又可能失去可比性。因此，应先画清任务执行、改进生成和独立验收之间的边界，再问哪些部分真的递归、哪些仍由外部固定。

> 主线位置：第 3 级及其安全边界。接 STOP、Gödel Agent、HyperAgents 和 AI 研究 agent 的递归实验。

**[MetaSkill-Evolve](https://arxiv.org/abs/2607.05297)**让任务技能在快时间尺度更新，让影响分析、检索、分配、提议与演化过程的元技能在较慢尺度更新，并采用冻结的共享基础模型。它为区分“改任务技能”与“改改进过程”提供了具体对象，多轮搜索本身还算不上递归。作者报告了留出任务上的对照收益，但这仍是指定流程和预算内的结果，开放式提升能否一直持续还没有证据。先读[综述章的 RSI 入口](00_surveys.md)，再检查这类方法的更新与验收路径，会更容易分清主张的强弱。

**[Dream-RSI: Recursive Self-Improvement through Evolving Worlds](https://arxiv.org/abs/2609.14858)**（`2609.14858`） 把发现历史组织成回放模拟器，在已经探索过的搜索空间中低成本评估新的探索策略，底层编码智能体保持不变。它降低延迟反馈带来的试验负担，但回放能评价的范围受历史覆盖限制；对未见区域的真正探索仍需要新的环境交互。

**[Recursive self-improvement of AI research agents](https://arxiv.org/abs/2609.26457)**（`2609.26457`） 让研究智能体修改自己的代码，用隐藏评估选择版本，再由新版本参与下一轮修改。作者报告一次持续多天的自主运行及对留出研究基准的迁移。这比只改固定外壳更接近代码级递归循环，但有限轮次仍不足以推出改进速度会长期增长；应检查继承关系、每轮预算和无递归搜索对照。

**[MetaRSI / RSI2: A Meta-Recursive Self-Improving System for Recursive Self-Improving Systems Themselves](https://arxiv.org/abs/2609.06396)**（`2609.06396`） 将数据、执行系统和模型更新组织为可组合操作，希望面向更开放的科学与工程任务。它提供的是理解修改对象如何组合的入口；跨越可机器检查任务之后，评价可能需要论证、实验或复现，不能把验证器原封不动沿用。

**[SafeEvolve: Harness-Policy Co-Evolution from Agent Experience for Safety Alignment](https://arxiv.org/abs/2609.02786)**（`2609.02786`） 将安全经验用于有边界、可审计、可回滚的执行系统修改，并结合监督与强化学习更新策略。这把改进目标从任务成绩扩展到多步执行安全，但安全集的覆盖与新能力的副作用仍需单独检查。**[LLM Agents Can Easily Tamper With Their Own Traces](https://arxiv.org/abs/2609.30266)**（`2609.30266`） 则研究执行日志完整性，报告部分本地智能体基础设施允许日志被修改或删除。这里最关键的启示是，改进者不应同时控制自己用来证明改进的全部证据。

这组工作应放在同一条边界上理解：可以允许系统提出广泛修改，但最终评估、权限和审计应有独立控制。运行时可以将修改限制在副本中，保留差异并在隔离环境测试，同时由独立组件管理评分器和审计记录。这样的分工让系统能够探索较大的修改空间，又保留回滚与外部验收的条件。

## 四、方法对照表

前述路线覆盖技能的形成、使用与维护，也涉及模型和改进机制的更新。它们可能出现在同一系统中，但改动对象与成本不同，需要分别检查经验是否被正确提炼、调用和迁移。

| 问题 | 方法选择 | 主要代价 | 证据不足时要追问 |
|---|---|---|---|
| 缺少操作知识 | 人写技能、仓库提炼、经历抽象 | 人工维护、版本与环境核查 | 文档可用是否等于任务有效 |
| 库大且任务简单 | 分层展开、表示路由、范围估计 | 路由训练或错误拒绝 | 是否比简单检索与不用技能更好 |
| 技能膨胀与相互冲突 | 回放门控、程序家族、图结构、删除审计 | 重跑旧任务和维护复杂度 | 罕见能力会不会被合并丢失 |
| 外部提示依赖重 | 教师差异补丁、技能使用训练、参数内化 | 教师、合成环境和训练费用 | 去掉技能提示后是否仍有收益 |
| 执行系统难设计 | 模块演化、候选档案、历史重新校准 | 多轮搜索与验证 | 跨任务迁移和总搜索成本 |
| 改进真假难分 | 等预算基线、逐任务退化、隐藏测试 | 可信评测基础设施 | 是否重复使用测试反馈选版本 |
| 模型与系统失配 | 交替优化、在策略局部纠正 | 数据非平稳、训练与搜索耦合 | 多轮稳定性和教师兼容性 |
| 递归闭环难控制 | 有限修改、独立日志、安全联合优化 | 权限隔离与恢复成本 | 谁掌握评分器，能否回滚 |

## 五、开放问题与研究机会

技能积累与系统自改进共享一个目标：让过去的尝试减少未来的重复试错。但发现一个有用程序、维护一组可组合技能，以及改进产生这些程序的机制，是不同层次的问题。研究需要沿这三个层次建立证据，并让评价标准独立于被优化的系统。

**1. 如何主动发现值得沉淀的技能，并识别其迁移边界？**

成功轨迹混合了偶然步骤与可迁移结构，并非每次成功都值得保存为技能。可以研究候选发现、抽象和接纳机制，用未来任务收益、调用成本与覆盖缺口决定保留内容。技能还应表达正例、反例和不确定范围：外观相似的任务可能遵循不同制度，格式不同的任务也可能共享处理规则。评价需要改变任务表面与执行条件，检验系统能否根据证据识别边界，而不只依靠语义相似度选择程序。

**2. 如何维护能够组合和迁移的技能库，而不牺牲必要多样性？**

库规模增长后，依赖冲突、版本变化和局部修改会影响组合执行。研究机会是让技能具有可检查的前后条件、可维护依赖与失效检测，支持自主合并、替换和停用。只保留当前最优技能可能丢掉应对罕见任务的办法，全部保留又会增加路由成本。因此需要在环境变化和新任务组合中追踪覆盖、退化与恢复，并检验被删技能的功能能否由其他组合替代。

**3. 如何让改进机制自身演化，并辨认真正的递归收益？**

提示、工具和工作流可以被自动修改，但多轮分数上涨也可能只是更多搜索的结果。可以在同等总预算下比较固定改进者、仅保存历史的改进者，以及继承新版本改进机制的系统，观察有效修改率、发现时间和留出任务表现。关键是新机制是否更善于产生下一轮有效改动，而不只是当前执行器得分更高；改进计算、旧能力保持和回滚成本也应纳入比较。

**4. 如何学习新的评价方式，又不让系统自行放宽成功标准？**

开放任务可能需要新准则，但准则变化会破坏跨版本可比性。研究机会是区分评价器的提出、验证与批准，允许系统发现现有指标遗漏的目标，同时保留独立检查和人工纠正渠道。实验应将开发、选择和最终测试隔离，主动加入目标偏移与评价器漏洞，检验系统能否发现这些问题，并防止它借修改评分规则制造表面进步。
