# 06｜评测：更长的任务链，更广的场景与能力

[首页](../README.md) · [专题索引](../README.md#topics) · [文献目录](../catalog/06_evaluation.md)

## 一、方向背景：为什么 Agent 需要更长、更宽的评测

智能体的应用范围从单次问答扩展到软件开发、网页操作、企业业务、科研与物理环境，任务也从一个明确步骤延伸为持续交互。系统不仅需要在某一时刻给出正确答案，还要发现缺失信息、协调多个工具、维护中间状态，并在环境变化或执行失败后继续推进。评测因此需要同时回答两个问题：能力能够沿多长的任务链保持，以及能够覆盖哪些场景和能力组合。

这两条方向可以概括为**更长**与**更宽**。更长并不只是增加 token、运行时间或工具调用次数，而是让前后步骤产生更强依赖，让目标、约束和工作状态跨越更多阶段。更宽也不只是增加题目数量，而是覆盖不同任务环境、知识领域、输入模态、动作接口与验收标准。一个系统可以擅长持续编码，却不擅长与用户澄清需求；也可以在许多短任务上得分较高，却无法稳定完成任何一个长流程。

复杂度是连接两条方向的关键。同样长度的任务，若需要在多个应用之间传递状态、同时满足多项约束并处理不完整反馈，难度可能完全不同。因此，需要把长程执行、场景覆盖和具体能力组合一起描述，而不是只给系统贴上“通用”或“长任务”的标签。

本章先用经典工作说明这两条方向怎样形成，再沿任务长度与复杂度展开，并按软件、数字工作、GUI、多模态、科研和具身等场景比较能力需求。评分器、验证器、失败诊断与校准属于支撑这些评测的方法，放在后文讨论，不与应用场景并列为整章的分类主轴。理解一个基准，首先要知道它让系统完成什么、需要哪些能力，再看它怎样评分。

## 二、发展脉络：从局部能力，到跨场景的持续工作

理解 Agent 评测的演进，可以先问两个问题：**一次测试要求系统负责到哪一步，又把系统放进了多大的世界？** 只要求回答一道题时，模型不必管理后续行动；要求完成一个实际任务时，检索、选择、执行和验证就需要连起来。与此同时，同一种能力在网页、代码仓库、桌面和业务服务中，会遇到不同的输入、操作和约束。前一个变化推动任务变长，后一个变化推动覆盖变宽。

这两条线并不是一组基准依次取代另一组。局部能力测试仍然有助于定位短板，交互环境则检验这些能力能否共同工作。下面按评测对象的扩展组织经典工作，而不是把发布时间先后当作单一的进步顺序。

### 2.1 起点：先知道模型能处理哪些知识与局部任务

在评价持续行动以前，需要先了解模型是否具备基本的理解与求解能力。[MMLU](https://arxiv.org/abs/2009.03300)把多种学科的知识与推理放入同一测试，体现了较早的“更宽”：不再只看一个领域，但大部分任务仍以独立问题为单位。它可以描述知识覆盖，却不要求系统在环境中执行后续操作。

代码领域的 [HumanEval](https://arxiv.org/abs/2107.03374)则根据说明生成函数，再用测试检查功能是否正确。它提供了比文字相似更贴近程序用途的验收方式，但任务上下文和交付范围仍然较局部：系统不必自行定位真实仓库中的缺陷，也不必协调多文件改动。由此可以区分两件事：模型会解多少类问题，以及模型能否把这些能力接成完整工作。

### 2.2 引入环境：行动必须根据反馈连续推进

为了检验后一种能力，基准需要让行动改变后续条件。Agent 不再一次性给出答案，而是观察环境、选择动作、接收反馈，再决定下一步。[ALFWorld](https://arxiv.org/abs/2010.03768)连接文本中的抽象任务与具身环境中的执行，使语言理解、规划、导航和视觉感知能够围绕同一目标被研究。任务的关键不只是说出动作名称，而是让一系列动作满足目标所要求的状态。

[WebShop](https://arxiv.org/abs/2207.01206)将这种连续决策放到模拟购物网站：根据需求搜索、阅读商品信息、比较属性，再选择合适商品。这里增加的难度不是对话轮数本身，而是前面获取的信息必须支持后面的选择。它把研究范围从受控的操作任务延伸到带有真实商品描述和组合需求的网页场景，同时仍保留可控的环境与反馈。

这两项工作分别说明更长与更宽如何相互作用：执行链增长以后，需要维持中间状态；换到新的环境以后，又需要理解新的对象、动作和约束。但单一模拟环境仍然不能代表跨领域的 Agent 能力。

### 2.3 扩展场景：通用性需要不同环境共同检验

跨环境评测首先要避免把某个任务接口当成通用能力的全部。[AgentBench](https://arxiv.org/abs/2308.03688)将操作系统、数据库、网页等不同交互环境放入同一评测框架，使模型在不同决策条件下的差异能够被观察。它扩展的是环境与任务类型的覆盖，而不是简单增加同一种题的数量。

与这种横向覆盖并行，[WebArena](https://arxiv.org/abs/2307.13854)在网页方向做得更深：通过功能完整、可复现的网站承载任务，要求 Agent 真正改变或查找外部对象。相较于只研究一次搜索或选择，系统需要维护登录状态、跨页面理解信息并完成业务目标。这说明“更宽”不只有增加领域标签，也包括在一个领域内纳入更完整的真实工作结构。

[GAIA](https://arxiv.org/abs/2311.12983)提供另一种组合方式：最终问题看起来可能很简短，求解却需要推理、网页浏览、多模态理解和工具使用。它说明，题面长度与任务复杂度并不等价。不过，最终答案型任务与持续改变环境状态的任务仍有区别；二者分别检验能力组合的不同部分，不能仅凭总分视为同一种长程能力。

### 2.4 进入实际工作：代码、桌面与业务约束同时增加跨度和宽度

当交付目标转向真实工作产物，局部正确还不够。[SWE-bench](https://arxiv.org/abs/2310.06770)以真实软件仓库中的问题为起点，要求理解已有代码、定位问题并提交可验证的修改。与 HumanEval 的局部函数生成相比，增加的不只是代码量，还有寻找相关上下文、遵守既有接口和验证改动影响等前后依赖。但不同实例的跨度并不相同，不能把仓库级任务都视为同样长。

桌面方向的 [OSWorld](https://arxiv.org/abs/2404.07972)把环境扩大到真实操作系统中的网页与桌面应用，并包含跨应用工作流。系统需要把视觉定位、软件操作和文件状态连接起来：在一个窗口里判断正确，并不代表跨应用交付已经完成。这同时增加了环境覆盖与行动链中的协调要求。

业务方向的 [τ-bench](https://arxiv.org/abs/2406.12045)进一步加入动态用户交互、领域 API 与政策规则，并检查对话结束后的数据库状态。它使“完成任务”不仅取决于工具是否调用成功，还取决于是否澄清了需求、遵守了规则并留下正确结果。用户在过程中提供信息，也使预先写死的动作序列难以覆盖全部情形。

这些基准不是在争夺一个唯一的通用榜单，而是在补齐不同能力组合：软件工程强调代码与测试依赖，桌面强调感知与操作，业务服务强调交流、规则和状态。每个领域继续向更完整的工作流程扩展，才构成更长、更宽的评测地图。

### 2.5 延续到长程任务：不仅执行更多，还要维持与恢复

上述经典基准逐步把知识、动作和环境反馈接到真实工作中，但“能够完成多步任务”仍不等于长期可靠。依赖链继续延长后，系统需要保存进度、处理工具失败，并在条件变化或中断后恢复；领域继续扩大后，同一机制又要适应不同的时间要求与验收标准。这正是前沿评测沿“更长”和“更宽”继续展开的起点。

它们延续的不是“题目越难越好”这条线，而是把原先未被测量的责任放进任务：系统是否持续知道目标，是否发现世界已经变化，是否能在失败后继续，以及最终结果是否仍满足约束。下面先按依赖、变化与积累讨论如何变得更长，再按领域和能力组合讨论如何变得更宽。

## 三、前沿研究方向：更长与更宽

前沿评测可以沿两个相交的方向展开。更长关注任务依赖、环境变化和跨任务积累，解释能力怎样在持续执行中失效；更宽关注软件、业务、GUI、科研与具身等场景，解释不同环境要求哪些能力共同工作。下面先展开长度与复杂度，再比较场景和能力组合。同一基准可以同时推进两条方向，分类的目的不是给它唯一贴标签，而是看清它补上了能力地图中的哪一部分。

### 3.1 更长：从完成一个步骤，到维持整个任务过程

长度的扩展首先改变任务内部的关系：阶段之间有依赖，执行期间的条件可能变化，前一次任务的经验还可能影响下一次行动。下面据此区分多阶段协调、动态状态维护与跨任务积累。三者都需要持续性，但不能只用运行时长衡量，也不一定由同一种记忆或规划方法解决。

#### 3.1.1 多阶段依赖：测量完整工作，而不是把短题串起来

长程任务中的前一步会改变后一步的条件：前期搜集的信息影响后续决策，中间产物成为下游输入，早期遗漏也可能直到交付时才暴露。真正增加难度的是这些依赖，而不只是调用数量。把互不相关的小题连续执行，可以增加总时长，却未必检验计划、状态管理或跨阶段协调。

[Long-Horizon-Terminal-Bench](https://arxiv.org/abs/2607.08964)通过细粒度子目标观察长任务进度，使评测能够区分完全没有推进、完成部分阶段与最终交付。这类分解适合研究瓶颈发生在哪里，但子目标得分不能直接替代完整成功率：如果最后缺少关键产物，前面的大量正确步骤仍可能没有形成可使用结果。[DeepSWE](https://arxiv.org/abs/2607.07946)把这种问题放到原创长程工程任务中，后文的软件场景会进一步比较其能力要求。

描述任务长度时，至少要说明最长依赖链、需要维持的状态、可并行与必须顺序执行的步骤，以及失败后是否允许重来。大量廉价调用与少量不可逆操作不能简单按同一长度尺度排序；跨越多个文件或应用，也需要说明它们之间是否存在真实的信息依赖。

因此，长任务评价应同时报告阶段进度与端到端完成情况。阶段指标帮助定位能力短板，完整交付率体现这些能力能否共同工作。两者之间的落差，往往比一个总分更能说明系统距离稳定完成长流程还有多远。

#### 3.1.2 动态环境与持续约束：任务进行时，世界也在变化

静态任务可以假设初始条件一直有效，持续运行则必须处理时间推进、外部状态变化和新的约束。系统需要知道何时重新观察、何时修改计划，以及哪些承诺在后续阶段仍然有效。这把评测从一次计划的执行，推进到对状态变化的持续响应。

**[VibeLifeBench: Can Your Life Agent Be Proactive and Persistent in a Living World?](https://arxiv.org/abs/2608.10875)，`2608.10875`**把时间推进、静默变化与长期承诺纳入任务，模型必须决定何时重新观察、行动、询问或保持沉默。其核心是环境会在没有新提示时发生变化，而不只是一次交互中完成更多步骤。模拟时间线仍是预设结构，不能据此声称覆盖现实生活全部突发事件。

长上下文和长期遵循也是两回事。[HANDBOOK.md](https://arxiv.org/abs/2607.25398)把政策手册作为持续约束，关注系统执行到后续阶段时是否仍避免禁止行为。与之相邻，[Harness-IF](https://arxiv.org/abs/2608.11727)通过撤除规则等对照区分真正遵循指令与默认行为恰好一致。前者强调约束能否跨过程保持，后者帮助判断观察到的行为究竟是不是指令产生的。

中断与恢复同样属于长程能力。评测需要明确恢复时保留什么：完整对话、摘要、文件、工作区状态，还是仅有目标。不同恢复条件对应不同记忆要求。如果每次重启都重新提供完整答案线索，就不能据此证明系统具备跨上下文维持任务的能力。

重复可靠性还应与单次长任务区分。允许多次尝试、只要求其中一次成功，测量的是系统利用重试找到解法的能力；要求多次运行都成功，测量的则是表现是否稳定。前一种标准通常会因增加尝试机会而更容易满足，后一种标准却会暴露偶发失败。实际运行还可能反复遇到相同错误，因此报告需要说明每次是否重置环境、是否共享经验，以及重试能否获得新信息。任务变长与多次运行更稳定是不同要求，不能互相替代。

#### 3.1.3 跨任务积累：从接着做，到在下一次做得更好

同一任务跨会话继续，主要检验状态延续；连续任务中的表现变化，则进一步涉及经验迁移、偏好适配和技能维护。评测如果只观察后一项任务是否成功，很难分辨收益来自可复用方法、剩余上下文，还是先前已经见过类似答案。

[ContextWeave](https://arxiv.org/abs/2608.04830)研究工作经验能否帮助后续流程及个体偏好适配，把记忆放回任务表现中评价。[ContinualSkillBench](https://arxiv.org/abs/2608.03874)进一步比较连续上下文与显式技能维护，追问顺序执行的收益是否来自真正可复用的抽象。两者连接的是“过去的任务如何影响未来”，而不是简单测量记忆库能够保存多少内容。

为了分离技能自身的贡献，[Evaluating Skills, Not Just Agents](https://arxiv.org/abs/2608.20614)固定模型、工作区和评分器，配对比较有无技能的运行结果。技能文档写得规范与实际调用产生增益是不同证据；评价还应检查新技能是否损害原有能力，以及环境变化后能否停止使用失效的方法。

更大的更新对象是整个执行框架。[Rethinking the Evaluation of Harness Evolution for Agents](https://arxiv.org/abs/2607.12227)在反馈和推理预算可比的条件下，将框架演化与任务级搜索对照，并用留出任务检查泛化。它提醒持续改进评测必须把候选选择与最终测试分开：在同一批反馈上不断选优，不足以证明系统在新的任务流中也会持续进步。

### 3.2 更宽：不同场景要求不同的能力组合

场景的扩展会同时改变观察、动作与成功条件。软件任务需要理解仓库和测试，业务任务需要遵守规则与交流，GUI、科研和物理环境又引入不同的感知与验证要求。下面按这些任务结构比较近期基准，再讨论跨领域能力怎样组合，避免把覆盖宽度简单等同于领域名称的数量。

#### 3.2.1 软件工程与终端：从局部修复到跨文件、跨阶段开发

软件环境同时提供代码、文档、命令行和执行反馈，适合研究长程工具使用。但软件任务并不是同一种能力的不同题目：按明确 issue 修复、主动发现问题、大规模重构和复现应用功能，对需求理解、代码定位、依赖管理与验证的要求各不相同。

[SWE-bench](https://arxiv.org/abs/2310.06770)连接真实软件问题与执行测试，为仓库级任务提供了重要入口。沿着任务范围扩展，[DeepSWE](https://arxiv.org/abs/2607.07946)使用原创工程任务和功能验证器，减少对已有公开补丁与原测试的直接依赖；[SWE-Bench ProMax](https://arxiv.org/abs/2608.09802)关注多语言大规模重构与跨文件协调。前者强调更完整且独立构造的工程任务，后者扩展需要同时维持的代码关系，不能只根据运行步数判断谁更接近实际开发。

任务说明是否充分，也会改变被测能力。[Active-SWE](https://arxiv.org/abs/2608.04682)减少详细 issue 引导，让系统主动定位并修复多处问题，从而把发现问题与按说明解决问题分开。[ProgramDistill](https://arxiv.org/abs/2609.18805)则从参考应用的可观察行为出发要求复现功能，增加了规格推断的要求。两者都比“给定位置后生成补丁”覆盖更宽，但一个扩展问题发现，一个扩展行为理解，并非同一难度轴。

重构与迁移又提出新的验收要求。[SWE Refactor Bench](https://arxiv.org/abs/2608.23564)先确认所要求的迁移实际发生，再检查行为保持，避免仅复制旧实现也能通过测试。[SWE-Bench Pro Verified](https://arxiv.org/abs/2609.08149)则修正题意、测试范围和评价信息泄漏之间的不一致。任务更复杂与验收更可靠是两个独立改进，需要分别说明。

[SWE-Proof](https://arxiv.org/abs/2609.21190)把机器检查证明引入真实问题修复，检查给定规格下的正确性。这扩展了可检验的性质，却仍依赖规格是否忠实：证明代码满足命题，并不等于命题完整表达需求。软件评测因此需要一张能力画像，区分需求理解、问题发现、跨文件修改、行为保持和最终交付，而不是仅比较测试通过率。

#### 3.2.2 网页与企业工作：检索、交互、工具状态和业务约束

数字工作往往跨越网页、文件和业务系统，既需要获取信息，也需要在明确权限下改变状态。这里的困难不只来自工具数量，还来自目标可能不充分、用户会补充要求，以及多个系统的状态必须一致。网页导航、引用核查、业务操作和对话协作应分别作为能力维度，再观察它们如何组成完整流程。

[WebArena](https://arxiv.org/abs/2307.13854)提供可控网站中的任务环境，使导航、信息定位和操作结果能够在同一流程中检查。[τ-bench](https://arxiv.org/abs/2406.12045)结合用户交互、工具与政策规则，强调完成业务目标时的可靠性。两者覆盖的对象有联系，但网页操作成功并不能推出系统擅长澄清需求或遵守业务规则，评价必须保留各自的环境条件。

**[One Success Isn't Reliability: Thinkingbox](https://arxiv.org/abs/2608.19741)，`2608.19741`**针对有持久状态的业务任务，检查最终后台状态以及缺失、错误或多余影响。它通过重复运行检查一次成功能否稳定重现，并区分工具调用合规、正常结束与最终业务状态正确，避免把偶然完成当作可靠执行。其沙箱覆盖特定业务结构，不能直接当生产事故率；真实并发、服务降级与权限变化仍要另测。

[Tencent WorkBuddy Bench](https://arxiv.org/abs/2607.20911)按工作域使用相应验收，体现数字工作评价向多领域产物扩展。其价值不在于把所有任务都交给同一个裁判，而在于承认不同工作有不同成功条件。若把所有子域分数直接平均，可能掩盖系统在某一类关键工作中完全无法交付的问题。

信息型任务还需要区分检索与论证。[Is this Citation on Point?](https://arxiv.org/abs/2608.12571)分别检查文献存在、主题关联与具体证据是否支持命题。能够搜索到真实文献，不表示报告中的引用成立。这一能力与修改业务状态不同，却常在同一个工作流中出现，适合通过分项测量判断失败来自检索、证据理解还是最终表达。

#### 3.2.3 GUI 与多模态：从识别内容到定位、操作与时序理解

多模态场景扩展了系统可观察的信息类型，也引入空间、时间和跨模态对应关系。图片描述、图表编辑、视频问答与桌面操作不是可以相互替代的任务。评测需要分清系统是否看到了必要证据、是否理解其关系，以及是否能够根据这些信息正确行动。

**[PerceptionBench: Evaluating Atomic Visual Perception in Multimodal Large Language Models](https://arxiv.org/abs/2607.24957)，`2607.24957`**从已有错误中构建原子感知能力分类，用短而明确的问题减少推理与知识干扰。它解决综合总分无法定位感知短板的问题，却不意味着原子感知成绩可以预测完整GUI任务：行动控制、记忆和状态变化仍然存在。

从基础感知进入计算机操作后，[OSReward](https://arxiv.org/abs/2607.28609)利用人工标注的操作轨迹检验视觉裁判，关注失败被误判为成功的问题。它检验的是识别执行结果的能力，不是行动模型本身的操作能力。[ChartSync](https://arxiv.org/abs/2607.10301)则用确定性渲染检查图表中文字与几何关系的联动修改：局部文本正确，并不能保证整张图的数据关系仍然成立。两者分别补充动作结果判断和结构化视觉编辑。

视频增加了时间维度。[Evidence-Backed Video Question Answering](https://arxiv.org/abs/2607.11862)同时要求答案与时空证据，区分依靠常识答对和真正定位支持片段。评价长视频时，还需要说明信息跨度、事件依赖和证据是否跨片段；输入更长不必然意味着答案需要更长程的理解。

同样的视觉表示也可能服务异常判断或多题决策。[A VLM Answer Is Not an Anomaly Score](https://arxiv.org/abs/2608.21244)讨论离散回答与概率加权评分对排序的影响；[Visual Jev](https://arxiv.org/abs/2609.25845)通过共享图像前缀处理多个选择问题。这里应把异常区分能力、判断准确性和推理效率分别测量，避免由一种评分或缓存机制推断整个多模态系统更强。

#### 3.2.4 科研与专业分析：从知识题到探索、实验和研究产物

专业场景之所以需要单独评测，是因为知识正确性、工具操作与领域有效性缺一不可。回答一道物理题、分析一份因果数据和完成一个开放研究请求，要求不同的能力链。领域知识测试仍有价值，但不能代表系统能够选择问题、设计实验并交付可信的新结果。

[How Good Are Frontier Models at Physics?](https://arxiv.org/abs/2609.13009)通过专家重审题意、参考解和模型回答，区分模型错误与评分错误。它帮助理解封闭专业题的能力边界，不能直接外推为开放科研能力。进入数据分析过程后，[CausalDS](https://arxiv.org/abs/2607.08093)用结构因果模型构造数据与场景，将可控真值连接到实际分析工作流，使评价能够观察知识如何被用于分析，而不只是最终选择了哪个答案。

开放科研的目标往往没有唯一标准答案。[K-Bench](https://arxiv.org/abs/2608.21601)关注真实、欠明确的科学请求，需要同时考察交付内容与夸大陈述。[FrontierChallenge](https://arxiv.org/abs/2608.24979)按科学产物包观察完整工作流，区分部分进度与全部交付。这两类任务拓宽了领域与成果形式，也让“更长”具体化为文献、代码、实验和结论之间的依赖。

研究过程中的不同能力还可以进一步拆开。[Ideas Have Genomes](https://arxiv.org/abs/2607.08758)通过带类型和证据的思想对象研究谱系推理及生成，让新想法的来路可检查；谱系合理仍不等于科学结论成立。[Jev for Scientific Decisions](https://arxiv.org/abs/2609.24965)将语义关系选择、程序计算和最终标签分别检查，揭示最终判断可能掩盖中间数量错误。两者关注的是研究链上的不同能力，不宜混成统一的“科研推理分”。

完整工作流失败后，[How Do Agents Fail on AutoResearch](https://arxiv.org/abs/2608.14905)结合轨迹与中间产物归纳错误类型，帮助识别问题发生在执行、证据处理还是研究判断。与此同时，[Can LLMs Write Reliable Rubrics?](https://arxiv.org/abs/2607.12835)提醒实验复现的自动评分清单本身也需要评价。开放领域越宽，越需要领域特定的验收，而不是用更长的通用评分表替代专业标准。

#### 3.2.5 物理环境与具身任务：预测、探索和闭环控制

物理场景把动作后果、时间延迟和安全约束加入评价，改变了任务成功的含义。视觉上合理的预测不一定符合动力学，正确的高层指令也不一定产生稳定控制。评测既要覆盖感知和规划，还要检查实际状态变化、接触过程、失败恢复与停止条件。

[GAUGE](https://arxiv.org/abs/2608.05948)通过真实测量轨迹与物理量比较模拟器和视频世界模型，强调视觉质量与动力学正确性不同。它属于预测与环境建模的能力评价，不能直接当作机器人控制成功率。[No Free Checker](https://arxiv.org/abs/2609.09250)整理机器人策略验证中的人类、规则、形式方法和学习信号，则帮助判断不同反馈能够排除哪些执行风险。

环境学习提供另一个可分离的能力维度。[ExplorationBench](https://arxiv.org/abs/2609.30199)使用与常识不同但可验证的合成规则，让系统通过试验学习环境。它并非真实机器人基准，其意义在于减少预训练记忆捷径，观察探索与规则推断。把它与物理测量研究放在一起，可以区分“知道已有规律”“从反馈发现新规律”和“据此可靠行动”三个层次，而不是把合成探索成绩直接外推到物理部署。

具身长任务还需要报告任务链、控制频率、观测延迟、人工介入与恢复条件。一次末端动作成功与多阶段操控完成不同，仿真结果与真实执行也不能混用。更完整的具身能力路线见[具身智能](11_embodied.md)，世界预测与规划的关系见[世界模型](10_world_models.md)。

#### 3.2.6 跨领域任务组合：覆盖更宽，也要看能力能否一起工作

扩大评测范围有两种方式：把多个领域的独立任务放进同一套测试，或让同一任务跨越多个工具、模态和应用。前者衡量覆盖面，后者检验组合能力。一个系统分别会检索、读图与写代码，不代表能够在同一流程中准确传递证据、维护状态并交付完整产物。

[AgentBench](https://arxiv.org/abs/2308.03688)将语言模型置于不同交互环境，提供跨场景观察的入口。[UniClawBench](https://arxiv.org/abs/2607.08768)沿技能使用、探索、长上下文、多模态与跨平台协调组织能力，并通过运行中检查点观察过程。阅读这类集合时，应区分每项能力是否被独立覆盖，以及哪些任务真正要求多种能力共同发挥作用。

覆盖扩大之后，可重复的评测基础设施变得重要。[AgentCompass](https://arxiv.org/abs/2607.13705)分离基准、执行框架与环境，帮助在相同系统接口下组织任务与诊断。[Harbor Adapters and Harbor-Index](https://arxiv.org/abs/2609.04298)通过适配器和等价性检查连接不同基准。统一运行方式有助于扩展场景，但不会自动统一任务含义，移植前后的评分和权限仍需核对。

真实部署还能补充固定基准遗漏的行为。[TraceDance](https://arxiv.org/abs/2609.33295)从部署轨迹构造特定决策点的续写测试，使评测更贴近实际失败位置；缺少完整环境回放时，它测到的仍是局部决策，而不是最终长程结果。将这种局部测试与完整任务评测结合，比直接把轨迹样本量当作覆盖宽度更有解释力。

## 四、把长度、场景与能力放进同一张评测画像

长度与场景不是两个互斥分类。软件、业务和科研都可以有短任务与长任务，同一种记忆能力也会在不同环境中呈现不同失效方式。阅读或设计基准时，可以用下面的坐标描述实际覆盖，而不必先寻找一个包办所有能力的总榜单。

| 维度 | 应描述的条件 | 能帮助区分什么 |
| --- | --- | --- |
| 任务跨度 | 依赖链、阶段数、上下文切换、持续时间 | 真正的长程协调与单纯增加运行长度 |
| 状态变化 | 外部更新、中断、恢复、目标与政策变化 | 静态执行与动态适应 |
| 应用场景 | 软件、网页业务、GUI、科研、物理环境 | 能力覆盖的领域与环境边界 |
| 具体能力 | 感知、检索、规划、工具、记忆、探索、验证 | 局部短板与系统整体失败 |
| 组合复杂度 | 工具依赖、跨应用交接、约束冲突 | 独立能力集合与协同完成任务 |
| 迁移与积累 | 未见任务、环境变化、技能更新与遗忘 | 已有题型适应与可持续增长 |

这张画像首先用于确认比较对象。若一个基准只提供短期视觉问答，另一个要求在动态界面中完成业务流程，不能因为都涉及图像就直接对比分数。若两个软件基准使用不同终态验证与任务依赖结构，也需要先说明差异，再讨论模型或系统的进步。

[What AI Benchmarks Actually Measure](https://arxiv.org/abs/2609.08812)从测量效度出发，追问声称测量同一能力的任务是否真的提供相近证据。[Benchmarking the Benchmarks](https://arxiv.org/abs/2608.06329)则从一致性、复杂度和政策覆盖检查对话基准。这些研究适合用来审视能力画像是否可靠，而不应取代对实际任务场景的梳理。更长、更宽是覆盖方向，不是只要增加难度和领域标签就自然成立的质量保证。

## 五、支撑方法：怎样让更复杂的评测可解释、可复现

评测对象变长、变宽以后，测量本身也会遇到新的困难：终态分数不容易解释长轨迹中的失败，开放产物需要不同的验收方式，重复运行和裁判调用又增加成本。下面按诊断、评分、不确定性处理和预算控制展开。它们共同决定复杂任务的得分能否被解释，以及不同系统的结果能否在同一条件下比较。

### 5.1 长轨迹诊断：失败发生在哪里，能否被恢复

长任务的终态能够说明是否完成，却未必解释为什么失败。过程分析需要区分错误产生、传播和恢复，防止把最后报错的组件当作根因。[STRACE](https://arxiv.org/abs/2607.07702)从批量轨迹筛选代表失败，并通过文本依赖结构定位相关步骤；[TRAJDEBUG](https://arxiv.org/abs/2608.06346)跟踪错误生命周期，避免把已经恢复的早期错误继续视为最终失败来源。

[Failure as a Process](https://arxiv.org/abs/2607.09510)补充对 CLI 编码轨迹的过程标注，帮助观察隐藏的早期认知偏差；[Tracing Agentic Failure from the Flow of Success](https://arxiv.org/abs/2607.12747)从成功轨迹学习模式，再把偏离当作诊断线索。前者依赖错误标注，后者提供异常检测，但异常与原因都需要进一步检验。[Relational Uncertainty Propagation](https://arxiv.org/abs/2608.16002)沿推理、工具与观察关系传播不确定性，则说明局部高置信度不能排除远处依赖带来的错误。

这些方法支撑的是对长程能力的解释。文本依赖不自动构成因果证据，自动诊断也不等于修复已经有效。条件允许时，应通过重放或局部替换检验候选原因；对于不可恢复环境，则明确归因只能达到何种证据层级。

### 5.2 开放产物评分：不同领域不能只共用一套通用准则

程序测试、状态比较和领域专家能够验证不同产物，开放文本或多模态输出有时需要模型裁判辅助。[MT-Bench 与 Chatbot Arena 相关研究](https://arxiv.org/abs/2306.05685)讨论语言模型裁判的能力与偏差，提醒顺序、表达和长度都可能影响评价。因此裁判应根据任务目标设计，而不是让评分方式反过来决定哪些场景值得测。

[LLM-as-a-Verifier](https://arxiv.org/abs/2607.05391)使用评分 token 的概率分布形成连续分数，减少离散档位造成的信息损失；[GAMUT](https://arxiv.org/abs/2607.19322)将丰富准则编译为二元检查，关注评价结构与执行的一致性。前者改变分数表示，后者组织评分条件，都不能替代对领域事实和真正交付要求的理解。

[Mitigating Scoring Bias in LLM-as-a-Judge via Random Number Generation](https://arxiv.org/abs/2608.05726)进一步校正评分数字的先验偏好。这种校正针对数值偏置，不意味着语义判断已经正确。开放场景越多，越应保留分领域的人类或程序检查，特别审计高分但缺少实际产物、引用不支持结论和过程违反约束的情况。

### 5.3 不确定性与升级：把复核预算分给难判样本

更长、更宽的任务使全面人工检查难以扩展，选择性验证尝试把较贵的检查集中到有争议的样本。[选择性分类](https://arxiv.org/abs/1705.08500)与[模型校准](https://arxiv.org/abs/1706.04599)提供相应基础：置信度需要和实际错误率对应，自动处理范围与剩余风险要一起报告。

[JEV-as-a-Judge](https://arxiv.org/abs/2609.26550)将高置信度裁决直接接受，其余交给后备裁判；[JEV vs. LLMs as Rubric Judges](https://arxiv.org/abs/2609.29769)则在其他设置中观察到廉价决策器和语言模型裁判具有相近错误。二者共同提示，路由有效既要求识别不确定性，也要求后备者能够纠正被交接的错误。因此，级联评价应同时测量总成本、升级比例和升级后的错误变化，而不能只记录少调用了多少次昂贵裁判。

类似问题出现在 [REFLEX](https://arxiv.org/abs/2609.26532) 的选择性控制、[ORACLE](https://arxiv.org/abs/2607.22465) 的验证器调度与 [LLMRouter](https://arxiv.org/abs/2608.06867) 的模型路由中。它们分别改变任务由谁处理、验证何时发生及资源如何分配，比较时必须同时报告质量与成本。自动接受区仍需随机复查，不能只审计已经被路由器挑出的难题。

### 5.4 预算与重复运行：评测更大之后，如何保持可比

[EarlyEval](https://arxiv.org/abs/2609.02783)使用中间轨迹预测结果并提前终止，可以降低开发阶段的评测成本。但早停预测不是实际完成，新系统若更擅长晚期恢复，旧预测器可能误判。因此，节约方法应保留完整运行对照，并检查它是否改变能力排名或失败类型分布。

[Test-Time Scaling in Reasoning LLMs](https://arxiv.org/abs/2608.04001)区分单轨迹延长、候选采样和前缀搜索，说明相同 token 预算也可能对应不同探索条件。长程评测还包含环境运行、工具等待、状态保存与人工介入成本，不能只统计生成长度。多领域任务的预算比较尤其需要明确单位，避免把某类环境廉价的重试当作另一类环境也能获得的资源。

最终报告应按任务或环境组织重复实验，保留超时、启动失败与模型失败，不选择性删除困难样本。公开任务还需要独立留出、时间切分与版本记录，以区分能力进步、评价条件改变和对固定基准的适应。

## 六、研究机会

更长、更宽的评测需要同时扩展任务来源与能力目标：一方面尽可能保留真实工作系统，另一方面把希望 Agent 具备的新能力变成可检验要求。在此基础上，还要持续构造足以区分前沿模型的复杂任务。

**1. 如何把现有真实世界，或其中足够完整的一部分，做成测量 Agent 表现的 benchmark？**

真实世界包含持久状态、业务规则、工具依赖、多人交互和不可预先枚举的异常。研究机会不是把页面或接口简单复制进沙箱，而是选择一个有明确边界的真实系统，尽可能保留其任务结构、状态转移与约束，使 Agent 完成的工作具有真实含义。需要回答哪些部分必须真实执行，哪些可以模拟，如何验证任务可行性，以及如何在重置与复现时保留决定难度的条件。

基准还需要覆盖自然产生的任务分布，而非只选容易自动验收的工作。可以从真实流程提取任务，构建可追溯的环境和结果检查，再比较沙箱表现与真实流程中的表现是否一致。成功标准不仅是基准能够运行，还包括它是否遗漏了重要能力、是否保留失败与恢复，以及得分能否解释系统在对应现实场景中的实际表现。

**2. 如何把未来希望 Agent 拥有的能力形式化为 benchmark？**

并非所有重要能力都有现成任务可供抓取。长期自主工作、主动发现问题、跨领域协调、持续积累经验等目标，需要先被转化为可观察的行为要求，再设计任务与成功条件。研究机会是把这些能力目标形式化为受控任务族，明确哪些信息可获得、系统能够采取哪些行动，以及完成任务为什么必须使用目标能力。

关键难点是避免用一个方便测量的代理替代真正的能力。主动性不等于多调用工具，长程能力不等于输入更长，自我改进也不等于第二次分数更高。基准需要能够排除捷径：系统若只有更大上下文、更多采样或预设工作流，是否也能完成？能够区分这些替代解释，才能把未来能力从概念描述转化为有研究价值的测量对象。

**3. 如何构造足以挑战 SOTA 模型的复杂任务，同时保证任务合理、可解且可评价？**

任务难并不自动意味着基准好。歧义、不完整环境和错误验收也会降低得分，却不能说明模型缺少某种能力。研究机会是可控地组合任务依赖、信息缺失、动态变化、多工具交接和约束冲突，让挑战来自真实能力需求，而非随机增加长度或隐藏关键信息。SOTA 指当前所比较的最先进系统，具体模型、版本和预算应由实验固定，不能作为永久不变的参照。

可以研究任务生成、难度校准与对抗式扩展，并用独立检查保证任务可执行、目标一致和验收可信。除整体成功率外，还要观察任务在哪个复杂度维度上区分系统、失败是否具有稳定机制，以及模型进步后基准能否继续产生有效挑战。可扩展的难度机制比一批暂时让模型低分的固定题目更有长期价值。
