## 方向背景：为什么需要人机协作与多智能体组织

设想组会前一周，导师交给你两件事：一是整理一份某个新方向的文献综述，二是把实验仓库里一个牵涉好几个模块的 bug 修掉。你手边有一个很能干的 agent，于是很自然地想到，何不多开几个？综述这件事，让三个 agent 分别去查三条线索，各自读完再交回一份摘要，听上去顺理成章；修 bug 这件事，让一个 agent 改数据加载、另一个改训练循环、第三个补测试，似乎也能省下不少时间。

真正跑起来，两件事的结局往往很不一样。查文献的那组 agent 大概率会交回一份覆盖面更广的材料，偶尔有重复，但汇总时删掉就好。改代码的那组却常常出事：改数据加载的那位默认把字段名改成了小写，改训练循环的那位还在按旧字段读取，补测试的那位又按自己的理解写了一套期望行为。三份修改单看都说得通，合在一起却跑不起来，最后还得由一个人从头读一遍、把这些隐含的决定对齐。

这个小故事几乎浓缩了多智能体协作这两年的全部争论。分工确实能带来并行和专长，可它同时引入了交接、协调和错误传播的成本。多个成员可能共享同一个盲点，彼此附和也构不成独立证据；人的反馈如果来得太晚，往往只能触发一场大返工。哪些工作适合拆开，拆开以后各自看到什么、能改什么，分歧出现时谁说了算，成果最后由谁来验收，这些问题必须一起设计。

本章把人机协作和多智能体系统放在一起讨论，因为它们回答的是同一个问题的两面：知识、能力和决策权分散在不同参与者手里时，怎样让大家一起做成单个参与者做不好的事。人机协作更关心人的控制权、反馈时机和工作负担，多智能体系统更关心执行单元之间怎样组织和通信。两者经常结合在一起，但关注点各有侧重。下面会沿着工作流、伙伴选择、失败归因、通信、用户模拟、人类反馈和长期团队这几条线展开，始终同时看三笔账：结果质量、总成本，以及出了问题能否追到责任。

## 先读这几篇

这一章的主线借自几篇写得很好的工程长文。有意思的是，其中两篇在 2025 年 6 月同一周发布，标题看上去针锋相对，一篇讲怎样搭多智能体系统，一篇劝人别搭；后面几篇则记录了业界怎样在争论中慢慢收敛。按下面的顺序读，基本就能复原这场讨论的来龙去脉，再回来看各分支的新论文，会清楚得多。

| 顺序 | 文章 | 为什么读 |
|---|---|---|
| 1 | Anthropic（Jeremy Hadfield、Barry Zhang 等），[How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)（2025-06） | 支持多智能体一方最有分量的一篇。作者讲的是 Claude 的 Research 功能：一个主研究员 agent 先做计划，再并行派出多个子 agent 去搜索，最后汇总结果，并由一个单独的引用 agent 把结论对回来源。文章给出了一个很有冲击力的数字，在内部研究评测上，Opus 4 做主 agent、Sonnet 4 做子 agent 的组合比单个 Opus 4 高出 90.2%。可作者也很坦率：在 BrowseComp 上，token 用量一项就解释了约 80% 的表现差异，多智能体之所以有效，主要是因为它帮系统花够了解决问题所需的 token，代价是约为普通对话 15 倍的消耗。读完能带走的，是一套关于委派、预算和评测的实用原则，以及对"多智能体在什么任务上划算"的清醒判断。 |
| 2 | Walden Yan（Cognition），[Don't Build Multi-Agents](https://cognition.com/blog/dont-build-multi-agents)（2025-06） | 反方的代表作，比 Anthropic 那篇早一天发布。作者认为上下文工程是构建 agent 的工程师的头号工作，并提出两条原则：子 agent 之间要共享完整的执行轨迹，单传几条消息远远不够；每个动作都携带着隐含的决定，决定一旦冲突，结果就会变坏。文中那个 Flappy Bird 的例子很好记：两个子 agent 分头做背景和小鸟，一个做出了马里奥风格的背景，另一个做出的小鸟又和游戏机制对不上。他由此主张默认使用单线程的线性 agent，上下文太长时再用专门的模型压缩历史。读完会对"并行写"的危险有切身体会。 |
| 3 | Harrison Chase（LangChain），[How and when to build multi-agent systems](https://www.langchain.com/blog/how-and-when-to-build-multi-agent-systems)（2025-06） | 两篇文章发布几天后的一篇调和之作，篇幅不长，却把争论的焦点说得最透。作者指出两篇其实有共识：给子 agent 恰当的上下文是最难的部分；读操作天然比写操作更容易并行。Anthropic 的系统让子 agent 只做检索，最终报告仍由一个 agent 写，正好符合这一点。这篇文章是本章主线中"读写之分"的来源，读它能帮你把开头那个故事里两组 agent 的不同结局讲清楚。 |
| 4 | Cara Phillips 等（Anthropic），[When to use multi-agent systems (and when not to)](https://www.claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)（2026-01） | 一年半之后的总结性指南，立场比 2025 年那篇更克制。作者认为大多数工作流用单个 agent 就能处理好，多智能体通常要多花 3 到 10 倍 token，只在三种情况下稳定有用：保护上下文不被无关信息污染，并行覆盖更大的搜索空间，以及工具或角色需要专门化。最有价值的是两个判断：拆分工作要以上下文边界为准，按"写功能、写测试、做审查"这样的问题类型拆分，会像传话游戏一样一层层失真；验证子 agent 之所以好用，是因为验证几乎不需要转交上下文。读完可以得到一张很实用的决策清单。 |
| 5 | Walden Yan（Cognition），[Multi-Agents: What's Actually Working](https://cognition.com/blog/multi-agents-working)（2026-04） | 反方作者十个月后的更新，很值得和第 2 篇对照着读。他承认一类窄一些的多智能体结构已经在生产中跑通了，共同点是写操作仍然保持单线程，新增的 agent 只贡献判断，不贡献动作。他具体讲了三种模式：编码 agent 和不共享上下文的审查 agent 来回迭代；便宜的主模型遇到难题时去请教更强的模型；管理者 agent 把大任务拆给子 agent，按"映射、归约再管理"的方式协调。他对无结构的 agent 群体协商依然不看好，并说剩下的开放问题全都是通信问题。 |

如果还想多读一点，Anthropic 在 2024 年底写的 [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) 是这一切的词汇表，提示链、路由、并行（分段与投票）、协调者与工作者、评估者与优化者这些模式名称，后来几乎成了行业通用语；Google Research 2026 年 1 月的博客 [Towards a science of scaling agent systems](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/) 则是本章第二节引用的那篇规模研究的通俗版，几张图把"什么任务该多开、什么任务不该多开"讲得很直观。

## 一、先把“团队”拆成可以观察的设计

读这个方向的论文之前，先把几个基本概念摆清楚。如果还不熟悉大模型调用，可以先读[大模型基础](../docs/llm_primer.md)。模型按 token 处理输入并生成输出，token 是文本的编码单位，和"一个词"并不一一对应；智能体则在一次次模型调用之间执行工具、接收反馈并维护状态。所以"一次任务"背后通常是多次模型推理，多加一名智能体，可能就多出许多次调用。这也是为什么本章总要把三件事分开说：最终质量，**延迟**（用户要等多久），以及**总计算成本**（所有成员合计消耗多少资源）。并行可以缩短前者，却常常推高后者，Anthropic 2026 年那篇指南说得很直白，并行的主要好处是查得更全，速度倒在其次。

智能体是围绕目标反复观察、决策与行动的执行单元。几个智能体可以用同一个基础模型，各自拥有不同的状态、工具和权限，也可以由不同模型组成。这里有个很容易被忽略的地方：三个角色如果读的是同一份草稿，通常并没有带来三份独立证据。审稿要真正发挥作用，审稿者得能访问原始来源、独立做检查，或者运行一套和写作者不同的验证过程。Cognition 在 2026 年的文章里报告过一个耐人寻味的现象，他们的代码审查 agent 恰恰在完全不共享编码者上下文的时候效果最好，只看 diff 反倒让它看见了编码者看不见的 bug。

最常见的组织方式有三种。**流水线**让检索、写作、审查依次交接，容易追踪，可后面的环节会继承前面的遗漏。**协调者与工作者**把可以拆分的任务并行派发出去，再汇总结果，适合不同主题的独立检索，协调者却可能成为瓶颈。**去中心或共享工作区**允许成员自己认领任务、交换发现，适合探索性的工作，代价是要处理冲突、重复劳动和停止条件。[AutoGen](https://arxiv.org/abs/2308.08155)与 [MetaGPT](https://arxiv.org/abs/2308.00352)是可编程交互和标准工作流程这两类思路的经典入口。

画出一张组织图，只是协作设计的开始。拓扑描述谁能和谁通信，协议规定发什么、何时发、怎样解释，运行时才决定这些规则是否真的被执行。写作者声称"已经交给审稿者"，系统里却没有强制的检查步骤，实际运行就可能在这里直接结束。所以任务分配、消息、文件修改、工具调用和验收记录最好都完整保留下来，事后才能核对设计和实际是否一致。

最后还要分清并行尝试和协作。让五个助手各自回答，再挑出最好的一份，这是多次尝试；让它们共享发现，并据此改变后续行动，通信才真正起了作用。挑选结果本身也需要机制：多数投票按答案出现的频次来选，**模型裁判（LLM-as-a-Judge）**让另一个模型按标准评估输出，代码验证器则检查可以执行的条件。裁判可能和答题者犯同样的错，测试也可能只覆盖一部分要求，三者提供的是强度不同的证据。因此评价一个团队，至少要拿它和单个强助手、等预算的独立尝试放在一起比较，否则很难知道收益来自交流本身，还是仅仅来自更多的计算。

## 二、发展主线：从角色扮演到按上下文分工

这一节以 Cognition 的两篇文章为骨架，再把 Anthropic 的两篇和 Harrison Chase 的调和文章填进去。之所以选它们，是因为它们恰好记录了一次完整的认识转变：2023 年大家热衷于给模型分配角色、让它们彼此对话；2024 年开始有人冷静地追问，多出来的收益到底来自协作，还是来自更多算力；2025 年生产系统里爆发了"该不该多开"的正面争论；2026 年争论逐渐收敛成一组更精细的原则。把这条线和学界的失败分析、规模研究对照着读，多智能体这几年的历史可以读成一段"先放开、再收紧、最后找到边界"的过程。

### 前史：最准的模型，未必是最好的队友

在大模型会写代码、会调工具之前，"协作"首先是一个人机共同决策的问题。模型给出建议，任务还远没有完成，人要决定是否接受、是否核实、什么时候干脆自己处理。这样一来，错误落在哪些样本上，人的优势在哪里，判断一条建议是否可信要花多少成本，都可能比平均准确率更要紧。一个更准确、却让人难以判断它何时出错的助手，未必能带来更好的合作。

2020 年的 [Is the Most Accurate AI the Best Teammate?](https://arxiv.org/abs/2004.13102)把这种区别落实为团队效用问题，把最终决策质量、核验成本和人机各自的能力放在一起考虑。它为后来的协作研究定下了一个朴素的起点：挑选成员时，要优化的是大家共同完成任务的结果，把每个人的独立分数加起来并不能说明这件事。这个起点后来被多智能体研究反复重新发现，只是这一次，队友换成了另一个模型。

### 第一阶段：给模型分角色，让它们聊起来

2023 年，大模型第一次强到可以扮演一个像样的角色，研究者很快开始尝试把几个模型放在一起。3 月的 [CAMEL](https://arxiv.org/abs/2303.17760) 用"起始提示"让两个 agent 分别扮演用户和助手，在很少人工干预的情况下一来一回地完成任务；4 月的 [Generative Agents](https://arxiv.org/abs/2304.03442) 在一个类似模拟人生的小镇里放进了一群能记忆、反思和计划的 agent，它们展现出相当可信的社会行为，这也是本章三.5 那些模拟用户与群体研究的源头。5 月的 [Improving Factuality and Reasoning in Language Models through Multiagent Debate](https://arxiv.org/abs/2305.14325) 让同一模型的多个实例提出答案、互相辩驳若干轮，报告了推理和事实性上的提升。

与此同时，"团队"开始被用来干正经活。7 月的 [ChatDev](https://arxiv.org/abs/2307.07924) 让扮演不同岗位的 agent 通过自然语言对话完成软件的设计、编码和测试；同年的 [AutoGen](https://arxiv.org/abs/2308.08155)支持模型、工具与人参与可编程对话，让协作流程可以被显式组织；[MetaGPT](https://arxiv.org/abs/2308.00352)同样以软件开发为场景，用角色、标准作业程序和中间产物来约束分工。这两类框架强调的组织手段不同，一个提供可编程的交互方式，一个强调流程与产物的规范，它们让搭建协作系统这件事变得具体可行。

这一阶段的热情很好理解：人类组织靠分工取得成功，模型似乎也可以。可这些框架都没有自动解决误解、错误传递和验证缺位这几件事，回头看，第二阶段的追问其实早已埋在这里了。

### 第二阶段：冷静下来，收益到底从哪里来

2024 年，几篇工作开始给这股热情降温。2 月的 [More Agents Is All You Need](https://arxiv.org/abs/2402.05120) 用一个极其简单的办法，多次采样再投票，就让性能随 agent 数量增加而上升，而且任务越难，提升越明显。这个结果本身是正面的，但它暗示了一件让人不太舒服的事：很多"协作"的收益，也许单靠多算几遍就能拿到。同月的 [Rethinking the Bounds of LLM Reasoning: Are Multi-Agent Discussions the Key?](https://arxiv.org/abs/2402.18272) 说得更直接，在大量推理任务和多种基座模型上，提示写得好的单个模型几乎能追平当时最好的多智能体讨论方法，只有在提示中不给示例时，讨论才明显占优。

同年 12 月，Anthropic 的 [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) 从工程侧给出了同样的建议。作者把常见的组织方式整理成几种可组合的模式，其中"协调者与工作者"和"评估者与优化者"后来成了多智能体系统最常见的两种骨架；但文章反复强调先从最简单的方案开始，只在复杂度能被证明带来更好结果时才往上加。这一阶段留下的最重要的方法论，就是第一节说的那组对照：任何多智能体系统，都应该和等预算的单体、独立多次尝试放在一起比较。

### 第三阶段：一周之内的两篇文章

真正把讨论推到台前的，是 2025 年 6 月同一周的两篇文章。

Anthropic 那篇讲的是一个已经上线的系统。研究类问题天然是开放的，事先没法把步骤写死，所以他们让主 agent 边查边决定追哪条线索，并行派出三到五个子 agent，每个子 agent 在自己的上下文窗口里检索和压缩信息，只把精华交回来。效果很好，复杂查询的研究时间最多缩短了九成。但作者也把账算得很清楚：多智能体之所以有效，主要是因为它帮系统花够了 token，代价大约是普通对话的 15 倍，只有高价值的任务才值得这么做。文章还明确划出了不适合的场景，凡是 agent 之间要共享大量上下文、彼此依赖很多的领域都不合适，作者举的例子正是编程，大部分编程任务里真正能并行的部分远少于研究。

Cognition 那篇几乎是从编程这一侧出发的。Walden Yan 的核心判断是，可靠性取决于上下文工程，而多智能体结构天然违反他提出的两条原则：子 agent 只拿到任务摘要，容易误解任务；各自行动时又会做出彼此看不见的隐含决定。他提到 Claude Code 自己也会派生子 agent，但不让它们和主 agent 并行运行，这些子 agent 通常只回答范围很窄的问题，很少动手写代码，价值在于把调查过程挡在主 agent 的历史之外。

几天后，Harrison Chase 指出这两篇其实没有表面上那么对立。两边都把"给子 agent 恰当的上下文"当作最难的事，区别在于任务性质：读操作天然容易并行，写操作并行时就得共享上下文、合并冲突的产出，而冲突的写入通常比冲突的读取后果严重得多。回到本章开头那个例子，查文献的那组 agent 做的是读，改代码的那组做的是写，结局不同几乎是注定的。本章三.1 讨论工作流怎样组织，三.4 讨论信息怎样共享，都是在这一阶段提出的问题上继续往下做。

### 第四阶段：把失败和规模变成可以测量的东西

工程上的争论需要证据来裁决，学界在差不多同一时间给出了两类证据。

第一类是失败分析。2025 年 3 月伯克利等机构的 [Why Do Multi-Agent LLM Systems Fail?](https://arxiv.org/abs/2503.13657) 先从 150 条执行轨迹中归纳出多智能体失败分类 MAST，标注者之间的一致性 Cohen's kappa 达到 0.88，再把数据扩展到 7 个流行框架的 1600 多条标注轨迹。14 种失败模式被归入三大类：系统设计问题、智能体之间的不一致，以及任务验证失误。这项工作把问题从"最终得分为什么不高"推进到"协作过程在哪里出了错"，Cognition 说的隐含决定冲突，在这里大致落在第二类；Anthropic 说的子任务描述含糊导致重复劳动，则落在第一类。本章三.3 讨论失败后该改谁，正是以这套分类为起点。

第二类是规模研究。[Towards a Science of Scaling Agent Systems](https://arxiv.org/abs/2512.08296)在控制工具、提示和计算的条件下，比较了单体、独立、集中、去中心和混合五种架构，研究任务可分解性、单体能力和协调开销怎样共同影响收益。按 Google Research 博客的介绍，这项研究覆盖了 180 种配置、4 个基准和 3 个模型家族：在可以并行拆分的金融推理任务上，有协调者的集中式结构比单体高出 80.9%；在步骤严格依赖前一步的 PlanCraft 上，所有多智能体变体都下降了 39% 到 70%。独立工作的多智能体系统会把错误放大 17.2 倍，有协调者的结构把这个数字压到 4.4 倍，协调者在这里起到了验证关口的作用。作者用任务性质建立的预测模型，在未见过的任务配置上为 87% 的情况选对了架构。这类结果可以支撑"按任务结构选架构"的实验假设，但它给不出适用于所有场景的固定人数或组织规则。本章三.2 讨论伙伴选择，背景就是这组数字。

### 第五阶段：收敛成几条可操作的原则

到 2026 年，争论双方的立场明显靠近了。Anthropic 1 月的指南把话说得比 2025 年保守许多：多数工作流一个 agent 就够，先试试上下文压缩和按需加载工具，确实碰到上下文、并行或专门化的硬约束时再加 agent。它提出的"以上下文为中心切分"几乎是对 Cognition 原则的正面回应，好的切分边界是独立的研究路径、接口清晰的组件和黑盒式的验证，坏的边界是同一项工作的前后阶段、紧密耦合的组件以及需要共享状态的工作。它也指出了验证子 agent 最常见的失败，叫作"过早宣布胜利"：跑了几个测试、看到通过就宣布成功。

4 月，Walden Yan 自己写了更新。他的旧判断对"并行写"依然成立，但一类更窄的结构已经跑通：写操作保持单线程，额外的 agent 只贡献判断。他们的审查 agent 平均每个 PR 能找出约 2 个 bug，其中约 58% 属于严重问题；而让弱一些的快模型在遇到难题时去请教强模型，效果却不理想，原因是弱模型不太知道该在什么时候求助、该问什么。他把这类委派称作能力路由，而且明确说剩下的开放问题全都是通信问题。

把这一阶段的共识压缩成一句话，大概是：按上下文边界拆分，让写操作有唯一的负责人，把验证交给一个不受原作者上下文影响的独立方。本章三.1 里那些动态拓扑与可控运行时的工作，三.7 里那些动辄成百上千个 agent 的大规模实验，都可以拿这三条原则去检验。

### 边界：人在哪里，记录归谁

主线讲到这里，几乎全是 agent 和 agent 之间的事。可开头那个故事里，最后对齐三份修改的仍然是人，导师那里还有一份要汇报的综述。协作的另一半问题始终是人在什么时候介入、看到什么、能撤销什么，以及长期合作中谁来保管证据。本章三.5 讨论模拟用户能否代表真人，三.6 讨论人的反馈怎样进入系统，三.7 讨论长时间、大规模团队怎样验证成果、保留责任，都落在这条边界上。这些方向目前的论文还不多，可从前史那篇团队效用研究一路读下来，会发现它们问的其实是同一个老问题：协作的价值要用整个团队的结果来衡量。

## 三、前沿研究方向

下面七个分支收录的都是 2026 年的新论文，它们大致沿着上一节的主线展开：先讨论团队怎样组成、伙伴怎样选择，再进入失败归因与信息共享，最后研究怎样表示用户、利用人的反馈并维持长期团队。每个分支开头先交代它要回答的问题，第一段之后标出它在主线上的位置。读这些论文时，可以始终带着两个问题：它做的是读多的工作还是写多的工作？它拿什么对照来证明收益来自协作本身，与单纯多调用几次的效果区分开？前者决定它该和哪些经典工作比较，后者决定它的结论能信几分。

### 1. 工作流程应该固定、按任务选择，还是边做边变？

固定流程的好处是容易复现、容易检查，可遇到没见过的任务时，它可能根本不适用；动态组织更灵活，却要额外付出计划、调度和通信的成本。真正要比较的，是任务之间的依赖是否稳定，执行结果什么时候返回，以及哪些失败需要改变分工。这里有个很朴素的道理：多开几个成员消除不了串行依赖。如果大家总在等同一个关键结果，并行组织只会增加成本，完成时间却一点也没缩短，Google 那组研究里顺序任务上的大幅下降，说的正是这件事。

> 主线位置：第三阶段到第五阶段。接 Building effective agents 的协调者与工作者模式、Anthropic Research 系统的动态派发，以及"按上下文边界切分"的原则。

先看一个把 Anthropic 那套思路往前推了一步的例子。**[SearchOS-V1](https://arxiv.org/abs/2607.15257)**将开放搜索的进展保存为任务前沿、证据图、覆盖图和失败记忆，并用流水式调度持续填补尚未完成的信息需求。它和一次性拆题、再等所有子任务返回的做法不同，后续的调度依赖共享的进度。这让人想起 Anthropic 文中提到的同步执行瓶颈：主 agent 必须等一批子 agent 全部完成才能继续。SearchOS-V1 说明，协作的收益也可以来自状态组织和槽位利用，并不全都要归功于"更多模型一起思考"。

把组织结构做成显式程序，是另一条路。**[GaP: A Graph-as-Policy Multi-Agent Self-Learning Harness For Variational Automation Tasks](https://arxiv.org/abs/2607.05369)**（`2607.05369`） 从机器人变式自动化出发，把感知、规划和控制技能组织成一张有向计算图，并生成内部模拟环境来排练不同的图结构和参数。组织结果因此成了一段可以解释的执行程序，适合针对环境变化反复测试。它的前提也很明显：机器人技能库和模拟环境都是方法成立的重要条件，这套组织方式不能无条件地搬到开放的网页研究里去。

如果说 GaP 的图是事先排练好的，**[MANTA: Multi-Agent Network Topology Adaptation for Self-Evolving Multi-Agent Systems](https://arxiv.org/abs/2607.28527)**（`2607.28527`） 则让通信拓扑在推理时变化：先根据任务和历史结构初始化，再一边监测协作轨迹，一边在需要时调整角色、连接、执行顺序和可见信息，同时限制智能体的预算。它和固定流水线最大的差别，是组织本身成了可以修改的对象。灵活性随之带来新的归因难题：收益究竟来自换了角色、换了信息路径，还是多加了一道验证？这几件事需要分开观察。

每个任务都从头搜索一张新图，代价显然不小。**[Codebook Agent: Amortized Topology Design for LLM Multi-Agent Systems](https://arxiv.org/abs/2609.02264)**（`2609.02264`） 正是从这里出发，它认为每次都从巨大的邻接空间里生成新图太昂贵，于是改为学习一本由成功拓扑组成的紧凑码本，再按查询去选择和重排。论文还专门检查了边数和真实 token 消耗之间的关系，提醒我们连接更少，成本未必就更低。它和 MANTA 之间的取舍，可以理解为预先积累可复用结构与运行中随时适应这两种分工。

前面几篇设计了各种组织方式，可组织图画得再好，运行时有没有真的照着做，是另一回事。**[OpenCollab: A Multi-Agent Coding Framework with Programmable Collaboration and Controllable Runtime](https://arxiv.org/abs/2609.38345)**（`2609.38345`） 把运行时控制和组织遵循程度放到了中心：它统一系统组件，记录细粒度事件，并测量声明的组织结构是否实际发生。这为动态图、拓扑码本等方法提供了一套检验运行过程的思路。如果两个团队用的工具和停止机制都不同，仅比较最终分数，就很难把差异归功于组织设计。

把这一组放在一起看，动态组织仍然需要保留一些稳定的约束。比如可以允许团队调整检索分工，但要求发布之前必须完成来源检查，并记录实际执行的事件。这样一来，就能比较结构调整是否减少了等待、补齐了证据或者改善了结果，也能顺便检查收益是否只是来自更多的调用。流程图描述的是预期中的关系，事件记录才能说明这些关系是否真的生效了。

### 2. 怎样选择伙伴，怎样判断成员真的在合作？

挑队友这件事，包含两个容易混在一起的问题。一个是能力匹配，这个模型擅不擅长这类任务；另一个是边际贡献，它加入这支队伍之后，有没有带来别人给不了的新信息。前者高，后者未必高。比较不同团队时，要把工具、预算和任务分配都固定下来，必要时把某个成员拿掉或者换掉，看结果会不会变。不这样做，团队总分提高了，也可能只是其中一个强成员包办了全部工作，其余成员只是在旁边陪跑。

> 主线位置：第二阶段与第四阶段。接 More Agents Is All You Need 的"多算几遍"基线、Scaling Agent Systems 的架构与任务匹配，以及 Cognition 2026 年文中"能力路由"的说法。

先看一个把路由和验证放在一起考虑的例子。**[ORACLE](https://arxiv.org/abs/2607.22465)**按任务类型适配验证器，并用延迟反馈减少验证过程对并发派发关键路径的阻塞。在这里，协作的对象除了解题模型，还包括路由与验证之间的配合。它很适合用来分析为什么静态地选模型解释不了部署效果：同一个选择策略，放在不同的反馈延迟和负载下，服务质量可能大不相同。这和 Cognition 在"请教强模型"那个模式里遇到的问题是同一类，路由策略好不好，离不开运行时的条件。

选好伙伴之前，还得先认识伙伴。**[Multi-Agent LLMs Fail to Explore Each Other](https://arxiv.org/abs/2607.11250)**（`2607.11250`） 把相互了解建模成一个多智能体探索问题：成员需要先试探伙伴的能力和交互策略，才能有效协调。作者观察到短视、两极化的交互模式，并提出了结构化的伙伴探索机制。这篇工作说明，给角色贴上"专家"标签，代替不了真正的能力识别，这正好呼应了 Cognition 的观察，弱一些的模型往往不知道什么时候该去找别人帮忙。当然，探索本身也要花成本，收益应当和任务长度、成员差异放在一起评估。

伙伴池该怎样组建，是更上游的问题。**[Mo' Models, Mo' Problems: How to best select model pools when designing Multi-Agent Systems](https://arxiv.org/abs/2609.17306)**（`2609.17306`） 系统比较了按能力、规模和答案多样性来选择模型池的几种策略，并在路由、投票和裁判等架构下分别评估。作者发现，扩大候选池可能让结果反而低于最强的单个模型。理论上存在一个能挑出好答案的理想选择器，可真实系统未必造得出来；新成员既可能带来互补的知识，也可能带来更难被筛掉的错误。这个结论和第二阶段 More Agents Is All You Need 的乐观结果放在一起读，会很有意思。

另一组工作关心的是，一支固定的团队能不能学会一起推理。**[Self-Organizing Agent Teams Learn to Reason Together](https://arxiv.org/abs/2609.22682)**（`2609.22682`） 让固定团队从以往的协作中学习角色、交流阶段和信息流策略，再把这套策略用到没见过的任务上，并和最强成员、等计算量的单体以及理想的独立答案路由做比较。它支持研究一个很有分量的问题：共同推理能否产生任何成员单独工作时都想不到的解法。不过收益随基准而变化，还要具体检查哪些任务真的需要共享部分解答，只看总体平均容易被误导。

要回答"成员是否真的在合作"，最终还得落到可以观测的行为上。**[When Agents Coordinate: Measuring Coordination in Multi-Agent AI Coding](https://arxiv.org/abs/2608.16801)**（`2608.16801`） 把一次协作运行表示成一张带时间和成本的网络：智能体和文件是节点，消息和读写是边。它比较了团队规模、结构和文件政策，让协调过程变得可以测量。这些事件记录正好为前两篇提供了观测工具：伙伴探索有没有改变通信，团队策略有没有减少重复读写，都可以落到具体事件上去检查。放在 Chase 的读写框架里看，这张网络里的"写边"尤其值得关注，多个 agent 同时写同一个文件的地方，往往就是隐含决定发生冲突的地方。

检验成员是否互补，有一个简单的办法：让不同成员处理彼此独立的来源，再比较证据覆盖、重复劳动、错误被发现的时机和最终质量。如果消息主要在复述已有的内容，新成员带来的多半只是协调开销；如果成员能提供独有的证据，并纠正彼此的错误，才更接近有效的协作。

### 3. 团队失败后，应改哪个成员，知识又怎样留下来？

一支团队失败了，原因可能出在某个成员的能力上，也可能出在任务拆解、信息交接或者成员之间的相互等待上。如果只让最后给出答案的那位成员去反思，很容易把组织问题错算到个人头上，就像项目延期了只批评最后交付的那位同事。改进之前，应当先保留每个角色的输入、输出和依赖关系，分清是该换成员还是该重组流程，然后再决定经验应该存成个人技能、团队规则，还是一份共享状态。

> 主线位置：第四阶段。接 MAST 的三类失败分类，把"在哪里出错"往前推进到"该改哪里、怎样记住"。

先看一种把团队经验固化成技能的做法。**[MASkills: Continual Skills Optimization for Multi-Agent LLM Systems](https://arxiv.org/abs/2609.02094)**（`2609.02094`） 把多智能体持续改进的单位换成了技能，结合技能条件下的贡献分配、层次聚合和较平滑的优化，支持技能的提炼、合并和剪枝。它试图把难以调用的经验记忆变成可以执行的指导。难点在于共同成功之后，功劳该怎样分：某个成员输出的文字不多，却可能提供了最关键的那条约束，按消息长度分功劳显然不合理。

要找出该改的成员，最可靠的办法是做干预实验。**[AgentGrad: Intervention-guided Prompt Optimization for Multi Agent Systems](https://arxiv.org/abs/2609.08572)**（`2609.08572`） 用顺序干预来定位应该修改的成员：每次只改变一个成员的行为，观察失败是否因此消除，再据此提炼和聚合对提示的修改建议。比起根据最终的错误去猜责任，这更接近因果诊断。代价是每次干预都要重跑，优化成本会上升；而且由多个成员共同造成的故障，未必能用单点修复来解释，这恰恰是 MAST 里"智能体之间不一致"那一类失败的特点。

团队产生的经验，还可以离开团队继续发挥作用。**[From Proprietary to Open-Source: Bridging the Distribution Gap via Multi-Agent Protocol Distillation in Agentic Search](https://arxiv.org/abs/2607.24280)**（`2607.24280`） 把多智能体搜索产生的探索过程转成结构化的协议，保留任务类型、计划和抽取式证据，再拿去做蒸馏和强化学习。在这里，多智能体主要服务于离线的知识生产，部署时并不一定需要同样的团队。它帮助我们分清两条路线：一条是让团队帮忙收集学习信号，另一条是让团队在每次推理时都协作。

经验留在哪里，也是一个组织问题。跨类的 **[Agora: Git as Shared Memory for Collective AutoResearch](https://arxiv.org/abs/2609.18094)**（`2609.18094`） 用 Git 中只追加的有向无环贡献记录来保存结果、假设、验证和报告，并把它们和前人的工作关联起来，让分散在不同会话里的研究者能找到已经尝试过的路径和有待验证的分支。它持续多天的实例展示了共享研究记忆可以怎样组织；但单个研究案例代表不了所有领域的协作收益，账号不同也不能当成统计上的独立。

这些工作把团队学习拆成了几件事：判断贡献，局部修改，结构化地转移知识，以及维护公共记录。共享经验时，最好把具体依据一起保留下来：哪个判断后来被结果推翻了，哪种方法只在特定条件下才成立，哪些依赖随版本变化已经失效。把记录和证据、责任、版本连在一起，成员就能复用经过检查的经验，用不着把全部讨论重新读一遍。

### 4. 怎样共享信息，避免把所有内容广播给所有人？

通信要在带宽、可解释性和有用性之间找平衡。把全文都共享出去最简单，但又长又杂；只共享摘要，又可能在压缩中失真；共享模型内部的表示，就更难检查对方到底有没有用上这条消息。所以一个好的协作系统，要能证明消息的内容对结果有贡献，仅仅证明"接上一个新接口后分数提高了"远远不够。把消息错配、打乱或者删掉，看结果怎样变化，是区分内容作用和接口本身作用的好办法。

> 主线位置：第三阶段的核心问题。接 Cognition 的"共享完整轨迹"原则与上下文压缩，以及 Anthropic 子 agent 在各自窗口里压缩信息的做法。

先看一篇把这条检验原则做得很彻底的工作。**[Draft-KV](https://arxiv.org/abs/2609.34754)**通过草拟答案时形成的键值状态在模型之间通信，并使用投影、门控读取和分阶段的接口训练。论文先用来自无关问题的消息替换原消息，揭示出部分潜在通信方法的收益其实不依赖消息内容，再用这种对照去检验自己的新接口。它和普通的多角色文本交流很不一样，却提供了一条通用的评测原则：真正的协作，应当对正确伙伴提供的相关信息敏感。

另一个问题是，通信到底在什么时候值得。**[Scaling Discovery through Test-Time Communication](https://arxiv.org/abs/2609.21032)**（`2609.21032`） 比较了测试时通信与独立并行尝试，让成员通过一个共享目录传播发现，并在探索和研究任务上分析收益。它和普通的多数投票不同，交流会改变之后探索的方向。但这种收益取决于任务里是否真的存在值得传播的突破，也受总计算预算的影响；对于那些各自就能查证的简单问题，持续通信可能只会增加延迟。这和 Anthropic 的判断一致，并行最适合广度优先的问题。

"共享状态"这个词，在别的领域里也有很不一样的含义。**[Streaming Multi-Agent Autoregressive Diffusion Model with World State Registers](https://arxiv.org/abs/2607.21594)**（`2607.21594`） 是一个必须先分清任务类型的相关方向：它研究多智能体、多视角的视频世界模型，用共享的状态寄存器维护世界信息和各自的状态，并在双智能体的 Minecraft 视频生成中评估一致性。这里的"多智能体"和写代码的聊天团队完全是两回事。它和本组相关，是因为它展示了共享状态无法仅靠各自的观察历史隐式地对齐；它的生成质量，也不能拿来当作协作任务的成功率。

信息可以按性质分工处理。跨类的 **[Seeing and Reflecting: Multimodal Memory-Enhanced Agent Collaboration for Recommendation](https://arxiv.org/abs/2607.07108)**（`2607.07108`） 把用户与物品记忆智能体的可解释推理，和细粒度的多模态嵌入匹配分开处理，再把结果融合起来，用来应对推荐中的视觉证据和偏好变化。它说明共享可以按信息的性质来分工，用不着把所有原始内容都塞进同一段对话里。局限在于，推荐任务的排序评价回答不了开放式团队决策的问题。

还有一个更细的问题：哪些经验该共享，哪些该留给个人。跨类的 **[Learning What to Share and What to Personalize: Hierarchical Strategy Co-Evolution for Agent Memory](https://arxiv.org/abs/2608.25329)**（`2608.25329`） 把记忆管理策略分成全局共享的原则和针对特定用户的调整两层，并根据证据在两层之间提升或下放规则。它的目标和增加团队人数无关，处理的是"哪些经验应该共享、哪些必须个性化"。这对同时服务很多用户的系统尤其重要：个人的表达偏好适合留在个性化的那一层，只有那些具有共同适用条件的经验，才应当进入共享规则。

落到实际系统里，可以把共享分成三层：公共事实与已经核验的来源，当前任务的进度，以及成员或用户的私有偏好。共享一个索引和共享完整的数据，也是两件事。出现冲突时，先去定位事实的来源和有效时间，再决定由谁来修改，让成员反复投票解决不了这种问题。通信协议还要能表达"不确定"和"仅适用于本任务"这类状态，否则一条局部经验在传播过程中，很容易变成一条人人遵守的通用命令。

### 5. 模拟用户与群体行为，能否可靠地代表真实协作？

用模型来扮演用户，可以低成本地产生大量交互，这对测试协作系统非常有吸引力。可模拟者可能和被测系统共享同一种模型偏差，也可能把研究者的预设直接写进结果里。表面上像人的对话，和真实的行为分布之间还隔着很远，离长期的群体规律就更远了。所以用模拟来检验系统内部的机制，和据此预测真实人群的反应，是两种强度不同的主张，后者需要独立的数据、校准和迁移验证。

> 主线位置：第一阶段的延续。接 Generative Agents 的小镇模拟，以及后来"用 agent 代表真人"的一系列尝试。

先看规模最大的一个。**[MatrAIx: Simulating the World with 8.3 Billion Persona Agents](https://arxiv.org/abs/2608.04205)**（`2608.04205`） 构建了人格记录、问卷、聊天、网页和应用环境，用模拟用户预先考察不同背景的人会怎样反应。题名里的 83 亿是人格记录的规模，和真实参与者人数、同时运行的团队规模都没有关系。人格遵循和档案提取的质量是重要的检查项，可它们还回答不了模拟行为是否对应真实人群；应用时，更稳妥的做法是先把它当作发现潜在问题的工具，再找真人来校准。

模拟器本身的多样性，比人格数量更要紧。**[One Frozen Simulator Is Not Enough: Simulator Collapse in Multi-Agent RL](https://arxiv.org/abs/2608.12253)**（`2608.12253`） 进一步指出，如果长期只和一个冻结的模拟器一起训练，策略可能会过拟合于它狭窄的行为模式。作者通过扩大模拟反应的分布、让多个模拟器共同参与训练来缓解这个问题，并比较了在没见过的模拟器和真人上的表现。这和单纯扩大人格记录的数量很不一样：大量人物设定如果仍由同一种模式生成行为，未必能提供有效的行为多样性。

群体的另一面是风险。**[Mind Viruses: Self-Propagating Ideas in Multi-Agent LLM Systems](https://arxiv.org/abs/2608.10218)**（`2608.10218`） 研究信息在智能体之间自我传播的风险，在协作编码团队和短暂的交互链里构造并分析了这种传播现象，比较了指令、模型、负载和网络结构各自的影响。它的意义在于提醒我们，通信既能传播有用的发现，也能传播不可信的目标。在特定实验中，一条简短的警告就有效果，可这代替不了真实系统中的权限与证据边界。

把视角放得更长，**[Reproducible macroscopic dynamics in a closed-loop human-AI learning system](https://arxiv.org/abs/2608.30946)**（`2608.30946`） 从大量自适应教学记录中研究闭环人机学习系统的宏观行为，通过按用户隔离的群体和对照分析来考察动态模式。它是一份理解长时间人机交互怎样形成群体轨迹的相关证据，和多模型聊天实验关系不大。观察到可重复的动态，与证明某种教学干预带来了改善，是两种不同的结论，读的时候要分开。

这一组研究连接了个体和群体两个尺度：模拟交互需要覆盖不同的目标和行为，群体分析则需要分清相关性和干预效果。比较稳妥的用法是，先用模拟去筛查可能失败的情境，再用真实交互去检验它的代表性；两者分歧明显时，应当回头调整模拟器的假设和任务分布，一味扩大同质样本的数量于事无补。

### 6. 人的反馈怎样进入系统，才不会变成额外的返工？

人的介入可以提供目标澄清、领域知识或授权决定，这几种东西的性质很不一样，没法统一当成一句文本奖励来处理。系统如果在错误的时机请求帮助，会让人白白等待；如果给人的证据不完整，反馈的质量又会下降。所以设计时要记录清楚：什么时候升级给人，向人呈现哪些信息，人可以撤销什么，并且把人的时间也算进效用比较里。回到开头那个故事，导师最在意的，大概是最后那份综述能不能经得起追问，至于中间开了几个 agent，他未必关心。

> 主线位置：前史与边界。接 Is the Most Accurate AI the Best Teammate? 的团队效用视角，以及 Building effective agents 中"在检查点暂停、等待人工输入"的设计。

人往往要看到作品之后，才知道自己想要什么。**[Efficient Test-Time Adaptation through Human-AI Interaction](https://arxiv.org/abs/2609.04141)**（`2609.04141`） 从跨会话的交互中学习个人标准，把反馈用于上下文和权重的适应，并用一套持续变化的评价细则来明确个体的要求。作者在写作和视觉创作两类任务中，对多个真实个体做了评估。这和一次满意度打分很不一样。跨用户的结果还要结合人数、领域和任务分布来理解，不能据此假定任何专业都能很快完成个性化。

多轮修改中，最容易出的问题是改了新的、丢了旧的。**[PaperBanana-Interact: Scientific Diagram Refinement with Multi-Turn Human Feedback](https://arxiv.org/abs/2608.30241)**（`2608.30241`） 研究科学图示的多轮修改，构建了带需求的评测和模拟反馈，通过内部的批判与修订来减少质量下降和旧要求被遗忘。它初步的真人研究有 14 位参与者，大规模的模拟评估应当和这部分分开理解。多轮图示修改要同时满足新提出的要求和已经确认过的约束：删掉一个术语时，不受这次修改影响的图例和结构都应当保留。所以评价要追踪每一条需求是否持续被满足，只看最终图像漂不漂亮是不够的。

再往上一层，要问的是一整段工作流有没有因为 AI 而变好。**[When Does AI Augment Work? A Workflow-Level Framework for Human-Agent Collaboration](https://arxiv.org/abs/2609.12482)**（`2609.12482`） 把判断的单位从单项任务移到了工作流，提出持续的净价值、人的控制、责任与恢复以及长期发展等几项条件。它是一套评价框架，帮我们决定应该测什么，本身并不证明某款产品提升了生产率。和 [2020 年团队效用研究](https://arxiv.org/abs/2004.13102)对照着读，前者扩展了"工作价值"的范围，后者提供了把质量和核验成本放在一起建模的具体思路。

[Human–AI Collaboration at Scale: Task Criticality, Agency, and Friction Across 250,000 Conversations](https://www.alphaxiv.org/abs/2608.human-ai-collaboration-at-scale)将任务重要性、人的控制和交互摩擦放在同一个研究议题下。沿着这个问题，可以继续比较不同风险等级的任务中人机怎样分工：什么时候需要人工确认，哪些信息能支持人的判断，以及确认过程本身增加了多少等待和返工。这样的评价把人的参与看作工作流程的一部分。

人的介入应当和决策责任相匹配。没有副作用的资料检索可以自动执行；涉及目标变更、争议判断和最终发布的环节，则需要由有权负责的人在理解依据之后做决定。评价时应当计入核查、反馈、等待和返工的时间，同时观察人能否理解产物、发现错误、恢复旧版本。交互次数少了，只说明流程变了，最终还要看任务质量和人的控制能力有没有真正改善。

### 7. 团队扩到长时间、大规模研究时，怎样验证成果和责任？

团队规模一大、时间一长，事情的性质就变了。长期协作要维护共同的目标、资源的归属和尚未完成的依赖，局部的成功不一定能汇合成整体的完成。评价时除了看任务分数，还要检查通信中断、角色混淆、资源争用和重复劳动。责任归属也应当建立在可以追踪的行动和证据上，看最后的署名、看谁提交了答案都靠不住。Cognition 对无结构的大规模 agent 群体一直持怀疑态度，这一节的论文恰好可以看作对这种怀疑的回应和检验。

> 主线位置：第五阶段与边界。接"写操作单线程、验证独立"的原则、MAST 中的任务验证失败类别，以及 Anthropic 关于长时运行中错误会累积、需要可恢复检查点的经验。

先看一个专门为长程合作设计的环境。**[AgentWorld](https://arxiv.org/abs/2609.31590)**在角色和能力不对称的多智能体环境中设置长程合作任务，并尝试用动作依赖图来衡量哪些团队行动对结果真正有贡献。这个设计和把多个独立解题成绩简单相加不同，它能观察到分工、通信和资源共享。不过图上的贡献指标仍然取决于任务怎样建模、依赖怎样定义，不宜把它当作所有现实团队贡献的无争议真值。

去中心的协作要想可信，最好有一个硬的验收标准。**[Autonomous Mathematical Discovery in an Open-World Multi-Agent Environment](https://arxiv.org/abs/2608.23691)**（`2608.23691`） 研究的是一个没有中央协调者、也没有固定流水线的数学发现环境，成员自己选择方向、做实验，并发表可以互相引用的成果。作者报告的发现由精确构造或 Lean 形式验证来支撑。比起只让模型裁判点头认可，这是强得多的结果检查。可数学构造和可形式化证明这两个条件，很难原样复制到开放的社会问题或实验科学问题上。Cognition 在 2026 年的文章里也注意到，那些令人惊叹的大规模 agent 演示，往往都有简单、可验证的成功标准。

规模可以推到多大？跨类的 **[Agensh: Scaling Organizational Intelligence to 1,024 Agents](https://arxiv.org/abs/2609.26781)**（`2609.26781`） 用共享工作区、消息和共同上下文来支持去中心的任务认领、执行、验证与合并，研究大规模并发的工作者。摘要展示的是若干困难的编程任务和扩展实验，说明不了任意任务都能遵循这样的规模规律。读的时候，最好把完成时间、测试通过比例和总 token 分开来看，尤其要留意更大的团队是否只是更早地用掉了更多预算。放在主线里看，这是一个直接挑战"写操作单线程"原则的实验，它的合并与验证机制怎样处理冲突的写入，是最值得细读的部分。

最后是一个关于证据本身的问题。跨类的 **[LLM Agents Can Easily Tamper With Their Own Traces](https://arxiv.org/abs/2609.30266)**（`2609.30266`） 研究本地智能体能否修改自己的执行记录。对研究团队来说，这远远超出了单体安全的范围：如果贡献者能改写失败日志、清除验证记录，就再也无法可靠地追溯谁提出了结论、谁检查过它。审计记录和正式结果应当存放在贡献者无权随意改写的位置，可编辑的工作笔记和不可任意覆盖的证据记录也要分开。

[Why Do Multi-Agent LLM Systems Fail?](https://arxiv.org/abs/2503.13657)的 MAST 分类提供了一个跨任务的观察框架：组织设计、成员之间的不一致和验证失误，可以分别定位。它和开放式数学发现环境的严格结果验证、Agensh 的运行组织、日志完整性研究放在一起，正好串成一条链：先弄清怎样干活，再确认干对了没有，最后把证据妥善保存下来。单靠一个最终分数，概括不了一支团队的能力。

研究性的协作，还应当允许部分失败公开留下来。共享目录如果只保留最好的成果，后来的成员就可能一次次重复已知无效的方向；如果每次修改都覆盖旧文件，推理的来源也会随之丢失。可以为每份成果保留提出者、依赖关系、验证状态和反例，并把"暂时有效"和"已通过独立复核"区分开。这些机制保证不了一定会有新发现，但能让别人判断一项发现是否可信。

## 四、方法对照：组织设计的收益与代价

读完七个分支，可以发现它们改动的对象其实就那么几类：任务怎样分工，成员怎样选择，信息怎样共享，人怎样参与。下面这张表把这些设计对象和它们的代价、检验条件放在一起。读表时可以一直拿主线上的那几条原则去对照：新增的组织有没有带来独立的信息，交接是否按上下文边界进行，写操作有没有唯一的负责人，验证是否独立于被验证者。如果这些问题都答不上来，新增的组织多半只是带来了更多调用。

| 问题 | 方法 | 主要代价 | 重点检验条件 |
|---|---|---|---|
| 任务怎样分工 | 固定流程、动态拓扑、结构码本 | 搜索组织与额外交接 | 同运行时、同预算下的真实遵循 |
| 谁适合合作 | 伙伴探索、模型池选择、团队策略学习 | 试探成本和选择错误 | 超过强单体与独立尝试的增益 |
| 失败该改谁 | 顺序干预、技能贡献分配 | 重跑与多成员交互混杂 | 联合故障、跨任务迁移 |
| 信息如何共享 | 公共目录、共享状态、分层策略 | 同步、冲突、泄露与传播风险 | 内容作用域与过期规则维护 |
| 用户怎样模拟 | 人格库、行为采样、多模拟器训练 | 校准、合成偏差与评测成本 | 未见用户和真实长期行为 |
| 人如何参与 | 个体评价细则、多轮需求追踪、工作流评价 | 人的反馈与核验负担 | 长期净价值、学习与可恢复性 |
| 大团队如何可靠 | 异步任务认领、独立验证、受保护审计 | 总计算、合并和验证成本 | 长期复现、责任追踪与成果真实性 |

这张表不是系统排名。拓扑、成员模型、工具、任务可分解性和验收方式往往同时影响结果，做研究时应尽量把其他因素固定住。做应用时，则先去找真实的瓶颈：资料不够，就增加独立的证据来源；检查缺位，就补上验证环节；人数往往是最后才需要动的那个变量。这和 Anthropic 2026 年那篇指南的建议如出一辙，先用最简单的可行方案，有证据时再加复杂度。

## 五、开放问题与研究机会

回到开头那个组会前的一周。查文献的那组 agent 之所以顺利，是因为它们做的是读，各自的线索彼此独立，汇总时只需要去重；改代码的那组之所以出事，是因为它们同时在写，每一处修改都带着别人看不见的决定，最后又没有一个独立的人或 agent 去验收。这一个故事里，其实藏着协作研究眼下最大的几道坎：什么任务值得拆，拆开后怎样传递真正有用的信息，长期合作中人和 agent 怎样共同维护一份可以恢复的状态，以及共享的经验怎样不越过个人和责任的边界。下面四个问题按这个顺序排列，每一个都还有大片空白，适合作为选题的起点。

**1. 如何根据任务结构决定是否协作，以及怎样组织协作？**

有些任务可以并行拆分，有些任务的每一步都严格依赖上一步的结果，同一种组织方式放在这两类任务上，可能一边节省时间，一边徒增等待。Google 那组规模研究已经给出了一个起点，用任务性质预测最优架构，在未见配置上能选对大多数情况，可它覆盖的基准和架构仍然有限。可以继续研究怎样用依赖关系、信息分布和验收成本来预测组织收益，并允许系统在执行中途重新分工。对照组应当包括强单体、等预算的独立尝试和实际协作，以便分清收益来自能力互补还是额外计算。组织选择规则还需要在没见过的任务上检验，只解释已经成功的团队案例说服力不够。

**2. 如何让通信提供可核查的新信息，避免形成错误共识？**

同源的模型、共享的草稿和相同的资料，很容易产生相关的错误，多数人赞同构不成独立证据。Cognition 用不共享上下文的审查者取得了好效果，这提示我们，有时候少共享一点反而更好；可另一方面，Walden Yan 2025 年的原则又要求共享完整轨迹。什么信息该共享、什么信息该隔离，至今没有一般性的答案。研究机会在于设计带来源的交接、保留分歧和选择性传递信息的机制，让接收者可以检查关键结论，又不必把全部工作重做一遍。可以比较独立检索、只共享答案、共享过程发现和完整协作这几种设置，并通过删除或错配消息来检验内容的贡献。实验中还要控制上下文预算、工具访问和行动节奏，避免把关闭通信后的调度变化误当成信息本身的作用。

**3. 如何使人机团队在长期任务中保持共同状态与可恢复性？**

长期任务里，目标、人员和工具都会变化，人的介入也可能承担需求澄清、专业判断或授权等不同职责。可以研究一种持续更新的共享工作状态，明确谁能修改目标、合并成果、停止执行和撤销操作。Anthropic 在生产中遇到的问题很能说明难度：agent 长时间运行，错误会不断累积，系统必须能从检查点恢复，升级部署时还得照顾到正在运行中的 agent。评价时应检查参与者能否理解尚未完成的依赖、定位错误并恢复旧版本，同时把核查、等待和返工的时间都算进去。人在环中的价值，取决于他真实拥有多少控制能力，确认按钮被点了多少次说明不了什么。

**4. 如何在共享经验的同时保留个性化与责任边界？**

个人的偏好未必适合作为团队规则，一次局部的成功也未必适用于其他角色。研究机会在于为共享策略保留来源、适用条件和修改责任，把公共事实、任务进度和私有信息区分开。撤销个人数据或纠正错误结论时，还需要追踪由它派生出来的那些团队规则；持续协作时，失败和反例也应当保留下来，免得后来的成员重复无效的尝试。只有这样，才能判断一支团队积累下来的是可靠的经验，还是仅仅是越来越多的讨论记录。
