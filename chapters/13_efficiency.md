# 13｜效率与循环架构：少算一些，真的会更快吗？

[首页](../README.md) · [专题索引](../README.md#topics) · [文献目录](../catalog/13_efficiency.md)

## 方向背景：为什么效率必须按完整任务衡量

设想让一个编程 agent 去修一个仓库里的 bug。它先读需求，再列目录、打开几个文件、跑一遍测试、看报错、改两行代码、再跑测试，前前后后五十来步才收工。每一步，它都要把系统提示、工具说明和到目前为止的全部历史重新交给模型，模型读完这一大段上下文，最后只吐出一小段函数调用，接着就是等工具返回。Manus 团队在一篇工程博客里给过一个很直观的数字：他们的 agent 平均每产出 1 个 token，要先读进去大约 100 个 token。换句话说，这样的任务里，模型大部分时间在“读”，很少在“写”，中间还夹着大量等待工具的空档。

这就是效率问题在 agent 时代的样子。过去谈推理加速，默认的场景是一问一答：一段提示进去，一段回答出来，量的是每秒生成多少 token。可一旦模型被放进多轮循环，成本就从单次调用摊到了整个任务上：上下文越滚越长，同一段前缀被反复读取，多个子 agent 并行运行，工具执行的时间也算在等待里。Anthropic 在介绍自家多 agent 研究系统时说，agent 通常比普通对话多用约 4 倍的 token，多 agent 系统则多用约 15 倍。效率决定的因此远不止账单，它还决定 agent 一次能承受多少探索、多少回溯，以及能不能部署在有限的硬件上。

难点在于，“快”是一个牵涉很多层的结果。参数少了，运算量未必少；运算量少了，延迟未必低；单个算子快了，瓶颈可能转移到缓存搬运、请求排队或者工具等待上。循环架构用同一组参数反复加工，省的是权重，多花的是运算；量化省的是存储和带宽，代价是误差；推测解码省的是串行等待，代价是草稿被拒绝时的浪费。每条路线省下的是不同的资源，只有放回具体的工作负载、硬件和质量要求里，才能判断它到底让任务快了多少。本章想帮你建立这样一种习惯：看到一项加速，先问它省了哪一种资源，再问这份节省能不能一路兑现到完整任务上。

## 一、先分清几个容易混在一起的概念

读效率方向的论文，最容易被几组相近的词带偏。这里先把它们摆开说清楚。token、Transformer、训练与推理等基础概念可以查阅 [LLM 前置知识](../docs/llm_primer.md)。

第一组是**几种不同的预算**。参数量描述模型有多少独立的权重；对 MoE 来说，还要区分总参数和每个 token 实际激活的参数。FLOPs 描述浮点运算的次数，它数不进等待和数据搬运。显存里装着权重、计算中的临时张量，以及历史 token 的 KV 缓存。延迟是一个请求从发出到拿到结果花的时间，吞吐量是单位时间里处理了多少请求或 token。这几样东西经常朝不同方向走：参数少的模型可能多算，多算的模型可能因为批量大而吞吐更高，吞吐高的系统又可能让单个请求排更久的队。读论文时，第一件事就是看清它省的是哪一项，又是拿哪几项做了匹配。

拿循环模型来说。让同一组参数多次加工一个位置的内部表示，每多转一轮，存储的权重基本不变，实际执行的运算却跟着增加；循环之外的输入输出模块、注意力的组织方式、是否提前停下，又都会改变每一轮的成本。所以参数复用首先改变的是权重的共享方式，计算量和延迟会怎样变化，要看具体结构再算。和不共享参数的模型比较时，“参数量相同”与“计算量相同”是两种条件，想同时匹配好几项预算，往往还得调整宽度、专家配置或层的布局。[SMELT](https://arxiv.org/abs/2609.01343) 这类工作的价值，正在于先把预算约束摆明，再比较质量，这样额外计算带来的收益就不会被整个记在架构的功劳簿上。

第二组是**预填充和解码**。生成一段回答分两个阶段：预填充一次性处理已有的提示，解码再一个接一个地生成新 token。前者可以并行，后者每一步都要等上一步。长输入短输出和短输入长输出，压力落在完全不同的地方。agent 的工作负载更特别，它会反复读取同一段越来越长的前缀，发出大量短小的调用，再停下来等工具返回。因此一张完整的性能卡至少要写明输入输出长度、并发数、请求到达的方式、设备、数值精度、缓存策略、质量要求和失败重试。只测单次模型调用，得到的是模型性能，离完整任务的成本还隔着好几层。

和预填充、解码紧密相关的是 **KV 缓存**。它保存注意力计算中已经算好的键和值，让后续生成不必重新处理全部历史。它占多少显存，取决于同时处理多少条序列、每条保留多长历史、有多少层或多少组注意力头需要各自保存状态，以及每个数值用多高的精度存储。并发增加、历史变长或者独立状态组变多，缓存都会跟着长。实际分配时还有实现上的细节：不同序列长度不一，分页和管理信息会占额外空间；滑动窗口可以限制保留多少历史，共享前缀和跨层复用则可能省掉重复的存储。还要提醒一点，独立的缓存状态组和独立的权重模块是两回事，循环轮次即使共享权重，也可能各自产生需要保存的键和值，所以参数复用能不能省缓存，要看具体实现。[PagedAttention](https://arxiv.org/abs/2309.06180) 则提醒我们把“逻辑上需要保存多少”和“实际分配得有多高效”分开看：减少碎片、复用已有状态，每个状态的大小没变，显存利用率却能明显提高。

第三组是**三种“循环”**。跨深度的循环，是在同一个 token 的表示上反复做变换；跨时间的递归，是把状态一路带到后面的 token；工具循环，则是模型和外部环境之间一轮轮的交互。三者都叫循环，缓存方式、训练方法和验证要求却各不相同。另外要记住，有效深度描述的是执行路径有多长，拿它直接衡量模型想得好不好并不合适。

第四组是**精确加速和近似加速**。精确执行优化尽量保持目标函数或目标分布不变，满足校正条件的推测采样就属于这一类；近似优化接受一定误差，换取存储或运行上的收益，量化、跳层和某些缓存裁剪属于这一类。近似方法完全可以可靠，前提是讲清楚误差预算，并画出完整的质量与成本曲线，挑出最省的那一个点来报告是远远不够的。

最后一组是**怎样把质量和成本放进同一个对照**。一种方法在增加预算后提升得更快，未必说明它在实际可用的预算下已经更好，如果起点低，增幅再大也可能追不上另一种方法。所以一份可信的报告要同时回答三个问题：用相同预算时谁做得更好，达到相同质量时谁花得更少，放进真实系统后谁更快交付结果。这三个问题分别对应方法效果、资源效率和可部署性。比较时任务集合与质量标准要保持一致，等待、工具调用和失败重试也要算进端到端成本里。对 agent 来说，最终合适的指标往往是同一质量门槛下每个成功任务花掉的时间和资源，单看输出速度只能说明其中一小部分。

## 二、发展主线：从一个算子到一整个任务，时间花在哪里

这条主线以《How To Scale Your Model》推理一章的展开顺序为骨架，再用 Horace He 的三种瓶颈作为最底下的一层，用 Lilian Weng 和 Manus 的文章补上架构与 agent 两层。把它们叠在一起，效率研究的这些年可以读成一架由内向外的梯子：每往外走一层，要考虑的东西就多一些，局部的节省也就越难原样兑现到最终的等待时间上。

### 第 1 层：先弄清楚卡在哪里

Horace He 在 2022 年那篇文章里打过一个比方：GPU 像一座工厂，计算单元是车间，显存是仓库，数据要从仓库运到车间才能加工。车间再快，运货的路堵了，整座工厂照样闲着。他由此把耗时分成三块。第一块是计算，主要是大矩阵乘法，这是你花钱买 GPU 想要得到的东西。第二块是带宽，像逐元素的余弦、归一化这类操作，几乎所有时间都花在把数据读进来、写回去上，算力再强也帮不上忙。第三块是开销，Python 解释器、框架分发、内核启动都在这里，它通常不随问题规模增长，所以一个简单的诊断方法是把批量翻倍，看运行时间是否也大致翻倍。

这篇文章的重要性在于它给后来的一切优化定了调子：先诊断，再动手。它举的 BERT 例子很能说明问题，非矩阵乘法的操作只占约 0.2% 的浮点运算，可它们的实际算力利用率远低于矩阵乘法，在运行时间里占了不小的份额。算子融合之所以被他称为深度学习编译器里最重要的优化，就是因为它把好几次显存往返合并成一次。

2022 年的 [FlashAttention](https://arxiv.org/abs/2205.14135)（`2205.14135`）把这个思路用到了注意力上。注意力的公式一个字没改，作者通过分块计算、避免把完整的注意力矩阵写回显存，大幅减少了数据搬运。它让大家意识到，算子内部的数据流动本身就是算法的一部分：公式层面算得一样多，系统性能可以差很多；反过来，公式层面算得更少，也可能因为执行不规则而变慢。低精度这条线也从这一层开始。2022 年的 [LLM.int8()](https://arxiv.org/abs/2208.07339)（`2208.07339`）发现大模型里会冒出一些系统性的离群特征维度，于是把它们单独留在 16 位里计算，其余绝大部分数值用 8 位；同年的 [GPTQ](https://arxiv.org/abs/2210.17323)（`2210.17323`）用近似的二阶信息做一次性的后训练量化，把权重压到每个 3 到 4 位。两篇共同说明，位宽降下来之后，误差落在哪里、算子能不能真的用上低精度，决定了收益能不能兑现。本章三.7 的新论文就接在这里。

### 第 2 层：一次生成里，解码被带宽卡住

把视角从单个算子放大到一次完整的生成，问题的形状就变了。kipply 2022 年的博客用纸笔算清了这件事。每生成一个 token，前向计算大约需要参数量两倍次的浮点运算，同时要把全部权重从显存里读一遍。A100 的算力和带宽之比约为 208，意思是每读进一个字节，要做两百多次运算才能让计算单元忙起来。解码一次只处理一个 token，批量又小的时候，运算远远填不满这个比例，于是时间几乎全花在读权重上。《How To Scale Your Model》用 TPU v5e 做了同样的推算，结论是 bf16 下大约要攒到 240 个 token 的批量，解码才能摸到算力上限。预填充正好相反，长提示天然带来大量可以并行的运算，它是受算力限制的。

这两个阶段的不对称，解释了后来几乎所有推理优化的动机。既然解码是在“读”，那就想办法少读：要么让每一步读的东西变少，要么让一次读进来的东西多干点活。

让 KV 缓存变小是第一条路。早在 2019 年，Noam Shazeer 的 [Fast Transformer Decoding: One Write-Head is All You Need](https://arxiv.org/abs/1911.02150)（`1911.02150`）就提出多查询注意力（MQA）：所有注意力头共用一组键和值，解码时要反复读入的张量一下子小了很多，质量只略有下降。2023 年的 [GQA](https://arxiv.org/abs/2305.13245)（`2305.13245`）取了个折中，让若干个查询头共享一组键值，并且展示了只用原始预训练约 5% 的计算，就能把现成的多头模型改造成这种结构。2024 年的 [DeepSeek-V2](https://arxiv.org/abs/2405.04434)（`2405.04434`）提出多头潜在注意力（MLA），走得更远，把键值压进一个低维的潜在向量，报告的 KV 缓存比自家 67B 模型减少了 93.3%。《How To Scale Your Model》把这些手段和局部注意力、跨层共享、量化放在一起，统一解释为减少显存流量、换取更大批量的办法。

当历史长到缓存装不下时，另一组工作开始考虑“丢掉一部分”。2023 年的 [H2O](https://arxiv.org/abs/2306.14048)（`2306.14048`，Heavy-Hitter Oracle for Efficient Generative Inference of Large Language Models）观察到少数 token 贡献了大部分注意力分数，于是只保留最近的 token 和这些“重击手”；同年的 [StreamingLLM](https://arxiv.org/abs/2309.17453)（`2309.17453`，Efficient Streaming Language Models with Attention Sinks）发现模型会把大量注意力投向开头几个 token，哪怕它们在语义上并不重要，保住这几个“注意力汇”再加一个滑动窗口，就能稳定地处理很长的输入流。它们为后来的缓存裁剪研究立下了基线，也留下一个问题：被丢掉的那部分，在哪些任务上其实是关键证据？本章三.6 正是在追问这个问题。

让一次读进来的东西多干点活，是第二条路。2022 年底 Google 的 [Speculative Decoding](https://arxiv.org/abs/2211.17192)（`2211.17192`）和 2023 年初 DeepMind 的 [Accelerating Large Language Model Decoding with Speculative Sampling](https://arxiv.org/abs/2302.01318)（`2302.01318`）几乎同时提出了同一个想法：先让一个便宜的草稿模型猜几个 token，再让大模型一次性并行验证，配合一套接受与拒绝的校正规则，输出分布可以和直接用大模型采样保持一致。后者报告在 70B 的 Chinchilla 上取得了 2 到 2.5 倍的解码加速。2024 年的 [EAGLE](https://arxiv.org/abs/2401.15077)（`2401.15077`）把草稿从“猜 token”改成“猜目标模型倒数第二层的特征”，再喂入提前一步的 token 序列来降低不确定性。《How To Scale Your Model》对推测解码的评价很到位：它用额外的运算换更低的延迟，在批量受限、算力闲置时最有用。本章三.5 的新论文都在这条线上，讨论的是草稿从哪里来、缓存怎么省、工作负载变了怎么办。

### 第 3 层：很多请求一起来，调度成了算法

真实的服务里，几十上百个请求同时到达，长短不一，有的刚开始预填充，有的已经生成到一半。批量越大吞吐越高，可 KV 缓存会随批量线性增长，单个请求的等待也会变长。《How To Scale Your Model》把这个两难放在推理一章的中心：同一套硬件，追求低延迟和追求低成本会走向完全不同的配置。

2023 年的 [PagedAttention](https://arxiv.org/abs/2309.06180)（`2309.06180`）借用操作系统的分页思想管理 KV 缓存，把每条序列的缓存切成小块按需分配，减少碎片，让同一块显存能装下更多并发请求，配套的 vLLM 也成了常用的开源推理引擎。同年的 [SGLang](https://arxiv.org/abs/2312.07104)（`2312.07104`）提出 RadixAttention，用一棵基数树组织缓存，让共享前缀的请求复用已经算好的键值。这正是 Manus 文章里那句“KV 缓存命中率最重要”在系统一侧的落脚点：agent 的系统提示、工具说明和对话历史大段重复，前缀复用得好，预填充就能省掉一大半。

预填充和解码混在一起调度，又会互相干扰。2024 年的 [Sarathi-Serve](https://arxiv.org/abs/2403.02310)（`2403.02310`）把长预填充切成大小相近的块，和正在进行的解码拼在同一批里执行，新请求进来时不会卡住已经在跑的请求。同年的 [DistServe](https://arxiv.org/abs/2401.09670)（`2401.09670`）干脆把两个阶段放到不同的 GPU 上，按首 token 延迟和每 token 延迟两个目标分别配置资源。《How To Scale Your Model》把连续批处理、前缀缓存和预填充解码分离并列为服务引擎设计的几项关键技术。这一层的教训是，一项模型层面的节省，要接进这些批处理和缓存机制里才能变成真实的收益；接不进去，单独测时再快，上线后也可能变慢。本章三.8 的 vSkipper 恰好给出了这样一个例子。

### 第 4 层：每个 token 该分到多少计算

前三层讨论的都是“给定一个模型，怎样把它跑快”。还有一条更早就开始的线索，从架构入手，问的是每个 token 到底该分到多少计算。

2017 年的 [Attention Is All You Need](https://arxiv.org/abs/1706.03762)（`1706.03762`）用注意力取代了循环，让序列中所有位置可以并行计算，奠定了今天大模型的基本结构。仅仅一年后，Dehghani 等人的 [Universal Transformers](https://arxiv.org/abs/1807.03819)（`1807.03819`）又把循环请了回来，这次换成在深度方向上循环：同一组层反复作用于每个位置的表示，循环次数可以由自适应计算时间来决定。Lilian Weng 在《Why We Think》里点明了它和普通 Transformer 的关系：循环步数固定时，它就等价于一个跨层共享参数的多层 Transformer。这里说的自适应计算时间，出自 Alex Graves 2016 年的 [Adaptive Computation Time for Recurrent Neural Networks](https://arxiv.org/abs/1603.08983)（`1603.08983`），让网络自己学会在每个输入上走多少步。Weng 评价说，这项工作早于大模型，却开创了同一个方向。

另一条分配计算的路是稀疏激活。2021 年的 [Switch Transformers](https://arxiv.org/abs/2101.03961)（`2101.03961`）让每个 token 只经过众多专家中的一个，总容量可以做得很大，单个 token 的计算却保持不变。它把“模型大小”拆成了存储容量和活跃计算两项，同时带来了路由和负载均衡的新问题。2023 年的 [Mamba](https://arxiv.org/abs/2312.00752)（`2312.00752`）则从状态表示出发，用选择性状态空间模型替代注意力，生成时只需维护固定大小的状态，它改变的是信息如何被保存在模型里。

这条线在 2025 年迎来了一个转折。Geiping 等人的 [Scaling up Test-Time Compute with Latent Reasoning: A Recurrent Depth Approach](https://arxiv.org/abs/2502.05171)（`2502.05171`）训练了一个 35 亿参数、用 8000 亿 token 训练的模型，在标准 Transformer 上叠一个可以反复调用的循环块，测试时多转几圈，推理基准上的表现就随之上升，某些情况下的计算负载相当于一个 500 亿参数的模型。Lilian Weng 把这类工作看作纵向的“多想一会儿”，和横向多生成思维链 token 互为补充；她也坦率地指出了问题：训练时只反传最后几轮，隐藏状态容易塌缩成同一个值，需要小心调参，而且增加循环次数后的收益会饱和，能否外推到更多轮仍是未知数。

本章前四个分支的新论文几乎都在回应这些问题。循环的收益到底来自结构，还是来自多花的计算？共享参数被反复使用，训练怎样才能稳定？哪些样本值得多转几圈，停止判断本身又要花多少？已经训练好的模型能不能不重训也循环起来？

### 第 5 层：放大到完整任务

最外面一层是 agent 本身。到这里，前面几层的问题全都还在，又叠加了新的结构。Manus 的文章说得很直白：agent 的输入输出比大约是 100 比 1，上下文每一步都在变长，输出却往往只是一段结构化的函数调用，所以预填充和缓存命中率才是成本的大头。他们为此做的一系列取舍，比如保持前缀稳定、上下文只追加不回改、序列化时保证 JSON 键的顺序固定、用屏蔽 logits 代替中途增删工具，本质上都是在服务第 3 层的前缀缓存。把文件系统当作外部记忆，网页内容可以从上下文里丢掉、只要留下 URL 就能找回，则是在第 2 层的缓存压缩之外另辟了一条可恢复的路。

Anthropic 的多 agent 文章补上了另一面。并行的子 agent 和并行的工具调用能把复杂查询的研究时间缩短最多 90%，可总 token 用量也成倍上升。这说明在任务层面，延迟和成本可以朝相反的方向变化，值不值最终取决于任务本身有多大价值。这一层的研究目前还很零散，本章三.4 讨论组合工具调用，三.6 讨论长上下文，三.8 讨论完整服务，都只碰到了它的一角。2026 年的综述 [Toward Efficient Agents](https://arxiv.org/abs/2601.14192) 开始把这些碎片收拢起来：它把 agent 的成本拆成 token 数、延迟和工具调用次数，主张在效果与成本的帕累托前沿上比较方法，并按记忆、工具使用和规划三块梳理已有工作；它观察到的几条共同原则，比如给上下文设上限、在奖励里惩罚多余的工具调用，和 Manus 的经验遥相呼应。

### 边界：省下的东西能不能兑现

梯子每往外走一层，局部节省被稀释或抵消的机会就多一些。kipply 自己的估算和实测就差了约三成，原因是带宽达不到标称值、中间操作有额外开销、内核启动也要时间。到了服务层，排队和批处理会改变每个请求的实际延迟；到了任务层，工具等待和上下文重读又可能把模型层面的加速吞掉。本章各分支里有不少负结果，比如门控循环省了内存却增加了延迟、跳层脱离服务引擎后反而变慢、复杂的缓存选择器输给了保护提示后的随机裁剪，它们的价值就在于准确地标出了这些兑现失败的位置。2026 年 7 月一篇关于服务系统中 KV 缓存优化的[综述](https://arxiv.org/abs/2607.08057)从更大的范围印证了这一点：作者发现，研究最多的压缩类方法贡献了大部分显存节省，真正直接作用于延迟和吞吐的却是调度类方法，压缩又很少和调度、放置一起设计；能耗普遍没人报告，每一类方法都会带来质量损失，尾延迟和最坏情况下的失效也常常被平均指标掩盖。第四节的对照表会把它们集中摆出来。

## 三、前沿研究方向

下面八个分支收录的都是 2026 年的新论文。前四个分支集中在主线的第 4 层，讨论循环与自适应深度这类“给每个 token 分配计算”的架构问题；后四个分支沿着第 2、1、3 层往外走，分别对应推测解码、长上下文缓存、低精度和完整服务。每个分支开头先交代它要回答的问题，再标出它在主线上的位置。读这些论文时，建议始终带着两个问题：它省下的是哪一种资源，它用什么证据说明这份节省在完整任务上依然成立。

### 1. 公平比较：循环收益来自结构，还是额外计算？

让同一组参数多转几轮，模型就能在不增加权重的情况下获得更深的计算路径。这听上去像是白捡的深度，可我们等待的是完整结果，参数文件变小本身并不缩短等待。多转的每一轮都要花时间、花运算，所以一个循环模型比普通模型分数高，首先要问的是：它是因为结构更好，还是因为多算了？这两个问题经常被混在一起。同样模型大小下的能力收益，和同样计算预算下的结构收益，回答的是完全不同的问题，这个分支的论文首先就是在把比较对象厘清。

> 主线位置：第 4 层，循环深度的公平比较。接 Universal Transformers 的跨层共享参数和 Geiping 等人的循环深度模型，同时借用 Switch Transformers 把“总容量”和“活跃计算”分开记账的思路。

有一种做法干脆绕开了深度方向。**[Hidden Decoding at Scale](https://arxiv.org/abs/2607.08186)**（`2607.08186`）沿序列维度为每个 token 引入多条内部计算流，用流内与跨流的注意力来组织这些额外计算，避免单纯沿网络深度循环。它保持主干层数不变，代价是需要继续预训练，还会增加内部序列和缓存的开销。拿它和深度循环比较大规模训练下的兼容性很合适，只是要记住“主干没有扩大”的意思仅限于层数，训练和推理成本都实打实地增加了。

真正把预算账算细的是 **SMELT（`2609.01343`）**。它在每 token 运算量、非嵌入参数和 KV 缓存三项都接近匹配的条件下研究循环 MoE，设计是让中间部分层循环两次。[论文](https://arxiv.org/abs/2609.01343)报告，在所拟合的计算最优前沿上节省 6.8%—18.0% 的训练 FLOPs，优势还迁移到了下游基准，其中代码任务上的收益最大。这里的“计算最优前沿”，指的是在不同计算预算下，通过选择模型规模和训练量所能达到的最佳损失边界。这项实验瞄准的正是那个关键的混杂因素：参数相同的循环模型，实际可能多算了很多；而在同时匹配多项预算之后，作者仍然观察到了收益。当然，这些结果有其模型规模、数据和拟合范围，训练计算上的节省也没法按相同比例直接换算成推理服务的加速。

**Loop the Loopies!（[`2607.16051`](https://arxiv.org/abs/2607.16051)）**同样在计算匹配的条件下比较循环 MoE 和普通 Transformer。它和 SMELT 适合放在一起读，只是两篇都写着 matched compute，预算口径却未必相同：预训练数据、有效层数、激活专家数、训练时长和调参范围都可能有差别。更有说服力的做法是报告完整的质量与计算曲线，避免拿某个循环模型的最佳点去对照普通模型一个没有调好的点。

**MoRE（[`2609.18176`](https://arxiv.org/abs/2609.18176)）**把共享的粒度从整个循环块细化到邻近层之间的专家池复用，再用深度嵌入帮助专家识别自己正在服务哪一层。它让人看到，参数复用可以有很多种粒度，共享整层、共享专家、共享缓存，各自带来的信息约束都不一样。真正的研究问题是哪些模块确实在重复做相似的事，哪些位置必须保留独立的容量；把一切权重共享都笼统地叫作“更深的思考”，会把这些区别抹掉。

### 2. 稳定循环：重复访问会改变训练动力学

Lilian Weng 在介绍循环深度模型时特意提到，这类模型训练起来很脆弱，隐藏状态可能塌缩成同一个值。问题的根源在于共享参数被多次使用：同一次参数更新会同时作用于好几个计算阶段，对某一轮有利的变化，可能破坏另一轮；梯度的大小和状态的分布，也可能随循环次数一起漂移。所以研究循环的稳定性，要把初始化、归一化、训练时的深度和测试时的深度分开来看，还要观察多轮之后的状态是否收敛到有用的结果，训练损失下降只是其中一个信号。

> 主线位置：第 4 层，循环模型怎样训得稳。接 Geiping 等人在循环深度模型中用到的随机循环次数与截断反传，以及 Universal Transformers 的共享参数结构。

**DeepLoop（`2607.13491`）**从梯度的角度把问题讲清楚了：共享参数会汇聚多次访问带来的梯度，在下一次前向里又被多次使用，因此普通深层网络的残差缩放规则没法直接照搬。[论文](https://arxiv.org/abs/2607.13491)用访问对齐来分析这种效应，并据此修改了缩放配方。结果来自所测的小中规模语言模型，还谈不上对任意架构的稳定性保证。它设计了一个很好的对照：没有参数复用时，新配方应当基本不改变表现，只有启用复用后才显出针对性的收益。

**Gated Recurrent Transformers（`2608.15062`）**在固定的输入和输出模块之间放一个共享核心，用门控调节每一轮的更新幅度。[论文](https://arxiv.org/abs/2608.15062)坦率地给出了一项具体的权衡：参数量和峰值解码内存下降了，可在某个大规模设置下，编译后的生成延迟仍然增加。这算不上失败，它把省了什么、付出了什么都摆在了明处，恰好印证了主线第 1 层的判断，省下的显存和省下的时间是两笔账。**LoopMTP（[`2608.03624`](https://arxiv.org/abs/2608.03624)）**换了个角度，用未来 token 目标帮助不同循环轮次分担任务，说明训练目标本身也能塑造复用的方式。

**Thinking with Looped Flows（[`2609.11801`](https://arxiv.org/abs/2609.11801)）**针对的是只反传少数几轮循环带来的训练困难，这正是 Weng 提到的截断反传，它的办法是引入局部去噪目标。**Looped Transformers as Optimizers（[`2609.37379`](https://arxiv.org/abs/2609.37379)）**则把状态更新解释为对某个局部目标的优化步骤，由此推导出循环变换的形式。前者改变了训练信号，后者约束了变换的结构。它们都提供了有用的设计工具，可哪一篇都没有证明多转几轮总是有效，在训练范围之外的深度和不同任务上，稳定性仍然要单独测。

### 3. 深度诊断与自适应：更陡的曲线也可能更差

Graves 提出自适应计算时间时的愿景很美好：简单的输入早点停，困难的输入多想一会儿。可停止器本身也会犯错，停早了可能漏掉必要的推理，停晚了可能在错误的方向上越陷越深。要评价一种动态深度方法，得在相同的平均预算下比较样本之间的分配是否合理，只看最大深度下的表现会把真正的问题藏起来。深度带来的收益、做停止判断的成本、以及分布变化之后停止器是否依然校准，这三件事要分开测。

> 主线位置：第 4 层，自适应深度。接 Adaptive Computation Time 和 Universal Transformers 的动态停止，也回应 Lilian Weng 对循环深度“增加轮数后会饱和”的疑问。

**What Makes Recurrence Effective（`2609.36636`）**在知识类和推理类任务上比较了训练范围内外的循环预算。[论文](https://arxiv.org/abs/2609.36636)报告，推理任务可以从更多循环中受益，知识任务的表现却会下降，难题也不总是能从更多轮计算中获益；输入输出层的布局、历史状态如何注入、是否有时间条件，都会影响结果。这些发现提醒我们，循环次数没法当作普遍有效的“思考预算”来用，困难样本也不会自动地值得多算。

**Beyond Depth Truncation（`2609.19934`）**进一步质疑了一种常用的测法。截断深度看起来只是少转几圈，实际上同时减少了模块调用、改变了实际执行的计算，还可能把读出头放到训练时没见过的残差分布上。[论文](https://arxiv.org/abs/2609.19934)提出了一套控制协议来拆开这些因素。它说明，即使质量随深度下降，也没法立刻断定被删掉的每一轮都做了新的、有用的推理，因为测量这一干预本身就会造成损伤。这和 Horace He 强调的“先诊断再优化”是一个道理，诊断工具不可靠，后面的结论就跟着不可靠。

**TaH2（`2609.35748`）**研究按 token 分配循环次数。[论文](https://arxiv.org/abs/2609.35748)先指出一个容易被忽视的现象：一些循环模型的准确率随计算增长得更快，可因为起点低，在相同的计算点上仍然落后；然后它用前瞻深度监督来训练迭代决策器。剩下的开放问题是决策器本身的开销、判断失误的代价，以及跨任务的迁移。同一组质量与计算曲线，应当同时展示增长幅度、相同预算下的绝对水平和能达到的最好结果，单凭斜率来概括测试时扩展的能力，很容易得出误导性的结论。

### 4. 冻结模型与局部回流：有些循环可以免去重训

前面三个分支讨论的循环模型，大多要从头训练或者大规模继续预训练，成本很高。一个自然的想法是：能不能在现成的模型上动点小手术，让它把某些计算再用一遍？这类局部修改通常便宜得多，但也受制于原模型已有的表示和接口。而且冻结权重往往伴随着其他组件的训练，适配器、停止器或选择规则都可能需要学习。比较这类方法时，要说清楚哪些组件被训练了、哪些输入被重复处理了，以及新增的计算是在提供新信息，还是只是把已有的错误再重复一遍。

> 主线位置：第 4 层向第 5 层过渡。架构上接 Universal Transformers 的深度循环和跨时间递归，任务上接 agent 的工具循环；预填充代价的分析则回到第 2 层的预填充与解码之分。

**Recirculation（`2608.17981`）**研究在现成模型上做推理时的结构增强，把较深层的信号反馈给较早的位置。[论文](https://arxiv.org/abs/2608.17981)有一个很重要的限制：生成阶段增加的延迟很小，但预填充需要串行处理。回想开头那个读 100 个 token 才写 1 个的编程 agent，对这种长提示、短回答的工作负载，预填充的代价很可能决定净收益是正是负；只展示生成速度，就会把主要成本藏起来。**Write Back the Δ（[`2609.32457`](https://arxiv.org/abs/2609.32457)）**则只反馈层与层之间新增的信息，避免把整个状态回传，并且学习如何选择和组合回流路径。

**T^2MLR（[`2607.15178`](https://arxiv.org/abs/2607.15178)）**把前一个 token 的中间层表示送入当前 token 的较早层，让中间计算跨越时间延续下去。它和对同一个 token 反复做完整前向是两回事，和把自然语言笔记写进上下文也是两回事，更接近主线里说的跨时间递归。**Looped Language Models Improve Compositional Tool Calling（[`2608.18171`](https://arxiv.org/abs/2608.18171)）**把架构上的收益拿到组合工具任务里检验，并区分了孤立调用和相互依赖的调用。它支持的结论是任务结构值得仔细分析，循环架构的收益没法笼统地全部归功于工具调用格式写得更准。

这组研究共同提出了一个问题：哪些状态值得再加工一遍，哪些状态可以跨步保留？一个可行的实验是固定底座模型和输出预算，分别改变反馈的位置、反馈的内容和循环次数。如果同时增加了可训练模块和测试时计算，就应当承认结论属于整个新系统，把功劳全部记在“冻结模型也能循环”上是不公平的。

### 5. 推测解码：草稿质量、缓存与工作负载共同决定收益

推测解码的账看起来很简单：草稿猜对得越多，大模型被调用的次数就越少。可草稿被拒绝时，花在它身上的计算就白费了；接受率又会随着领域、草稿中的位置和上下文变化，固定的草稿长度不一定适合所有任务。《How To Scale Your Model》提醒过，推测解码是用额外运算换延迟，在批量受限时最划算，批量一大、算力不再闲置，账就可能算不过来。所以这个分支的论文都在联合考虑草稿成本、验证成本、接受长度和并发条件，单单比较一次生成了多少候选 token 说明不了什么。

> 主线位置：第 2 层，让一次读入的权重多干点活。接 Speculative Decoding、Speculative Sampling 的校正规则和 EAGLE 的特征级草稿。

先看草稿本身的质量。**[AdaFlash](https://arxiv.org/abs/2607.19223)**（`2607.19223`）分析了扩散式草稿器在不同领域、不同草稿位置上的接受率波动，再结合在策略蒸馏和自适应机制改善草稿。扩散草稿的双向依赖带来了并行生成的能力，也可能让各个位置的质量参差不齐。这项工作的价值在于把草稿的训练和运行时的分配联系起来，并行草稿是否越长越快，要靠数据说话。

循环模型给推测解码提供了一个天然的草稿来源。**LoopSpec（`2609.17184`）**用早期循环轮次的状态产生草稿，用后期状态验证，并让下一批草稿和当前的验证流水线重叠起来。[论文](https://arxiv.org/abs/2609.17184)宣称在其校正机制下实现了无损解码。在采样模式中，“无损”的含义是保持目标分布，任意两次随机运行逐 token 相同并不在承诺之内。**LoopCD（[`2610.02185`](https://arxiv.org/abs/2610.02185)）**利用早晚循环之间的对比信号来指导选择，它改变的是解码策略本身，虽然也用到了早期状态，却不能因此和 LoopSpec 共享同样的无损保证。

另一组工作关心的是草稿结构怎样适应具体的工作负载。**DeLS-Spec（[`2607.07409`](https://arxiv.org/abs/2607.07409)）**把长短上下文拆开处理来改进并行草稿；**AngelSpec（[`2607.25852`](https://arxiv.org/abs/2607.25852)）**按对话、代码和数学等不同负载协调草稿结构与训练数据。**H-Spec（[`2609.24197`](https://arxiv.org/abs/2609.24197)）**则盯着主线第 2 层的老问题，也就是显存：它复用目标模型的 KV 缓存，再补充最后一个位置的隐藏状态，从而省掉独立的草稿缓存。三篇分别处理草稿依赖、数据分工和状态开销，各有侧重，仅凭接受长度没法给它们排出一个公平的总榜。

最后，目标模型本身也可能在变。**Online Draft Co-Training（[`2609.07108`](https://arxiv.org/abs/2609.07108)）**研究在长期强化学习训练中，草稿和目标一起更新时会遇到哪些系统障碍；**FOVEA（[`2608.22883`](https://arxiv.org/abs/2608.22883)）**研究多模态草稿在什么时候需要多少视觉证据，它指出，给草稿加多少视觉输入，要和草稿任务真正的信息需求相匹配。下一步的实验应当同时报告草稿计算、接受率、验证成本和每个请求的缓存占用，并且分清静态的目标、正在训练的目标，以及视觉状态不断变化的任务。

### 6. 长上下文：压缩历史，不能把关键证据一起删掉

开头那个编程 agent 跑到第五十步时，上下文里已经堆满了文件内容、测试输出和之前的思考。长上下文的效率问题包括三块：处理输入要花的算力，存储缓存要占的显存，以及每一步都要把缓存读一遍的带宽。滑动窗口、状态压缩和外部检索都改变了信息被访问的方式，对需要精确回看某一行代码的任务，影响可能和对只需要大意的任务完全不同。比较这类方法时，要检查质量退化发生在哪一类依赖上，还要确认预填充和解码两个阶段的成本都被算了进去。

> 主线位置：第 2 层，KV 缓存的裁剪与压缩，同时触及第 5 层 agent 的上下文管理。接 H2O、StreamingLLM 的缓存驱逐，MQA、GQA、MLA 的结构性压缩，以及 Mamba 的固定大小状态；Manus 的“可恢复压缩”可以作为任务层面的参照。

**Random Attention（`2609.03430`）**是值得先读的一个负结果。它保留提示，然后在注意力头内随机裁剪推理轨迹，发现在测试设置中，复杂的选择信号带来的收益很有限。[论文](https://arxiv.org/abs/2609.03430)把这一结果和提示的重要性、以及文本和注意力头之间的冗余联系起来。结论是有条件的：它说明的是在保住提示的前提下推理轨迹有相当的冗余，原始提示依然重要，KV 也绝非可以随便删。这也让人想起 StreamingLLM 的发现，开头那几个 token 丢不得。公平的对照必须固定提示的保护方式，否则比来比去，实际比的是谁碰巧保住了题目。

**A Probabilistic Interpretation of KV Cache Eviction（[`2608.28293`](https://arxiv.org/abs/2608.28293)）**把缓存裁剪解释为一种期望估计，并讨论了解码时怎样对被删除的项做校正，相当于给 H2O 这类启发式规则补上了一个统计视角。**HiSparse（[`2608.07009`](https://arxiv.org/abs/2608.07009)）**面对的是另一种瓶颈：稀疏注意力每一步只访问少量位置，可全部历史仍然要放在显存里，于是它采用分层的缓存管理。前者研究近似带来的偏差，后者研究状态应该放在哪里；“访问得少”和“存得少”是两件事，要分开评估。

状态模型提供了更深层的替代方案，思路和 Mamba 一脉相承。**DART（[`2608.02032`](https://arxiv.org/abs/2608.02032)）**从递归状态的键值解释出发改造读取方式，**Maglev（[`2608.02870`](https://arxiv.org/abs/2608.02870)）**使用固定容量的记忆并在训练时加入一致性约束，**Sparse Delta Memory（[`2607.07386`](https://arxiv.org/abs/2607.07386)）**用稀疏寻址扩大递归状态的容量。另外两篇走的是复用路线：**Cross-Model KV Cache Transfer（[`2608.03893`](https://arxiv.org/abs/2608.03893)）**利用同家族模型之间的线性关系复用预填充结果；**DeepSeek-V4.1-Flash（[`2609.19969`](https://arxiv.org/abs/2609.19969)）**把跨层复用、低精度存储和重放组合在一起，延续了 MLA 那条压缩缓存的路线。这些方法省掉的状态不同，需要的校准不同，能恢复的信息范围也不同，长期检索能力和任务质量都要分别测量。

### 7. 低精度：存储位数、运算精度和最终误差是三件事

低精度听起来最直接：位数砍一半，显存和带宽也省一半。可主线第 1 层已经说过，收益能不能兑现，要看量化、反量化以及具体算子是否真的支持低精度运算。LLM.int8() 当年发现的离群特征也提醒我们，平均数值误差很小，并不保证每个关键位置都安全，误差在路由、长链生成或者敏感决策中可能被放大。所以读这类论文要看它报告了哪些东西：实际用的内核、累加时的精度、校准数据，以及最终的任务质量。只凭理论位宽推算部署吞吐，往往会过于乐观。

> 主线位置：第 1 层，算子与数值格式。接 FlashAttention 的“把数据搬运当作算法的一部分”，以及 LLM.int8()、GPTQ 的离群值处理和后训练量化。

**VC-Attention（`2609.15810`）**针对的是视频扩散模型里的注意力，它把值向量平滑和融合的概率转换结合起来，分别对付量化中的离群值和 softmax 的开销。[论文](https://arxiv.org/abs/2609.15810)同时报告了算子层面和整段生成的速度，很适合用来练习区分这两个测量层级。它的结论属于视频扩散这个场景，换到文本模型、换了硬件、序列形态或误差指标，都需要重新测量。

**Breaking the 1.58-bit Barrier（[`2609.16338`](https://arxiv.org/abs/2609.16338)）**从三值权重的符号分布出发研究编码方式，提醒我们平均存储位数和直接参与运算的格式是两个概念。**KronQ（[`2607.07964`](https://arxiv.org/abs/2607.07964)）**把梯度协方差的信息引入后训练量化，和 GPTQ 借助二阶信息指导量化的思路一脉相承；**Quantization Degradation（[`2608.08188`](https://arxiv.org/abs/2608.08188)）**研究量化噪声如何产生、又如何沿网络一层层累积。编码和量化方法改变的是存储方式或误差的分配，退化分析则解释它们在什么条件下会失效，仅凭“位数更低”推断不出延迟更低。

**FlashLoop（[`2609.29812`](https://arxiv.org/abs/2609.29812)）**把跨循环轮次的冗余、稀疏更新和 KV 残差量化组合起来，把第 4 层的循环架构和第 1 层的低精度联合优化。问题在于多个近似叠加之后，每一项单独都很小的误差合起来未必还小。值得保留的研究方法是一个组件一个组件地加进去，观察错误最先出现在哪一类任务、哪一段上下文上；用一个平均分宣布“质量几乎不变”，会把这些信息全部抹平。

### 8. 动态服务与输入表示：把收益兑现到完整请求

一个请求从到达到完成，经过的远不止模型的前向计算，还有排队、通信、媒体预处理、缓存调度和负载均衡。某个算子变快了，瓶颈很可能转移到别的环节；缓存命中率提高了，也可能让设备之间的负载失衡。《How To Scale Your Model》把连续批处理、前缀缓存和预填充解码分离列为服务引擎设计的关键技术，任何新方法都要和这些机制和睦相处才能上线。端到端的比较应当给出请求长度和并发的分布，区分冷启动和热缓存，只展示最有利的那一条吞吐曲线是不够的。

> 主线位置：第 3 层向第 5 层延伸。接 PagedAttention 与 vLLM 的分页缓存、SGLang 的前缀复用、Sarathi-Serve 与 DistServe 的预填充解码调度；输入表示一段则回到每个任务到底有多少 token 这个起点。

**[MiMo-V2.5 全流程推理优化](https://arxiv.org/abs/2607.13095)**（`2607.13095`）把滑动窗口缓存、前缀树、分布式缓存、路由和多模态预处理放在一起优化，展示了架构上的理论节省需要多少工程配合才能落地。**[Non-GPU AI Accelerators 的部署实地研究](https://arxiv.org/abs/2607.08215)**（`2607.08215`）记录了在特定 Ascend 软硬件栈上部署 MoE 和多模态服务时，在算子、数值正确性和维护上遇到的困难。后者是特定配置下的现场研究，结论的适用范围就是那套配置，对其他非 GPU 平台没有定论；两篇合起来说明，迁移和维护的成本同样是效率的一部分。

**vSkipper（`2609.37062`）**的故事很有代表性。它先展示了一个反直觉的现象：跳层方法脱离现代服务引擎单独运行时，反而变慢了；然后它把动态路径重新接回连续批处理、分页缓存和计算图。[论文](https://arxiv.org/abs/2609.37062)控制了提示、请求到达过程、输出长度和启动设置，着重分析了什么时候值得执行路由。它所说的“服务没有额外可分辨的质量损失”，是相对于跳层检查点而言的，这个检查点本身和原模型的质量是否完全一致，是另一个问题。这是一个模型误差和服务误差必须分开看的典型例子。

**You Only Need 2/3 of the Chosen Experts（`2609.25809`）**在多种细粒度 MoE 上研究专家裁剪，相当于在 Switch Transformers 开创的稀疏激活上再省一刀。[论文](https://arxiv.org/abs/2609.25809)报告了指定保留比例下的平均质量和实测速率；这个比例是实验得到的结果，没法当作所有模型都适用的安全常数。尤其要看任务尾部的损失、路由行为和不同的服务后端，平均分不变，可能掩盖了少数依赖稀有专家的任务。

**Objective vs. Search（[`2609.19145`](https://arxiv.org/abs/2609.19145)）**把分词器的训练目标和搜索过程拆开比较。它把效率的起点往前推到了输入表示：token 少了，模型未必更容易学；词表和语言覆盖的变化，又会改变什么才算公平的预算。完整的研究应当同时报告字符数或任务规模、token 数、质量和运行开销。换了分词器之后仍把“相同 token 数”当作相同的数据量，比较就失去了基准。

## 四、跨路线对照：资源节约与适用条件

读完八个分支，可以把它们放回主线的梯子上再看一遍：每条路线省下的资源不同，付出的代价不同，要和对手匹配的条件也不同。减少权重、减少缓存和减少串行等待，最后兑现到端到端收益上的比例各不一样。下面这张表把这些放在一起，最右边一列是判断一项优势能否迁移到你自己的工作负载时，最需要核对的条件。

| 路线 | 主要节省对象 | 可能付出的代价 | 必须匹配的条件 |
|---|---|---|---|
| 循环与专家复用 | 独立权重、部分训练预算 | 更多顺序计算、训练不稳定 | 激活计算、缓存、数据与调参 |
| 自适应深度 | 不必要的重复轮次 | 决策器成本、错误提前退出 | 绝对质量和计算曲线，不只斜率 |
| 推测解码 | 目标模型的串行等待 | 草稿训练、缓存和拒绝开销 | 目标分布、草稿成本、负载 |
| 缓存裁剪与状态压缩 | 长上下文存储 | 关键证据丢失、检索质量下降 | 提示保护、序列长度、任务类型 |
| 量化与编码 | 存储、带宽、部分运算成本 | 误差累积、解码和转换开销 | 硬件、内核与端到端质量 |
| 动态服务 | 有效计算与排队时间 | 路由、同步、批处理破坏 | 到达过程、并发和延迟分位数 |

有几条负结果应当直接写进结论里：门控循环可能省了内存却增加了延迟；Recirculation 的预填充代价不能忽略；更陡的扩展曲线在相同预算下仍可能落后；复杂的 KV 选择器可能输给保护了提示的随机基线；视频内核上的加速，也没法按同样比例搬到智能体任务上。这些结果标出的正是主线“边界”一节里说的兑现失败的位置，它们是判断一种方法是否适用的主要证据，分量一点不比正面结果轻。

## 五、开放问题与研究机会

回到开头那个修 bug 的编程 agent。它五十来步的执行过程里，时间大致花在三个地方：每一步都要重新读一遍越来越长的上下文，有些步骤要想得很深、有些步骤几乎不用想，以及模型之外的工具执行和网络等待。这三处正好对应三个尚未解决的问题：计算该怎样按难度分配，记忆、推理和工具该怎样放在一起优化，以及结构上的优势怎样在真实的硬件和服务里兑现。三个方向都要求在固定的质量要求下比较资源投入。

**1. 如何按任务难度动态分配计算，并保持可控的质量边界？**

那个 agent 在“打开某个文件”这一步和“定位 bug 的根因”这一步上，需要的思考量显然天差地别。固定深度或固定推理预算，会同时在简单步骤上浪费资源、在困难步骤上限制发挥。研究机会在于让循环次数、提前停止、搜索和模型选择依据可以校准的信号协同调整，把 Graves 当年的自适应计算时间真正做到 agent 的每一步上。评价时要特别检查难例和长任务上的退化，平均意义上的计算节省，不能掩盖少数关键步骤上的失败。

**2. 如何围绕完整 Agent 工作负载联合优化记忆、推理和工具执行？**

Manus 的经验说明，在输入远多于输出的 agent 里，缓存命中率比解码速度更能决定成本；Anthropic 的经验说明，并行能大幅缩短时间，代价是成倍的 token。模型内核上的加速，很可能被工具等待、上下文重读和数据传输抵消掉。这里可以研究任务感知的缓存、可恢复的状态压缩和跨步骤的调度，把“保留哪些信息”和“怎样分配资源”放在同一个目标下优化。关键是用真实的请求到达过程、任务长度和并发条件做实验，确认局部的节约确实能转化为端到端的延迟、吞吐或成本收益。

**3. 如何让结构上的计算优势在不同硬件与服务条件下稳定兑现？**

低精度、稀疏化和参数复用的收益，都依赖具体的实现和硬件支持，理论计算量预测不了部署效果，vSkipper 和非 GPU 部署的实地研究都说明了这一点。研究机会在于联合设计模型结构、算子和服务策略，建立可以迁移的成本模型和适配机制，就像 kipply 和《How To Scale Your Model》用纸笔估算那样，先给出一个可信的下界，再解释实测和下界之间的每一处偏差。报告时还应同时给出维护复杂度、数值正确性和完整任务的表现，只比较理想配置下的峰值速度意义有限。
