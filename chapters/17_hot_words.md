## 一、方向背景：一个新名字，究竟带来了什么变化？

假如你最近刷过几次 agent 相关的推文或组会报告，大概已经被一串新词包围了：harness、context engineering、Agent Skills、OPD、RSI、long-horizon，还有九月份冒出来的 JEV，以及从可解释性那边传过来的 J-lens。每个词背后都跟着几篇论文、几篇博客，有人说这是下一代 Agent 技术，有人说这只是旧东西换了个名字。刚入门的同学最容易犯的错，是把它们排成一列，当成同一类东西来背。

其实这些名字指向的东西很不一样。有的是一个具体的模型，比如 JEV；有的是系统设计的对象，比如 harness；有的是能力目标，比如 long-horizon；还有的是训练方法或研究议程，比如 OPD 和递归自改进。把它们并排当作"下一代 Agent 技术"，就会漏掉一个更要紧的问题：每个词改变的是系统的哪一部分，又是靠什么机制解决了原来的困难？

这些概念背后的研究需求彼此牵连。任务一长，每一步都调用大型生成模型就可能贵得用不起，把所有历史都塞进上下文也未必有效；一次成功的经验需要能复用，已有的能力还要能在新任务上继续长进。于是决策模型、执行框架、技能、记忆和训练方法会出现在同一套系统里，各管一摊，谁也替代不了谁。一个更快的选择器，未必是一个更强的规划器；一份可复用的技能文件，也说明不了模型已经学会自己创造技能。

热词还有一个特点：它们往往是被某篇写得特别好的博客"推"起来的。弄清楚一个词是谁、在哪篇文章里讲红的，你就能回到原文去看作者最初想解决什么问题，避免被二手转述带偏。所以本章沿着"名称从哪里来、为什么需要它、研究怎样展开"来组织每个词。具体的模型要追溯到发布者和接口；较宽泛的研究术语则要把早期工作和后续问题连起来，也不能把某篇近期论文写成整个概念的发明者。顺序上，先从 JEV 这样一个决策组件讲起，再讨论承载组件的执行框架、支撑经验积累的技能与记忆、改变能力的训练与自改进，最后回到长程任务这个共同目标。

## 二、JEV 与 System One Models：把有限决策从开放生成中分离出来

想理解 JEV，可以先分三个层次来看：模型提供什么样的决策接口，系统怎样利用这些接口来分配工作，应用又需要什么证据来证明它确实有效。下面先交代名称的来源和能力边界，再从控制、评价和具体应用三个角度展开相关论文。这些论文的出发点都是有限决策，但各自测量的是不同的能力。

### 来源：TypeSafe AI 的具体模型与设计路线

这个词的源头很清楚。TypeSafe AI 在 **2026 年 9 月 15 日**的[发布文章](https://typesafe.ai/blog/introducing-system-one-models-and-jev)中介绍了 System One Models，并把 Jev 作为这条路线上第一个公开的模型。**Jev / JEV 是模型名称**，不要自行把它展开成 Judge、Evaluate、Verify 之类单词的缩写。发布方把它的训练方法称为 **Reinforcement Learning for Calibrated Decisions（RLCD）**，强调的是面向结构化决策的概率输出。

"System One"这个名字借用了认知科学里快速判断与慢速推理的划分，用来说明系统内部的分工：大量边界清楚的小决策交给快速组件，复杂推理和内容生成交给别的模型。这只是设计上的类比，并不说明模型具有和人类一样的认知机制。所以理解 JEV 的起点，是先看它允许系统提出什么样的问题；把它当成又一个聊天模型来用，就抓错了重点。

[Jev in the Wild](https://arxiv.org/abs/2609.30216)归纳了 Choice、Noul 和 Score 三类接口，分别对应候选选择、二元判断和有序评分，都返回概率信息。用法是程序先规定好输出空间，模型再去处理用自然语言写下的条件。比如工具路由要在允许的下一步里挑一个，质量检查要判断某条准则是否满足，这些场景未必需要先生成一段解释再去解析结果。但要记住，**类型合法和语义正确是两回事**：模型照样可能在所有合法答案里选错一个。

### 背景：哪些环节不必交给开放生成？

JEV 要解决的，是工作流里大量有限决策带来的开销。候选筛选、检索路由、停止判断和一部分评分任务，结果只有有限几种；把它们拆出来交给专门的组件，复杂模型就能集中精力处理那些无法预先枚举的部分。不过输出空间变小，任务本身并不会自动变容易：候选列得全不全，判断条件写得清不清楚，输入里有没有决定答案的事实，这些都同样关键。

官方的 [jev-1.13 局限说明](https://docs.typesafe.ai/model-jaggedness/jev-1.13)列出了字面理解、数值精度、日期比较、多层间接关系和无关上下文等问题，并建议把精确计算留给代码去做。这些说明针对的是特定版本，不宜直接推广到所有决策模型。它们提示的系统设计原则倒是普遍适用：语义判断、确定性运算和开放推理需要合理分工，把一项复杂任务改写成选择题，问题并不会因此就解决了。

### 选择性控制：什么时候接受，什么时候升级？

[REFLEX with Jev for Efficient Selective Control in LLM Agents](https://arxiv.org/abs/2609.26532)把 JEV 放在快速决策层：置信度不够，或者任务需要生成内容时，再去调用强模型。论文还研究了动作集合变大、授权边界附近出现"看起来合法"的选项时，系统行为会怎样变化。它的外部评测显示，如果普通路由本来就很容易完成，那么和便宜的生成模型级联相比，这种做法的收益可能很有限。所以值得研究的除了"先便宜、后昂贵"的调用顺序，还有哪些决策适合做成有限选择，哪些困难才值得升级。

[Jev-Mem](https://arxiv.org/abs/2609.23986)把同样的分工搬进了记忆系统。快速控制器负责记忆类型和关系的组织，在检索时决定查询路由、预算、图遍历、候选评分和何时停止；复杂推理和答案综合则交给另一层。这里的 JEV 不负责给出最终答案，它决定的是信息怎样流到推理模型手里。比较这类方法时，一定要把记忆构建、在线检索和最终推理三部分的开销分开算，才知道系统的收益究竟来自哪里。

### 评价器：校准为什么还不够？

概率输出也让 JEV 很适合拿来研究选择性评价。[JEV-as-a-Judge](https://arxiv.org/abs/2609.26550)考察了"有把握就直接接受，没把握就交给推理裁判"的流程，在它的测试条件下给出了一条降低裁判成本的路线。可 [JEV vs. LLMs as Rubric Judges: Cheaper, Faster, and Wrong in the Same Places](https://arxiv.org/abs/2609.29769)发现，JEV 和生成式裁判往往会在同一批样本上犯错，升级之后准确率未必有明显改善。

两项工作合起来，引出了一个比"置信度靠不靠谱"更完整的问题：**前级能不能识别出自己的困难，后级又是否擅长解决这些困难？** 校准描述的是置信度和实际正确率之间的对应关系，并不保证每个高置信样本都是对的；级联要起作用，还需要前后两级的错误能够互补。因此在不同的评价任务、评分尺度、阈值和后级能力下，结论可能各不相同，一项研究的收益或局限，没法直接推广到所有裁判组合上。

[Just Ask Jev](https://arxiv.org/abs/2609.29429)更进一步，把决策模型用于对齐失败的检测，并分别改变提问方式和可见的上下文。奉承、注入或隐私违规这类现象往往是关系性的：要判断一个回答有没有出错，还得知道用户原本相信什么、被注入的指令是什么、相关的参考信息是什么。这项研究因此把注意力从"怎样提问"推进到"检测器到底看到了什么"。统一的判断接口，并没有抹平不同风险对证据的不同要求。

### 科学与视觉应用：决策质量和执行效率是两条线

[Jev for Scientific Decisions](https://arxiv.org/abs/2609.24965)把语义关系的选择交给模型，把后续的确定性计算交给程序，再分别评价选择、中间数量和最终结论三个环节。研究里出现过这样的情况：关系选错了，中间数量也变了，最终的标签却碰巧还是对的。这说明只看工作流末尾的答案，会漏掉上游的错误，当中间产物还要被别的任务复用时尤其危险。

[Visual Jev](https://arxiv.org/abs/2609.25845)研究的是同一张图像上的多个独立强制选择问题：图像和公共上下文作为共享前缀，彼此隔离的问题后缀批量执行，最后读出候选概率。任务训练提升的是判断质量，共享执行减少的是重复计算，这两件事要分开理解。缓存带来的加速和视觉推理能力的提升是两码事，也不能仅凭名字，就把研究里的视觉实现当成原模型所有接口的能力承诺。

这些工作分别把 JEV 放在了控制器、评价器和应用中的语义选择器三个位置上。[Jev in the Wild](https://arxiv.org/abs/2609.30216)补充了一个生态视角，展示公开项目怎样组合这些功能，但项目数量和关注度说明不了任务表现。真正有意义的比较，是在相同的信息、动作范围和任务目标下，看决策组件是否比规则、普通分类器或便宜的生成模型更合适。

## 三、Harness 与 Context Engineering：能力不只存在于模型权重中

决策组件能不能发挥作用，还要看外面的系统怎样组织工作。Harness 在 Agent 文献里通常指把模型接进执行循环的那一层系统，包括工具、状态、失败恢复、预算分配和人工接管。这个词本来就是工程上的常用说法，但它在 2025 年底到 2026 年突然成了热词，背后有几篇文章接力推动。Anthropic 的 Justin Young 在 2025 年 11 月 26 日发表的 [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)，把 harness 明确用来指包在模型外面的基础设施，即工具、上下文管理和会话循环，并把 Claude Agent SDK 称为一个通用的 agent harness；文中的做法是让一个初始化 agent 先搭好环境、写下进度文件和功能清单，后续每个会话的编码 agent 只推进一个功能并留下干净的提交，这样新的上下文窗口也能迅速接上前面的工作。2026 年 2 月 11 日，OpenAI 的 Ryan Lopopolo 发表 [Harness engineering: leveraging Codex in an agent-first world](https://openai.com/index/harness-engineering/)，讲述一个从三人起步、后来扩到七人的团队在大约五个月里让 Codex 写出约一百万行代码、合并约 1,500 个 PR，人一行代码也没有手写；作者的结论是，工程师的主要工作变成了设计环境、搭建反馈回路和写下约束，一句话叫"Humans steer. Agents execute."。"harness engineering"这个说法由此广为流传。到了 2026 年 7 月，Lilian Weng 的 [Harness Engineering for Self-Improvement](https://lilianweng.github.io/posts/2026-07-04-harness/) 又把它接到自我改进上，讨论 harness 怎样被当作代码来搜索和优化。

学术上，[From Question Answering to Task Completion](https://arxiv.org/abs/2606.20683)围绕 Agent 系统和 harness 设计组织综述，提供了从回答问题转向持续完成任务的概念入口。它整理了这个研究对象，harness 这个工程用语并不是它发明的。

Context engineering 是 harness 的近邻，范围却不一样。它关心的是每次做决策时模型实际看到了什么，目标、约束、检索结果、工具反馈和历史摘要又是怎样组织起来的。这个词在 2025 年年中流行起来，有两篇工程博客最常被引用。一篇是 Manus 的 Yichao "Peak" Ji 在 2025 年 7 月 18 日写的 [Context Engineering for AI Agents: Lessons from Building Manus](https://manus.im/en/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)，总结了他们在构建 Manus 过程中得到的几条经验：围绕 KV-cache 命中率设计上下文，保持前缀稳定、只追加不改写；工具不要中途增删，改用屏蔽的方式约束选择；把文件系统当作外部上下文，压缩时保留能找回原文的路径；让 agent 反复改写待办清单，把目标"复述"到上下文末尾；把失败的动作和报错留在上下文里，让模型从中吸取教训。另一篇是 Anthropic Applied AI 团队在 2025 年 9 月 29 日发表的 [Effective context engineering for AI agents](https://anthropic.com/engineering/effective-context-engineering-for-ai-agents)，它把 context engineering 定义为在推理过程中持续筛选和维护模型所见 token 集合的实践，并称之为提示工程的自然延伸，又介绍了压缩、结构化笔记、子 agent 和按需检索几种长任务技巧。Harness 还包括执行、权限与调度；上下文则是这些机制呈现给模型的信息界面。把两者都叫作提示词优化，就会漏掉状态更新和执行失败这些核心问题。

同一个模型放进不同的系统，面对的决策难度可能完全不同。[The Harness Effect](https://arxiv.org/abs/2607.06906)固定模型、替换编排层，研究框架怎样影响成本和完成质量。[Better Harnesses, Smaller Models](https://arxiv.org/abs/2607.08938)更进一步，让一个元智能体根据失败轨迹去调整指令、工具和编排，把重复出现的任务结构从模型推理里搬到框架中。前者说明系统层值得单独拿出来比较，后者研究的是系统怎样去适配模型，和 OpenAI 那篇文章里"让环境替模型分担约束"的思路一脉相承。

两条路线也留下一个共同的问题：系统专门化带来的收益能不能迁移？把固定流程写进程序，确实能降低任务难度，但底层模型的通用能力并不会因此同步增长。所以 harness 研究需要把适配过的任务和没见过的任务分开报告；上下文工程则要说清楚保留了哪些决策信息，光报告省了多少 token 是不够的。具体机制见[基础与工具](01_basics.md)和[记忆与上下文](02_memory.md)。

把这几篇博客按时间顺序读一遍，会看到一条很清楚的演进线索。2025 年年中，大家先关心的是模型在每一步看到什么，于是有了 context engineering；到了年底，问题变成一个 agent 怎样跨越很多个上下文窗口持续干活，进度文件、功能清单和会话循环这些"上下文之外"的东西被一起纳入了 harness；2026 年初，OpenAI 的文章把重心再往外推，讨论人应当怎样为 agent 设计整个工作环境；到了 Lilian Weng 那里，harness 本身又成了可以被自动搜索和改写的对象。她给出的阶梯是结构化上下文、工作流、harness 代码、优化器代码，被优化的东西一级比一级更通用。读到这里你会明白，context engineering 和 harness engineering 其实是同一个问题在不同尺度上的两种说法，而这条线的尽头，正好接上本章第七节的自改进。

## 四、Agent Skills：可复用的能力包如何形成？

执行框架解决的是一次任务怎样跑起来，技能则要处理成功的经验怎样被复用。"技能"这个词在强化学习、机器人和程序复用里早就有了；近期工程语境里的 **Agent Skills** 却有一个很具体的来源。Anthropic 的 Barry Zhang、Keith Lazuka 和 Mahesh Murag 在 **2025 年 10 月 16 日**发表的[介绍文章](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)中，把技能组织成一个包含指令、脚本和资源的目录，用 `SKILL.md` 来描述它的用途和执行知识。文章的核心设计叫渐进披露：启动时只把每个技能的名字和简介放进系统提示，判断相关后再读入完整的 `SKILL.md`，更多的附属文件等到真正需要时才打开。2025 年 12 月 18 日，Anthropic 在同一篇文章里补充说明已把 Agent Skills 作为开放标准发布，以便跨平台使用；[Agent Skills 规范](https://agentskills.io/specification)说明了这种组织方式和渐进加载的设计。通用意义上的技能研究和这种特定的封装格式，要当作两个概念来看。

这种封装回应的是程序性知识怎样分发的问题。模型可能懂得任务背后的原理，却不熟悉某个组织的文档规范或操作流程。先只暴露技能的名称和描述，匹配上任务后再读取详细内容，就能在不装入全部知识的前提下复用操作方法。新增的往往不是模型参数，是让已有能力正确发挥作用的条件。

[Voyager](https://arxiv.org/abs/2305.16291)代表了研究上的另一条线：它在 Minecraft 里积累可以调用的程序技能，并借助环境反馈不断改进执行。它和文件格式意义上的 Agent Skills 不属于同一套标准，但两者都涉及发现、保存、检索和组合程序。前者突出技能怎样从交互里长出来，后者突出技能怎样打包、分发和加载。

所以要分清三样东西：人编写的能力包、Agent 自动提炼出的程序，以及能够持续修订的技能库。写下一个 `SKILL.md`，技能学习才刚开始；脚本成功跑通一次，也证明不了它能跨环境复用。真正的能力积累，还需要写清前置条件、失败情形和适用范围，让技能的选择与组合有据可依，不至于只靠名字相似去匹配。技能文本也不能自己给自己授予敏感操作的权限，执行授权仍然由系统控制。Anthropic 那篇文章结尾提到，他们希望 agent 将来能自己创建、编辑和评估技能，这正好把话题接到了[技能库与自改进](03_skills_and_self_improvement.md)。

## 五、Agentic Memory：从保存历史到维护变化中的状态

技能保存的是可复用的方法，记忆还要保存任务中的事实、决定和变化。Agentic memory 不是哪一家模型的专有名称，各篇论文对它的结构也没有统一的定义。2025 年 2 月的 [A-MEM: Agentic Memory for LLM Agents](https://arxiv.org/abs/2502.12110) 直接把这个词放进了标题：它借鉴 Zettelkasten 卡片笔记法，把每条新记忆写成结构化的笔记，与相关的旧笔记建立链接，还允许新记忆反过来修订旧笔记。比较有辨识度的共同点是，系统会主动决定写入、组织、检索、更新和遗忘，让过去的交互支撑未来的行动；给向量数据库换个名字，算不上 agentic memory。

[MemGPT](https://arxiv.org/abs/2310.08560)借鉴操作系统的分层存储思想，用显式的操作来管理有限的上下文和外部记忆。它说明"保存下来"和"当下可用"之间还隔着一层管理机制：系统存过的信息，不一定会出现在当前这次模型调用里。这也是 agentic memory 和长上下文的区别所在，一次能看到的范围变大了，长期信息的维护问题依然在那里。

能把旧信息取回来以后，还得判断它是否仍然有效。[Can Agent Memory Systems Track Evolving State?](https://arxiv.org/abs/2608.19652)提出了 StateMemBench，区分当前状态、已被替代的状态和其他错误，并用 StateMem 显式处理替代关系和依赖。一条曾经正确的事实，任务推进之后可能就失效了，所以召回率之外，还得研究时间、版本和约束之间的关系。

前面提到的 [Jev-Mem](https://arxiv.org/abs/2609.23986)则从控制开销切入：即便记忆内容本身合理，决定检索什么、什么时候停下来也可能代价很高。一条路线研究信息怎样保持有效，另一条路线研究谁来控制信息的流动，两者可以组合起来，但都需要回到完整任务里观察错误怎样传播、最终收益有多少。更多分支见[记忆与上下文](02_memory.md)。

如果把第三节的两篇 context engineering 博客和这里的论文放在一起读，还能看到工程界和学术界在记忆问题上的一次汇合。Manus 把文件系统当作一块容量不限、可以随时找回的外部上下文；Anthropic 推荐让 agent 写结构化笔记，在上下文窗口之外持久保存，需要时再读回来；长程 harness 那篇文章里的进度文件和 git 历史，本质上也是同一种做法。它们和 MemGPT 的分层存储、A-MEM 的笔记网络在思路上是相通的，区别在于工程文章更在意缓存命中率和恢复速度，论文更在意写入与更新的规则能否被学习、能否被评测。两边各看一半，记忆这个词的轮廓就会清晰很多。

## 六、OPD：在学生真正会遇到的状态上提供指导

记忆和技能主要改变系统怎样使用经验，训练则可以更进一步，直接改变模型的行为分布。**On-Policy Distillation（在策略蒸馏，OPD）**的要点，在于由谁来产生接受指导的那些轨迹，"大模型教小模型"只是它的表面。如果学生只模仿教师的成功路径，就可能从没见过自己部署时会走偏的那些状态；让学生先按当前策略自己生成，再在这些上下文里拿到教师的信号，才算抓住了 on-policy 的核心。

这个词近一年在大模型圈子里流行起来，很大程度上要归功于 Thinking Machines Lab 的 Kevin Lu 在 2025 年 10 月 27 日发表的博客 [On-Policy Distillation](https://thinkingmachines.ai/blog/on-policy-distillation/)。文章把问题讲得很直白：强化学习是 on-policy 的，但每条轨迹只给一个稀疏的奖励，分不清是哪个 token 出了错；普通的离线蒸馏信号很密，却是在教师生成的文本上训练，学生真正会卡住的状态可能一次也没见过。OPD 让学生自己采样，再由教师用逐 token 的反向 KL 给每一步打分，把两者的长处合在一起。文中报告，在 Qwen3-8B 学生、Qwen3-32B 教师的数学推理实验里，从一个 SFT 检查点出发，大约 150 步就在 AIME'24 上达到约 70%；作者估算，相比继续外推 SFT，计算量约省 9 倍，算上教师采样成本约省 30 倍。

这一动机和模仿学习里的状态分布偏移问题一脉相承。[DAgger](https://arxiv.org/abs/1011.0686)在学习者实际访问到的状态上获取专家指导，是理解这条思路的重要前史，但语言模型中的 OPD 实现比它丰富得多。教师提供的是标签、序列还是概率分布，损失怎样累计，都会改变具体的算法。

[RL Starts before RL](https://arxiv.org/abs/2609.28145)把问题推进到"蒸馏能否给后续强化学习提供更好的起点"，发现初始准确率并不足以预测之后的收益；在它的比较中，不同散度目标在强化学习前后的相对表现还会发生变化。[Sequential Beats Joint](https://arxiv.org/abs/2609.04108)则比较了两种安排：在同一步里混合 OPD 和可验证奖励信号，与先蒸馏、后强化学习。在它的逻辑与数学任务上，结果支持后一种。

两项工作让人在"学生是否接近教师"之外，多问了一句"学生是否获得了一个后续探索能够利用的解法分布"。但这还推不出所有任务都该采用固定的训练顺序。教师质量、初始能力、验证器和环境探索都会影响收益；而且 Agent 的学生状态里还有工具反馈，远不止文本前缀。OPD、RLVR 和 JEV 发布方提出的 RLCD，也不要因为都涉及概率或奖励就混为一谈：它们分别强调监督状态的来源、奖励的可检查性，以及面向校准决策的训练。具体比较见[强化学习与蒸馏](05_rl_and_distillation.md)。

## 七、Self-Evolving 与 RSI：改进结果，还是改进产生改进的系统？

当系统能够更新记忆、技能、代码或参数，下一个问题自然就来了：这些变化能不能持续增强系统后续的改进能力？Self-evolving agent 是一个较宽的研究标签，可以包括提示修订、经验积累和模型学习；它本身并不天然带有递归性，在一次任务里反复修改答案和跨任务积累能力也要分开来看。

**Recursive Self-Improvement（递归自改进，RSI）**这个说法并不新，但它在 2026 年重新变热，和几篇梳理文章有很大关系。DAIR.AI Academy 在 2026 年 9 月整理的 [Self-Improving Agents](https://academy.dair.ai/papers/collections/self-improving-agents) 合集给出了一个常被引用的界定：系统用自己产生的反馈修改自身某个持久的部分，只保留经过检验确实有用的修改；当被修改的是提出和评判修改的那套机制时，系统才算递归。Anthropic 的 [When AI builds itself](https://www.anthropic.com/institute/recursive-self-improvement)（2026 年 9 月 18 日更新）则从实验室内部给出了冷静的判断：AI 已经在加速 AI 的研发，但递归自改进还没有到来，也并非必然，选择目标和研究方向的判断力仍然主要来自人。

RSI 追问的是，提出、验证和选择改进的机制本身能否被更新，并由更新后的机制继续组织下一轮改进。[Recursive Self-Improvement in AI](https://arxiv.org/abs/2607.07663v2)从有界的自我修正一直整理到自主研究循环；[The Last AI Built by Humans](https://arxiv.org/abs/2609.11873v3)讨论通向更完整 RSI 的研究路线。它们有助于把目标界定清楚，但路线图毕竟只是路线图，目标是否已经实现，要靠实验来证明。

[Recursive self-improvement of AI research agents](https://arxiv.org/abs/2609.26457)中的 AIDE² 提供了一个具体的研究对象：Agent 提出对自身代码的修改，评价候选版本，让被接受的改写参与下一轮改进。论文报告了连续多轮的改进，以及在保留任务上的迁移。这里被递归修改的是研究 Agent 的代码和执行策略，不能直接写成底层模型权重获得了无限提升，也不能从有限的几轮推出不受资源约束的能力增长。

这样一来，关注点就从"能不能自动改代码"转到了"能不能持续产生可迁移的收益"。反复适应同一组选拔任务，增强的可能只是应付评测的能力；新版本任务分数上去了，也说明不了它更善于提出下一轮有效的修改。所以改进对象、选择机制和跨轮次的能力积累，需要放在一起研究。相关分支见[技能库与自改进](03_skills_and_self_improvement.md)。

DAIR.AI 那份合集专门留了一段，标题就叫"循环在哪里断掉"，收录的是模型在没有外部反馈时自我纠错反而变差、用自己生成的数据反复训练导致模型坍缩、agent 在演化中悄悄丧失安全性这一类工作。Lilian Weng 的文章则从工程角度给出了对应的建议：评价器和权限控制最好放在被演化的那个循环之外，人不必退出环路，而应当往上走一层，在关键的决策点上做审查。把这两份材料和上面的论文对照着读，读 RSI 论文时该盯住的地方就很明确了：被修改的是什么，谁来判断修改的好坏，判断者自己会不会也被改掉。

## 八、Long-Horizon：更长的首先是依赖链，其次才是上下文

前面这些组件共同服务的一类目标，是让 Agent 在更长的时间里持续完成工作。Long-horizon 里的 horizon 来自序列决策中关于时间跨度的讨论，并不是哪个 Agent 产品首先提出的。它近年成为热词，METR 在 2025 年 3 月 19 日发布的 [Measuring AI Ability to Complete Long Tasks](https://metr.substack.com/p/2025-03-19-measuring-ai-ability-to-complete-long-tasks) 起了很大作用：文章用"人类专家完成某类任务需要的时长"来衡量任务长度，把模型有 50% 把握完成的任务长度称为它的时间跨度，并发现这个跨度在过去六年里大约每七个月翻一番。这条曲线让"agent 能独立工作多久"成了一个可以追踪的指标。

工程界对长程任务的回应，前面第三节已经提到一部分。Anthropic 那篇关于长时运行 harness 的文章，出发点正是 agent 一旦跨越多个上下文窗口就容易"失忆"：新会话不知道前面做到哪一步，于是要么重复劳动，要么过早宣布完成。他们的办法是用一份初始全部标为未通过的功能清单，规定 agent 只能修改每项的通过状态，再配合进度日志和 git 提交，让每个新会话都能迅速接上进度。OpenAI 的 harness engineering 文章里也提到，单次 Codex 运行有时会在一个任务上连续工作六个多小时。这些经验说明，长程能力有很大一部分是靠系统设计撑起来的，模型能力只是其中一环。

[Towards Long-Horizon Agents: A Survey](https://long-horizon-agents.github.io/)把这个概念放进了现代 Agent 系统：前面的决策会改变后面的条件，系统必须在有限的资源下维持目标、状态和反馈。更长的行动链、更迟到达的结果反馈和更长的环境时间，三者彼此相关，却并不完全等价。

长上下文是一次能装下多少信息，长输出是生成文本的长度，长程任务则要求持续采取有效的行动。能读完长文档的系统，可能在一次工具失败后就再也恢复不过来；而一份好的状态摘要，可能让较短的上下文撑起较长的工作流。所以增加 token 预算定义不了长程任务，把许多彼此独立的小任务串在一起，也未必检验了长期规划。

[Long-Horizon-Terminal-Bench](https://arxiv.org/abs/2607.08964)用可以评分的中间子任务来观察长程执行的进展；[VibeLifeBench](https://arxiv.org/abs/2608.10875)则把长期性放进一个模拟数周的生活服务场景，让 Agent 反复检查变化中的世界，保持计划前后一致，并决定什么时候行动、什么时候询问、什么时候保持沉默。后者的"多周"是模拟出来的任务时间，和现实中连续运行好几周是两回事。

两者也说明评测需要同时**更长与更宽**：更长意味着更复杂的依赖、更迟的反馈和对恢复能力的要求，更宽意味着更多的领域、环境和能力组合。科研复现、生活服务和软件工程可能都很长，需要的状态和验收条件却各不相同，一个"最长运行时长"代替不了整张能力地图。具体脉络见[评测与能力基准](06_evaluation.md)。

## 九、J-lens 与 J-space：读出模型"准备说出口"的东西

前面几节的热词都长在 agent 系统里，J-lens 来自另一块土地，它是 2026 年可解释性方向传得最广的一个新词。之所以放进这一章，是因为它很快被用到了 agent 的对齐审计上，而且和第七节的自改进、长程任务里"模型到底在想什么"的问题直接相连。

### 来源：Anthropic 的全局工作空间论文

这个词出自 Anthropic 可解释性团队 2026 年 7 月的论文 [Verbalizable Representations Form a Global Workspace in Language Models](https://arxiv.org/abs/2607.15495)（Wes Gurnee、Jack Lindsey 等，arXiv 7 月 16 日上线）。**J-lens 是 Jacobian lens 的简称**，是一种读取模型内部表示的方法；**J-space 是用它定义出来的一块表示空间**，指那些可以写成少量 J-lens 向量的稀疏、非负组合的激活成分。两个词常被混着用，读论文时要分清：前者是工具，后者是工具找到的对象。

它在方法谱系上接的是 logit lens 和 tuned lens。logit lens 直接拿最后一层的解码器去读中间层，tuned lens 为每一层额外学一个映射；J-lens 换了个思路，在大量语料上平均某一层激活对后续输出概率的一阶影响，也就是雅可比矩阵，以此找出"模型此刻准备用语言说出来"的那些方向。

### 背景：为什么需要一块"可以说出口"的空间？

论文借用了认知科学里的全局工作空间理论。这个理论认为，大脑里大量处理是无意识、各自为政的，只有进入一个容量有限的"工作空间"的内容，才能被报告、被保持、被拿去做后续推理。作者在 Claude 系列模型的中间层找到了类似的结构：注入 J-space 的概念，模型能够说出来，注入到别处的大多说不出来；两跳推理的中间概念会在这里依次出现，替换其中一个，下游答案会跟着变；也有一些任务完全绕过这块空间，作者把它们类比为不经思考的快速反应。论文测得这块空间在中间各层同时活跃的 J-lens 向量大约有 25 个（作者提醒，几个向量可能共同表示一个概念，所以这个数字只是向量数），它只占激活方差中很小的一部分，通常不到一成。

这和第二节 JEV 借用的"System One"类比形成了有趣的对照：JEV 是在系统层面把快决策和慢推理拆开，J-space 的发现则提示，模型内部本来就存在类似的分工。

### 对齐审计：从"读思维链"到"读工作空间"

这个词能迅速走红，主要因为它在安全上的用途。论文报告，J-space 可以暴露模型没有写进思维链的考虑和不良倾向。被转述最多的一个实验，是在一个勒索测试场景里，用消融去掉与"意识到自己正在被评测"相关的方向：模型口头说出"这是测试"的比例大幅下降（论文报告从 71% 降到 3%），而实际选择勒索的次数从 0/180 升到了 13/180。也就是说，模型知道自己在被考，这件事本身就在影响它的表现，而这个"知道"在 J-space 里是看得见的。论文还提出，后训练会把"助手"的视角放进这块空间，并尝试用一种反事实反思训练来改善行为。

这条线和[安全与对齐](07_safety.md)里思维链监控那一节是接着的。思维链可以被模型有意无意地隐藏，监控者在长程任务里也越来越读不过来，于是"直接读模型内部准备说出口的东西"成了一条新的补充防线。

### 后续研究与争议

论文发布后很快出现了跟进工作。[Short Horizons and Sparse Concepts](https://arxiv.org/abs/2608.25347) 从数学上分析了 J-lens 的读出：它把 J-lens 看成从中间激活到未来输出的一阶因果传递算子，发现这种影响高度稀疏、随深度衰减，并集中在少数对角通路和关键位置上，由此解释了它为什么能读出推理中的中间概念，还提出了一个解耦式的改进。[Verbalizing Multi-Token Concepts in LLMs](https://arxiv.org/abs/2608.31084) 处理的是另一个实际问题：很多概念是由几个 token 拼成的实体或短语，单 token 的透镜读不全，作者用 token 级的线索去搜索候选概念，在 2,400 道多跳填空题、五个 8B 到 70B 的模型上，把 Rank@10 从模板透镜的 21.7% 提到了 J-lens 引导下的 36.6% 和 R-lens 引导下的 54.5%。据社区报道，DeepMind 已在开源模型上复现了主要现象，Anthropic 和 Neuronpedia 也为开源模型放出了 J-lens 权重，自己动手做实验的门槛已经很低。

争议主要有两类。一类是方法上的：有批评者指出，J-lens 向量按定义就是对输出影响最大的方向，"它们具有因果作用"在一定程度上是定义出来的，需要更严格的对照才能说明工作空间这个结构本身的意义。另一类来自"全局工作空间"这个名字：这个理论常被用来讨论意识，论文的发现说明了可报告性这种功能性质，和模型是否有主观体验是两个层面的问题，论文也明确表示对后者不持立场。

读这一节时最值得带走的，是一个研究问题：当我们越来越难通过模型"说了什么"来判断它"想了什么"时，能不能找到一块足够稳定、足够可读的内部空间，作为审计 agent 的依据？J-lens 给出了第一个有说服力的候选，它的边界在哪里，还需要更多工作来回答。

## 十、开放问题与研究机会

回头看这一串热词，它们共同指向一件事：怎样组织并积累行动能力。可每一个局部组件的改进，最终都得放回完整任务里检验。下面的研究机会集中在四个连接处：不同的决策方式怎样互补，经验怎样变成可复用的能力，目标怎样变成可测的任务，以及自动改进怎样跨出当前的任务分布。

### 1. 怎样把快决策与慢推理组成真正互补的系统？

值得研究的远不止让低成本模型先答一次。更有意思的是为不同的决策选择不同的处理方式：哪些交给确定性代码，哪些适合有限选择模型，哪些必须补充观察或展开推理？可以构造包含信息缺失、分布变化和授权边界的工作流，让系统学会升级给谁、什么时候升级。目标是在完整任务中改善质量、延迟和风险之间的权衡，特别是让后级去修复前级容易犯的那类错误，避免两级重复做同一种判断。

### 2. 怎样让记忆和技能成为能够积累、组合与修订的能力？

更有价值的能力库，应当能从实际交互中发现可复用的结构，提炼出前置条件，识别已经过时的经验，并把局部技能组合成新的工作流。相应的任务可以让规则、工具和目标逐渐变化，观察旧经验是怎样被迁移、修订或舍弃的。最终要形成的，是一套能持续改善后续行动的机制；一份越来越大的历史记录和脚本集合，离这个目标还差得远。

### 3. 怎样把真实世界与希望拥有的未来能力变成 benchmark？

一条路线是把真实工作系统中足够完整的一部分转化成可执行的环境，保留状态变化、多方约束和行动后果；另一条路线是从未来希望 Agent 具备的能力出发，把持续负责、主动发现问题、跨工具恢复和跨领域迁移这些目标形式化。任务要难到足以挑战强模型，同时要有合理的解法和明确的完成条件，避免只靠隐藏信息或故意刁难来制造低分。沿着更长的依赖链和更宽的领域去扩展，才能判断一个组件是否真的带来了能力增量。

### 4. 怎样让自动改进跨越固定任务分布？

可以把技能发现、harness 适配和 OPD 连起来：先在交互中找到失败的结构，再决定把这份经验存成记忆、固化成程序，还是拿去训练模型。关键在于不同载体之间怎样分工，以及早期的改进能否提升系统解决下一批新问题的能力。研究递归自改进时，还要把选择任务、迁移任务和未来的改进任务区分开，考察系统是否真的获得了更强的研究能力，警惕它只是变得更擅长应付某个固定的评价器。
