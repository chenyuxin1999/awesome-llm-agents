# 17｜Hot Words：热门概念的来源、机制与研究脉络

## 一、方向背景：一个新名字，究竟带来了什么变化？

Agent 研究中的新名字并不都指向同一种东西。有的是模型名称，如 JEV；有的是系统设计对象，如 harness；有的是能力目标，如 long-horizon；还有的是训练方式或研究议程，如 OPD 和递归自改进。把它们并排当作“下一代 Agent 技术”，容易忽略一个更重要的问题：它们分别改变了系统的哪一部分，又依靠什么机制解决原来的困难？

这些概念背后有相互关联的研究需求。任务持续时间增长以后，每一步都调用大型生成模型可能代价过高，所有历史都塞入上下文也未必有效；一次成功的经验需要能够复用，已有能力还需要在新任务中持续改进。因此，决策模型、执行框架、技能、记忆和训练方法可以出现在同一套系统里，但不能彼此替代。更快的选择器不等于更强的规划器，可复用的技能文件也不等于模型已经学会自主创造技能。

本章沿着“名称从哪里来—为什么需要它—研究如何展开”组织这些概念。具体模型需要追溯发布者和接口；较宽泛的研究术语则需要连接早期工作与后续问题，而不能把某篇近期论文写成整个概念的发明者。JEV 首先展示一种决策组件，随后讨论承载这些组件的执行框架、支持经验积累的技能与记忆，以及改变能力的训练和自改进机制，最后回到长程任务这一共同目标。

## 二、JEV 与 System One Models：把有限决策从开放生成中分离出来

理解 JEV 可以先区分三个层次：模型提供什么决策接口，系统怎样利用这些接口分配工作，以及应用需要什么证据证明它确实有效。下面先交代名称来源与能力边界，再从控制、评价和具体应用展开相关论文。它们共享有限决策这一出发点，但并不是对同一种能力重复测量。

### 来源：TypeSafe AI 的具体模型与设计路线

TypeSafe AI 在 **2026 年 9 月 15 日**的[发布文章](https://typesafe.ai/blog/introducing-system-one-models-and-jev)中介绍了 System One Models，并将 Jev 作为这一路线的首个公开模型。**Jev / JEV 是模型名称**，不应自行展开为 Judge、Evaluate、Verify 等词的缩写。发布方把其训练方法称为 **Reinforcement Learning for Calibrated Decisions（RLCD）**，强调面向结构化决策的概率输出。

这一命名借用快速判断与较慢推理的认知划分，解释系统中的分工：大量边界清楚的小决策交给快速组件，复杂推理或内容生成交给其他模型。这是设计上的类比，不说明模型具有与人类相同的认知机制。理解 JEV 的起点也不是把它当作另一个聊天模型，而是先看它允许系统提出什么问题。

[Jev in the Wild](https://arxiv.org/abs/2609.30216)归纳了 Choice、Noul 和 Score 三类接口，分别围绕候选选择、二元判断和有序评分返回概率信息。程序先规定输出空间，模型再处理自然语言定义的条件。例如工具路由需要选择允许的下一步，质量检查需要判断准则是否满足，它们未必需要生成一段解释再解析成结果。但**类型合法不等于语义正确**：模型仍然可能在所有允许答案中选错一个。

### 背景：哪些环节不必交给开放生成？

JEV 回应的是工作流中大量有限决策的开销问题。候选筛选、检索路由、停止判断和部分评分任务只有有限种结果，把它们拆出来，可以让复杂模型集中处理无法预先枚举的部分。不过，输出空间受限并不自动使任务容易：候选是否完整、判断条件是否写清、输入是否包含决定答案的事实，同样重要。

官方的 [jev-1.13 局限说明](https://docs.typesafe.ai/model-jaggedness/jev-1.13)列出了字面理解、数值精度、日期比较、多层间接关系和无关上下文等问题，并建议将精确计算留在代码中。这些是特定版本的说明，不宜直接外推到所有决策模型。它们提示的系统设计原则是：语义判断、确定性运算与开放推理需要合理分工，而不是把一项复杂任务改写成选择题就认为问题已经解决。

### 选择性控制：什么时候接受，什么时候升级？

[REFLEX with Jev for Efficient Selective Control in LLM Agents](https://arxiv.org/abs/2609.26532)将 JEV 放在快速决策层：置信度不足或任务需要生成时，再调用强模型。论文还研究动作集合扩大、授权边界附近出现近似合法选项时的行为变化。其外部评测显示，当普通路由已经容易完成时，相比便宜的生成模型级联，收益可能有限。因此，需要研究的不只是“先便宜、后昂贵”的调用顺序，还包括哪些决策适合有限选择，什么困难值得升级。

[Jev-Mem](https://arxiv.org/abs/2609.23986)把这种分工引入记忆系统。快速控制器负责记忆类型与关系组织，并在检索时决定查询路由、预算、图遍历、候选评分和停止；复杂推理与答案综合由另一层承担。这里的 JEV 不直接包办最终答案，而是决定信息怎样到达推理模型。比较这类方法时，必须区分记忆构建、在线检索和最终推理的开销，才能知道系统收益来自哪里。

### 评价器：校准为什么还不够？

概率输出也使 JEV 适合研究选择性评价。[JEV-as-a-Judge](https://arxiv.org/abs/2609.26550)考察“有把握就接受，不确定就交给推理裁判”的流程，在其测试条件下提供了一条降低裁判成本的路线。但 [JEV vs. LLMs as Rubric Judges: Cheaper, Faster, and Wrong in the Same Places](https://arxiv.org/abs/2609.29769)发现，JEV 与生成式裁判可能在同一批样本上犯错，升级未必显著改善准确率。

两项工作连接出一个比“置信度是否可靠”更完整的问题：**前级能否识别自己的困难，后级又是否擅长解决这些困难？** 校准描述置信度与实际正确率的对应，不保证每个高置信样本都正确；级联还需要错误互补。因此，不同评价任务、评分尺度、阈值和后级能力下的结果可以不同，不能把一项研究的收益或局限直接推广到所有裁判组合。

[Just Ask Jev](https://arxiv.org/abs/2609.29429)进一步将决策模型用于对齐失败检测，分别改变提问方式和可见上下文。奉承、注入或隐私违规等现象往往具有关系性：判断回答是否出错，还需要用户信念、被注入指令或相关参考信息。该研究因此将注意力从“怎样提问”推进到“检测器究竟观察到了什么”。统一的判断接口，并没有消除不同风险对证据的不同要求。

### 科学与视觉应用：决策质量和执行效率是两条线

[Jev for Scientific Decisions](https://arxiv.org/abs/2609.24965)把语义关系选择交给模型，把后续确定性计算交给程序，并分别评价选择、中间数量与最终结论。研究中出现过关系选错、中间数量改变，最终标签却仍然正确的情况。这说明只检查工作流末尾的答案，会遗漏上游错误，尤其当中间产物还要被其他任务复用时。

[Visual Jev](https://arxiv.org/abs/2609.25845)研究同一图像上的多个独立强制选择问题：共享图像与公共上下文前缀，批量执行彼此隔离的问题后缀，再读取候选概率。任务训练改善判断质量，共享执行减少重复计算，两者需要分开理解；缓存加速并不等于视觉推理能力提升，也不能仅凭名称把研究中的视觉实现当作原模型所有接口的能力承诺。

这些工作将 JEV 分别放在控制器、评价器和应用中的语义选择器位置。[Jev in the Wild](https://arxiv.org/abs/2609.30216)补充了公开项目如何组合这些功能的生态视角，但项目数量和关注度不等于任务表现。真正有意义的比较，是在相同信息、动作范围与任务目标下，决策组件是否比规则、普通分类器或便宜的生成模型更合适。

## 三、Harness 与 Context Engineering：能力不只存在于模型权重中

决策组件能否发挥作用，还取决于外部系统怎样组织工作。Harness 在 Agent 文献中通常指把模型接入执行循环的系统层，包括工具、状态、失败恢复、预算分配和人工接管。[From Question Answering to Task Completion](https://arxiv.org/abs/2606.20683)围绕 Agent 系统和 harness 设计组织综述，提供了从回答问题转向持续完成任务的概念入口。它整理了这一研究对象，而不是发明了 harness 这个工程用语。

Context engineering 与之相邻，但范围不同：它关注每次决策时模型实际看见什么，目标、约束、检索结果、工具反馈和历史摘要怎样组织。Harness 还包含执行、权限与调度；上下文则是这些机制向模型呈现的信息界面。把二者都称为提示词优化，会漏掉状态更新和执行失败等核心问题。

同一个模型在不同系统中，可能面对不同的决策难度。[The Harness Effect](https://arxiv.org/abs/2607.06906)固定模型、替换编排层，研究框架如何影响成本与完成质量。[Better Harnesses, Smaller Models](https://arxiv.org/abs/2607.08938)进一步让元智能体根据失败轨迹调整指令、工具和编排，把重复任务结构从模型推理中转移到框架中。前者强调系统层值得独立比较，后者研究系统如何适配模型。

两条路线也留下一个共同问题：系统专门化带来的收益能否迁移？把固定流程写入程序，可以降低任务难度，却不等于底层模型的通用能力同步增长。因此，harness 研究需要区分适配任务与未见任务；上下文工程需要说明保留了哪些决策信息，而不是只报告减少了多少 token。具体机制见[基础与工具](01_basics.md)和[记忆与上下文](02_memory.md)。

## 四、Agent Skills：可复用的能力包如何形成？

执行框架解决一次任务如何运行，技能则进一步处理成功经验怎样被复用。“技能”在强化学习、机器人和程序复用中早已存在；近期工程语境中的 **Agent Skills** 有更具体的来源。Anthropic 在 **2025 年 10 月 16 日**的[介绍文章](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)中，将技能组织为包含指令、脚本与资源的目录，通过 `SKILL.md` 描述用途和执行知识。[Agent Skills 规范](https://agentskills.io/specification)说明了这种组织方式与渐进加载设计。通用的技能研究与特定的封装格式，不是同一个概念。

这种封装回应的是程序性知识的分发问题。模型可能知道任务原理，却不熟悉某个组织的文档规范或操作流程。先暴露技能名称与描述，匹配任务后再读取详细内容，可以在不装入全部知识的情况下复用操作方法。新增的往往不是模型参数，而是让已有能力正确工作的条件。

[Voyager](https://arxiv.org/abs/2305.16291)提供了研究上的另一条线：在 Minecraft 中积累可调用的程序技能，并利用环境反馈改进执行。它与文件格式意义上的 Agent Skills 不是同一套标准，但共同涉及发现、保存、检索和组合程序。前者突出技能如何从交互中形成，后者突出技能如何打包、分发与加载。

由此需要分清人编写的能力包、Agent 自动提炼的程序，以及能够持续修订的技能库。写下一个 `SKILL.md` 不等于完成技能学习，脚本成功一次也不证明能够跨环境复用。真正的能力积累还需要前置条件、失败情形和适用范围，使选择与组合不只依赖名称相似。技能文本也不能自行授予敏感操作权限，执行授权仍属于系统控制。这些问题共同连接到[技能库与自改进](03_skills_and_self_improvement.md)。

## 五、Agentic Memory：从保存历史到维护变化中的状态

技能保存可复用的方法，记忆还要保存任务中的事实、决定和变化。Agentic memory 不是某家模型的专有名称，也没有一套在所有论文中一致的结构定义。较有辨识度的共同点是：系统主动决定写入、组织、检索、更新和遗忘，让过去交互支持未来行动，而不只是给向量数据库换个名字。

[MemGPT](https://arxiv.org/abs/2310.08560)借鉴分层存储思想，通过显式操作管理有限上下文和外部记忆。它说明持久保存与当下可用之间需要管理机制：系统存过的信息，不一定出现在当前模型调用中。这也是 agentic memory 与长上下文的区别，扩大一次可见范围并不自动解决长期信息维护。

能取回旧信息之后，还要判断它是否有效。[Can Agent Memory Systems Track Evolving State?](https://arxiv.org/abs/2608.19652)提出 StateMemBench，区分当前状态、已被替代的状态与其他错误，并通过 StateMem 显式处理替代关系和依赖。曾经正确的事实在任务推进后可能失效，因此召回率之外还要研究时间、版本和约束关系。

前述 [Jev-Mem](https://arxiv.org/abs/2609.23986)从控制开销切入：即使记忆内容合理，决定检索什么、何时停止也可能代价很高。一条路线研究信息怎样保持有效，另一条路线研究谁来控制信息流，两者可以组合，但需要回到完整任务观察错误传播与最终收益。更多分支见[记忆与上下文](02_memory.md)。

## 六、OPD：在学生真正会遇到的状态上提供指导

记忆和技能主要改变系统怎样使用经验，训练则可以进一步改变模型的行为分布。**On-Policy Distillation（在策略蒸馏，OPD）**不只是用大模型教小模型，其关键在于由谁产生接受指导的轨迹。只模仿教师的成功路径，可能没有覆盖学生部署时的偏离；学生先按当前策略生成，再在这些上下文中获得教师信号，才触及 on-policy 的核心问题。

这一动机与模仿学习的状态分布偏移相联系。[DAgger](https://arxiv.org/abs/1011.0686)在学习者实际访问的状态上获得专家指导，是理解这条思路的重要前史，但不等同于语言模型中的全部 OPD 实现。教师提供标签、序列还是概率分布，以及怎样累计损失，都会改变具体算法。

[RL Starts before RL](https://arxiv.org/abs/2609.28145)将问题推进到蒸馏能否为后续强化学习提供更好的起点，发现初始准确率不足以预测之后的收益；其比较中，不同散度目标在强化学习前后的相对表现也会变化。[Sequential Beats Joint](https://arxiv.org/abs/2609.04108)比较同一步混合 OPD 与可验证奖励信号，以及先蒸馏后强化学习，在其逻辑与数学任务中支持后者。

两项工作使“学生是否接近教师”之外，多出“学生是否获得后续探索可以利用的解法分布”这一问题。这不意味着所有任务都应采用固定训练顺序。教师质量、初始能力、验证器和环境探索共同影响收益；Agent 的学生状态还包括工具反馈，而不只是文本前缀。OPD、RLVR 与 JEV 发布方提出的 RLCD 也不应因都涉及概率或奖励而混为一谈：它们分别强调监督状态的来源、奖励的可检查性和面向校准决策的训练。具体比较见[强化学习与蒸馏](05_rl_and_distillation.md)。

## 七、Self-Evolving 与 RSI：改进结果，还是改进产生改进的系统？

当系统能够更新记忆、技能、代码或参数，一个更进一步的问题是：这些变化能否持续增强后续改进能力？Self-evolving agent 是较宽的研究标签，可以包含提示修订、经验积累和模型学习；它并不天然具有递归性，一次任务中反复改答案与跨任务积累能力也需要分开。

**Recursive Self-Improvement（递归自改进，RSI）**进一步追问，提出、验证和选择改进的机制能否被更新，并由更新后的机制继续组织下一轮改进。[Recursive Self-Improvement in AI](https://arxiv.org/abs/2607.07663v2)从有界自我修正到自主研究循环整理这一谱系；[The Last AI Built by Humans](https://arxiv.org/abs/2609.11873v3)讨论更完整 RSI 的研究路线。它们有助于界定目标，但路线图不是目标已经实现的实验证明。

[Recursive self-improvement of AI research agents](https://arxiv.org/abs/2609.26457)中的 AIDE² 则提供具体研究对象：Agent 提议修改自身代码，评价候选版本，让被接受的改写参与下一轮改进。论文报告了连续改进与保留任务上的迁移。这里递归修改的是研究 Agent 的代码和执行策略，不能自动写成底层模型权重获得无限提升，也不能从有限轮次推导出不受资源约束的能力增长。

这将关注点从“能否自动改代码”转向“能否持续产生可迁移收益”。反复适应同一组选拔任务，可能只增强评测适应能力；新版本任务分数上升，也不代表它更善于提出下一轮有效修改。因此，需要同时研究改进对象、选择机制和跨轮能力积累。相关分支见[技能库与自改进](03_skills_and_self_improvement.md)。

## 八、Long-Horizon：更长的是依赖链，而不只是上下文

前述组件共同服务的一类目标，是让 Agent 在更长时间内持续完成工作。Long-horizon 的 horizon 来自序列决策中对时间跨度的讨论，并不由某个 Agent 产品首次提出。[Towards Long-Horizon Agents: A Survey](https://long-horizon-agents.github.io/)将它放进现代 Agent 系统：前面的决策改变后续条件，系统必须在有限资源下维持目标、状态与反馈。更长的行动链、更迟的结果反馈与更长的环境时间可以相关，却不完全等价。

长上下文是一次容纳信息的能力，长输出是生成文本的长度，长程任务要求持续采取有效行动。能读长文档的系统可能无法在工具失败后恢复；良好的状态摘要则可能让较短上下文支持较长工作流。因此，增加 token 预算不是完整定义，串联许多彼此独立的小任务也未必检验了长期规划。

[Long-Horizon-Terminal-Bench](https://arxiv.org/abs/2607.08964)用可评分的中间子任务观察长程执行进展；[VibeLifeBench](https://arxiv.org/abs/2608.10875)则将长期性放到模拟多周的生活服务场景中，让 Agent 重新检查变化的世界，保持计划一致，并决定何时行动、询问或保持沉默。后者的多周是模拟任务时间，不等于现实中连续运行数周。

二者也说明评测需要同时**更长与更宽**：更长意味着更复杂的依赖、更迟的反馈和恢复要求，更宽意味着更多领域、环境与能力组合。科研复现、生活服务和软件工程可能都很长，却需要不同状态与验收条件，不能用一个最长运行时长代替能力地图。具体脉络见[评测与能力基准](06_evaluation.md)。

## 九、开放问题与研究机会

这些概念共同指向如何组织并积累行动能力，但局部组件的改进仍需要在完整任务中检验。研究机会集中在四个连接处：不同决策方式怎样互补，经验怎样变成可复用能力，目标怎样变成可测任务，以及自动改进怎样跨越当前任务分布。

### 1. 怎样把快决策与慢推理组成真正互补的系统？

值得研究的不只是让低成本模型先答一次，而是为不同决策选择处理方式：哪些交给确定性代码，哪些适合有限选择模型，哪些必须补充观察或展开推理？可以构造包含信息缺失、分布变化和授权边界的工作流，使系统学习升级对象与时机。目标是在完整任务中改善质量、延迟与风险的权衡，特别是让后级修复前级容易犯的错误，而不是重复同一种判断。

### 2. 怎样让记忆和技能成为能够积累、组合与修订的能力？

更有价值的能力库应从实际交互中发现可复用结构，提炼前置条件，识别过时经验，并将局部技能组合为新工作流。相应任务可以让规则、工具和目标逐渐变化，研究旧经验怎样迁移、修订或舍弃。最终需要形成持续改善后续行动的机制，而不只是越来越大的历史记录和脚本集合。

### 3. 怎样把真实世界与希望拥有的未来能力变成 benchmark？

一条路线是把真实工作系统中足够完整的一部分转化为可执行环境，保留状态变化、多方约束与行动后果；另一条路线是从未来希望 Agent 具备的能力出发，形式化持续负责、主动发现问题、跨工具恢复和跨领域迁移等目标。任务需要复杂到足以挑战强模型，同时有合理解法和明确完成条件，避免只靠隐藏信息或任意刁难制造低分。沿更长的依赖链和更宽的领域扩展，才能判断组件是否带来真实能力增量。

### 4. 怎样让自动改进跨越固定任务分布？

可以连接技能发现、harness 适配与 OPD：先在交互中找到失败结构，再选择把经验保存为记忆、固化为程序或用于模型训练。关键是不同载体怎样分工，早期改进能否提高系统解决下一批新问题的能力。研究递归自改进时，还需要区分选择任务、迁移任务和未来改进任务，考察系统是否获得更强的研究能力，而不只是更适合某个固定评价器。
