# 把方向连起来：八个值得带着读论文的问题

[返回首页](../README.md) · [全局总览](overview.md) · [专题覆盖](coverage.md)

专题目录让文献容易查找，但真实系统的问题常常跨越目录边界。记忆失效可能被误诊为推理不足，奖励漏洞可能来自环境而不只是模型，多代理的收益也可能只是多花了计算。这一页不宣布“八个从未有人做过的方向”，而是给出**编者建议的比较问题与实验思路**，帮助你把各章连接起来。

## 1. 长任务失败，到底是不会推理，还是丢了状态？

假设助手在第一个文件里找到关键限制，处理第五个文件时却忘记了。增加推理轮数、换更大的模型、压缩历史、建立任务清单，都可能改善结果，但它们处理的原因不同。若不定位失败发生在哪里，很容易把一种补救方法写成普遍能力提升。

把[基础与工具](../chapters/01_basics.md)、[记忆](../chapters/02_memory.md)和[长任务评测](../chapters/06_evaluation.md)一起读。可先设计一个有明确中间状态的小任务：限制保持不变，但让它距离最终动作越来越远。比较完整历史、摘要、结构化状态与按需检索，记录系统最后是否还能遵守限制。注意分别控制上下文长度和工具调用预算；更短不等于信息保留得更好。

一个有价值的失败分析应能说出：证据从未取得，取得后被丢弃，仍在上下文但未被使用，还是使用了错误版本。这四种错误不应都叫作“记忆差”。

## 2. 自改进真正改变了什么，收益能否带到新任务？

系统可以改提示词、代码、技能库、记忆策略，也可以更新模型参数。如果论文只说“系统迭代五次后提高”，仍无法判断改进对象，更无法确定它是否只是适应了那几道开发题。

连接[技能与自改进](../chapters/03_skills_and_self_improvement.md)、[训练数据](../chapters/04_training_data.md)与[强化学习和蒸馏](../chapters/05_rl_and_distillation.md)。建议先把实验分成开发任务、选方案的验证任务、最后一次才看的测试任务；保留只改框架、只改模型、两者都改的对照。同时记录失败回归：总分提高时，哪些原本能做的任务反而做坏了？

还应追踪经验的来源版本。旧框架里的成功轨迹，可能依赖后来被移除的工具；直接拿来训练新模型，未必是合理监督。讨论“经验能复用”时，需要先问复用所需条件还在不在。

## 3. 评价器是在测能力，还是在把系统训练成自己的偏好？

让一个模型评价另一个模型很方便，但被评价的系统可能学会迎合分数，而不是完成用户的真实目标。即使没有显式训练，人反复根据同一评价器改提示词，也可能逐渐适应其偏好。

连接[评测](../chapters/06_evaluation.md)、[强化学习](../chapters/05_rl_and_distillation.md)与[安全](../chapters/07_safety.md)。一个最小比较可以同时保留程序检查、盲评人工抽样和模型评分。不要只看三者总体相关性，还要逐项检查高分失败：最终文件是否真的存在，是否满足约束，是否用了不允许的数据或操作。

如果评价器参与训练，最终测试还需要一个独立检查来源。所谓独立，不只是换了提示词名称；应当说明检查器是否共享模型、数据、规则和失败盲区。

## 4. 多代理到底带来了分工，还是只是更多尝试？

五个代理比一个代理更容易得到好答案，并不能单独证明分工有效：它们也可能只是多采样了四次。另一方面，把所有代理预算压成和一次单模型调用一样，也未必是唯一合理比较。研究首先应该明确自己要解释哪一种收益。

把[协作](../chapters/08_collaboration.md)与[效率](../chapters/13_efficiency.md)放在一起。可以比较同预算单代理多次尝试、互不通信的多代理、共享工作区的多代理、显式分工的多代理。记录最终质量之外，还看重复工作、互相覆盖、沟通开销和整合失败。

若团队中存在不同工具或专长，再问这些差异是否真正被利用。角色名字不同不等于能力不同；消息数量多也不等于协作充分。一次可信的分析应能找到某个子任务依赖如何被满足，而不是只展示对话很热闹。

## 5. 更好的世界预测，为什么未必带来更好的行动？

预测画面更清晰，可能来自背景纹理更准确；机器人真正需要的却可能是物体是否被抓住、门是否打开、动作会不会碰撞。平均预测误差与任务相关状态之间并不存在自动等号。

连接[世界模型](../chapters/10_world_models.md)、[具身智能](../chapters/11_embodied.md)与[多模态生成](../chapters/16_generation.md)。阅读时分别看观测质量、动作条件是否生效、长序列是否保持一致，以及闭环执行结果。可以在可安全重置的模拟任务里控制动作相同、初始条件相近，只改变用于规划的预测模型，检查哪些预测错误最容易导致决策错误。

若论文强调从模拟迁移到真实，还要单独报告这一段差异。模拟中完成任务，是一项有价值的证据，但它没有自动包括传感器误差、执行延迟、物体损坏和现场安全约束。

## 6. 少用 token、少用参数和更便宜，是同一回事吗？

一个方法减少模型输出，却多调用了几个慢工具；另一个方法共享参数，却增加循环计算；第三个方法降低单次延迟，却需要更大批量才能保持吞吐。它们都可能被称作“高效”，实际优化对象不同。

连接[基础章的接口与调度](../chapters/01_basics.md)、[效率与架构](../chapters/13_efficiency.md)和[技术报告阅读](../chapters/15_frontier_reports.md)。建议至少分开记录任务成功、模型调用、输入输出 token、工具等待、峰值内存和总耗时。若不能测全部项目，就明确哪些未测，不用一个指标代替其余指标。

比较也可以从用户约束出发：例如在固定时间内完成多少任务，或在保证最低质量时需要多少计算。关键是预先说明约束，避免看到哪项数字好看，就临时把那项叫作主要目标。

## 7. 科研中的“对”，究竟是哪一种对？

形式证明可能检查通过，却证明了改写后的弱命题；实验程序可能跑完，却把测试数据用进训练；一个规律可能拟合已知观测，却不能解释新条件。把这些情况全部压成成功或失败，会遮住最需要研究的边界。

连接[科研与数学](../chapters/12_science.md)、[评测](../chapters/06_evaluation.md)与[模型科学](../chapters/14_model_science.md)。建议把题意忠实、程序执行、形式有效、经验支持和研究价值分别列出。不是每个任务都需要全部层次，但缺了哪一层应当看得出来。

这也解释了为什么自动生成更多候选不一定推进科研：如果检查能力没有同步增长，筛选负担可能转移给人。研究产出应包含失败候选和检查依据，而不只是最终漂亮的结论。

## 8. 系统长期运行时，谁负责判断什么时候停？

一个 Agent 反复尝试直到成功，演示可能很好看，但真实使用还需要回答：失败多久算不值得继续？什么时候需要更多信息？什么时候必须交还给人？什么时候应该撤销已经发生的修改？

连接[人机协作](../chapters/08_collaboration.md)、[安全](../chapters/07_safety.md)和[记忆](../chapters/02_memory.md)。可以从低风险、可恢复的文件副本任务开始，给超时、证据矛盾、权限不足和连续失败分别定义停止条件。比较系统是否在该停时停下，以及停止时能否提供足够清楚的状态供人接手。

人的参与也要进入成本分析。一个方法提高自主成功率，却需要人花更久排查少数严重失败，不一定改善整体体验。把人工确认、纠错和复核时间记下来，才能讨论系统对人的真实帮助。

## 把问题写成研究计划

最后，用一页纸回答五件事：我认为失败来自哪里；要改变哪个变量；哪些条件保持不变；什么结果会推翻我的判断；谁能用留下的材料复查它。再回到各章找相关论文，而不是先挑一个新缩写，再想办法给它找任务。

这八组问题是阅读与实验设计建议，不代表尚无人研究，也不保证适用于所有场景。它们的作用，是把丰富文献组织成可以比较和继续验证的问题。
