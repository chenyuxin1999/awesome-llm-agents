06｜评测

更长的任务链，更广的场景与能力
首页 · 专题索引 · 文献目录 · Markdown 版
任务与题目被测的模型或 agent轨迹与中间产物人：用户、专家、人工判断评分器与验收环境与环境状态失败、偏差与泄漏

方向背景：为什么 Agent 需要更长、更宽的评测

设想组里要给一个科研助手选底座模型。大家先翻排行榜：甲模型在知识问答上九十多分，在函数级代码题上也接近满分，看起来无可挑剔。于是把它接上文件系统、命令行和浏览器，让它去复现一篇论文的实验。前几步做得漂亮，它读懂了 README，装好了依赖，跑通了第一个脚本；可到了第三十步，它忘了自己两小时前改过一个配置，结果一路在错误的设置上做对比实验，最后交出一张漂亮却毫无意义的表格。换一个场景，让它在实验室的报销系统里替人填单，它又会在某个下拉框上反复点错，或者在规则不允许的情况下照样提交。排行榜上那串数字，和这两次真实使用的体验，几乎对不上。

这种落差，就是 Agent 评测要处理的核心问题。智能体的应用已经从单次问答扩展到软件开发、网页操作、企业业务、科研和物理环境，任务也从一个明确的步骤变成了持续的交互。系统在某一刻给出正确答案还远远不够，它还要自己发现缺了什么信息，协调好几个工具，记住中间状态，并在环境变化或执行失败以后接着往前推。一套好的评测因此要同时回答两个问题：系统的能力能沿着多长的任务链保持下去，以及它能覆盖哪些场景、哪些能力组合。

本章把这两个问题概括为更长和更宽。更长说的是前后步骤之间的依赖越来越强，目标、约束和工作状态要跨过越来越多的阶段；单纯堆 token、拉长运行时间或者增加工具调用次数，都还摸不到它的实质。更宽说的是覆盖不同的任务环境、知识领域、输入模态、动作接口和验收标准；题目数量多了，覆盖面未必就宽了。一个系统完全可能擅长连续写代码，却不擅长和人澄清需求；也可能在大量短任务上分数很高，却没有一个长流程能稳定做完。

把两条线连在一起的是复杂度。两个长度相同的任务，如果其中一个要在多个应用之间传递状态、同时满足好几条约束、还要处理不完整的反馈，难度就会完全不同。所以描述一个系统时，最好把长程执行、场景覆盖和具体能力组合放在一起说，给它贴一个"通用"或"长任务"的标签，信息量是很少的。

本章先借几篇写得很好的长文，讲清楚 Agent 评测这几年是怎样一步步从题库走向真实工作的；再沿任务长度与复杂度展开前沿工作，并按软件、数字工作、GUI、多模态、科研和具身等场景比较能力需求。评分器、验证器、失败诊断和校准这些方法，是支撑上述评测的工具，放在后文单独讨论。理解一个基准时，先弄明白它让系统完成什么、需要哪些能力，再去看它怎样打分，顺序会清楚很多。

先读这几篇

这一章的主线借自几篇人写的长文。它们的作者有的亲手做过最有影响的 Agent 基准，有的长期在实验室里维护评测体系，叙事里有取舍、有判断，比从论文分类倒推出来的脉络可靠得多。建议按下面的顺序读，读完再回来看各分支的新论文，会轻松很多。

顺序文章为什么读
1Shunyu Yao（姚顺雨），The Second Half（2025-04）本章发展主线的骨架。作者是 ReAct、WebShop 和 τ-bench 的第一作者，他把 AI 的历史分成上下两个半场：上半场大家比拼的是新方法、新模型，基准只是配角，Transformer 被引用了十六万多次，它所测试的 WMT'14 只有一千三百次左右；如今大规模预训练、规模扩展再加上"推理与行动"已经成了一套通用的配方，新基准出一个就被刷穿一个，于是下半场的关键问题变成了"该让 AI 做什么，怎样衡量真正的进步"。他把这叫作效用问题：AI 在棋类、考试和竞赛上早已超过人类，世界的经济面貌却没怎么变。文章还点名批评了两条被默认的评测假设，一是 agent 独自做完任务、最后拿一个奖励，二是题目彼此独立、分数取平均。读完你会明白，本章为什么要把"更长"和"更宽"当成评测的两条主线。
2METR，Measuring AI Ability to Complete Long Tasks（2025-03）"更长"这条线最有影响的一篇。METR 不再用基准分数描述能力，转而问：模型能以 50% 的成功率完成人类专家需要多长时间的任务？他们请人类专家实际计时，对每个模型拟合一条"成功率随人类耗时变化"的曲线，曲线跌到 50% 的位置就是这个模型的时间地平线。人类不到四分钟能做完的任务，模型几乎全对；超过四小时的，成功率不到一成；而这个地平线从 2019 年起大约每七个月翻一番。文章对自己的局限也写得很坦率，结论依赖任务选取和人类基线，外推的不确定性主要来自外部效度。读完能带走一种把"任务长度"量化的思路，以及对任何外推曲线保持警惕的习惯。
3Anthropic，Demystifying evals for AI agents（2026-01）工程一线的评测手册，作者是 Mikaela Grace 等四人。它先把术语理顺：任务、试次、评分器、轨迹、结果，以及评测框架和 agent 框架的区别，并强调评测"一个 agent"其实是在同时评测模型和它外面的那层框架。随后讲三类评分器（代码、模型、人工）各自的长处，讲 pass@k 和 pass^k 的区别，讲能力评测和回归评测的分工，最后给出从零开始搭评测的九个步骤。文中有几个例子很值得记住：一个评测上通过率为零，多半说明任务本身坏了；修好评分器的 bug 之后，同一个模型在 CORE-Bench 上从 42% 涨到了 95%。全文结尾的建议只有一句："去读轨迹"。本章第一节的概念和第五节的支撑方法大量借用了它。
4Jason Wei，Asymmetry of verification and verifier's rule（2025-07）一篇短而锋利的文章，讲的是"验证比求解容易"这件事。数独难解却好检查，一个大网站要写好几年，普通人却很快就能看出它能不能用；反过来，核查一篇文章里的事实，可能比写它还费劲。作者据此提出"验证者法则"：训练 AI 解决一项任务有多容易，取决于这项任务有多容易验证，并把可验证性拆成五个性质：有客观标准、验证快、能大规模验证、噪声低、奖励连续。它解释了为什么 AI 的能力会呈现"锯齿状"，在容易验证的领域突飞猛进。对做评测的人来说，这篇文章提醒我们：能被验证的东西会被优化，所以评测设计本身就在决定 AI 往哪个方向长。
5Jason Wei，Successful language model evals（2024-05）上半场评测文化的一份总结。作者列出了那些真正成功的评测，GLUE、MMLU、GSM8K、MATH、HumanEval，并归纳出它们的共同点：一个数字就能说明问题，分数含义清楚，测的是智能的核心，而且不会太快饱和。他也细数了评测失败的方式：题太少、标注错误多、指标太复杂、运行太贵、评分有争议。读它可以理解"上半场"的评测为什么长成那个样子，也能看清 Agent 评测在哪些地方必须打破这些传统。
6Tanzila Kehkashan 等，From benchmarks to deployment: a comprehensive review of agentic AI evaluation（Artificial Intelligence Review，2026-04）一篇 2026 年发表的 Agent 评测综述，问的正是 Yao 提出的那个效用问题：为什么在基准上得分很高的 agent，搬到真实部署里却常常失灵？作者细读了 AgentBench、WebArena、SWE-bench、GAIA、HumanEval 等 15 个基准，并以软件开发作为主要案例。他们的回答是，现有评测把重心压在"任务有没有完成"上，成本效率、安全合规、可维护性和能否融入真实工作流这些部署时真正要命的维度都被放到了一边。几个统计很能说明问题：15 个基准里没有一个把安全（safety）或安防（security）算进评分，没有一个在主评测协议里计入成本效率，13 个只用二元的成功与否来打分；而只看测试是否通过，又会漏掉代码质量、安全漏洞和集成复杂度。文章据此整理了一套跨领域的评测缺陷分类，讨论了在成本、可复现性和效度之间权衡的轨迹级评测框架，并给出一个很重的判断：眼下妨碍 agent 可靠部署的首要瓶颈出在评测方法上，模型能力倒在其次。它和 AI Agents That Matter 一脉相承，可以当作本章第四、五节的一份 2026 年总账来读。
7Mingguang Chen、Licheng Wang、Bo Qu，The Horizon Gap: Planning, Memory, Execution, Training, and Evaluation for Long-Horizon LLM Agents（arXiv，2026-08）"更长"这条线在 2026 年最新、覆盖面最广的一篇综述。作者系统收集了 2024 到 2026 年间的 1547 篇 arXiv 论文，用"地平线缺口"来概括一个现象：前沿模型能在一次前向推理里解出很难的题，到了需要几个小时的任务上却会忘掉早先的决定、把没做完的工作宣布为完成，或者慢慢偏离目标。它先把三个常被混用的概念分开：长时程是任务的性质，指要走多少步；长上下文是模型的性质，指能装下多少 token；长期记忆是系统的性质，指信息能否跨步骤、跨会话保留。然后把文献按规划、记忆、执行、训练、评测、基础与安全六类排开，再和"地平线落在上下文之内、超出上下文但仍在同一任务内、跨任务持续"这条轴交叉。贯穿全文的发现是，任务越长，只看最终结果的信号携带的信息越少，于是整个领域都在转向过程奖励、信用分配和轨迹级诊断这类更密的逐步信号。结尾留下三个测量上的开放问题：怎样把模型的能力和外层框架的能力分开，训练和评测共用同一种过程信号时怎样避免相关的偏差，长时程的可靠性能否有一个通用的预测理论。读完前面几篇再用它，可以把本章 3.1 的三个小节和第五节的轨迹诊断放进一张 2026 年的全景图里。

如果还想多读一点，Hamel Husain 的 Your AI Product Needs Evals（2024-03）是从产品工程角度写的经典，他把评测分成单元测试、人工与模型评审、A/B 测试三层，并反复强调"去看你的数据"；Kapoor 和 Narayanan 等人的 AI Agents That Matter 则从研究角度批评了只看准确率、不看成本，以及缺少留出集的 Agent 基准，是理解本章第五节预算问题的好起点。

一、先看全景，再分清几个容易混在一起的概念

这一节先用三张总图把整章的骨架摆出来：一张画评测一个 agent 时到底发生了什么，一张画“更长”和“更宽”两条主线怎样把前沿工作排开，一张把第二节要讲的经典工作按时间排成一条线。把这三张图看熟，再去分辨几组容易混在一起的说法，后面读任何一篇评测论文，都能很快找到它在图上的位置。

评测一个 agent，是把任务交给“模型加外层框架”，让它在环境里多步行动，再根据环境的终态打分、用轨迹诊断失败，并把同一任务跑上多次。“更长”和“更宽”是本章排开所有工作的两条坐标，六组概念辨析则是读论文时最常用到的六把尺子。

先看第一张图。它画的是评测一个 agent 时的基本回路，术语取自 Anthropic 的评测手册。

图的左边是一个任务，它包括给系统的指令、环境的初始状态和判断成功的标准。任务交给中间那个紫色的框，也就是被测对象；这里特意写成“模型加 agent harness”，因为同一个模型外面套的提示、工具和重试策略不同，表现就会不同，评测测到的永远是两者的组合。被测对象和下方的环境之间有一来一回两条箭头：它发出动作，环境改变状态并返回观察，这样循环许多步。一次试次结束时会留下两样东西，右上方琥珀色的是轨迹，记下了每一步的输出、工具调用和推理；右下方灰色的是结果，也就是环境此刻的终态。评分器主要依据结果打分，轨迹则用来诊断失败发生在哪里；评分器本身又分代码、模型和人工三类，各有长短。最后，同一个任务要在干净的环境里跑上好几次，才能汇总出 pass@k 或 pass^k 这样的指标。整张图被一个虚线框包住，那是评测框架，它负责给出指令和工具、运行任务、记录步骤、打分和汇总。后文提到的大多数基准，都是在这张图上的某一格做文章：有的换了任务和环境，有的换了评分器，有的改了汇总方式。

第二张图把本章的两条主线摊成一张地图。

纵向是“更长”：从下往上依次是多阶段依赖、动态环境与持续约束、跨任务积累，对应第三节的 3.1.1 到 3.1.3。横向是“更宽”：从左到右是软件与终端、网页与企业、GUI 与多模态、科研与专业、物理与具身和跨领域组合，对应 3.2.1 到 3.2.6。平面里的点是那些同时推进两条线的基准，比如 Long-Horizon-Terminal-Bench 落在“软件”和“多阶段依赖”的交叉处，HANDBOOK.md 和 Thinkingbox 落在“网页与企业”和“持续约束”的交叉处。那条斜着的虚线表示复杂度：越往右上，任务既要维持更长的依赖，又要在更多样的环境和验收标准下工作。这张图的用处在于提醒我们，分类只是为了看清一个基准补上了地图的哪一块，同一个工作完全可以同时属于两条线。

第三张图是主线时间轴，它按第二节的六个阶段分行，把经典工作和几篇主线长文按发表时间排开。

从这张图上能看出两件事。第一，阶段和年份并不严格对齐：ALFWorld 早在 2020 年就出现了，可“进入环境”真正成为主流，要等到 2022 年 ReAct 把推理和行动接起来以后。第二，2023 到 2024 年是基准集中涌现的两年，扩展场景和下半场的代表工作几乎挤在一起；进入 2025 年以后，增长最快的一行变成了“评测成为工程”，大家开始回头追问测量本身靠不靠得住。

几个容易混在一起的概念

读 Agent 评测的论文，最容易被几组相近的说法绕晕。这里先把它们摆开说清楚，每两组配一张小图。

第一组是更长和更多。直觉上，一个任务调用的工具越多、运行时间越久、上下文越长，它就越"长"。可真正让任务变难的，是前后步骤之间的依赖：前面搜集的信息决定后面的选择，中间产物成了下游的输入，早期的一个遗漏要等到交付时才暴露出来。把一百道互不相干的小题连起来做，总时长确实变长了，系统却从来不需要记住第一题做了什么。METR 用人类专家的耗时来衡量任务长度，背后也是这个想法：人类要花四个小时的任务，难就难在这四个小时里的每一步都要接着上一步。

第二组是更宽和更多题。一个基准把题量从一千道扩到一万道，如果这些题都是同一种接口、同一种验收方式，它测到的能力范围其实没变。更宽指的是环境、领域、模态、动作接口和验收标准的扩展：从网页到桌面，从代码仓库到业务系统，从文本到视频，从"答案对不对"到"数据库里的状态对不对"。同一个领域里纳入更完整的真实工作结构，也算一种变宽。

上图左半边的上一排，是一串互相依赖的步骤：搜集到的信息决定后面的选择，中间产物被下游继续加工，最后才交付；那条橙色虚线表示早期的一个遗漏，一直要到交付时才暴露出来。下一排是十道互不相干的小题，做完的总时间也许更长，系统却从来不需要记住前一题。右半边的上一排是同一种题的简单复制，题量翻了十倍，测到的能力范围没有变；下面两排则是真正的变宽，环境从网页扩展到桌面、代码仓库、业务系统和视频，验收方式也从“答案对不对”变成了“数据库里的状态对不对”。

第三组是模型和 agent。Anthropic 的评测手册里有一句很朴素的话：评测一个 agent，评测的是模型和它外面那层框架的组合。同一个模型换一套提示、换一组工具、换一种重试策略，分数可能差出一大截。所以读到"某模型在某基准上得了多少分"时，最好顺手问一句：用的是哪套框架，给了多少预算？

第四组是过程和结果。Anthropic 把一次尝试留下的完整记录叫作轨迹，把尝试结束时环境的最终状态叫作结果。他们举的例子是：agent 说"机票已经订好了"，这是轨迹里的一句话；数据库里是否真有这条预订，才是结果。好的 Agent 评测尽量对结果打分，对过程的检查则用来诊断失败发生在哪里。他们还特别提醒，按照固定步骤序列去评分往往太死板，agent 完全可能找到一条评测设计者没想到的、同样正确的路。

上图左半边对应第三组概念。两个虚线框里放的是同一个模型，只是外面的提示、工具、重试和预算不一样，下面的两个分数就可能差出一大截，所以比较分数之前，先要确认两边用的是同一套框架和同样的预算。右半边对应第四组概念。上面一行是 Anthropic 举的那个例子：轨迹里 agent 说机票已经订好了，评分时要去数据库里核对，有这条预订才算通过，没有就算失败。下面一行画的是按步骤评分的风险：评测设计者预想了一条路径，agent 却可能沿着下方那条虚线，走出另一条同样到达目标状态的路；对结果打分能接受这两条路，按步骤序列打分就会错杀后一条。

第五组是能做到和能稳定做到。同一个任务跑好几次，pass@k 问的是"k 次里至少成功一次"的概率，k 越大它越高；pass^k 问的是"k 次全都成功"的概率，k 越大它越低。前者适合"只要找到一个好解就行"的场景，后者适合面对真实客户、每次都得做对的场景。Anthropic 给过一个直观的算例：单次成功率 75% 的系统，连续三次全对的概率只有 42% 左右。pass^k 这个指标本身来自 τ-bench 论文，作者在那里发现，即便是当时最好的函数调用 agent，在零售场景里八次全对的比例也不到四分之一。

最后一组是能力评测和回归评测。前者问"系统能做到什么"，一开始通过率应该偏低，留出进步的空间；后者问"以前会做的事，现在还会不会"，通过率应该接近满分。一项能力评测被刷到很高以后，就可以"毕业"成回归评测，持续地守住底线。研究论文里报告的大多是前一种，工程实践里天天在跑的往往是后一种，两者回答的问题不一样。

上图左边把第五组概念画成了两条曲线。横轴是试次数 k，两条线都从单次成功率 75% 出发：蓝线是 pass@k，只要 k 次里有一次成功就算数，所以 k 越大越接近满分；橙线是 pass^k，要求 k 次全都成功，所以 k 越大越低，到 k 等于 3 时只剩 42% 左右，和 Anthropic 给的算例一致。图里按各次相互独立来计算，真实系统的失败往往彼此相关，曲线的形状会有偏差，可两条线朝相反方向走这一点不会变。右边对应最后一组概念：能力评测问系统能做到什么，起初通过率偏低；被刷到很高以后，它就可以“毕业”，变成守住底线的回归评测。

二、发展主线：从上半场的题库，到下半场的真实工作

这条主线以 Shunyu Yao 的 The Second Half 为骨架，再用 METR 的时间地平线、Anthropic 的评测手册和 Jason Wei 的两篇文章补上细节。按 Yao 的说法，评测的历史可以读成两个半场：上半场评测是方法的配角，一个数字说明一种能力；下半场评测成了主角，它要追问模型到底能在真实世界里做多少有用的事。从上半场走到下半场，评测一步步把更多的责任交给系统，从回答一道题，到在环境里行动，到在多种环境里行动，到完成真实工作，再到在长时间里可靠地完成真实工作。每多交出一份责任，评测就变得更长或更宽一些，测量本身也变得更难。

上半场：一个数字说明一种能力

上半场的评测由彼此独立的题目组成，模型作答一次，最后平均成一个数字。这种设计简洁好用，也埋下了后来被反复质疑的两条假设。

在评价持续行动以前，人们先要知道模型具备哪些基本的理解与求解能力。Jason Wei 在 Successful language model evals 里回顾过这个时期最成功的一批评测，它们有几个共同的长相：一个数字就能说清楚，分数的含义一看就懂，测的是大家公认的智能核心，而且不会一两年就被刷满。

上图从左往右读。左边一列是题目，它们之间没有任何箭头，表示彼此独立；中间的模型对每道题作答一次。右边分成两种判分方式：MMLU 把答案和标准选项对照，HumanEval 则真的运行单元测试，看写出的函数能不能用。两条路最后汇到同一个框里，平均成一个数字。这套流程的好处正是 Jason Wei 说的那几条：一个数字说明问题，含义一看就懂。底部两个橙色框是这套流程默认成立、后来却被 Yao 质疑的两条假设，下文会反复回到它们。

MMLU 是其中的典型。它把几十个学科的知识与推理题放进同一份试卷，体现的是一种早期的"更宽"：不再只看一个领域。可它的每道题仍然是独立的，系统答完这一题就结束，从不需要在环境里执行后续操作。代码领域的 HumanEval 则让模型根据说明写一个函数，再用测试用例检查功能是否正确，这比比较文字相似度更贴近程序的真实用途。可它的上下文和交付范围依然很小，系统用不着在真实仓库里找缺陷，也用不着协调多个文件的改动。

Yao 对这个时期的评价很直接：上半场真正被奖励的是方法，基准只是用来证明方法有效的考场。这种文化留下了宝贵的遗产，也留下了两个后来被反复质疑的假设：题目之间彼此独立，系统独自作答、最后拿一个分数。Jason Wei 归纳的失败模式在今天依然适用，题太少会让结果充满噪声，标注错误多了大家就不信任它，指标太复杂或者跑一次太贵，就没人愿意用。可一旦评测对象从"回答问题"变成"完成工作"，这些单题、单分数的设计就开始捉襟见肘。上半场的评测告诉我们模型会解多少类题，却回答不了另一个问题：模型能不能把这些能力接成一份完整的工作。

进入环境：推理和行动连起来

从这一阶段起，系统的每个动作都会改变环境，后面的观察取决于前面做了什么。评测因此开始检查一连串动作之后环境的终态，单个答案对不对退到了次要位置。

要回答后一个问题，就得让行动去改变后续的条件。Agent 不再一次性给出答案，它观察环境，选择动作，接收反馈，再决定下一步。Yao 本人 2022 年的 ReAct 让模型在"思考"和"行动"之间交替：先用语言推理当前该做什么，再调用一个动作，读回结果，接着推理。他在 The Second Half 里回头看这件事，认为把推理当作一种动作，是语言模型的先验知识能够迁移到各种任务上的关键，也是今天那套通用配方的最后一块拼图。

上图上半部分是 ReAct 的循环：左上的“思考”用语言推理当前该做什么，右上的“行动”调用一个动作，动作改变了右下的环境，左下的“观察”把结果读回来，再进入下一轮思考。循环结束时，评测去检查绿色框里的终态，看环境有没有达到目标要求的状态；最右边的橙色框写着这一阶段新冒出来的难度，中间状态要维持，前面读到的信息要支撑后面的选择。下半部分是两个考场。ALFWorld 先在 TextWorld 的文本环境里学高层策略，再对齐到 ALFRED 的视觉家居环境里执行，最后检查物体有没有放到位；WebShop 让 agent 在约 118 万件真实商品里按指令搜索、读商品页、选颜色尺寸等选项，最后按所购商品和指令的匹配程度打分。

有了能行动的模型，就需要能让它行动的考场。ALFWorld 把文本中的抽象任务和具身环境中的执行连在一起，让语言理解、规划、导航和视觉感知围绕同一个目标被研究。这里的关键在于，说出正确的动作名称还不够，一连串动作最后要让环境达到目标所要求的状态。WebShop（第一作者同样是 Yao）把连续决策搬进了一个模拟购物网站：系统要根据需求去搜索、阅读商品信息、比较属性，再选出合适的商品。这里增加的难度来自信息的传递，前面读到的商品细节必须支撑后面的选择。它把研究范围从受控的操作任务延伸到带有真实商品描述和组合需求的网页场景，同时仍然保留了可控的环境与反馈。

这两项工作分别展示了更长和更宽怎样相互作用：执行链一长，系统就得维持中间状态；换到一个新环境，它又得理解新的对象、动作和约束。可单一的模拟环境，终究代表不了跨领域的 Agent 能力。

扩展场景：通用性要靠多种环境共同检验

同一个系统要放进多种环境里检验，才谈得上通用。这一阶段出现了三种扩展方式：横向铺开环境、在一个领域里挖深、在一道短题里组合多种能力。

跨环境评测首先要防止一件事：把某一个任务接口上的表现当成通用能力的全部。AgentBench 把操作系统、数据库、网页等不同的交互环境放进同一个评测框架，让模型在不同决策条件下的差异能被看到。它扩展的是环境和任务类型的覆盖面，同一种题的数量倒没有增加多少。

上图三栏各代表一种扩展。左栏是横向铺开：同一个模型被放进 AgentBench 的 8 个环境，从操作系统、数据库、知识图谱到卡牌游戏、横向思维谜题、家务、网购和网页浏览，比较的是它在不同决策条件下的差异。中栏是纵向挖深：WebArena 部署了电商、社交论坛、协作开发和内容管理四类功能完整的网站，还配了地图这样的工具和手册这样的知识来源，agent 要维持登录状态、跨页面理解信息，最后按任务结果的功能正确性评分；论文里最好的 GPT-4 agent 只有 14.41%，人类是 78.24%。右栏是能力组合：GAIA 的题面很短，对人来说概念上也简单，求解却要把推理、浏览、多模态和工具使用接起来，最后只核对答案；人类答对 92%，带插件的 GPT-4 只有 15%。三栏放在一起看，“更宽”至少有三种含义，在读一个声称“通用”的基准时，值得先分清它属于哪一种。

与这种横向铺开同时进行的，是在一个领域里往深处挖。WebArena 搭建了功能完整、可复现的网站，要求 agent 真正去改变或查找外部对象。比起只做一次搜索或一次选择，系统需要维持登录状态，跨页面理解信息，完成实际的业务目标。由此可以看到，"更宽"除了增加领域标签，还包括在一个领域内纳入更完整的真实工作结构。

GAIA 提供了第三种组合方式。它的题面往往很短，求解却需要推理、浏览网页、理解多模态内容和使用工具。这说明题面长度和任务复杂度是两回事。另一方面，这种只看最终答案的任务，和那些要持续改变环境状态的任务，检验的是能力组合的不同部分，仅凭总分很难把它们看成同一种长程能力。

下半场：评测开始追问真实效用

考场被直接换成工作现场：真实仓库、真实操作系统、会说话的用户和真人投票。τ-bench 还把“每次都做对”写成了 pass^k 这个指标。

Yao 在文章里提出的效用问题，在这一阶段变得格外尖锐。模型在考试和竞赛上早已超过多数人，可它到底能不能在真实工作里派上用场？评测给出的回应，是把考场直接换成真实的工作现场。

SWE-bench 从真实软件仓库的问题出发，要求系统读懂已有代码、定位问题，并提交一份能被测试验证的修改。和 HumanEval 的局部函数生成相比，多出来的远不止代码量，还有寻找相关上下文、遵守既有接口、验证改动影响这一连串前后依赖。当然，不同实例的跨度差别很大，仓库级任务也有长有短。Anthropic 的手册里提到，SWE-bench Verified 上的成绩在大约一年里从 40% 左右涨到了 80% 以上，这正是 Yao 所说的基准被刷穿得越来越快。

桌面方向的 OSWorld 把环境扩大到真实操作系统里的网页和桌面应用，并包含跨应用的工作流。系统要把视觉定位、软件操作和文件状态连接起来，在一个窗口里判断正确，离跨应用的完整交付还有不少距离。这同时增加了环境的覆盖面和行动链上的协调要求。

业务方向的 τ-bench 正好对准了 Yao 批评的第一条假设：agent 独自完成任务。它加入了由模型模拟的动态用户、领域 API 和政策规则，并在对话结束后检查数据库的状态。于是"完成任务"取决于三件事：工具有没有调用成功，需求有没有澄清，规则有没有遵守。对话的另一方在过程中陆续提供信息，预先写死的动作序列也就很难覆盖所有情形。同样体现"人在回路里"的，还有 Chatbot Arena：它让真实的人对两个匿名模型的回答投票，论文发表时已经收集了超过二十四万张选票。Yao 把这两项工作并列为突破"自主评测"假设的例子。

上图按编号读。① 左边粉色的是由语言模型扮演的用户，它握有这次任务的目标，却不会一次说完，只在对话中逐步透露；② agent 要追问、澄清，再给出答复；③ 它一边遵守右上方政策文档里的领域规则，一边调用零售或航空的领域 API；④ 这些调用改写了数据库；⑤ 对话结束后，评测把数据库的终态和事先标注的目标状态比对，中间那份对话与调用记录只用来诊断，评分只看终态；⑥ 同一个任务重复 k 次，pass^k 要求 k 次全都成功。论文摘要报告，当时最好的函数调用 agent 成功率不到一半，零售场景里 pass^8 不到 25%。这张图正好把 Yao 批评的第一条假设拆掉了：对话的另一方在过程中不断带来新信息，预先写死的动作序列很难覆盖所有情形。

Yao 批评的第二条假设是题目独立同分布。他举的例子很生动：一位工程师刚进公司时对代码库一无所知，在同一个代码库里待久了就越做越快；可今天的软件 agent 每次都从零开始，前一个任务学到的东西不会带到下一个任务。他呼吁出现能测试长期记忆和经验积累的基准，本章 3.1.3 收录的工作，正是在回应这个呼吁。

这些基准并没有在争夺一个唯一的通用榜单，它们各自补上了一种能力组合：软件工程强调代码与测试的依赖，桌面强调感知和操作，业务服务强调交流、规则和状态。每个领域都在往更完整的工作流程延伸，拼在一起，才是一张更长、更宽的评测地图。

用时间丈量任务：时间地平线

各个基准的百分比没法互相比较。METR 改用“人类完成同一任务要多久”当尺子，把“更长”变成了一个能画趋势线的量；RE-Bench 则显示，给更多时间能多做出多少，本身就是一种能力。

到了这一步，一个新的困难冒了出来。基准越来越多，每个基准的分数都有自己的含义，SWE-bench 上的一个百分比和 OSWorld 上的一个百分比根本没法放在一起比较，更没法回答"Agent 的能力到底长得多快"。METR 在 2025 年 3 月给出了一个很聪明的统一尺度：用人类完成同一任务所需的时间来衡量任务长度。

他们的论文 Measuring AI Ability to Complete Long Software Tasks 从 RE-Bench、HCAST 和 66 个新写的短任务中取题，请人类专家实际计时，再看每个模型在不同长度任务上的成功率。成功率会随任务变长而下降，拟合出的曲线跌到 50% 的位置，就是这个模型的"50% 时间地平线"。按论文摘要，Claude 3.7 Sonnet 的时间地平线大约是 50 分钟；从 2019 年起，前沿模型的时间地平线大约每七个月翻一番，2024 年这个趋势可能还在加快。作者据此外推，如果结论能推广到真实的软件工作，五年之内 AI 就可能自动完成许多人类要花一个月的软件任务。

上图左边是五个步骤。先从 RE-Bench、HCAST 和 66 个新写的短任务里取题，再请有相关经验的人类专家实际去做并计时，每个任务的耗时就是它的长度；然后让模型逐题去跑，记录成败；对每个模型拟合一条成功率随人类耗时变化的逻辑斯蒂曲线；最后读出曲线跌到 50% 处对应的那个耗时。右边的曲线是示意：人类不到 4 分钟的任务，模型几乎全对；超过 4 小时的，成功率不到一成；虚线交点就是 50% 时间地平线。这样一来，不同来源的任务被放在了同一把尺子上，不同年份的模型也就能画进同一张趋势图。

这项工作的意义在于把"更长"变成了一个可以画趋势线的量。它也很坦诚地写出了自己的边界：结果依赖于选了哪些任务、找了哪些人类来做基线，外推的大部分不确定性来自外部效度，也就是实验室任务能在多大程度上代表真实工作。他们还按任务的"混乱程度"划出子集来检验趋势是否稳健，这也提醒读者，干净任务上量出来的地平线，搬到真实场景时要多打几个问号。

METR 早些时候的 RE-Bench 则从另一个角度刻画了长度的作用。它让 agent 和人类专家在七个开放式的 AI 研发环境里比拼：总预算两小时时，最好的 agent 得分是人类专家的四倍；预算拉到八小时，人类略微反超；到三十二小时，人类的得分大约是最好 agent 的两倍。人类从额外时间里获得的收益比 agent 多得多，可见"给更多时间能多做出多少"本身就是一种能力测量，而眼下 agent 恰恰在这里落后。

上图把这组数字画成了柱子，虚线是人类的水平。时间预算短的时候，agent 动手快、试得多，遥遥领先；预算一拉长，人类能在第一次尝试的基础上调整方向，柱子就一路掉到虚线以下。读这张图时可以把它和上一张对照：时间地平线问的是“多长的任务还能做成”，RE-Bench 问的是“多给时间能多做出多少”，两者从不同方向刻画了同一种长程能力。

评测本身成了工程

任务一旦又长又宽，评分器、任务质量、环境隔离、成本和可验证性都可能出错，测量本身就要像工程一样设计和检验。五篇长文从不同角度说的都是这件事。

当任务又长又宽，测量本身就成了一项需要精心设计的工程。Anthropic 的评测手册把这一阶段的经验写得很具体。首先是评分器的选择：代码评分器快、便宜、可复现，却容易僵硬；模型评分器灵活，适合开放任务，可结果不确定，需要和人工判断校准；人工评分质量最高，可又贵又慢，主要用来校准前两者。其次是任务本身的质量：两位领域专家看同一个结果，应该得出相同的通过或不通过的结论，否则问题出在任务上。再次是环境隔离：每次试次都要从干净的环境开始，共享的状态会让失败彼此相关，也会虚高分数。他们举的 CORE-Bench 例子最能说明问题，修好评分 bug、放开过紧的框架限制以后，同一个模型的分数从 42% 变成了 95%。所以他们说，在有人深入看过细节之前，不会把任何评测分数当真。

上图把这段话拆成了三栏。左栏是评分器的选择，三类评分器各有一行长处和一行短处，它们彼此补位：代码评分器负责能写成规则的部分，模型评分器负责开放的部分，人工评分负责校准前两者。中栏是任务质量的检验，同一个结果交给两位专家独立判定，结论不一致，就说明问题出在任务上，这也是“通过率为零多半是任务坏了”的来由。右栏是环境隔离，三次试次各自从干净的环境开始；一旦共享状态，前一次的失败会传染给后一次，分数也会被虚高。底部的 CORE-Bench 例子把三栏串了起来：修好评分 bug、放开过紧的框架限制以后，同一个模型的分数从 42% 变成了 95%，被测的模型一点没变，变的是测量。

Jason Wei 的验证者法则则从更高处解释了评测为什么如此重要。能被快速、大规模、低噪声地验证的任务，就能被构造成强化学习的环境，也就会被优化。评测因此兼具两重身份：它是测量工具，同时也是训练信号的来源。这既是好消息，也意味深长，AI 的能力会呈现锯齿状，在好验证的地方飞速进步，在难验证的地方原地踏步。下半场的评测设计者，其实也在决定 AI 往哪里长。

上图左边是可验证性的五条性质：有客观标准、验证快、能大规模验证、噪声低、奖励连续。一项任务越多地满足这五条，就越容易被构造成强化学习的环境。右边把几类任务按可验证性从高到低排开：数独难解却好验，有测试的代码也很好验；一个网站写起来要好几年，可普通人很快就能看出它能不能用；事实核查有时比写文章还费劲；开放科研的验证又慢又贵还常有争议。柱子从左往右变矮，就是文章说的锯齿状能力。对做评测的人来说，这张图的含义是：把一类任务做成好验证的评测，等于给它开了一条通向快速进步的路。

AI Agents That Matter 补上了第三块：成本和可复现性。作者指出，只报告准确率的 Agent 基准会催生又贵又复杂的系统，也会让人误判准确率的提升究竟来自哪里；许多基准缺少像样的留出集，agent 容易走捷径、过拟合；评测做法不统一，结果就很难复现。这些问题在任务变长、变宽以后只会更严重，本章第五节会逐一展开。

到了 2026 年，这些经验开始被成体系地汇总。Kehkashan 等人在 4 月发表的综述 From benchmarks to deployment 细查了 15 个常用的 Agent 基准，发现没有一个把安全或成本效率放进主评分，绝大多数只看二元的成功与否，作者因此认为，妨碍 agent 可靠部署的首要瓶颈出在评测方法上。8 月的 The Horizon Gap 则从任务长度这一侧给出呼应：它梳理了 2024 到 2026 年的 1547 篇论文，发现任务越长，只看最终结果的信号越不够用，评测和训练都在转向轨迹级的诊断与逐步信号，同时也提醒，如何把模型的能力和外层框架的能力分开，至今仍是一个没有解决的测量问题。这和 Anthropic 手册里"评测一个 agent 就是在同时评测模型和框架"的提醒，说的是同一件事。

边界：仍未解决的问题

经典基准已经能测“完成多步任务”，离“长期可靠”还差四份没被测量的责任。第三节的分支正是把这几份责任一份份放进任务里。

上述经典基准逐步把知识、动作和环境反馈接进了真实工作，可"能够完成多步任务"和"长期可靠"之间还隔着很远。依赖链继续拉长以后，系统需要保存进度、处理工具失败，并在条件变化或中断后恢复；领域继续扩大以后，同一套机制又要适应不同的时间要求和验收标准。METR 的趋势线告诉我们地平线在变长，Yao 的批评告诉我们评测的假设需要改写，Anthropic 的手册告诉我们测量本身就可能出错。这三件事加在一起，就是前沿评测继续沿着更长和更宽展开的起点。

上图顶部的三个框分别对应这一段提到的三件事：METR 的趋势线、Yao 对默认假设的批评，以及 Anthropic 手册里“测量本身可能出错”的提醒。中间从左边的“能完成多步任务”走到右边的“长期可靠”，要经过四份责任：始终知道目标，发现世界已经变了，失败以后能接着做，最终结果仍满足约束。每份责任右侧标出了第三节里专门测它的小节。这四个橙色框，就是下面一段话所说的“原先没被测量的责任”。

前沿工作延续的方向，可以理解为把原先没被测量的责任放进任务里：系统是否始终知道目标，是否发现世界已经变了，是否能在失败后接着做，最终结果是否仍然满足约束。下面先按依赖、变化和积累讨论怎样变得更长，再按领域和能力组合讨论怎样变得更宽。

三、前沿研究方向：更长与更宽

前沿评测沿着两个彼此交叉的方向展开。更长关注任务内部的依赖、执行期间的环境变化和跨任务的经验积累，想解释能力是怎样在持续执行中一点点失效的；更宽关注软件、业务、GUI、科研和具身等场景，想解释不同环境各自要求哪些能力一起工作。下面先展开长度与复杂度，再比较场景和能力组合。同一个基准完全可以同时推进两条方向，分类只是为了看清它补上了能力地图中的哪一块，并不打算给每篇论文贴一个唯一的标签。读这些论文时，可以始终带着两个问题：它把哪一份新的责任交给了系统？它用什么办法确认系统真的承担起了这份责任？

九个小分支收录的都是 2026 年的新论文。每个分支开头先讲问题怎么来的，接着用一行“主线位置”把它挂回第二节的阶段，再用一张图把本分支几篇论文的做法摆在一起。第一节那张“更长与更宽”的地图可以当作本节的目录。

3.1 更长：从完成一个步骤，到维持整个任务过程

任务一旦变长，任务内部的关系就跟着变了。阶段和阶段之间有了依赖，执行期间外部条件可能悄悄改变，前一次任务里攒下的经验还可能影响下一次行动。这三种情况都要求系统有持续性，可它们考验的东西并不相同，也不一定能用同一种记忆或规划方法解决。下面据此分成多阶段协调、动态状态维护和跨任务积累三个小节，单纯用运行时长去衡量它们，会把三者混成一团。

主线位置用时间丈量

对应主线中"用时间丈量任务"一段。接 METR 的时间地平线和 RE-Bench，也回应 Yao 对独立同分布假设的批评。

任务变长以后，难处分成三种：阶段之间的依赖、执行期间的变化，以及跨任务的积累。三者都要求持续性，考验的东西却各不相同。

3.1.1 多阶段依赖：测量完整工作，避免把短题串起来

长程任务里，前一步会改变后一步的条件。前期搜集的信息影响后续决策，中间产物成为下游输入，早期的遗漏也可能直到交付时才暴露出来。真正让任务变难的是这些依赖，调用次数本身反倒是次要的。把一串互不相关的小题接连执行，总时长当然增加了，可它几乎检验不到计划能力、状态管理和跨阶段协调，这就好比让学生连做五十道口算题，看不出他会不会写一篇课程论文。

主线位置用时间丈量

对应"用时间丈量任务"一段。METR 用人类耗时衡量任务长度，这一节关心的是长度背后的依赖结构，以及如何看清系统卡在了哪一段。

要测出长任务卡在哪里，先要把进度拆开来看，再把阶段进度和完整交付分开报告。

上图上半部分是三次运行的对照。每一行有六格，前五格是带分数的子目标，最后一格是最终产物，格与格之间的小箭头表示前一段的产出是后一段的输入。运行甲一格都没亮，属于完全没有推进；运行乙亮了四格，却停在了第五个子目标前，缺了关键产物；运行丙六格全亮，才算最终交付。子目标的分数能告诉我们乙卡在哪里，可只有丙这种完整的一行，才说明几种能力真的一起工作了。左下角是论文摘要里的数字：46 个任务、9 个类别，每次运行平均约 231 个回合、85.3 分钟；即使是最强的模型，部分奖励阈值 0.95 时也只有 15.2%，满分阈值时只有 10.9%。右下角是这一节后文说的“描述长度至少要交代的四件事”。

要看清系统卡在哪里，第一步是把长任务的进度拆开来看。Long-Horizon-Terminal-Bench 就是这样做的，它用细粒度的子目标观察长任务的推进，让评测能区分三种情形：完全没有推进，完成了部分阶段，以及最终交付。这种分解很适合研究瓶颈发生在哪里。问题在于，子目标得分代替不了完整成功率：如果最后缺了关键产物，前面再多正确的步骤也可能没有变成一个能用的结果，就像实验做了九成却没写出报告，导师那里依然算没交。DeepSWE 把同样的问题放进原创的长程工程任务里，后文的软件场景会再比较它的能力要求。

描述一个任务有多长，比报一个运行时长要讲究得多。至少要交代清楚最长的依赖链有多长，需要维持哪些状态，哪些步骤可以并行、哪些必须顺序执行，以及失败后是否允许重来。大量廉价的调用和少量不可逆的操作，很难放在同一把长度尺子上排序；一个任务跨越了多个文件或应用，也要说明这些文件和应用之间是否真的存在信息依赖。

所以，长任务的评价最好同时报告阶段进度和端到端的完成情况。阶段指标帮我们定位能力短板，完整交付率体现这些能力能否一起工作。两者之间的落差，往往比任何一个总分都更能说明，系统离稳定完成长流程还有多远。

3.1.2 动态环境与持续约束：任务进行时，世界也在变化

静态任务可以假设初始条件一直有效，持续运行的系统却躲不开时间推进、外部状态变化和不断冒出来的新约束。设想一个替你管理日程的助手，周一安排好的会议，周三可能被对方取消，它若照着周一的计划继续准备材料，就白忙一场。系统要知道什么时候该重新观察，什么时候该修改计划，以及哪些承诺到了后面的阶段依然有效。评测也就从检验一次计划能否执行到底，推进到检验系统对状态变化的持续响应。

主线位置下半场

对应"下半场"一段对自主评测假设的突破。接 τ-bench 的动态对话方，把"环境在变"从对话扩展到时间和长期约束。

世界会在没有提示的时候自己变化，规则要从头到尾一直有效，还要分清行为到底是不是规则带来的。

上图上半部分是 VibeLifeBench 的设定。一条横线是按自己时钟前进的多周时间线，用户在第一周提出请求，之后橙色的圆点是几次没人宣布的静默变化；agent 在没有任何新提示的情况下，要自己在重新观察、行动、询问和保持沉默之间做选择。右侧的绿色框说明它怎样评分：只读 agent 实际留下的东西，看终态、看行动是否及时、看有没有守住隐含约束。下半部分左边是 HANDBOOK.md：一本 20 到 124 页的操作手册在整个长程工具使用中持续生效，评分同时检查必须做的事发生了、禁止做的事没发生；在每条都过才算通过的严格评分下，最强的模型也只有 36.2%。右边是 Harness-IF 的对照：同一个任务带着规则跑一遍，撤掉规则再跑一遍，如果默认行为本来就符合规则，这条规则就说明不了遵循能力；只计那些违背默认倾向的规则，12 个前沿模型的成绩都会下降 3.6 到 7.4 分。

VibeLifeBench: Can Your Life Agent Be Proactive and Persistent in a Living World?，2608.10875把时间推进、静默变化和长期承诺放进了任务，模型必须自己决定何时重新观察、何时行动、何时询问，以及何时保持沉默。它的核心设定是，环境会在没有任何新提示的情况下自行变化，这比在一次交互中多做几步要难得多。当然，它的模拟时间线仍然是预先设计好的结构，据此还不能说已经覆盖了现实生活里的各种突发事件。

长上下文和长期遵循是两回事，下面两篇工作正好从两个方向说明这一点。HANDBOOK.md 把一本政策手册当作持续生效的约束，观察系统执行到后面的阶段时，是否仍然避开了被禁止的行为。Harness-IF 则通过撤除规则等对照，区分系统是真的在遵循指令，还是它的默认行为恰好和指令一致。前者看约束能否跨过整个过程保持下来，后者帮助判断观察到的行为究竟是不是指令带来的。打个比方，前者考的是新同学三个月后还记不记得实验室的安全守则，后者考的是他戴护目镜到底是因为守则，还是因为他本来就习惯戴。

中断与恢复同样属于长程能力。评测要讲明白恢复时保留了什么：完整的对话、一段摘要、文件、工作区状态，还是只剩一个目标。不同的恢复条件对应着不同的记忆要求。如果每次重启都把完整的答案线索重新喂给系统，就无法据此证明它具备跨上下文维持任务的能力。

重复可靠性也要和单次长任务分开看。允许多次尝试、只要其中一次成功，测的是系统利用重试找到解法的能力，也就是第一节说的 pass@k；要求多次运行都成功，测的则是表现稳不稳定，对应 pass^k。前一种标准会随着尝试机会增加而越来越容易满足，后一种却会把偶发的失败暴露无遗。实际运行中，系统还可能反复撞上同一个错误，所以报告里要说清楚每次是否重置环境、是否共享经验，以及重试能否带来新信息。任务变长和多次运行更稳定是两种不同的要求，彼此替代不了。

3.1.3 跨任务积累：从接着做，到在下一次做得更好

Yao 在 The Second Half 里举过一个例子：工程师在同一个代码库里工作得越久就越熟练，可今天的 agent 每接一个新任务都从零开始。要评测"下一次做得更好"，就得先分清两件事。同一个任务跨会话继续，主要检验状态能否延续；一连串任务中表现的变化，则进一步牵涉经验迁移、偏好适配和技能维护。如果评测只看后一个任务成没成功，就很难分辨收益来自一套可复用的方法、上下文里残留的信息，还是系统先前已经见过类似的答案。

主线位置下半场

对应"下半场"一段 Yao 对独立同分布假设的批评。接 RE-Bench 中人类随时间积累收益的观察，和第 03 章自我改进的评测问题相通。

要证明系统在下一次做得更好，关键是对照：固定其余条件，比较两种运行，再把挑选和测试分开。

上图三行各画了一种对照。第一行来自 Evaluating Skills, Not Just Agents：模型、harness、工作区和评分器全部固定，只改变带不带目标技能，两次运行的差值就是这个技能的贡献；在 947 组配对里，平均综合提升是 0.2134，72.8% 的配对为正。第二行来自 ContinualSkillBench：一串由易到难、相互关联的子任务按顺序执行，一边让系统直接带着之前的记录，一边让它把经验写成显式技能；两者平均表现相近，说明顺序执行带来的收益多半来自对先前上下文和反馈的适应，显式技能只在需要可复用流程的任务上有选择性的帮助。第三行来自 Rethinking the Evaluation of Harness Evolution：如果挑选 harness 用的反馈和最后报告的成绩来自同一个基准，就等于拿测试集挑版本，那条橙色虚线就是这种泄漏；在留出任务上报告，再和同等预算的简单测试时扩展比较，Terminal-Bench 2.1 上的 harness 演化并没有胜过这条基线。

ContextWeave 研究的是工作经验能否帮助后续的流程以及对个体偏好的适配，它把记忆放回任务表现中去评价。ContinualSkillBench 更进一步，比较连续上下文和显式技能维护，追问顺序执行带来的收益是不是来自真正可复用的抽象。两者关心的都是"过去的任务怎样影响未来"，记忆库能存下多少内容，倒在其次。

想把技能自身的贡献单独拎出来，就要做严格的配对。Evaluating Skills, Not Just Agents 固定模型、工作区和评分器，比较有技能和没技能两种运行的结果。技能文档写得规范，和实际调用时带来增益，是两种不同的证据；评价时还要检查新技能会不会损害原有能力，以及环境变化以后系统能否停止使用已经失效的方法。

被更新的对象还可以更大，大到整个执行框架。Rethinking the Evaluation of Harness Evolution for Agents 在反馈和推理预算可比的条件下，把框架演化和任务级搜索放在一起对照，并用留出任务检查泛化。它提醒我们，持续改进的评测必须把候选选择和最终测试分开：在同一批反馈上反复挑最好的版本，证明不了系统在新的任务流里也会持续进步。这和 Jason Wei 当年建议评测同时保留公开测试集和私有测试集，是同一个道理。

3.2 更宽：不同场景要求不同的能力组合

场景一扩展，观察方式、动作接口和成功条件就会一起改变。软件任务要理解仓库和测试，业务任务要遵守规则、和人交流，GUI、科研和物理环境又各自带来不同的感知与验证要求。下面按这些任务结构比较近期的基准，最后再讨论跨领域的能力怎样组合在一起。读的时候请记住，覆盖宽度要看能力和环境的差异，列出来的领域名称有多少个只是表面。

3.2.1 软件工程与终端：从局部修复到跨文件、跨阶段开发

软件环境同时提供代码、文档、命令行和执行反馈，又有现成的测试可以当验收标准，用 Jason Wei 的话说，它是一个很容易验证的领域，所以长程工具使用的研究最先在这里扎根。可软件任务远远不止同一种能力换着题目考：照着明确的 issue 修复、主动发现问题、大规模重构、复现一个应用的功能，对需求理解、代码定位、依赖管理和验证的要求各不相同。

主线位置下半场

对应"下半场"一段的 SWE-bench。这一节的工作沿着任务范围、需求说明和验收方式三个方向扩展它。

软件评测沿任务范围、需求说明和验收方式三条轴往外扩，三条轴上的进展最好分别说明。

上图左边三列各是一条扩展轴，每列从上往下读。第一列是任务范围：从 SWE-bench 的真实 issue 和局部补丁出发，DeepSWE 改用从头写成的长程任务和手写的功能验证器，SWE-Bench ProMax 则把任务扩大到多语言的大规模重构，平均每个实例要改 11.4 个文件。第二列是需求说明：从“告诉你问题在哪”的详细 issue，到 Active-SWE 去掉 issue、让系统主动发现多处问题，再到 ProgramDistill 只给一个能运行的参考应用、让系统从行为里推断功能。第三列是验收方式：随补丁一起提交的测试可能错杀正确的解法，也可能放过不完整的解法；SWE-Bench Pro Verified 堵住了泄漏渠道并修正了题意与测试，SWE-Proof 更进一步用机器检查的证明来验收，前提是规格本身写得忠实。右边是 SWE Refactor Bench 的漏斗：520 次运行先过迁移审计，确认迁移真的发生了，再过固定的行为测试，最后由 6 个独立的 agent 写针对性测试找隐藏的行为差异，三关全过的只有 28 次，约 5.4%。

SWE-bench 把真实的软件问题和执行测试连了起来，是仓库级任务的重要入口。沿着任务范围往外扩，DeepSWE 使用原创的工程任务和功能验证器，减少对公开补丁和原有测试的直接依赖；SWE-Bench ProMax 关注多语言的大规模重构和跨文件协调。前者强调更完整、独立构造的工程任务，后者扩大了需要同时维持的代码关系。判断谁更接近实际开发，要看这些结构上的差别，光看运行步数是看不出来的。

任务说明给得充不充分，也会改变被测的能力。Active-SWE 去掉了详细的 issue 引导，让系统主动定位并修复多处问题，这样就把"发现问题"和"按说明解决问题"分开了。ProgramDistill 则从参考应用的可观察行为出发，要求系统复现功能，额外考验了规格推断的能力。两者的覆盖面都比"给定位置、生成补丁"要宽，可一个扩展的是问题发现，一个扩展的是行为理解，它们落在两条不同的难度轴上。

重构和迁移又带来了新的验收要求。SWE Refactor Bench 先确认所要求的迁移确实发生了，再检查行为是否保持，以免系统把旧实现原样复制一遍也能通过测试。SWE-Bench Pro Verified 则修正了题意、测试范围和评价信息泄漏之间的不一致。任务变复杂和验收变可靠是两项独立的改进，最好分别说明。这让人想起 Anthropic 手册里那句话：一个评测上通过率为零，多半是任务本身坏了。

SWE-Proof 把机器检查的证明引入真实问题的修复，在给定规格下检查正确性。这扩展了可以被检验的性质，可它依然取决于规格是否忠实：证明了代码满足某个命题，还要追问这个命题有没有完整表达需求。说到底，软件评测需要一张能力画像，把需求理解、问题发现、跨文件修改、行为保持和最终交付分开来看，测试通过率只是这张画像里的一格。

3.2.2 网页与企业工作：检索、交互、工具状态和业务约束

数字工作常常横跨网页、文件和业务系统，既要获取信息，也要在明确的权限下改变状态。这里的困难不只来自工具多，还来自目标可能说得不够清楚，对方会在过程中补充要求，以及好几个系统的状态必须保持一致。就像帮导师订一次出差，要查航班、填报销单、同步日历，中途导师还可能说"改成周四出发"。网页导航、引用核查、业务操作和对话协作最好分别当作能力维度来测，再观察它们怎样组成完整的流程。

One Success Isn't Reliability: Thinkingbox，2608.19741面向有持久状态的业务任务，检查最终的后台状态，以及有没有缺失、错误或多余的影响。它的标题就是本节的主旨：一次成功算不上可靠。它通过重复运行检查一次成功能否稳定重现，并把工具调用合规、正常结束和最终业务状态正确区分开，以免把偶然完成当作可靠执行。它的沙箱覆盖的是特定的业务结构，结果不能直接当作生产环境的事故率；真实的并发、服务降级和权限变化仍需另行测试。

Tencent WorkBuddy Bench 按工作域使用相应的验收方式，体现了数字工作评价向多领域产物的扩展。它的价值在于承认不同的工作有不同的成功条件，所有任务交给同一个裁判反倒会失真。如果把各个子域的分数直接平均，系统在某一类关键工作上完全交不了差的问题，就可能被掩盖掉。

3.2.3 GUI 与多模态：从识别内容到定位、操作与时序理解

多模态场景扩大了系统能观察的信息类型，也带进了空间、时间和跨模态对应关系。描述一张图片、编辑一张图表、回答一段视频的问题、在桌面上完成操作，这几件事互相替代不了。评测要分清三层：系统有没有看到必要的证据，有没有理解证据之间的关系，以及能不能根据这些信息正确行动。

主线位置进入环境下半场

多模态评测要分三层测：看没看到必要的证据，理没理解证据之间的关系，能不能据此行动或判断结果。

上图上半部分从左往右是三层能力。第一层是看到证据，PerceptionBench 用十种原子感知能力、3,000 道短答案题把感知单独拎出来，没有哪个模型超过 60%。第二层是理解关系，ChartSync 要求改了数据以后图上的几何跟着联动，Evidence-Backed VQA 要求答案之外还给出时空证据。第三层是行动与判断结果，OSReward 检验的是给计算机操作打分的视觉裁判，发现它们普遍偏宽松，容易把失败判成成功。下半部分左边是同一份 VLM 输出的两种读法：只取解码出来的那个答案，许多样本会并列，排序信息就丢了；按各个答案的概率加权，排序得以保留，在各个异常检测基准上平均高出 7.66 到 19.95 分。右边是 Visual Jev：一张图和上下文只编码一次，多道选择题批量执行、直接读出候选概率，每张图 32 道题时比逐题串行快 8.9 倍。这两项工作提醒我们，评分方式和推理效率都会影响报告出来的数字，要和判断准确率分开测。

PerceptionBench: Evaluating Atomic Visual Perception in Multimodal Large Language Models，2607.24957从已有的错误中整理出一套原子感知能力的分类，用短而明确的问题减少推理和知识的干扰。它解决的是综合总分无法定位感知短板的问题。可原子感知的成绩未必能预测完整 GUI 任务的表现，行动控制、记忆和状态变化这些环节依然在那里。

从基础感知走到计算机操作以后，OSReward 用人工标注的操作轨迹来检验视觉裁判，重点关注失败被误判成成功的情况。它检验的是识别执行结果的能力，行动模型本身会不会操作则是另一回事。ChartSync 用确定性渲染检查图表中文字和几何关系的联动修改：局部文字改对了，整张图的数据关系未必还成立。两者一个补充动作结果的判断，一个补充结构化的视觉编辑。

视频又多了一个时间维度。Evidence-Backed Video Question Answering 同时要求给出答案和时空证据，把靠常识猜对和真正定位到支持片段区分开来。评价长视频时，还要说清楚信息跨度、事件依赖，以及证据是否横跨多个片段；输入变长了，答案未必就需要更长程的理解。

同样的视觉表示，也可能被用来做异常判断或多题决策。A VLM Answer Is Not an Anomaly Score 讨论离散的回答和按概率加权的评分会怎样影响排序；Visual Jev 通过共享图像前缀处理多个选择问题。这里应当把异常区分能力、判断准确性和推理效率分开测量，避免因为某一种评分方式或缓存机制更好，就推断整个多模态系统更强。

3.2.4 科研与专业分析：从知识题到探索、实验和研究产物

专业场景之所以要单独评测，是因为知识正确、工具会用和领域上站得住脚三者缺一不可。回答一道物理题、分析一份因果数据、完成一个开放的研究请求，需要的是三条不同的能力链。领域知识测试仍然有用，可它代表不了系统会选问题、会设计实验、能交付可信的新结果。用 Jason Wei 的验证者法则来看，越往开放科研走，验证就越慢、越贵、越有争议，评测也就越难做。

3.2.5 物理环境与具身任务：预测、探索和闭环控制

到了物理场景，动作的后果、时间延迟和安全约束都被纳入评价，任务成功的含义也随之改变。一段看起来很合理的预测视频，未必符合动力学；一条正确的高层指令，也未必能产生稳定的控制。物理世界的验证又慢又贵，正是验证者法则里最难的那一类。评测既要覆盖感知和规划，也要检查实际的状态变化、接触过程、失败恢复和停止条件。

主线位置进入环境

对应"进入环境"一段的 ALFWorld。从文本具身走向真实的物理量和控制闭环，也是数字世界进步快于物理世界的一个缩影。

物理场景里要一级级检验三个层次：知道已有的规律，从反馈里发现新规律，据此可靠地行动。

上图左边是三级台阶。最下面一级是知道已有的规律，GAUGE 用真实测量的轨迹和物理量去检查模拟器与视频世界模型，结果发现没有哪个物理引擎处处可信，视频模型可能把方程的形式画对，却把加速度、动量传递和振荡时序弄错。中间一级是从反馈里发现新规律，ExplorationBench 造了一些和常识冲突、却能执行验证的“外星世界”规则，系统只有靠试验才能学会。最上面一级是据此可靠地行动，这里要报告任务链、控制频率、观测延迟、人工介入和恢复条件。把合成探索的成绩直接外推到物理部署，就等于跳过了中间那一级。右边是 No Free Checker 的结论：它把约 150 个机器人策略的验证器按“谁来判断”分成四族，人类、规则与形式化方法、学习与预训练的模型，以及策略模型自带的信号；越便宜、越早、越密的验证，可信度就越低，图上那条往右下走的虚线就是这个意思。

3.2.6 跨领域任务组合：覆盖更宽，也要看能力能否一起工作

扩大评测范围有两种办法：把多个领域的独立任务放进同一套测试，或者让同一个任务跨越多个工具、模态和应用。前者衡量的是覆盖面，后者检验的是组合能力。一个系统分别会检索、会读图、会写代码，还说明不了它能在同一个流程里准确地传递证据、维持状态并交付完整的产物，就像一位同学各门课成绩都不错，第一次独立带项目时照样可能手忙脚乱。

主线位置扩展场景评测成为工程

对应"扩展场景"一段的 AgentBench 和"评测成为工程"一段。接 AI Agents That Matter 对可复现性的要求，处理宽覆盖带来的基础设施问题。

扩大范围有两种办法；覆盖面一宽，就需要可重复的基础设施，以及来自真实部署的测试。

上图左栏对比了两种变宽。上排的检索、读图、写代码彼此独立，放进同一套测试，衡量的是覆盖面；下排把它们用箭头串在同一个任务里，证据要传下去、状态要维持住、产物要完整，检验的才是组合能力；UniClawBench 按五种能力组织任务，并在运行中设检查点。中栏是基础设施：AgentCompass 把基准、执行框架和环境拆成三个独立组件，自由组合；Harbor 用适配器把 80 多个基准接进同一套运行方式，并用代码审查和等价性实验核对，再从中精选出 82 道难题组成 Harbor-Index，没有哪种配置的通过率超过 30%。右栏是 TraceDance 的四步：从部署轨迹里找到出现过某种不良行为的决策点，让模型续写下一轮，再按针对这种行为的评分表打分；它不回放环境，所以测到的是局部决策。

AgentBench 把语言模型放进不同的交互环境，提供了跨场景观察的入口。UniClawBench 沿着技能使用、探索、长上下文、多模态和跨平台协调来组织能力，并在运行中设置检查点观察过程。读这类集合时，要分清每项能力是否被单独覆盖，以及哪些任务真正要求多种能力一起发挥作用。

覆盖面扩大以后，可重复的评测基础设施就变得重要起来。AgentCompass 把基准、执行框架和环境分开，帮助在同一套系统接口下组织任务和诊断。Harbor Adapters and Harbor-Index 通过适配器和等价性检查把不同的基准连接起来。统一的运行方式有助于扩展场景，可它不会自动统一任务的含义，移植前后的评分和权限仍然要核对，这和 Anthropic 手册里"评测一个 agent 就是在评测模型加框架"的提醒是一回事。

真实部署还能补上固定基准遗漏的行为。TraceDance 从部署轨迹里构造特定决策点的续写测试，让评测更贴近实际失败的位置；在缺少完整环境回放的时候，它测到的仍是局部决策，最终的长程结果还需要另外检验。把这种局部测试和完整任务评测结合起来，比直接拿轨迹样本量充当覆盖宽度更有解释力。

四、把长度、场景与能力放进同一张评测画像

读完前面这些分支，可以发现长度和场景并不是两个互斥的分类。软件、业务和科研里都有短任务和长任务，同一种记忆能力在不同的环境里也会以不同的方式失效。Yao 在 The Second Half 里说，下半场的研究者要像产品经理一样思考评测；落到实处，就是在读或设计一个基准时，先把它实际覆盖了什么描述清楚，用不着先去找一个包办一切能力的总榜单。下面这张表可以当作描述的坐标。

六个维度组成一张评测画像：读或设计一个基准时，先把它在每个维度上覆盖了什么描述清楚，再拿分数去比较。

维度应描述的条件能帮助区分什么

这张画像的第一个用处是确认比较对象。一个基准只做短期的视觉问答，另一个要求在动态界面里完成业务流程，两者都涉及图像，分数却不能直接放在一起比。两个软件基准如果使用不同的终态验证和任务依赖结构，也要先说清差异，再去讨论模型或系统的进步。

上图把这段话画了出来。六条轴就是上表的六个维度，越往外表示覆盖得越多。橙色的小轮廓是一个只做短期视觉问答的基准，它在具体能力那一轴上有一点长度，其余几条轴都贴着中心；蓝色的大轮廓是一个要在动态界面里完成业务流程的基准，任务跨度、状态变化和组合复杂度都伸得很远。两个基准都涉及图像，可它们的轮廓几乎没有重叠，把两者的分数放在一起比，就像拿一份口算成绩和一篇课程论文的分数比高低。

画像本身是否可靠，也可以被检验。What AI Benchmarks Actually Measure 从测量效度出发，追问那些声称测量同一种能力的任务，是否真的提供了相近的证据。Benchmarking the Benchmarks 则从一致性、复杂度和政策覆盖三个角度检查对话基准。这些研究适合用来审视能力画像，可它们替代不了对实际任务场景的梳理。更长、更宽是覆盖的方向，只靠加难度、加领域标签，质量并不会自然而然地跟上。

五、支撑方法：怎样让更复杂的评测可解释、可复现

评测对象变长、变宽以后，测量本身也遇到了新麻烦。终态分数很难解释长轨迹里的失败，开放的产物需要不同的验收方式，重复运行和裁判调用又把成本推得越来越高。Anthropic 的手册把应对办法比作瑞士奶酪：每一层检查都有漏洞，多叠几层，漏过一层的问题就可能被下一层接住。下面按诊断、评分、不确定性处理和预算控制四层来讲，它们共同决定了复杂任务的得分能不能被解释，不同系统的结果能不能在同样的条件下比较。

四层支撑方法依次回答：失败发生在哪里，开放产物怎样打分，昂贵的复核怎样分配，评测变大以后怎样保持可比。每一层都配一张图。

5.1 长轨迹诊断：失败发生在哪里，能否被恢复

一条失败轨迹里往往有好几个错误，最后报错的地方未必是根因；诊断方法要分清错误在哪里产生、怎样传播、有没有被恢复。

长任务的终态能说明有没有完成，却未必能解释为什么失败。Anthropic 那句"去读轨迹"放在长任务上就更难做到了，一条轨迹动辄几百步，人读不过来。过程分析要区分错误在哪里产生、怎样传播、有没有被恢复，避免把最后报错的那个组件当成根因。STRACE 从批量轨迹中筛出有代表性的失败，再通过文本依赖结构定位相关的步骤；TRAJDEBUG 跟踪错误的整个生命周期，避免把早已恢复的早期错误继续当成最终失败的来源。

上图是一条示意的失败轨迹，从第 1 步走到第 13 步宣告失败。第 3 步出过一个错，到第 5 步已经被恢复，绿色的虚线表示这段经过；真正的根因出在第 6 步，它沿着依赖一路传下去，直到第 12 步才报错。如果只看最后报错的位置，就会把第 12 步当成罪魁祸首。下方五行是本节的方法各自管哪一环：TRAJDEBUG 跟踪每个错误的生命周期，把第 3 步这种已恢复的错误排除在根因之外；STRACE 先从大批轨迹里筛出有代表性的失败，再在文本依赖图上定位根因；Failure as a Process 发现，CLI 编码轨迹里的失败多半在最初几步就开始了，一直藏到无法恢复；OAT 只用成功轨迹学习正常的模式，把偏离之处当作线索；RUPA 则沿着推理、工具和观察之间的依赖边传播不确定性。

Failure as a Process 为 CLI 编码轨迹补充了过程标注，帮助观察那些隐藏在早期的认知偏差；Tracing Agentic Failure from the Flow of Success 先从成功轨迹里学习模式，再把偏离这些模式的地方当作诊断线索。前者依赖错误标注，后者提供异常检测，可异常和原因之间还隔着一步，两者都需要进一步检验。Relational Uncertainty Propagation 沿着推理、工具和观察之间的关系传播不确定性，说明局部的高置信度排除不了远处依赖带来的错误。

这些方法支撑的是对长程能力的解释。文本上的依赖还构不成因果证据，自动诊断给出的原因也未必能指导出有效的修复。条件允许时，最好通过重放或局部替换来检验候选原因；对于没法恢复的环境，则要讲明归因能达到哪一级证据。

5.2 开放产物评分：不同领域难以共用一套通用准则

模型裁判灵活，却会受顺序、措辞、长度和数字偏好影响。近期的改法一种改变分数的表示，一种改变评分的条件。

程序测试、状态比较和领域专家，各自能验证不同类型的产物；开放的文本或多模态输出，有时就得请模型裁判来帮忙。Anthropic 的手册对模型评分器的态度很清楚：它灵活、适合开放任务，可结果不确定，必须和人工判断校准。MT-Bench 与 Chatbot Arena 相关研究讨论了语言模型当裁判的能力与偏差，提醒我们回答的顺序、表达方式和长度都可能影响评价。因此裁判应当围绕任务目标来设计，如果反过来让评分方式决定哪些场景值得测，就本末倒置了。

LLM-as-a-Verifier 利用评分 token 的概率分布形成连续分数，减少离散档位带来的信息损失，这恰好对应 Jason Wei 可验证性五条性质里的"奖励连续"；GAMUT 把内容丰富的评分准则编译成一组二元检查，关注评价结构和实际执行是否一致。前者改变分数的表示，后者组织评分的条件，两者都替代不了对领域事实和真实交付要求的理解。

上图左边是一个示意的评分分布：裁判对 1 到 5 分各给了一个概率，传统做法只取概率最大的 4 分，LLM-as-a-Verifier 则对整个分布求期望，得到约 3.6 分这样的连续值，档位之间的信息因此保留下来。右边是 GAMUT 的两级结构：作者在写评分准则时可以写得很丰富，比如可接受的选项集合、有先后顺序的过程、各条事实的重要性；评分时，一组固定规则把它编译成扁平的二元检查，裁判只需逐条判断是或否，结果就稳定得多。右下角是下一段要讲的随机数校正，它只纠正数值上的偏置。

Mitigating Scoring Bias in LLM-as-a-Judge via Random Number Generation 更进一步，校正裁判在评分数字上的先验偏好。这种校正针对的是数值上的偏置，语义判断对不对仍需另外检查。开放场景越多，越应当保留分领域的人工或程序检查，尤其要审计三种情况：分数很高却没有实际产物，引用支持不了结论，以及过程违反了约束。

5.3 不确定性与升级：把复核预算分给难判样本

级联裁判要同时满足两个条件：路由能识别不确定性，后备者真能纠正交过来的错误。

任务又长又宽以后，逐一人工检查很快就扩展不下去了。选择性验证想做的，是把较贵的检查集中到有争议的样本上。选择性分类与模型校准提供了理论基础：置信度要和实际错误率对得上，自动处理的范围和剩下的风险也要一起报告。

JEV-as-a-Judge 直接接受高置信度的裁决，其余的交给后备裁判；JEV vs. LLMs as Rubric Judges 则在另一些设置里观察到，廉价的决策器和语言模型裁判会犯相近的错误。两项工作合起来看，路由要有效，既要能识别不确定性，也要求后备者真能纠正被交过来的错误。所以评价一个级联系统时，要同时测量总成本、升级比例和升级前后错误的变化，省下了多少次昂贵的裁判调用只是账本的一半。

上图从左往右读。待评的样本先交给廉价裁判，它直接返回标签概率和置信度；置信度高的直接接受，不确定的升级给又慢又贵的后备推理裁判，两路汇合成最终判决。上方那条橙色虚线是本节最后一段的提醒：被自动接受的那一部分也要随机抽查。下方左边是 JEV-as-a-Judge 的结果，阈值事先冻结，在 1,610 对留出样本上，级联比 GPT-6 高 0.9 分，费用只有它的 41%；右边是 JEV vs. LLMs as Rubric Judges 的发现，在 JEV 最有把握的那些错误上，约 96% 的 LLM 裁决重复了同样的错，后备者和前一级错在同一处，升级也就纠正不了什么。

类似的问题也出现在 REFLEX 的选择性控制、ORACLE 的验证器调度和 LLMRouter 的模型路由里。它们分别改变了任务由谁来处理、验证在什么时候发生、资源怎样分配，比较时必须同时报告质量和成本。被自动接受的那一部分样本也要随机抽查，只审计路由器挑出来的难题，会漏掉路由器自己看走眼的地方。

5.4 预算与重复运行：评测更大之后，如何保持可比

早停和抽样能省钱，可省下来的部分要用完整运行的对照来核对；成本的单位也要讲清楚。

AI Agents That Matter 批评过只报告准确率的做法，因为准确率可以用更多的预算买来。评测规模变大以后，预算本身也成了要管理的对象。EarlyEval 利用中间轨迹预测最终结果并提前终止，可以降低开发阶段的评测成本。可早停时的预测并非真正的完成，一个新系统如果更擅长在后期恢复，旧的预测器就可能误判它。所以这类节约方法要保留完整运行的对照，并检查它有没有改变能力排名或失败类型的分布。

上图上方是一次 agent 运行，紫色的方块是已经执行的步骤，灰色的是被省下的步骤。每走一步，成功和失败两个分类器各给出一次预测，任一越过置信阈值就停下。右上角是摘要里的数字：能省掉 13% 到 26% 的步骤，预测准确率在 89% 到 97% 之间，各 agent 的通过率平均只变动一到两个百分点。右边的橙色框是这一段的提醒，早停时的预测并非真正的完成，一个擅长在后期恢复的新系统可能被误判。底部一排是下一段要讲的成本单位，生成 token 只是其中一项。

Test-Time Scaling in Reasoning LLMs 区分了单条轨迹延长、候选采样和前缀搜索三种做法，说明相同的 token 预算也可能对应完全不同的探索条件。长程评测的成本还包括环境运行、工具等待、状态保存和人工介入，只统计生成长度是远远不够的。跨领域比较预算时尤其要讲清楚单位，以免把某类环境里廉价的重试，当成另一类环境也能获得的资源。

最终的报告应当按任务或环境组织重复实验，保留超时、启动失败和模型失败的记录，不要有选择地删掉困难样本。公开任务还需要独立的留出集、按时间切分和版本记录，才能区分能力真的进步了、评价条件变了，还是系统适应了一个固定的基准。这和 Jason Wei 建议同时维护公开和私有测试集、并留意两者分数是否背离，是一脉相承的。

六、研究机会

回到本章开头那个科研助手。它在排行榜上分数很高，却在第三十步忘了自己改过的配置，又在报销系统里违反了规则。这些遭遇恰好对应 Agent 评测还没做好的三件事：真实世界的工作很少被完整地搬进基准；我们希望 agent 具备的那些新能力，比如长期记住自己做过什么、主动遵守规则，还很少被写成可检验的任务；而能让最强模型露出短板、同时又合理可解的任务，本身就很难造。Yao 说下半场的玩法是先定义有用的任务，再用通用配方去解，然后循环往复；下面三个问题，就是这个循环里最缺人做的几块。

三个研究机会分别对应：把真实世界做成基准，把未来的能力写成可检验的任务，以及造出既难又合理、还能评价的任务。它们都回到第一节那张回路图上，分别改的是任务、成功标准和评分器。

1. 如何把现有真实世界，或其中足够完整的一部分，做成测量 Agent 表现的 benchmark？

真实世界里有持久的状态、业务规则、工具依赖、多人交互，以及没法预先列举的异常。这里的研究机会，在于选一个边界清楚的真实系统，尽量保留它的任务结构、状态转移和约束，让 agent 完成的工作有真实的含义；把页面或接口照搬进沙箱只是第一步。要回答的问题包括：哪些部分必须真实执行，哪些可以模拟，怎样验证任务是可行的，以及重置和复现时怎样保住那些决定难度的条件。

基准还应当覆盖自然产生的任务分布，避免只挑那些容易自动验收的工作。可以从真实流程中提取任务，构建可追溯的环境和结果检查，再比较沙箱里的表现和真实流程中的表现是否一致。Anthropic 建议从二十到五十个取自真实失败的任务起步，这对研究型基准同样是个好起点。衡量成功的标准，除了基准能跑起来，还包括它有没有漏掉重要能力，有没有保留失败和恢复，以及得分能不能解释系统在对应现实场景中的实际表现。

2. 如何把未来希望 Agent 拥有的能力形式化为 benchmark？

很多重要的能力，眼下还找不到现成的任务可以抓取。长期自主工作、主动发现问题、跨领域协调、持续积累经验，这些目标都要先转化成可以观察的行为要求，再去设计任务和成功条件。Anthropic 把类似的做法叫作评测驱动的开发：在 agent 还做不到之前，先把计划中的能力写成评测。研究机会在于把这些能力目标形式化为受控的任务族，讲清楚系统能获得哪些信息、能采取哪些行动，以及为什么完成任务就必须用到目标能力。

难点在于防止用一个方便测量的代理悄悄替换掉真正的能力。主动性和多调用几次工具是两回事，长程能力和输入更长是两回事，自我改进和第二次分数更高也是两回事。基准要能排除捷径：一个只是上下文更大、采样更多或者带了预设工作流的系统，是否也能完成？能把这些替代解释区分开，未来的能力才算从概念描述变成了有研究价值的测量对象。

3. 如何构造足以挑战 SOTA 模型的复杂任务，同时保证任务合理、可解且可评价？

任务难，基准未必就好。歧义、不完整的环境和错误的验收都会拉低分数，可这些低分说明不了模型缺少哪种能力；Anthropic 的 CORE-Bench 例子就是前车之鉴。研究机会在于可控地组合任务依赖、信息缺失、动态变化、多工具交接和约束冲突，让挑战来自真实的能力需求，随机加长度或者藏起关键信息都做不到这一点。这里的 SOTA 指当前被比较的最先进系统，具体的模型、版本和预算应当由实验固定下来，它本身是一个会移动的参照。

可以研究任务生成、难度校准和对抗式扩展，并用独立的检查保证任务能执行、目标一致、验收可信。除了整体成功率，还要观察任务在哪个复杂度维度上把系统区分开，失败是否有稳定的机制，以及模型进步以后基准还能不能继续产生有效的挑战。METR 的时间地平线给了一个思路：一把能随能力增长不断延长的尺子，比一批暂时让模型拿低分的固定题目更有长期价值。
