13｜效率与循环架构

少算一些，真的会更快吗？
首页 · 专题索引 · 文献目录 · Markdown 版

方向背景：为什么效率必须按完整任务衡量

设想让一个编程 agent 去修一个仓库里的 bug。它先读需求，再列目录、打开几个文件、跑一遍测试、看报错、改两行代码、再跑测试，前前后后五十来步才收工。每一步，它都要把系统提示、工具说明和到目前为止的全部历史重新交给模型，模型读完这一大段上下文，最后只吐出一小段函数调用，接着就是等工具返回。Manus 团队在一篇工程博客里给过一个很直观的数字：他们的 agent 平均每产出 1 个 token，要先读进去大约 100 个 token。这样的任务里，模型大部分时间在“读”，很少在“写”，中间还夹着大量等待工具的空档。

这就是效率问题在 agent 时代的样子。过去谈推理加速，默认的场景是一问一答：一段提示进去，一段回答出来，量的是每秒生成多少 token。可一旦模型被放进多轮循环，成本就从单次调用摊到了整个任务上：上下文越滚越长，同一段开头被反复读取，多个子 agent 并行运行，工具执行的时间也算在等待里。Anthropic 在介绍自家多 agent 研究系统时说，agent 通常比普通对话多用约 4 倍的 token，多 agent 系统则多用约 15 倍。效率因此决定的远不止账单，它还决定 agent 一次能承受多少探索、多少回溯，以及能不能部署在有限的硬件上。

难点在于，“快”是一个牵涉很多层的结果。参数少了，运算量未必少；运算量少了，等待时间未必短；单个算子快了，瓶颈可能转移到数据搬运、请求排队或者工具等待上。每一种加速办法省下的是不同的资源，只有放回具体的任务、硬件和质量要求里，才能判断它到底让任务快了多少。所以本章读每一项加速，都先问它省了哪一种资源，再问这份节省能不能一路兑现到完整任务上。

先读这几篇

这一章的主线借自几篇写得很好的长文。前三篇讲清了“时间到底花在哪里”这件事，从单个算子一直讲到整套推理服务；后两篇把视角移到模型架构和 agent 任务上。它们大多带着可以手算的例子，读完再去看本章的新论文，很多结论都能自己估算出个大概。最后两篇是 2026 年的综述，一篇收拢推理服务系统里围绕 KV 缓存的工作，一篇收拢 agent 层面的效率工作。

顺序文章为什么读
1Horace He，Making Deep Learning Go Brrrr From First Principles（2022）一切效率分析的起点。作者把深度学习程序的耗时拆成三块：真正在做浮点运算的计算时间，把张量在显存里搬来搬去的带宽时间，以及 Python 解释器、框架调度和内核启动带来的额外开销。他的核心判断很简单：先弄清自己卡在哪一块，再去对症下药。卡在计算上，就该让矩阵乘法用满 Tensor Core；卡在带宽上，算子融合是最有效的手段；卡在开销上，就要靠追踪编译或 CUDA Graphs。文中用连续两次余弦运算说明融合能把显存读写从四次降到两次，读完会对“运算少不一定快”有切身体会。本章第二节的第 1 层就来自这篇。
2Jacob Austin、Sholto Douglas 等，How To Scale Your Model 第 7 章：All About Transformer Inference（2025-02）本章主线的骨架。这本在线书的推理一章按“由内到外”的顺序展开：先讲 KV 缓存为什么必要，再讲预填充受计算限制、逐 token 生成受带宽限制，然后讲批大小怎样在吞吐和延迟之间拉扯，接着介绍缩小 KV 缓存的各种手段，包括分组查询注意力、局部注意力、跨层共享、量化和分页注意力，最后落到服务引擎的设计：连续批处理、前缀缓存、预填充与解码分离，以及推测解码。它给出的估算方法很好用：一步生成的时间下界，大致等于这一步要读的全部字节（参数加 KV 缓存）除以显存带宽。读完它，本章大部分论文在哪一层发力都能一眼看出来。
3kipply，Transformer Inference Arithmetic（2022-03）一篇“只用纸笔估算推理性能”的经典博客。作者推导了 KV 缓存每个 token 的大小，指出每个 token 的前向计算约为参数量两倍次的浮点运算，又用 A100 的算力与带宽之比（约 208）解释为什么小批量解码几乎总是被显存带宽卡住。最有意思的是它的诚实：用这套简单模型估算 13B 模型的单卡延迟得到约 16.8 毫秒，实测是 22.0 毫秒，作者把差距逐项拆给读者看。它教给读者的，是先估一个下界、再解释偏差的工作方式。
4Lilian Weng，Why We Think（2025-05）这篇长文主要讲测试时计算，也就是模型在回答时多花的计算，其中“在连续空间里思考”一节正好是本章循环架构的背景。她把多想一会儿分成两个方向：横向是多生成几步 token，纵向是让同一组层反复计算，并沿着 Adaptive Computation Time、Universal Transformer 一路讲到 2025 年 Geiping 等人的循环深度模型。她的出发点是：一个网络能做到什么，取决于它在一次前向里能用多少计算；如果测试时能多算，并且训练它学会用这份资源，它就会更好。她也提醒，这类模型训练很脆弱，隐藏状态可能塌缩，增加循环次数后的表现还会饱和。
5Yichao 'Peak' Ji，Context Engineering for AI Agents: Lessons from Building Manus（2025-07）一线 agent 产品团队写的工程复盘，把效率问题直接放到了完整任务上。作者认为 KV 缓存命中率是生产环境 agent 最重要的单一指标，因为它同时决定延迟和成本；他举的例子是，按 Claude Sonnet 的价格，命中缓存的输入 token 比未命中的便宜十倍。由此引出一串很实用的做法：开头保持稳定，系统提示开头别放精确到秒的时间戳；上下文只追加、不回改；工具列表不在任务中途增删，改用解码时屏蔽 logits 的方式限制可选动作；把文件系统当成可恢复的外部记忆。读它可以把前几篇里抽象的“前缀缓存”落到具体的产品决策上。
6Jiantong Jiang、Peiyu Yang、Rui Zhang、Feng Liu，Towards Efficient Large Language Model Serving: A Survey on System-Aware KV Cache Optimization（arXiv，2026-07）读完前面几篇，再用这篇 2026 年的综述把第 2、3 层的工作一次铺开。作者只收不重训、不改模型结构的服务期方法，按三个问题归类：什么时候做（执行与调度，包括围绕 KV 缓存的请求调度、把传输和计算重叠起来的流水线、预填充与解码分离、把计算卸载到 CPU 或存储），放在哪里（KV 缓存怎样在显存、内存、SSD 和 CXL 内存池之间搬动，又怎样在集群的设备之间调度），以及存成什么样（量化、低秩近似、剪枝合并这些压缩手段，PagedAttention 式的分页分配和前缀共享，以及 H2O、StreamingLLM、SnapKV 这类在预算内淘汰缓存的做法）。它的几条总结和本章的主线正好呼应：“存成什么样”这一类研究得最多，贡献了大部分显存节省，直接作用于延迟和吞吐的却是“什么时候做”这一类；KV 压缩虽然热门，却很少和其他做法联合设计；能耗普遍没有被报告；而所有类别的方法都会带来质量损失。作者因此把尾延迟、能耗、最坏情况下的失效和统一的评测协议列为接下来的机会。
7Xiaofang Yang、Lijun Li 等（上海人工智能实验室、复旦等），Toward Efficient Agents: Memory, Tool learning, and Planning（arXiv，2026-01，2026-07 修订）这篇综述把视角放到本章最外面的第 5 层。作者认为 agent 的效率对真实部署至关重要，却常常被忽视，于是把 agent 的成本拆成处理的 token 数、推理延迟和外部工具调用次数三项，并给效率下了两种定义：在固定成本预算下效果更好，或者在效果相当时成本更低，两者合起来看就是效果与成本之间的最优边界（帕累托前沿）。全文按记忆、工具使用和规划三块组织：记忆这边讨论怎样构建和压缩文本记忆与参数化记忆、怎样管理和检索；工具这边讨论先用检索器缩小候选工具、并行调用工具、用强化学习训练模型少调用工具，以及只在自己没把握时才调用工具；规划这边讨论快慢两条路径的自适应预算、把任务路由给更小的模型，以及在多 agent 系统里精简通信，因为不加控制时 token 数量会爆炸。作者观察到，实现各异的方法常常收敛到几条共同原则上，比如用压缩给上下文设上限、在奖励里惩罚多余的工具调用、对搜索加以控制。它还整理了评测协议和效率指标。

如果还想多读一点，Anthropic 的 How we built our multi-agent research system（2025-06）从另一个角度谈 agent 的成本：在他们的评测里，token 用量一项就解释了约 80% 的表现差异，并行启动子 agent 和并行调用工具能把复杂查询的研究时间缩短最多 90%，代价是多 agent 系统要用掉约 15 倍于对话的 token，所以只适合价值足够高的任务。

一、基本概念：agent 的一步里，时间花在哪里

agent 的每一步都把越来越长的输入整段读一遍，再写出一小段调用，然后等工具返回。读的那段叫预填充，写的那段叫解码，读时算好存下的中间结果叫 KV 缓存；开头不变的部分可以直接复用缓存。参数量、运算量、显存、延迟和吞吐是几种不同的预算，一项改动常常省了这一种、多花那一种。

可以把模型推理想成一位翻译在工作。他先把整份原稿读一遍，边读边在本子上记下每一句的要点；然后一个字一个字地写译文，每写一个字都要翻回本子看看前面记了什么。读原稿可以一目十行，写译文却只能一个字接一个字。模型也一样：先把输入整段读一遍，这一步叫预填充，它可以对所有 token 同时计算；然后逐个生成输出，这一步叫解码，每生成一个 token 都要等上一个生成完。读输入时，模型为每个 token 算出一对向量，叫键和值，存起来供后面生成时查阅，这份存储就是 KV 缓存，相当于翻译的那本笔记。

下图把编程 agent 的一步画成一圈。每一步交给模型的输入，开头是固定不变的系统提示和工具说明，后面接着越来越长的历史，里面有读过的文件、测试输出和之前的调用。模型先预填充，把这一大段读一遍；再解码，写出一小段函数调用；然后工具去跑测试、读文件，这段时间模型只能空等；工具的结果被追加到历史末尾，下一步再从头读一遍。底下那根长条是 Manus 给出的比例，读进去的大约是写出来的一百倍。

左上角那行字是全章最实用的一个观察：系统提示和工具说明只要一个字不改，这一步的开头就和上一步一模一样，它们的 KV 缓存可以直接拿来用，省掉这一段的预填充，这叫前缀缓存。在读远多于写的 agent 里，这份复用省下的比解码快一点要多得多，Manus 的整套上下文工程几乎都在围绕这一点做取舍。

几种不同的预算

回到那位翻译。要让他交稿更快，可以给他配更快的笔，可以让他少翻笔记，也可以让好几位翻译同时开工；每种办法省下的东西不一样，付出的代价也不一样。模型推理也有几种不同的预算。参数量是模型有多少独立的权重，决定了要占多少存储；运算量是一次前向要做多少次浮点运算，论文里常写作 FLOPs；显存里装着权重、计算中的临时数据和 KV 缓存；延迟是一个请求从发出到拿到结果花的时间；吞吐是单位时间里能处理多少请求或 token。

这几样经常朝不同方向走。参数少的模型可能要多算几遍；一次处理很多请求能提高吞吐，可每个请求要排更久的队，延迟反而变长；运算量少了，如果数据要在显存里多搬几趟，等待时间照样不短。所以读一篇效率论文，第一件事是看清它省的是哪一项，又在哪几项上和对手做了对齐。只说“快了”或“小了”，读者没法判断这份节省在自己的任务上能不能兑现。

二、发展主线：从一个算子到一整个任务，时间花在哪里

这条主线以《How To Scale Your Model》推理一章的展开顺序为骨架，再用 Horace He 的三种瓶颈作为最底下的一层，用 Lilian Weng 和 Manus 的文章补上架构与 agent 两层。把它们叠在一起，效率研究的这些年可以读成一架由内向外的梯子：每往外走一层，要考虑的东西就多一些，局部的节省也就越难原样兑现到最终的等待时间上。

五层研究问的都是同一个问题：时间花在哪里，怎样少花。它们只在一点上不同：看的范围有多大。第 1 层只看一个算子，第 2 层看一次完整的生成，第 3 层看许多请求一起服务，第 4 层回到模型结构本身、问每个 token 该分多少计算，第 5 层看整个 agent 任务。范围越大，局部的节省越容易在别处被抵消，边界一节记下的就是这些抵消。

第 1 层：先弄清楚卡在哪里

一切优化从诊断开始：先弄清时间花在计算、显存搬运还是调度开销上。FlashAttention 和低精度这两条线都从这里出发，它们共同的教训是，数据怎样在显存里流动，本身就是算法的一部分。

Horace He 在 2022 年那篇文章里打过一个比方：GPU 像一座工厂，计算单元是车间，显存是仓库，数据要从仓库运到车间才能加工。车间再快，运货的路堵了，整座工厂照样闲着。他由此把耗时分成三块。第一块是计算，主要是大矩阵乘法，这是你花钱买 GPU 想要得到的东西。第二块是带宽，像逐元素的余弦、归一化这类操作，几乎所有时间都花在把数据读进来、写回去上，算力再强也帮不上忙。第三块是开销，Python 解释器、框架分发、内核启动都在这里，它通常不随问题规模增长，所以一个简单的诊断方法是把批量翻倍，看运行时间是否也大致翻倍。

卡在带宽上时，最有效的对策是算子融合，下图下半部分是他的例子。对同一个张量连做两次余弦，不融合时，第一次余弦要从显存读进来、把中间结果写回去，第二次再读进来、再写回去，一共四次显存读写；融合成一个内核以后，中间结果留在片上，只需要读一次输入、写一次输出。两次余弦的运算量一点没少，省下的全是搬运。这类操作在运算量里占比很小，在运行时间里却不小：他举的 BERT 例子里，非矩阵乘法的操作只占约 0.2% 的浮点运算，实际算力利用率却远低于矩阵乘法。

2022 年的 FlashAttention（2205.14135）把同一个思路用到了注意力上。标准实现要先算出整张序列长度乘序列长度的分数矩阵写回显存，再读回来做 softmax，再写回去，再读回来乘上值矩阵；序列越长，这张中间矩阵越大，来回搬运也越重。FlashAttention 把输入切成小块，一次只把一块搬进片上存储，在块内算分数、边算边更新 softmax 需要的统计量、把结果累加到输出上，完整的分数矩阵从头到尾没有落回显存。注意力的公式一个字没改，变的只是数据流动的路线，可速度和能处理的序列长度都上了一个台阶。

低精度是这一层的另一条线，它从“每个数存几位”入手减少搬运：权重从 16 位降到 8 位或 4 位，同样的带宽就能多运一倍甚至几倍的数。难处在于误差。2022 年的 LLM.int8()（2208.07339）发现，大模型里会系统性地冒出少数数值特别大的特征维度，直接压成 8 位会严重损伤精度，于是把这些离群维度单独留在 16 位里计算，其余绝大部分数值用 8 位。同年的 GPTQ（2210.17323）用少量校准数据和近似的二阶信息估计每个权重对误差有多敏感，一次性把权重压到每个 3 到 4 位。两篇都说明，位宽降下来之后，误差落在哪里、算子能不能真的用上低精度，决定了收益能不能兑现。本章三.7 的新论文就接在这里。

第 2 层：一次生成里，解码被带宽卡住

解码一次只出一个 token，时间几乎都花在读权重和 KV 缓存上。于是出现了两条路：让每一步要读的东西变少，也就是缩小 KV 缓存；或者让一次读进来的东西多干点活，也就是推测解码。

把视角从单个算子放大到一次完整的生成，问题的形状就变了。kipply 2022 年的博客用纸笔算清了这件事。每生成一个 token，前向计算大约需要参数量两倍次的浮点运算，同时要把全部权重从显存里读一遍。A100 的算力和带宽之比约为 208，意思是每读进一个字节，要做两百多次运算才能让计算单元忙起来。解码一次只处理一个 token，批量又小的时候，运算远远填不满这个比例，于是时间几乎全花在读权重上。《How To Scale Your Model》用 TPU v5e 做了同样的推算，结论是 bf16 下大约要攒到 240 个 token 的批量，解码才能摸到算力上限。预填充正好相反，长提示天然带来大量可以同时计算的运算，它受算力限制。

下图把这两个阶段并排画了出来。左边的预填充让提示里的 8 个 token 一起进入同一次前向，顺手把每个位置的键和值写进 KV 缓存；右边的解码每一步只有一个新 token，却要把全部权重和 KV 缓存读一遍，并且每走一步，缓存就多一格。agent 恰好两头都占：每一步都要预填充一段很长的输入，再解码一段很短的输出。

既然解码的时间花在“读”上，就有两条路：要么让每一步读的东西变少，要么让一次读进来的东西多干点活。先看第一条路。权重的大小是固定的，KV 缓存却随历史变长、随并发变多，所以压缩的目标落在缓存上。下图把缓存的大小拆成几个相乘的因子：同时处理多少条序列，每条保留多长的历史，有多少层，每层有多少组键值，每组多大维度，每个数用几个字节。压住任何一个因子，缓存都会变小。

最早压住“组数”的是 2019 年 Noam Shazeer 的 Fast Transformer Decoding: One Write-Head is All You Need（1911.02150）。注意力有很多个头，每个头本来各存一组键和值；他提出的多查询注意力（MQA）让所有头共用一组，解码时要反复读入的张量一下子小了很多，质量只略有下降。2023 年的 GQA（2305.13245）取了个折中，让若干个头共享一组键值，并且展示了只用原始预训练约 5% 的计算，就能把现成的多头模型改造成这种结构。2024 年的 DeepSeek-V2（2405.04434）提出多头潜在注意力（MLA），把键值压进一个低维向量，同时压住了组数和维度，报告的 KV 缓存比自家 67B 模型减少了 93.3%。跨层共享压的是层数，量化压的是字节。图最右边的分页分配不在这个乘式里，它改的是同样大小的缓存在显存里放得有多紧凑，第 3 层会讲到。

上面这些办法让每个 token 存得更少，可历史一长，缓存终究装不下，另一组工作于是考虑压住“历史长度”，只保留一部分 token。2023 年的 H2O（2306.14048，Heavy-Hitter Oracle for Efficient Generative Inference of Large Language Models）观察到少数 token 贡献了大部分注意力分数，于是只保留最近的 token 和这些“重击手”。同年的 StreamingLLM（2309.17453，Efficient Streaming Language Models with Attention Sinks）发现模型会把大量注意力投向开头几个 token，哪怕它们在语义上并不重要；如果把它们丢掉，长输入就处理不稳，保住这几个“注意力汇”再加一个只看最近一段的滑动窗口，就能稳定地处理很长的输入流。它们为后来的缓存裁剪研究立下了基线，也留下一个问题：被丢掉的那部分，在哪些任务上其实是关键证据？本章三.6 正在追问这个问题。

第二条路是让一次读进来的东西多干点活。解码慢，是因为大模型每次读一遍权重只产出一个 token；如果能让它读一遍权重就确认好几个 token，等待就短了。2022 年底 Google 的 Speculative Decoding（2211.17192）和 2023 年初 DeepMind 的 Accelerating Large Language Model Decoding with Speculative Sampling（2302.01318）几乎同时提出了这个想法：先让一个便宜的草稿模型猜几个 token，再让大模型一次性检查。下图是一轮的四步。草稿模型逐个猜出 4 个 token；大模型对这几个位置做一次前向，只读一遍权重就把它们的概率一起算出来；然后从左往右逐个检查，大模型给这个 token 的概率不低于草稿模型就直接收下，否则按两者之比的概率收下，一旦某个位置被拒绝，就在这里按修正后的分布重新采一个 token，后面的草稿全部作废。这套接受规则保证了输出的分布和直接用大模型采样完全一致，后者报告在 70B 的 Chinchilla 上取得了 2 到 2.5 倍的解码加速。

草稿猜得越准，每轮收下的 token 越多。2024 年的 EAGLE（2401.15077）因此不再用独立的小模型猜 token，改为猜大模型倒数第二层的特征，再喂入提前一步的 token 序列来降低不确定性。《How To Scale Your Model》对推测解码的评价很到位：它用额外的运算换更低的延迟，在批量小、算力闲置时最有用。本章三.5 的新论文都在这条线上，讨论的是草稿从哪里来、缓存怎么省、任务变了怎么办。

第 3 层：很多请求一起来，调度成了算法

许多请求一起来时，缓存怎么分配、开头相同的请求怎么复用、预填充和解码怎么排，本身就成了算法。一项模型层面的节省，要接进这些机制里才能变成真实的收益。

真实的服务里，几十上百个请求同时到达，长短不一，有的刚开始预填充，有的已经生成到一半。把它们拼成一批一起算，读一遍权重就能服务很多请求，吞吐因此提高；可 KV 缓存会随批量线性增长，单个请求的等待也会变长。《How To Scale Your Model》把这个两难放在推理一章的中心：同一套硬件，追求低延迟和追求低成本会走向完全不同的配置。

显存于是成了最紧的资源。每条序列最终有多长事先不知道，如果按最长可能预留连续的空间，大部分都会空着。2023 年的 PagedAttention（2309.06180）借用操作系统的分页思想，把每条序列的缓存切成固定大小的小块，写满一块再分配下一块，用一张块表记下每块放在显存的哪里，物理位置不必连续。碎片少了，同一块显存能装下更多并发请求，配套的 vLLM 也成了常用的开源推理引擎。块表还带来一个好处：两个请求开头相同，它们的第一块可以指向同一份缓存，只存一次。

同年的 SGLang（2312.07104）把这种共享推广成一棵基数树（RadixAttention）：根节点是所有请求共用的系统提示和工具说明，往下分出各段对话的历史，每来一个新请求，就沿树找到最长的公共开头，只有末端那段新输入需要重新预填充。这正是 Manus 那句“KV 缓存命中率最重要”在系统一侧的落脚点：agent 的系统提示、工具说明和对话历史大段重复，复用得好，预填充就能省掉一大半；可开头里改动一个字，这棵树就要从那里断开，后面的缓存全部作废。

预填充和解码混在一起调度，又会互相干扰。一个带着长提示的新请求进来，它的预填充会占满一整批，正在解码的请求只能停下来等，用户看到的就是输出突然卡住。2024 年的 Sarathi-Serve（2403.02310）把长预填充切成大小相近的块，每一块和正在进行的解码拼在同一批里执行，解码就一直在往前走。同年的 DistServe（2401.09670）干脆把两个阶段放到不同的 GPU 上，前一组算完把 KV 缓存传给后一组，两组分别按首 token 延迟和每 token 延迟配置资源，代价是中间多了一次缓存搬运。下图把三种调度方式画在同一条时间轴上。

第 4 层：每个 token 该分到多少计算

这一层的方法都在改模型结构，决定每个 token 分到多少计算，差别在怎样分：循环让同一组层多算几遍，自适应停止让难的 token 多算、易的少算，稀疏激活让每个 token 只用一部分参数，状态模型改变历史信息保存的方式。

前三层讨论的都是给定一个模型怎样把它跑快。还有一条更早就开始的线索，从架构入手，问的是每个 token 到底该分到多少计算。普通的 Transformer 对每个 token 一视同仁：不管是一个逗号还是一道题的关键一步，都走完全部层、用上全部参数。

第一种改法是让同一组层反复用。2017 年的 Attention Is All You Need（1706.03762）用注意力取代了循环网络，让序列中所有位置可以同时计算，奠定了今天大模型的基本结构。仅仅一年后，Dehghani 等人的 Universal Transformers（1807.03819）又把循环请了回来，这次换成在深度方向上循环：同一组层反复作用于每个位置的表示。Lilian Weng 在《Why We Think》里点明了它和普通 Transformer 的关系：循环步数固定时，它就等价于一个各层共用同一组参数的多层 Transformer。所以它省下的是权重，每多转一轮，运算就多一遍。

循环之后自然要问转几轮。Alex Graves 2016 年的 Adaptive Computation Time for Recurrent Neural Networks（1603.08983）给出的办法是自适应计算时间（ACT）：网络每走一步，一个停止单元给出停下的概率，累计够了就停，于是简单的输入早点停、困难的输入多走几步。Universal Transformers 用它来决定每个位置的循环次数。Weng 评价说，这项工作早于大模型，却开创了同一个方向。

另一种改法是让每个 token 只用一部分参数。2021 年的 Switch Transformers（2101.03961）把一层里的前馈网络复制成很多份“专家”，由一个路由器为每个 token 只选其中一个，这种结构叫混合专家（MoE）。专家越多，总容量越大，单个 token 的计算却保持不变；它把“模型大小”拆成了存储容量和活跃计算两项，同时带来了路由和负载均衡的新问题。2023 年的 Mamba（2312.00752）则从信息怎样保存入手：注意力要为每个历史 token 都存键和值，Mamba 用选择性状态空间模型替代注意力，生成时只维护一个固定大小的状态，从一个 token 传给下一个，缓存因此不再随历史变长。下图把这四种分配方式和普通的层堆叠并排画出。

这条线在 2025 年迎来了一个转折。Geiping 等人的 Scaling up Test-Time Compute with Latent Reasoning: A Recurrent Depth Approach（2502.05171）训练了一个 35 亿参数、用 8000 亿 token 训练的模型，在标准 Transformer 里放一个可以反复调用的循环块，测试时多转几圈，推理基准上的表现就随之上升，某些情况下的计算负载相当于一个 500 亿参数的模型。下图上半部分是它的一次前向：开头几层（论文叫 Prelude）把输入变成向量，循环块从一个随机初始化的状态出发，每一轮读入上一轮的状态和重新注入的输入向量，转若干轮之后，由末尾几层（Coda）把状态变回下一个 token 的概率。下半部分是训练方式：每个序列随机抽一个循环次数，平均 32 轮；为了让显存不随轮数增长，只对最后 8 轮做反向传播，这叫截断反传。本章三.1 到三.3 的许多论文都在这个结构上改动。

Lilian Weng 把这类工作看作纵向的“多想一会儿”，和横向多生成思维链 token 互为补充。她也坦率地指出了问题：只反传最后几轮，隐藏状态容易塌缩成同一个值，需要小心调参；增加循环次数后的收益会饱和，能否外推到更多轮仍是未知数。由此引出前四个分支要回答的问题：循环的收益来自结构，还是来自多花的计算（三.1）；共享参数被反复使用，训练怎样才能稳定（三.2）；哪些 token 值得多转几圈（三.3）；已经训练好的模型能不能不重训也循环起来（三.4）。

“循环”这个词在本章还有另外两种用法，读论文时要分清。下图左边是上面说的跨深度循环，同一个 token 的表示反复经过同一个共享块；中间是跨时间递归，状态从前一个位置传给后一个，Mamba 属于这一类；右边是工具循环，也就是开头那个 agent 与外部环境之间一轮轮的往返。三者的缓存方式、训练方法和验证要求各不相同，本章三.1 到三.3 讨论的几乎都是左边那一种，三.4 开始把中间和右边也牵扯进来。

第 5 层：放大到完整任务

到了完整任务，前几层的问题全都还在，又多了多轮上下文、工具等待和多 agent 并行。一线团队的经验是，在输入远多于输出的 agent 里，缓存命中率比解码速度更能决定成本。

最外面一层是 agent 本身。Manus 的文章说得很直白：agent 的输入输出比大约是 100 比 1，上下文每一步都在变长，输出却往往只是一段结构化的函数调用，所以预填充和缓存命中率才是成本的大头。他们的前四条做法都为了让第 3 层那棵前缀树不断开：保持开头稳定，上下文只追加不回改，序列化时保证 JSON 键的顺序固定，以及不在任务中途增删工具。最后一条最巧妙：工具列表一改，开头就变了，所以他们让列表保持不动，改为在解码时屏蔽不该选的工具对应的 logits，也就是把那些选项的生成概率压到零。

上下文终究会变得太长。Manus 的第五条做法是把文件系统当作外部记忆：网页正文可以从上下文里丢掉，只要留下 URL，需要时就能重新打开。这是一种可以恢复的压缩，和第 2 层那些丢了就找不回来的缓存驱逐正好互补。下图把这五条做法和它们服务的目标连了起来。

边界：省下的东西能不能兑现

梯子每往外走一层，局部节省被稀释或抵消的机会就多一些。本章各分支里的负结果，准确地标出了兑现失败的位置。

就连最底层的估算也会落空。kipply 用纸笔估出 13B 模型单卡延迟约 16.8 毫秒，实测是 22.0 毫秒，差了约三成，原因是带宽达不到标称值、中间操作有额外开销、内核启动也要时间。往外走，到了服务层，排队和批处理会改变每个请求的实际延迟；到了任务层，工具等待和上下文重读又可能把模型层面的加速吞掉。本章各分支里有不少负结果，比如门控循环省了内存却增加了延迟、跳层脱离服务引擎后反而变慢、复杂的缓存选择器输给了保护提示后的随机裁剪，它们的价值就在于准确地标出了这些兑现失败的位置。下图把它们按层排开。

“精确还是近似”一列要多说一句。精确的加速保持输出不变，或者保持输出的概率分布不变，满足校正条件的推测解码就属于这一类；近似的加速接受一定误差，换取存储或速度，量化、跳层和缓存裁剪属于这一类。近似方法完全可以可靠，前提是讲清误差有多大，并给出完整的质量随成本变化的曲线，只挑最省的那一个点来报告是远远不够的。

三、前沿研究方向

下面八个分支收录的都是 2026 年的新论文。前四个分支集中在主线的第 4 层，讨论循环与自适应深度这类“给每个 token 分配计算”的架构问题；后四个分支沿着第 2、1、3 层往外走，分别对应推测解码、长上下文缓存、低精度和完整服务。读这些论文时，建议始终带着两个问题：它省下的是哪一种资源，它用什么证据说明这份节省在完整任务上依然成立。

八个分支都在回答同一个问题：某一种节省能不能兑现成完整任务上的收益。它们的差别在节省落在哪一层：前四个在模型结构上，后四个依次在单次生成的解码和缓存、算子的数值精度以及多请求的服务上。

1. 公平比较：循环收益来自结构，还是额外计算？

让同一组参数多转几轮，模型就能在不增加权重的情况下获得更深的计算路径。这听上去像是白捡的深度，可我们等待的是完整结果，参数文件变小本身并不缩短等待。多转的每一轮都要花时间、花运算，所以一个循环模型比普通模型分数高，首先要问的是：它是因为结构更好，还是因为多算了？和不共享参数的模型比较时，“参数量相同”与“每 token 运算量相同”是两种条件，循环之外的输入输出模块、注意力的组织方式、是否提前停下，又都会改变每一轮的成本。这个分支的论文首先就是在把比较条件厘清。

主线位置第 4 层

第 4 层，循环深度的公平比较。接 Universal Transformers 的跨层共享参数和 Geiping 等人的循环深度模型，同时借用 Switch Transformers 把“总容量”和“活跃计算”分开记账的思路。

四篇工作都在比循环类模型和普通模型，差别在对齐了哪几项预算、怎样加计算：SMELT 同时对齐运算、参数和缓存三项，Loop the Loopies! 只说对齐了计算，MoRE 把共享细到专家一级，Hidden Decoding 干脆把额外计算加在序列方向。对齐的预算越全，剩下的收益越有把握归给结构。

下图上排是同一个循环模型在三种比较条件下的样子。按参数相同来比，循环模型每个 token 的运算明显多出一截，分数高了也说不清是结构好还是多算了；按每 token 运算相同来比，参数这一项又对不齐了；只有运算、参数和 KV 缓存几项同时接近相等，剩下的差别才有较大把握归给结构。

真正把预算账算细的是 SMELT（2609.01343）。它研究循环的 MoE 模型，设计是前段层和后段层各走一遍、中间一半层走两遍，并在每 token 运算量、非嵌入参数和 KV 缓存三项都接近匹配的条件下和普通模型比较。为了说明节省了多少，作者对每种结构拟合了计算最优前沿，也就是在不同训练预算下，通过选择模型规模和训练量所能达到的最低损失。论文报告，循环结构在这条前沿上节省 6.8% 到 18.0% 的训练 FLOPs，优势还迁移到了下游基准，其中代码任务上的收益最大。三项预算同时匹配之后仍然观察到收益，这项实验就排除了“只是多算了”这个最主要的混杂因素。当然，这些结果有其模型规模、数据和拟合范围，训练计算上的节省也没法按相同比例换算成推理服务的加速。

Loop the Loopies!（2607.16051） 同样在计算匹配的条件下比较循环 MoE 和普通 Transformer。它和 SMELT 适合放在一起读，只是两篇都写着 matched compute，预算口径却未必相同：预训练数据、有效层数、激活专家数、训练时长和调参范围都可能有差别。更有说服力的做法是报告完整的质量与计算曲线，避免拿某个循环模型的最佳点去对照普通模型一个没有调好的点。

共享参数不一定要以整个循环块为单位。MoRE（2609.18176） 让邻近几层共用一个专家池，再给每层一个深度嵌入，让专家知道自己正在服务哪一层。它让人看到，参数复用可以有很多种粒度，共享整层、共享专家、共享缓存，各自带来的信息约束都不一样。真正的研究问题是哪些模块确实在重复做相似的事，哪些位置必须保留独立的容量；把一切权重共享都笼统地叫作“更深的思考”，会把这些区别抹掉。

Hidden Decoding at Scale（2607.08186）换了一个方向加计算。它不沿深度循环，把每个 token 展开成几条内部计算流，多数层只在流内做注意力，少数层跨流混合，主干的层数一层没加。代价是需要继续预训练，内部序列和缓存也变多了。拿它和深度循环比较大规模训练下的兼容性很合适，只是要记住“主干没有扩大”的意思仅限于层数，训练和推理成本都实打实地增加了。

2. 稳定循环：重复访问会改变训练动力学

Lilian Weng 在介绍循环深度模型时特意提到，这类模型训练起来很脆弱，隐藏状态可能塌缩成同一个值。问题的根源在于共享参数被多次使用：同一次参数更新会同时作用于好几轮计算，对某一轮有利的变化，可能破坏另一轮；梯度的大小和状态的分布，也可能随循环次数一起漂移。截断反传又加了一层困难：只有最后几轮拿得到梯度，早期轮次很难学会为后面铺路。所以研究循环的稳定性，要把初始化、归一化、训练时的轮数和测试时的轮数分开来看，还要观察多轮之后的状态是否收敛到有用的结果，训练损失下降只是其中一个信号。

主线位置第 4 层

第 4 层，循环模型怎样训得稳。接 Geiping 等人在循环深度模型中用到的随机循环次数与截断反传，以及 Universal Transformers 的共享参数结构。

这组论文都想让共享参数被反复使用时训得稳，差别在从哪里下手：DeepLoop 调残差的缩放，Gated Recurrent Transformers 用门控限制每一轮改动多少，另外三篇改训练信号，让每一轮都有自己的学习目标。

普通深层网络有一套成熟的残差缩放规则，用来控制每一层对总输出贡献多大。DeepLoop（2607.13491） 指出这套规则在循环模型里会失效：同一个共享块在一次前向里被访问好几次，几次访问的梯度汇成一次更新，下一次前向又被几次访问一起用上，所以缩放要按访问次数来调。论文据此修改了缩放配方，结果来自所测的小中规模语言模型，还谈不上对任意架构的稳定性保证。它设计了一个很好的对照：没有参数复用时，新配方基本不改变表现，只有启用复用后才显出收益，可见收益确实来自对复用的处理。

Gated Recurrent Transformers（2608.15062） 在固定的输入和输出模块之间放一个共享核心，用门控决定每一轮的更新改动多少，免得某一轮把状态推得太远。论文坦率地给出了一项具体的权衡：参数量和峰值解码内存都大幅下降，可在某个大规模设置下，编译后的生成延迟增加了 10%。这算不上失败，它把省了什么、付出了什么都摆在了明处，正好印证了第 1 层的判断：省下的显存和省下的时间是两笔账。

另外三篇从训练信号入手，处理截断反传带来的早期轮次学不到东西的问题。Thinking with Looped Flows（2609.11801） 给每一轮加上局部的去噪目标；LoopMTP（2608.03624） 让第 t 轮去预测 t 步之后的 token，让不同轮次分担不同远近的预测；Looped Transformers as Optimizers（2609.37379） 把每一轮状态更新解释成对某个局部目标的一步优化，由此推导出循环变换的形式。前两篇改变了训练信号，后一篇约束了变换的结构。它们都提供了有用的设计工具，可哪一篇都没有证明多转几轮总是有效，在训练范围之外的轮数和不同任务上，稳定性仍然要单独测。

3. 深度诊断与自适应：更陡的曲线也可能更差

Graves 提出自适应计算时间时的愿景很美好：简单的输入早点停，困难的输入多想一会儿。可停止判断本身也会犯错，停早了可能漏掉必要的推理，停晚了可能在错误的方向上越陷越深。要评价一种动态深度方法，得在相同的平均预算下比较计算在样本之间分配得合不合理，只看最大深度下的表现会把真正的问题藏起来。深度带来的收益、做停止判断的成本、以及分布变化之后停止判断是否依然准确，这三件事要分开测。

主线位置第 4 层

第 4 层，自适应深度。接 Adaptive Computation Time 和 Universal Transformers 的动态停止，也回应 Lilian Weng 对循环深度“增加轮数后会饱和”的疑问。

三篇工作都在问多转的那几轮值不值，差别在问法：What Makes Recurrence Effective 比较哪类任务受益，Beyond Depth Truncation 检查常用的截断测法测得准不准，TaH2 让每个 token 自己决定转几轮。三篇合起来的教训是，曲线涨得快的方法，在相同计算下仍可能落后。

What Makes Recurrence Effective（2609.36636） 在知识类和推理类任务上比较了训练范围内外的循环次数。论文报告，推理任务可以从更多循环中受益，知识任务的表现却会下降，难题也不总是能从更多轮计算中获益；输入输出层的布局、历史状态如何注入、是否告诉模型当前是第几轮，都会影响结果。所以循环次数没法当作普遍有效的“思考预算”来用，困难样本也不会自动地值得多算。

要知道多转的几轮有没有用，常见的测法是推理时把循环截短，看质量掉多少。Beyond Depth Truncation（2609.19934） 指出这个测法同时改变了三件事：模块调用的次数变少了，真正执行的不同计算变少了，最后负责读出结果的那一层还被放到了训练时没见过的输入分布上。常见的读法把质量的下降全部归给第二件事，可第三件事本身就会造成损伤。论文用一组正、负对照把三件事拆开来测。这和 Horace He 强调的“先诊断再优化”是一个道理，诊断工具不可靠，后面的结论就跟着不可靠。

TaH2（2609.35748） 研究按 token 分配循环次数。它训练一个决策器，对每个 token 判断再转一轮能不能改善预测，于是有的 token 走了 4 轮，有的只走 1 轮；决策器和主干一起后训练，监督信号是在线得到的“再转一轮是否更好”的标注。论文先指出一个容易被忽视的现象：一些循环模型的准确率随计算增长得更快，可因为起点低，在相同的计算点上仍然落后于普通模型。按 token 分配之后，它把增长的速度和同计算下的水平都提了上去。剩下的开放问题是决策器本身的开销、判断失误的代价，以及换到别的任务还准不准。

下图是 TaH2 指出的那个现象的示意。方法 B 的曲线更陡，投入越多涨得越快，可它的起点低得多，在竖虚线标出的实际可用预算处，它的质量仍然落后于方法 A；横虚线代表一个质量门槛，A 用更少的计算就跨了过去。所以一份可信的报告要同时给出相同预算下谁做得更好、达到相同质量时谁花得更少，单凭斜率来概括测试时多算的能力，很容易得出误导性的结论。

4. 冻结模型与局部回流：有些循环可以免去重训

前面三个分支讨论的循环模型，大多要从头训练或者大规模继续预训练，成本很高。一个自然的想法是：能不能在现成的模型上动点小手术，让它把深层算出的东西送回浅层再用一遍？这类局部修改便宜得多，可也受制于原模型已有的表示和接口。而且冻结权重往往伴随着别的组件要训练，适配器、停止判断或选择规则都可能需要学习。比较这类方法时，要说清楚哪些组件被训练了、哪些输入被重复处理了，以及新增的计算是在提供新信息，还是只把已有的错误再重复一遍。

主线位置第 2 层第 4 层第 5 层

第 4 层向第 5 层过渡。架构上接 Universal Transformers 的深度循环和跨时间递归，任务上接 agent 的工具循环；预填充代价的分析则回到第 2 层的预填充与解码之分。

三篇回流工作都把深层的信号送回浅层，省掉从头训练循环模型的成本，差别在送什么、送到哪里：Write Back the Δ 只送两层之间新增的信息，T^2MLR 送给下一个 token，Recirculation 在推理时送回较早的层，代价落在预填充上。第四篇把这类架构拿到组合工具调用上检验。

Recirculation（2608.17981） 冻结模型权重，在推理时把较深层的信号反馈到较早处，让现成模型对同一段输入多加工一遍。论文有一个很重要的限制：生成阶段增加的延迟很小，预填充却要逐个位置串行处理。开头那个每读 100 个 token 才写 1 个的编程 agent，正是长提示、短回答的任务，预填充的代价很可能决定净收益是正是负；只展示生成速度，就会把主要成本藏起来。Write Back the Δ（2609.32457） 回传得更省：它只把两层之间新增的那部分信息写回较浅的层，避免回传整个状态，并且学习怎样选择和组合回流的路径。

T^2MLR（2607.15178） 把信号送往另一个方向：前一个 token 的中间层表示，被送进当前 token 的较早层，让中间计算跨越时间延续下去。它既不是对同一个 token 反复做完整前向，也和把文字笔记写进上下文不同，属于第 4 层说的跨时间递归，也就是把状态从前一个 token 带到后面的 token。

Looped Language Models Improve Compositional Tool Calling（2608.18171） 把循环架构拿到工具调用任务里检验，并区分了孤立的调用和相互依赖的多步调用：后者需要把前一步的结果用到下一步，受益更多，孤立调用的收益较小。所以收益来自任务结构，没法笼统地全部归功于工具调用格式写得更准。

这组研究共同提出了一个问题：哪些状态值得再加工一遍，哪些状态可以跨步保留？一个可行的实验是固定底座模型和输出预算，分别改变反馈的位置、反馈的内容和循环次数。如果同时增加了可训练模块和测试时计算，就应当承认结论属于整个新系统，把功劳全部记在“冻结模型也能循环”上是不公平的。

5. 推测解码：草稿质量、缓存与工作负载共同决定收益

推测解码的账看起来很简单：草稿猜对得越多，大模型被调用的次数就越少。可草稿被拒绝时，花在它身上的计算就白费了；接受率又会随着领域、草稿中的位置和上下文变化，固定的草稿长度不一定适合所有任务。《How To Scale Your Model》提醒过，推测解码是用额外运算换延迟，在批量小时最划算，批量一大、算力不再闲置，账就可能算不过来。所以这个分支的论文都在联合考虑草稿成本、验证成本、每轮收下的 token 数和并发条件，单单比较一次生成了多少候选 token 说明不了什么。

主线位置第 2 层

第 2 层，让一次读入的权重多干点活。接 Speculative Decoding、Speculative Sampling 的校正规则和 EAGLE 的特征级草稿。

这组论文都在改推测解码的流水线，差别在改的是哪一环：草稿从哪里来，草稿侧要存多少状态，验证怎么排，以及目标模型本身在变时怎么办。改动越深，越要分清它还能不能保证输出分布不变。

先看草稿本身的质量。扩散式草稿器能一次并行写出好几个位置，可各个位置的质量参差不齐。AdaFlash（2607.19223）分析了这种草稿器在不同领域、不同位置上的接受率波动，用在策略蒸馏让它适应部署时的分布，再用一个自适应长度的输出头决定每次猜几个。它把草稿的训练和运行时的分配联系了起来，并行草稿是否越长越快，要靠数据说话。

草稿也可以按任务来定制。DeLS-Spec（2607.07409） 把固定的并行草稿器当作长上下文的专家，再加一个可以单独训练的短上下文局部头；AngelSpec（2607.25852） 让对话交给一种草稿器，代码和数学交给另一种，并把验证当成整批请求共享的资源来排。H-Spec（2609.24197） 盯着第 2 层的老问题，也就是显存：草稿模型本来也要存一份自己的 KV 缓存，H-Spec 改为复用大模型的缓存，再补上最后一个位置的隐藏状态，从而省掉这一份。三篇分别处理草稿结构、任务分工和状态开销，仅凭每轮收下的 token 数没法给它们排出一个公平的总榜。

循环模型给推测解码提供了一个天然的草稿来源：早期轮次的状态已经能给出一个粗略的预测。LoopSpec（2609.17184） 用早期轮次的状态产生草稿，用后期状态验证，并让下一批草稿和当前的验证重叠起来。论文宣称在其校正机制下实现了无损解码。在采样模式中，“无损”的含义是保持输出的概率分布，任意两次随机运行逐 token 相同并不在承诺之内。LoopCD（2610.02185） 也用早期状态，可它拿早晚轮次之间的差异当信号来挑 token，改变的是解码策略本身，所以不能和 LoopSpec 共享同样的无损保证。

最后，目标模型本身也可能在变。Online Draft Co-Training（2609.07108） 研究在长时间的强化学习训练里，草稿和大模型一起更新时会遇到哪些系统障碍；FOVEA（2608.22883） 研究多模态草稿在什么时候需要多少视觉信息，指出给草稿加多少视觉输入，要和草稿任务真正的信息需求相匹配。下一步的实验应当同时报告草稿计算、接受率、验证成本和每个请求的缓存占用，并且分清固定不变的目标、正在训练的目标，以及视觉信息不断变化的任务。

6. 长上下文：压缩历史，不能把关键证据一起删掉

本分支的方法都在降低长上下文的成本，差别在压住的是哪一块：驱逐只留一部分缓存，同时省存储和读取；分层管理把缓存挪到主机内存，只省显存；状态模型用固定大小的状态代替逐 token 的缓存；复用则省掉重复的预填充。“访问得少”和“存得少”要分开评估。

先读一个负结果。Random Attention（2609.03430） 保留提示，然后在每个注意力头内随机裁剪推理过程留下的缓存，发现在测试设置中，复杂的选择规则比随机裁剪强不了多少。论文用对照实验解释了原因：缓存里最脆弱的是提示，各种选择规则之间的差距，大多只是看谁碰巧保住了提示；推理过程则自带冗余，模型在文字里会反复重述还需要的信息，各个注意力头也各自留着一份，所以提示保住之后，随机留下的部分已经够用。结论是有条件的：原始提示依然重要，KV 也绝非可以随便删。StreamingLLM 当年发现，丢掉开头那几个吸走大量注意力的 token，长输入就处理不稳，同样说明保住哪一部分比删掉多少更要紧。所以公平的对照必须固定提示的保护方式。

A Probabilistic Interpretation of KV Cache Eviction（2608.28293） 给驱逐补上了统计视角：只保留一部分 token 算注意力，相当于用一个样本去估计全体的期望，它讨论了解码时怎样对被删除的部分做校正，H2O 那种按累计注意力分数保留少数 token 的规则可以放进这个框架里理解。HiSparse（2608.07009） 面对的是另一种瓶颈：稀疏注意力每一步只访问少量位置，可全部历史仍然要放在显存里。它把全部历史放进主机内存，GPU 上只留一个固定大小的小缓存，模型输出保持不变，代价是主机和设备之间的传输。前者研究近似带来的偏差，后者研究状态应该放在哪里，这正是“访问得少”和“存得少”的区别。

状态模型提供了更彻底的替代，思路和 Mamba 一脉相承，生成时只维护一个固定大小的状态，用不着保存逐 token 的缓存。它的弱点是固定大小的状态装不下太多细节，精确回忆长上下文里的某一处会吃亏。DART（2608.02032） 把递归状态看作一种键值存储，据此改造读取方式；Maglev（2608.02870） 使用固定容量的记忆并在训练时加入一致性约束；Sparse Delta Memory（2607.07386） 用稀疏寻址扩大递归状态的容量。

另外两篇走的是复用路线。Cross-Model KV Cache Transfer（2608.03893） 利用同家族模型之间的线性关系，让一个模型直接用另一个模型已经做好的预填充结果；DeepSeek-V4.1-Flash（2609.19969） 把跨层复用、低精度存储和重放组合在一起，延续了 MLA 把键值压进低维向量的路线。这些方法省掉的状态不同，需要的校准不同，能恢复的信息范围也不同，长距离检索能力和任务质量都要分别测量。

7. 低精度：存储位数、运算精度和最终误差是三件事

低精度听起来最直接：位数砍一半，显存和带宽也省一半。可第 1 层已经说过，收益能不能兑现，要看量化、反量化以及具体算子是否真的支持低精度运算。LLM.int8() 当年发现，大模型里会系统性地冒出少数数值特别大的离群维度，这也提醒我们，平均误差很小，保证不了每个关键位置都安全，误差在专家路由、长链生成或者敏感决策中可能被放大。所以读这类论文要看它报告了哪些东西：实际用的内核、累加时的精度、校准数据，以及最终的任务质量。只凭理论位宽推算部署吞吐，往往会过于乐观。

主线位置第 1 层

第 1 层，算子与数值格式。接 FlashAttention 的“把数据搬运当作算法的一部分”，以及 LLM.int8()、GPTQ 的离群值处理和后训练量化。

低精度的收益要从存储一路过关到任务质量：解包与转换、内核运算、单层误差、跨层累积。本分支的论文各自负责其中一段，同一篇论文里内核的加速和整段生成的加速也可能差得不小。

最前面一关是存储。Breaking the 1.58-bit Barrier（2609.16338） 研究三值权重，也就是每个权重只取负一、零、正一三个值的模型。常用的部署格式把五个三值权重塞进一个字节，折合每个权重约 1.6 位，这种格式默认三个值出现得一样多。作者测了 29 个三值模型，发现零最多能占到 51.5%，于是按实际分布来编码，在最稀疏的模型上降到每个权重 1.485 位。它提醒我们，平均存储位数和直接参与运算的格式是两个概念，存得少了，运算前还要解包。

VC-Attention（2609.15810） 管的是内核运算这一关，场景是视频扩散模型里的注意力。它用值向量平滑压住量化时的离群值，再用一次融合的乘加把 softmax 的概率直接转成 FP8，省掉 FP32 的指数运算。论文同时报告了算子层面和整段生成的速度，两者差得不小，很适合用来练习区分这两个测量层级；它的结论也只属于视频扩散这个场景，换到文本模型、换了硬件或序列形态都需要重新测量。

后两关是误差。KronQ（2607.07964） 把梯度协方差的信息引入后训练量化，用来估计哪些权重的误差对输出影响最大，和 GPTQ 借助二阶信息指导量化的思路一脉相承。Quantization Degradation（2608.08188） 研究量化噪声如何产生、又如何沿网络一层层传下去，指出误差在层间可能被衰减、保持或放大。前者改变误差的分配，后者解释量化在什么条件下会失效，仅凭“位数更低”推断不出延迟更低。

FlashLoop（2609.29812） 同时动了好几关：它利用循环模型各轮之间的冗余做稀疏更新，再把 KV 缓存的残差量化，把第 4 层的循环架构和第 1 层的低精度联合优化。问题在于多个近似叠加之后，每一项单独都很小的误差合起来未必还小。值得采用的研究方法是一个组件一个组件地加进去，观察错误最先出现在哪一类任务、哪一段上下文上；用一个平均分宣布“质量几乎不变”，会把这些信息全部抹平。

8. 动态服务与输入表示：把收益兑现到完整请求

一个请求从到达到完成，经过的远不止模型的前向计算，还有排队、通信、媒体预处理、缓存调度和负载均衡。某个算子变快了，瓶颈很可能转移到别的环节；缓存命中率提高了，也可能让设备之间的负载失衡。《How To Scale Your Model》把连续批处理、前缀缓存和预填充解码分离列为服务引擎设计的关键技术，任何新方法都要和这些机制兼容才能上线。端到端的比较应当给出请求长度和并发的分布，区分冷启动和缓存已热的情形，只展示最有利的那一条吞吐曲线是不够的。

主线位置第 3 层第 5 层

第 3 层向第 5 层延伸。接 PagedAttention 与 vLLM 的分页缓存、SGLang 的前缀复用、Sarathi-Serve 与 DistServe 的预填充解码调度；输入表示一段则回到每个任务到底有多少 token 这个起点。

本分支的论文都在一个请求的生命周期里找节省，差别在落在哪个环节：分词决定有多少 token，媒体预处理和预填充决定首 token 多快，跳层和专家裁剪动的是解码和路由，部署研究看的是底下整套软硬件。迁移和维护的成本也算在效率里。

vSkipper（2609.37062） 的故事最有代表性。跳层方法让简单的 token 跳过一部分层，理论上省了计算，可它先展示了一个反直觉的现象：现有的跳层方法用的是自己专门的生成循环，接不进现代服务引擎，单独运行时反而比原模型解码得慢。vSkipper 于是把这种动态路径重新接回连续批处理、分页缓存和预编译的计算图。论文控制了提示、请求到达过程、输出长度和启动设置，着重分析了什么时候值得做跳层的判断。它所说的“服务没有额外可分辨的质量损失”，是相对于跳层模型本身而言的，跳层模型和原模型的质量是否一致，是另一个问题。模型误差和服务误差必须分开看。

You Only Need 2/3 of the Chosen Experts（2609.25809） 在多种细粒度 MoE 上研究专家裁剪：原本路由器为每个 token 选出几个专家，现在连这几个也只留一部分。论文报告了指定保留比例下的平均质量和实测速率；这个比例是实验得到的结果，没法当作所有模型都适用的安全常数。尤其要看少数难任务上的损失、路由行为和不同的服务后端，平均分不变，可能掩盖了少数依赖稀有专家的任务。

MiMo-V2.5 全流程推理优化（2607.13095）展示了架构上的理论节省需要多少工程配合才能落地：从 GPU 上的图像预处理、并行视频解码，一直做到专为滑动窗口设计的前缀树、分布式缓存和按缓存位置路由请求。Non-GPU AI Accelerators 的部署实地研究（2607.08215）记录了在 Ascend 软硬件栈上部署 MoE 和多模态服务时，在算子、数值正确性和维护上遇到的困难。它是特定配置下的现场研究，对其他非 GPU 平台没有定论；两篇合起来说明，迁移和维护的成本同样是效率的一部分。

Objective vs. Search（2609.19145） 把效率的起点往前推到了输入表示。分词器决定一段文字被切成多少个 token，它的训练目标和搜索过程常被混在一起，这篇把两者拆开比较。token 少了，模型未必更容易学；词表和语言覆盖的变化，又会改变什么才算公平的预算。完整的研究应当同时报告字符数或任务规模、token 数、质量和运行开销；换了分词器之后仍把“相同 token 数”当作相同的数据量，比较就失去了基准。

五、开放问题与研究机会

回到开头那个修 bug 的编程 agent。它五十来步的执行过程里，时间大致花在三个地方：每一步都要重新读一遍越来越长的上下文，有些步骤要想得很深、有些步骤几乎不用想，以及模型之外的工具执行和网络等待。这三处正好对应三个尚未解决的问题：计算该怎样按难度分配，记忆、推理和工具该怎样放在一起优化，以及结构上的优势怎样在真实的硬件和服务里兑现。三个方向都要求在固定的质量要求下比较资源投入。

三个开放问题对应那个 agent 时间花掉的三处：按难度分配计算，把记忆、推理和工具一起优化，让结构上的优势在真实硬件和服务里兑现。

1. 如何按任务难度动态分配计算，并保持可控的质量边界？

那个 agent 在“打开某个文件”这一步和“定位 bug 的根因”这一步上，需要的思考量显然天差地别。固定深度或固定推理预算，会同时在简单步骤上浪费资源、在困难步骤上限制发挥。研究机会在于让循环次数、提前停止、搜索和模型选择依据可以校准的信号协同调整，把 Graves 当年的自适应计算时间，也就是让网络自己学会在每个输入上走多少步，真正做到 agent 的每一步上。评价时要特别检查难例和长任务上的退化，平均意义上的计算节省，不能掩盖少数关键步骤上的失败。

2. 如何围绕完整 Agent 工作负载联合优化记忆、推理和工具执行？

Manus 的经验说明，在输入远多于输出的 agent 里，缓存命中率比解码速度更能决定成本；Anthropic 的经验说明，并行能大幅缩短时间，代价是成倍的 token。模型内核上的加速，很可能被工具等待、上下文重读和数据传输抵消掉。这里可以研究按任务决定保留什么的缓存、可以恢复的上下文压缩和跨步骤的调度，把“保留哪些信息”和“怎样分配资源”放在同一个目标下优化。关键是用真实的请求到达过程、任务长度和并发条件做实验，确认局部的节约确实能转化为端到端的延迟、吞吐或成本收益。

3. 如何让结构上的计算优势在不同硬件与服务条件下稳定兑现？

低精度、稀疏化和参数复用的收益，都依赖具体的实现和硬件支持，理论计算量预测不了部署效果。vSkipper 发现跳层方法脱离服务引擎单独运行时反而变慢，非 GPU 部署的实地研究在 Ascend 软硬件栈上碰到了算子、数值正确性和维护上的一连串困难，都说明了这一点。研究机会在于联合设计模型结构、算子和服务策略，建立可以迁移的成本模型，就像 kipply 和《How To Scale Your Model》用纸笔估算那样，先给出一个可信的下界，再解释实测和下界之间的每一处偏差。报告时还应同时给出维护复杂度、数值正确性和完整任务的表现，只比较理想配置下的峰值速度意义有限。
